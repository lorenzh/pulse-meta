## Disposition

Ready for `plan`. No owner question blocks the spec. The later decisions in [#460](https://github.com/lorenzh/pulse-meta/issues/460#issuecomment-6589563362) explicitly amend #562: SQLite only, the Console's API token supplied by a server token file or environment variable, and the connection test reading `x-pulse-contract`. - Console is a scaffold: `/` serves a constant page, ops routes exist, and every method except GET/HEAD is rejected. There is no account database, setup, password check, session or API request. Its CSP currently forbids forms, styles and scripts.
- `PULSE_API_URL` is currently required at startup. `PULSE_CONSOLE_ADMIN_TOKEN` and `_FILE` are mutually exclusive, optional, read once at startup, and already validated without disclosing their contents. The service and image run on Bun 1.4.0; the image runs as non-root `bun`. The only current runtime dependency is pulse-kit; it does not yet depend on pulse-contract.
- Contract exports wire version `1`, `WIRE_VERSION_HEADER`, validators and bounded `fetchJson`. `fetchJson` accepts an absent wire header as `wire: "absent"`; setup must make an explicit decision about that case rather than accidentally reporting a successful version check. `GET /admin/config` returns `{revision, checks, components, maintenance}` and can supply the check count.
- API `GET /admin/config` needs `read` or `checks`, which alone does not prove an admin-capable token. `GET /admin/tokens` requires `admin`. The inspected token router has no `/admin/tokens/self`; `self` is treated as an invalid token ID. There is no need for a new version route for this feature.
- Checked-in full/dev/demo setups supply the Console's API URL but no console data volume or admin token. Their ordinary API service does not enable admin-token bootstrap. `secrets-init.mjs` already supports admin provisioning in files mode when `PULSE_SECRETS_ADMIN=on`, including the console-specific token output; generate mode currently provisions probe tokens only.
- CLI-generated installations already generate/keep an admin token, enable the API bootstrap, and mount `console-secrets:/run/pulse:ro` with `PULSE_CONSOLE_ADMIN_TOKEN_FILE`. They have no console database volume. Reuse this machinery; do not introduce a second token generator or invalidate existing tokens on rerun.
- Neither console nor deploy currently contains `PULSE_CONSOLE_SECRET_KEY_FILE` or Postgres wiring. The future key is for encrypted TOTP seeds in #563; removing the superseded token database means #562 need not invent an unused encryption key or encryption subsystem.
- Existing deploy e2e checks only Console readiness, page text and a frame header. Its API overlay supplies a separate test admin token. The new setup test must ensure the API and Console actually receive the same credential, without relying on that unrelated fixture accidentally matching.

## Open points and planning assumptions

These are engineering choices to make explicit in the plan, not reasons for an owner hold.

1. **Scope and target boundaries.** Implement the account/setup/session foundation in console. Include a deploy child for persistent writable console storage, working admin-token provisioning, setup documentation and Compose acceptance in both checked-in setups and CLI output. Keep minimal-without-console working. No api or contract source change is intrinsically needed: add console's dependency on a full main SHA of pulse-contract and use its existing shapes. Keep any meta documentation correction small. #565 is a parallel wave, not an assumed prerequisite; build against current main and state any later compatibility follow-up.

2. **Amended credential contract.** The token comes exclusively from existing server settings. No setup field, POST parameter, browser storage, session payload, database column or settings export may contain it, even encrypted. Missing/malformed configuration cannot produce a successful setup; decide whether missing configuration stops startup or renders a safe operator instruction. Preserve existing validation and mutual exclusion. The original at-rest acceptance becomes “the Console never stores a recoverable API token in its database,” not a demand to encrypt a token that must not be stored. The designated server secret file remains an intentional plaintext input, outside that database assertion.

3. **API URL precedence.** The issue still asks to store an API URL. A reasonable assumption is to prefill the code-gated setup form from `PULSE_API_URL`, validate and persist the accepted nonsecret URL, and use the persisted choice afterward. The plan must specify whether env remains mandatory for bootstrap and exactly what happens if env changes after setup; avoid silently switching the existing owner's API. If choosing an env-authoritative, read-only URL instead, document that interpretation and its persistence semantics. Keep http(s)-only validation, no credentials/query/fragment or whitespace/control characters, and support the internal Compose URL `http://api:3000`.

4. **One-time setup authorization.** Generate a high-entropy code only for an uninitialized database and print it through a deliberate container-log bootstrap message, including when the normal log level suppresses info. The code is the sole exception to secret-free logging and must never enter routine logs, metrics, errors or URLs. Gate every setup read/action that exposes configuration or calls the API, not only the final owner-creation POST. The public entry page can ask for the code. Use POST submission and a short-lived setup grant if multiple steps are needed; that grant is not an authenticated owner session. Bound attempts and request bodies. Specify the code/grant lifetime and restart behavior; rotating an unused code on restart and invalidating the old grant is acceptable for this single-console deployment.

5. **Atomic completion and persistence.** Commit exactly one owner, the selected API URL and completed marker transactionally after validated inputs and a successful connection test. Concurrent final submissions cannot create two owners or change the winner's settings. A failed test, invalid form or failed database commit leaves setup retryable. After completion all setup entry points, old codes and outstanding grants fail, including after process/container recreation using the same volume. No automatic reset or new setup code for a corrupt/unreadable existing database. Document intentional reset as destructive operator action; build no recovery/account-reset flow here.

6. **Connection test and dependency order.** Use server-side requests with the configured token, bounded timeout/body size and contract validation; never let an unauthenticated visitor trigger a credentialed fetch. A feasible current-main check is `GET /admin/config` for the count plus `GET /admin/tokens` to establish `admin` permission, discarding token-list data rather than exposing it. Define the required scopes, normally the bootstrap full-access token, without performing a test mutation. This avoids a circular dependency on #566. Read the wire header, not a package/service version or nonexistent `/version`. Recommend failing completion on missing, malformed or incompatible headers. Zero checks is a successful count of zero. Distinguish network, timeout, auth, feature-disabled, version and invalid-response failures using safe messages; none may commit partial setup. Do not return upstream response bodies verbatim.

7. **Credentialed request destination.** The chosen API URL is security-sensitive even though it is not a secret. An authorized setup holder may select a private/self-hosted address. Validate before fetching, refuse cross-origin redirects/credential forwarding, and expose no general-purpose authenticated proxy. Once setup is complete, do not leave an anonymous connection-test or URL-update endpoint behind. Define path-prefix joining if base URLs support a prefix.

8. **Owner identity and password policy.** Assume one local owner identified by email, with a display name and password, no registration route and no team-management UI. Specify normalization/uniqueness and bounded fields in the schema and forms. Use at least 12 password characters, consistent with the amended invitation flow, and a documented maximum that bounds KDF work. Hash with `Bun.password` argon2id, using explicit reviewed cost parameters; store only the encoded salted verifier. Use the same generic failure for unknown account and incorrect password, avoid a cheap enumeration path, and never echo/log a password. Invitations, role matrix, ownership transfer, password recovery and mail are later work.

9. **Sessions and handoff to #563.** #562 needs a working server-side session store and sign-out now; #563 extends it with TOTP/recovery and session listing/revocation. Recommend SQLite-backed sessions keyed by a digest of an opaque cryptographically random cookie value, rotated at successful authentication, revoked at logout and checked on each protected request. Apply the already decided 30-day inactivity expiry, with injected-clock boundary tests. Specify persistence across restart, expiry cleanup and the minimal authenticated landing page. Treat password-only access as the #562 foundation, not completion of v1's mandatory owner TOTP; do not add unrelated admin screens before #563's enforcement exists.

10. **Throttling.** Reuse the decision's clear baseline: five failed attempts in 15 minutes lock the account and client IP for 15 minutes. Apply separate account and IP limits, not just an account/IP pair that can be bypassed by changing either. State the boundary response (`429`/`Retry-After`), counting/reset semantics, unknown-account behavior, restart behavior, concurrent attempts and bounded state. Do not trust arbitrary `Forwarded`/`X-Forwarded-For`; start with the TCP peer unless a narrowly configured trusted-proxy contract is explicitly designed. Bound work before KDF execution and protect setup-code guessing too. All of these belong in deterministic tests, not real-time waits.

11. **Cookies, origin and CSRF.** Require host-only, path-scoped, `HttpOnly`, `SameSite=Strict` cookies; `Secure` for HTTPS. Resolve the existing loopback HTTP Compose experience explicitly: either a deliberate HTTP-only local-development mode or local TLS is needed, with browser evidence for the chosen behavior. A production `NODE_ENV` alone cannot infer the browser's scheme because the current image uses it on loopback HTTP. Never let spoofed proxy headers weaken cookie flags or origin checks. State any public-origin setting and safe local defaults. Put CSRF protection on setup, connection tests, sign-in and sign-out as applicable, with server-side origin checks; SameSite alone is insufficient. Accept local return paths only to prevent redirect abuse.

12. **UI and ops behavior.** Use server-rendered forms that work without JavaScript, labels, keyboard focus and inline safe error messages; preserve nonsecret input on recoverable errors. Make setup progress and successful version/check count observable. Sign-in must work at 390 px without horizontal scrolling per #460. Widen the current CSP only as required by the decided self-origin policy; no inline/CDN dependency. Preserve raw-path routing, no-store responses, ops access, bounded metric labels and secret-free errors. Specify `/` and protected-page behavior before setup, after setup while signed out, after login, and after session expiry. No self-service “forgot password,” 2FA placeholder that pretends to enforce TOTP, or external-login buttons.

13. **Database and Compose lifecycle.** Pick and document a console-specific SQLite path/setting, migrations, file permissions and startup failures. The non-root image must write it on a durable named volume; do not share the API database or put writable state in the read-only token volume. Add the volume to CLI generation and its lifecycle/ownership checks as needed. Enable admin bootstrap for checked-in setups with console; generate/keep matching tokens safely in demo as well. Preserve existing probe tokens and imported API tokens on repeated init/up. `PULSE_CONSOLE_SECRET_KEY_FILE` remains a documented #563 deploy integration point unless this plan identifies an actual present use. Do not add Postgres dependencies or pretend `DATABASE_URL` selects a supported backend.

14. **Release and verification path.** Specify how new console behavior is tested in Compose using the branch image/dev setup and how published stacks receive the released image through the existing pin mechanism. Current published `0.1.0` pins do not contain this feature; do not fabricate a version/digest or claim a scaffold-image run verifies setup. The deploy task depends on the console contract being available; release/pin rollout prerequisites must be explicit. Preserve unrelated service readiness and full-stack e2e assertions. Update console README/configuration docs and affected deploy/CLI docs with bootstrap logs, URL precedence, persistence, cookies/HTTPS, required scopes and the #563 boundary.

## Derived acceptance check

1. **Uninitialized instance:** start with a fresh console database and valid server-side API settings. A bootstrap code is available only in the container log. Missing/wrong/expired code cannot unlock setup, trigger a credentialed connection test, create an owner or save settings. Direct HTTP calls cannot bypass the UI gate. Setup-code attempts are bounded/throttled, and invalid CSRF/origin requests are refused.
2. **Successful setup:** with the valid code, supply the owner identity/password and accepted API URL, test against a local API fixture and then the real stack, and see the supported wire header/version and correct check count (including a zero-check fixture). Completion creates exactly one owner and persists the nonsecret configuration. Concurrent completions produce a single winner. Failed upstream auth, missing scopes, disabled admin routes, incompatible/absent wire header, bad response, timeout and failed commit do not complete setup; a corrected retry succeeds.
3. **One-time property:** after completion, the original code, all outstanding setup grants and every setup mutation are refused. Restart and recreate the console with the same data volume; setup stays closed, no replacement code is printed, and the saved owner can still sign in. API or database failures must not reopen setup.
4. **Password sign-in and throttling:** a valid password creates a new opaque session; a wrong password or unknown account grants no access and has the same safe error behavior. Exercise the specified five-failure window and account/IP locks using an injected clock, including a correct password during lock, changing accounts/IPs, the expiry boundary and concurrent failures. No protected page accepts a fabricated, pre-authentication, expired or revoked session.
5. **Session security:** demonstrate authenticated landing, sign-out, session ID rotation and server-side revocation, 30-day idle expiry, restart behavior and safe return-path handling. Inspect cookie attributes under the chosen loopback HTTP and HTTPS deployment modes. CSRF/origin failures cannot change setup or authentication state; forwarded-header spoofing cannot bypass protections.
6. **Secret storage and disclosure:** inspect SQLite rows and database/WAL files with known test sentinels. The password appears only as an argon2id verifier, session identifiers are not recoverable from stored digests, and the API token is absent from all console database state. Inspect responses, headers, HTML, logs and metrics: no password, API token or session secret appears. The setup code appears only in its designated pre-setup log message. Credentialed redirects cannot send the API token to a second origin. A browser-provided token cannot override the server's credential.
7. **Browser acceptance:** use `agent-browser` against the implemented service to attempt setup without the code, complete setup with it, observe connection results, sign out, reject a wrong password, sign in correctly and reject reused setup authorization. Cover labels/keyboard access, reloads and errors; check sign-in at 390 px. Record the actual commands/results and safe screenshots if useful, without embedding live bootstrap codes or credentials in public evidence. Browser verification remains required at implementation; it was not performed for this review.
8. **Compose acceptance:** exercise the new console image with non-root writable storage, matching API bootstrap token and loopback publication. Complete setup, recreate without deleting volumes and sign in again. Check full/dev/demo and a CLI-generated installation, including repeated initialization preserving secrets/data and minimal remaining usable without console. Existing full-stack behavior and ops readiness stay green; adapt the e2e credential overlay deliberately. Validate generated/checked-in Compose models and relevant deploy helper/CLI tests.
9. **Quality and scope:** console `bun run check` and affected deploy CI jobs pass; retain coverage, shared lint/type rules and existing security tests. Use temporary databases/local HTTP fixtures and injected clocks for acceptance failures. Runtime changes use Bun/node built-ins, pulse-kit and pinned pulse-contract only. Docs explain the amended SQLite/server-token behavior and the later #563 work. No 2FA, roles/invitations, Postgres, SMTP or external auth implementation is smuggled into this feature.
