# Issue review: #288 Shared API client in pulse-contract

Verdict: specifiable. No blocking question. Open points and assumptions below.

## Findings in the current code (checked in `.repos/`)

- contract: `src/` has `index.ts`, `schema.ts`, `validate.ts`, `version.ts`. `checkWireVersion` and `WIRE_VERSION_HEADER` exist. Package `exports` only `.`; `files: [dist]`; deps: `zod` only.
- probe `loadChecks` (`src/client.ts`): `abortable` race plus `AbortSignal.timeout` (injectable `timeoutSignal`) plus shutdown `signal`. No size cap. Absent header is logged once per logger (`warnedAbsent` WeakSet). Mismatch throws `contract version mismatch: ...`. Non-OK throws `HTTP <n>`. Timeout message `timed out after 10000ms`. Invalid items are skipped and logged, heartbeats dropped. `postResult` also fetches with own timeout, but it is a POST with no body: out of scope (the client is for JSON GET).
- notify `src/api.ts` + `src/timeout.ts`: `fetchWithTimeout` with injected `schedule`, own `readJson` with cap (default 5 MiB), wire check before status check, error texts `GET <path> ...`, redaction of the API URL. `fetchWithTimeout` is also used elsewhere? `channels/http-post.ts` and `delivery.ts` use abort code; unverified whether they use `fetchWithTimeout`. The spec must keep `timeout.ts` if other callers remain (`defaultSchedule`, outgoing webhooks are not API calls).
- status `src/poller.ts` (also served to the browser as `/poller.js`): `getJson` with `abortion` race, order is status check, then wire check; absent logged once; mismatch -> `WireVersionError` -> error kind `version`; validation -> `InvalidResponseError` -> `invalid`; else `unreachable`. Optional endpoints (uptime, resolved) swallow errors except wire mismatch.
- status `src/api-poll.ts`: the issue says the readiness poll "skips the wire-version check". It does not: it reads the body, checks the header and records `mismatch`. The real differences are: it never validates the body and an absent header is silent. Spec should treat the goal as "uses the shared client", not "adds the check".
- status `src/server.ts` `fetchUpstream` (the proxy): own `AbortSignal.timeout` + race, `upstream.text()` with no cap, requires `application/json` content-type, parses, **filters** via `filterApiBody`, forwards non-OK as its own status, and forwards the upstream wire header value. It does not validate with a contract validator, and the api body has fields (hidden targets) the filter handles. It only partly fits `fetchJson`.
- status serves contract modules to the browser from an allow-list `contractModules = {index,schema,validate,version}.js` (`server.ts:140`) and a test (`server.contract-modules.test.ts`). A new contract module must be added to the allow-list, or `index.js` import of it fails in the page.
- Pins: status, probe, notify pin contract `c98a2d45...`; api pins a different commit (not relevant, no change to api).

## Open points (resolve in the plan)

1. Validator signature. The contract validators have the shape `(raw, path) => Validation<T>`. Items differ: probe, notify skip invalid items of an array (`validateCheck` per item), status validates the whole response. Decide: `fetchJson` takes `validate: (raw: unknown) => Validation<T>`; consumers that skip items pass an array-level "identity" validator (`unknown[]` check) and validate items afterwards. Assumption made: this one.
2. Status proxy: does not validate and filters raw JSON. Assumption: it uses `fetchJson` with a pass-through validator for timeout, size cap and wire check, and keeps content-type, filter, status forwarding and header forwarding itself. `fetchJson` must therefore expose the wire version result (ok/absent) or the raw header on success, or the proxy reads it otherwise. Needs a decision in the plan: return `{ value, wire }`? Also: a non-JSON content-type currently gives 502 `invalid API response`; the client does not check content-type (assume: not checked; proxy keeps its own check by a hook or leaves the proxy partly unchanged and documents it).
3. Proxy behavior changes to document: a new body cap (default) gives 502 for large bodies; a wire mismatch from upstream currently passes through to the page (page poller detects it). Keep this: the proxy must not turn a mismatch into 502 without the page seeing `version`. Decide and test.
4. HTTP status vs wire order. probe/status check status first (a non-2xx with a mismatching header gives `HTTP n`), notify checks the wire first (mismatch error even on 500). The plan picks one order; accepted difference must be documented, or the error type carries both. Assumption: status first, notify message for non-OK-plus-mismatch changes (document).
5. Error messages. Each consumer keeps its message via mapping typed errors. Examples: probe `timed out after 10000ms`, notify `timeout after 5000ms`, `GET <path> returned <n>`, `GET <path> response is larger than <n> bytes`, status `<url> returned HTTP <n>`. Typed errors need carry fields (timeoutMs, status, maxBytes, wire error text, path).
6. Timeout injection. notify injects `schedule` (tests use fake timers) and probe injects `timeoutSignal`; status uses injected `timer.setTimeout` and `api-poll` injects `setTimeout/clearTimeout`. The issue says "a timeout" only. Decide the injection point (e.g. `timeoutSignal?: (ms) => AbortSignal` or a `schedule`) and how consumers keep their fake-timer tests green. The stalled-body test needs a timer that covers the body, so a signal alone is not enough if the fetch ignores it: the client must also race (the current code does so on purpose: "also if fetch ignores it").
7. Timeout vs abort discrimination: the client must tell the timeout from the caller's signal (typed `timeout` vs `aborted`). With `AbortSignal.any`, check `signal.reason` (`TimeoutError`) or own flag. Probe maps abort to `StartupAbortedError` by checking its own signal, so that stays.
8. Absent-callback semantics: probe warns once per logger, status once per poller, notify per response. The callback is called per response; consumers keep once-logic.
9. Size cap default value: notify 5 MiB today; the contract default needs to be documented (assume 5 MiB). Cap without Content-Length counts streamed bytes; no stream -> parse after text length check. Status browser: `Response.body` readers exist in browsers; fine. Should the cap apply to decoded characters or bytes? Assume bytes.
10. Browser: no Node imports; `AbortSignal.any` needs a recent browser (Chrome 116+, Safari 17.4+). The page poller uses it only if a caller signal exists; document the browser floor or fall back by manual combining. Also the poller must keep working when the `fetch` is the page's `fetch` wrapped.
11. Packaging: contract `exports` has only `.`: export `fetchJson` and types from `index.ts` (the module must be in `dist` and, for the page, in the status allow-list and its file test). Decision: put it in `src/client.ts` (new), export from index. The coverage gate is 80% lines.
12. "Server side and browser poller where it fits": the poller wraps validation placeholders (`withPlaceholders`) and optional-endpoint swallow logic; these stay in status. The `InvalidResponseError`/`WireVersionError` classes become mapping from the typed contract errors; the error kinds `version`/`invalid`/`unreachable` must stay identical.
13. Notify keeps redaction of the API URL in messages (redactedError) and `code` copying from causes; the client's errors must preserve `cause` for network errors.
14. Pinning order: each consumer PR pins the merged contract commit, so the contract PR must be merged first; consumers are children blocked by contract (`targets.json` `dependsOn`). Consumers are independent of each other (the issue's "probe, status and notify" order is only a sequence; no dependency needed between them). The `dist` is built by the contract's prepare/build: check that the `github:` pin builds `dist` (existing pins work, so yes).
15. Docs: contract README (API, defaults, errors), and consumer docs on timeout/cap changes (status and probe gain a cap; both are behavior changes to document). Repos `config` and `api` untouched; `kit` untouched (non-goal).

## Assumptions

- `fetchJson` returns `Promise<{ ok: true; value; wire: "ok" | "absent" } | { ok: false; error: FetchJsonError }>` (never throws for expected failures), `FetchJsonError` is a discriminated union on `kind`: `timeout | aborted | http | too-large | invalid-json | wire-mismatch | validation`.
- No content-type check in the shared client.
- probe `postResult` and notify outgoing channel posts (http-post, smtp) are out of scope.
- #166 plan names it `fetchJson`; the name is final.
