# Issue review: #298 pulse-kit shared runtime helpers

Verdict: specifiable. No blocking question; open points below get a default in the plan.

## Current state (checked in `.repos/`)
- kit: `src/index.ts` has only `MAX_TIMER_DELAY_MS`; tests `test/smoke.test.ts`, `test/timer.test.ts`; `docs/index.md`; committed `dist`; no runtime deps (zod not yet added). kit `AGENTS.md` already says consumers pin a full commit SHA.
- No service depends on kit yet (no `pulse-kit` entry in api/probe/status/notify `package.json`).
- api serves `/healthz`, `/readyz`, `/metrics` inside its main API server (`api/src/server.ts` `serveOps`), on the API port, not on a separate ops listener. probe has its own `health.ts` (separate listener), status serves them from `server.ts` (the public page listener), notify has `health.ts` with `/healthz` and `/metrics` only.
- Each service has `log.ts`/`metrics.ts`; status has `shutdown.ts`, `settings.ts`; notify has `errors.ts`, `timeout.ts`.

## Open points (with default for the plan)
1. **`startOpsServer` does not fit three of four services.** api and status serve ops paths on their main listener; only probe and notify use a dedicated listener. Default: kit exposes `startOpsServer` for a standalone listener (probe, notify) plus a request-level handler (e.g. `handleOps(req, res, opts): boolean`) that api and status call from their own servers, so ops semantics live in one place without moving ports. The issue must not move api/status ops to a new port (external behavior).
2. **notify `/healthz` is readiness-like today** (503 with reason when polls fail) and notify has no `/readyz`. kit semantics: `/healthz` liveness, `/readyz` readiness. Default: notify keeps `/healthz` returning today's status and body (kit option for a custom live check), and `/readyz` is added as a documented difference, or `/readyz` is not added. Plan decides and documents. Same check for probe and status `/healthz` vs `/readyz` bodies, status codes, HEAD/405 handling and content types (notify accepts HEAD; api rejects non-GET with 405 via `HttpError`).
3. **`formatDuration` contradicts "keep external behavior".** status renders "2 h 5 min", "<1 min", "3 d 2 h" (covered by `render.test.ts`). The issue says "3h 5m" elsewhere, but only status has such a function in the clones; the second copy was not found (maybe in browser code or an in-flight branch). `Intl.DurationFormat` output differs from today's text (narrow gives "2h 5m", short gives "2 hr, 5 min") and has no "<1 min" form. Default: kit output uses `Intl.DurationFormat` style `narrow` with a `<1m` floor for under a minute, in `en`; status accepts the change as a documented difference and updates its tests and golden pages. Plan must pick the exact style and the sub-minute text, and the largest unit (days, hours, minutes; no seconds).
4. **Browser-safe use in status.** Decide: status's served-module mechanism (see `server.contract-modules.test.ts`) serves contract modules; extending it to serve kit's `format-duration` module needs kit `dist` files with no Node imports and a path allowlist. Default: serve it via that mechanism only if `formatDuration` is used in browser code today; otherwise status uses it server-side only.
5. **zod in kit.** Issue says "no runtime dependency except zod". Which helpers need zod? Default: none required; add zod only if the env readers use it, and align the version range with contract. Avoid adding it unused.
6. **Config bounds and error text.** `StartupError` is one line `pulse-<service>: <message>` with exit 2, naming the setting. Today's six error classes have message texts that tests assert (probe `settings.test.ts`, status `settings.test.ts`, api `config*.test.ts`, notify). Default: keep every current message text where tests assert it; kit readers take a message-builder or the plan lists accepted wording changes per repo. Needs the per-repo mapping in the plan. api and notify config-file parsing stays local (S5 non-goal), but their env reads move to kit.
7. **Logger unification.** Four loggers have different interfaces (api/probe/status/notify). External log lines and fields must stay. Default: kit logger = `{ debug, info, warn, error }(msg, fields?)`, line `{time, level, msg, ...fields}`; services adapt call sites. Check field-order and the `time` format of each service; differences accepted must be listed. `PULSE_LOG_LEVEL` parsing: api throws on invalid value; confirm all four do the same (kit reader should reject with a `StartupError`).
8. **Metrics registry.** Must keep metric names, labels, help text, bucket list and output order per service; api/notify render metrics from live state at scrape time (`ops.metrics.render(listCheckStates())`), so the registry needs gauge callbacks or a collect hook. Default: registry supports `collect` callbacks.
9. **`runService` exit codes.** "As today": 0 clean, 1 runtime failure, 2 startup error. probe also has a shutdown timeout log line (`shutdown did not finish within …ms; exiting anyway`); keep text. `timeoutMs` default per service must stay what it is today.
10. **`setTimeout` safe helper**: "rejects delays above `MAX_TIMER_DELAY_MS`" — throw a `RangeError` vs clamp. Default: throw `RangeError` synchronously; callers that cap or chunk today keep doing so.
11. **`readJsonBody` size limit and error mapping.** api/status error responses for oversize or invalid JSON must keep status codes (413/400) and bodies; kit throws a typed error carrying status, services map it.
12. **Cross-repo order and pins.** kit PR must merge first; services then pin the merged kit commit SHA (with `dist` committed on `main`). The child issues for probe, status, notify depend on kit, api depends on all. `targets.json` `dependsOn`: kit; probe, status, notify -> kit; api -> kit, probe, status, notify. The plan sees only `main` at its start, so it must not assume kit exports beyond what it specifies; the spec must define the kit API precisely (names and signatures) so all four children agree.
13. **`escapeHtml`/`escapeLabel`**: three `escapeLabel` copies may differ slightly (escaping of `\`, `"`, newline). Plan checks the copies and picks the Prometheus-correct one; any difference is documented.
14. **`AGENTS.md` rule** is needed in all repos: kit, contract, probe, api, status, notify, config (and meta?). "Every repo" is ambiguous: default to every target in `targets.json` and meta; contract and config get an AGENTS-only child if they are targets. Config and contract have no runtime code, so only a doc line.
15. **`compose-e2e`** builds the other services from `main`; api last is consistent. It needs the new pins to resolve offline in Docker (GitHub dependency on a SHA): check each Dockerfile can install a git dependency, or that `npm ci` has network/token access.
16. **Coverage gate**: kit test script enforces 80% lines; each module needs tests.

## Assumptions

- No wire format, contract, or config-file parser change (S4 only).
- Env var names, metric names/labels, log texts, exit codes and health semantics stay, except differences the plan lists per repo (at least: `formatDuration`, possibly notify `/readyz`).
