## Open points (none blocks the spec)
1. **Lighthouse is not in the repository and not on the approved-packages list.** The acceptance criteria compare Lighthouse scores on `main` and after. Assumption: the implementer runs Lighthouse ad hoc (for example `bunx lighthouse` or Chrome's Lighthouse against the local `dist/` served by the static server), outside the repository, and states both sets of numbers in the PR. Nothing is added to `package.json`. If a CI gate is wanted, that needs a separate issue plus an approved-packages entry. The numbers must be taken for Home and Hosted on `main` first, before any change.
2. **Reduced-motion test location.** "A test checks this in Chromium" and "a test checks the copied text…". Assumption: these are Playwright checks, part of `check:a11y` or a sibling script in `scripts/` that runs in the CI `site` job. `@playwright/test` is the approved test dependency. Clipboard permission must be granted in the test. The clipboard failure case is forced by stubbing `navigator.clipboard.writeText`. Pure logic (command-line extraction, link/node placement with distance and angle rules, frame throttle) goes into `.ts` modules with `bun:test` unit tests to keep the 80 % coverage.
3. **JS budget (30000 B per page).** The canvas, live preview, scroll-in, heart burst and copy islands add script. Assumption: islands stay small and the Preact alias is shared. Each page only ships the islands it contains. A budget increase needs a stated reason in the PR and must not weaken `budget.json` silently. The plan should ask for a size estimate per island. Scroll-in could be a tiny non-Preact script. The plan decides.
4. **Docs as "pages without islands ship no JS".** Docs pages now get the copy-button island only if a page has a command block. Command-block detection happens at build time in `src/docs/markdown.ts` (the markup of "command" vs "output" vs JSON blocks). Open: the rule to classify a block as a command block. Assumption: a fenced block whose language is `bash`/`sh`/`shell`/`console` and which has at least one `$ ` line or command line is a command block. `json`, plain output and `text` blocks are not. Lines starting with `#` are comments. Output lines (no `$ ` prefix after a `$ ` line in the same block) are skipped. The plan must check the real docs fixtures (`test/fixtures/`) and the pinned docs for edge cases: continuation lines with `\`, blocks without `$ ` where all lines are commands, multiple commands, heredocs.
5. **Canvas reduced-motion choice.** "No canvas, or one static frame". Assumption: one static frame is drawn once (nodes and links, no pulses), at resize only. Also the no-JS case shows no canvas (decorative, absence is fine).
6. **Canvas placement and contrast.** The canvas sits behind the content (fixed, `z-index` below, `pointer-events: none`, `aria-hidden`). Text over lines and nodes must keep 4.5:1 in light and dark. The axe color-contrast check cannot see canvas pixels. Assumption: low-alpha lines/nodes from tokens, with the check done by computing worst-case blend in a test or documenting the alpha values against the token colors. A visual check in both themes is part of the PR.
7. **"No layout work per frame" vs a fixed full-page canvas.** Sizes are measured on resize only (`ResizeObserver` or `resize` event, not in the loop). Assumption: the canvas is `position: fixed` viewport-sized, so scrolling needs no per-frame measuring. Whether the network covers the whole page height or only the viewport is not defined. Assumption: viewport-sized, fixed. Node count scales with area, and the phone scale-down factor (to 168/36 px minimum) is derived from the viewport width. The exact formula is a plan detail with tests for the minimum distances and angle rules (20°, 15° at 12 or more links), including the case that the rule cannot be satisfied (degree cap or drop a link).
8. **Hover rule.** "Every hover effect on all pages only under `@media (hover: hover)`". This includes existing hover rules in `components.css`, `docs.css` and `base.css`. The plan must list and migrate those. Sidebar links on docs keep a colour-only transition, also hover-only. Focus effects are not hover effects and stay outside the media query: nav underline and primary arrow loop also on `:focus-visible`.
9. **Outline button contrast during the fill.** Text must be at AA at every moment of the curtain transition, not only at the end. The curtain is a `transform` on a pseudo-element. Text colour must pass 4.5:1 on both the old background and the accent. Assumption: choose a text colour that passes on both (checked per theme with the token values), or switch the colour with a delay so no intermediate frame is below AA. The plan has to give the token pair numbers.
10. **Scroll-in without JS or observer.** Assumption: content is visible by default. A script adds a class `js-reveal` on `<html>` before first paint only when `IntersectionObserver` exists and reduced motion is not set, so the hidden initial state never shows without script. Elements above the fold must not flash (reveal at once if already intersecting). Must not hurt Lighthouse CLS/LCP. Transform/opacity only.
11. **Live status preview** (`status-mock.tsx`): today static, so it needs an island that crossfades states only while on screen and the tab is visible. Requirements: the screen-reader text equals the visible text. Only the visible state is exposed, the other state is `aria-hidden`. Labels are right-aligned in each row, also while crossfading (the two states overlap in the same grid cell). No-JS shows one fixed state. Reduced motion: no crossfade, so a static state.
12. **Heart burst.** Island creates 8 particles on hover or focus-within, one burst per hover. "One burst per hover" is read as: it re-arms after pointer leave and focus leaves. Under reduced motion, only the fill. Particle elements are `aria-hidden`, are removed after 1.1 s, and use transform/opacity. Keyboard: a focusable element in the card is required for focus-within (the card has a link or button? check `hosted.tsx`).
13. **Header order.** Markup order nav, then GitHub (Hosted: "Join the waitlist"), then theme toggle. This applies to all pages and desktop. On mobile (menu toggle) the issue says nothing. Assumption: the same DOM order, with the mobile menu layout unchanged unless it conflicts with the tab order. The existing keyboard check is extended for the order.
14. **Home content details.** The text lives in `src/content/home.tsx` and `facts.ts`. Product facts come from the pulse repositories, so the quorum wording (two or more locations reporting means down needs at least two), the probe token step (`openssl rand -hex 32`, `PULSE_PROBE_TOKEN`) and the heartbeat config example (`name`, `secret`) must be checked against `.repos/{api,probe,config}` docs and the config schema. Where design and code differ, the code wins (AGENTS.md). Any difference is stated in the PR and fed back. The privacy wording ("only check targets (URLs) and error details stay private by default; components group checks and the page shows the components") must also be checked against `.repos/status` and `.repos/api`. The facts test fixtures may need updates.
15. **Hosted content.** All offer facts placeholders with a note "Planned offer, details not final". The existing test `hosted.test.ts` covers placeholders. Extend it for new tokens (`[TRIAL]`, `[DISCOUNT]`, `[REGION]`, `[BACKUP REGION]`, `[RETENTION]`). No invented values.
16. **Design source for the implementer.** `design/website/*.dc.html` lives in pulse-meta, and `.repos/website/design` only holds the tokens. The implementer in the website repo must be given the needed design values (spacing token, timings, particle ranges) in the spec, since it may not see pulse-meta files. The plan should copy the exact numbers into the section for the website.
17. **No external request / no new dependency.** The canvas, observer and burst use plain browser APIs. Particle randomness uses `Math.random`, and tests inject a seeded random.

## Derived acceptance check
On a local build (`bun run check:all` green, budgets pass):
1. Home and Hosted use `--section-space: clamp(64px, 8vw, 128px)`; no borders or `<hr>` between sections.
2. With JS off or without IntersectionObserver, all content is visible. With JS, sections fade and rise once, using only transform and opacity.
3. A canvas with `aria-hidden`, `pointer-events: none` exists behind the content on Home and Hosted only. Unit tests prove min distances (280/60, down to 168/36 on phones) and angles (20°, 15° at 12 or more links). The loop skips frames closer than 33 ms, reads no layout, stops while `document.hidden` or off screen and restarts on `visibilitychange`/visibility.
4. With emulated `prefers-reduced-motion: reduce` in Chromium: no scroll-in, no micro-animations, no animated canvas, the heart only fills, the copy button only swaps its icon.
5. Hover styles exist only inside `@media (hover: hover)` (a test scans the built CSS).
6. The Hosted Open source card bursts 8 hearts once per hover and on focus-within; the burst particles are 6–10 px and travel 30–70 px.
7. Header tab order is nav, GitHub/waitlist, theme toggle, and visually the same on desktop.
8. Docs pages: every command block has a 44 px "Copy commands" button; output and JSON blocks have none; the copied text per block equals the command lines only; "Copied" and "Copy blocked" are announced via a live region; the icon returns after 1.5 s; no scroll-in or canvas on docs pages.
9. Pages without these islands ship no extra JS; no new runtime dependency; no cross-origin request.
10. axe and keyboard checks pass on Home and Hosted in light and dark; text on the background and on hovered buttons is at least 4.5:1.
11. The PR states Lighthouse performance/accessibility/best-practices (mobile, local build) for Home and Hosted on `main` before and after; none lower. The size budget passes.
12. Home and Hosted content matches design version 27 with facts verified against the product repositories, and all Hosted offer facts are marked placeholders.
