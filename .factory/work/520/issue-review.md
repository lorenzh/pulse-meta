## Open points for the plan

1. **Order of the children.** api's `compose.yaml` will build `https://github.com/lorenzh/pulse-console.git#main`. Until the console PR is merged, that build fails, and so do api's `docker` (`compose config` passes, the build does not) and `compose-e2e`. `targets.json` must make `api` depend on `console`. The meta docs in the spec PR describe the stack as it will be once both are merged. That is the same practice as in earlier specs, but the plan should say it.
2. **Port setting name.** The issue asks for `PULSE_CONSOLE_PORT`, while api and status listen on `PORT`. Assumption: follow the issue and have the container listen on `PULSE_CONSOLE_PORT`, so it does not clash with a generic `PORT` in a shared env. The Dockerfile `HEALTHCHECK` must read the same variable. In Compose, `${PULSE_CONSOLE_PORT:-<default>}` can also be the host-port variable in `.env`, as `PULSE_STATUS_PORT` is: Compose interpolation does not pass it into the container. The plan states both meanings and documents them in console `docs/configuration.md` and api `docs/configuration.md` (Compose variables).
3. **Default port.** It must not be any of 3000, 3001, 8080, 8081, 8090, 8000 or 9100. The plan picks one, for example 8082, and uses it for both the default and the Compose host port.
4. **Host binding in Compose.** This is an admin UI that later holds an admin token. Assumption: publish it on `127.0.0.1` only, like the api (`"127.0.0.1:${PULSE_API_PORT:-3000}:3000"`), not on all interfaces like status. Inside the container it listens on `0.0.0.0`.
5. **Admin token setting: name, required or optional.** The issue says it is "read and validated but used later". The regular stack has no admin tokens on the api side. If the console required a token now, Compose would have to set up `PULSE_API_ADMIN_TOKENS_FILE` and a secret in `.env`, which the issue does not ask for. Assumption: `PULSE_CONSOLE_ADMIN_TOKEN` xor `PULSE_CONSOLE_ADMIN_TOKEN_FILE`, following probe's `token.ts`. It is **optional** in this item. When set, it is validated: not both set, the file is readable, the value is non-empty after trimming, and it does not start with the placeholder `replace-with-`. Its value never goes into a log, an error or the page. A later item (login and API calls) makes it required. The plan states this. If the owner wants it required now, the Compose part must also add admin tokens to the api.
6. **PULSE_API_URL rule.** A missing or empty value stops the start, which is stricter than status (no `localhost` fallback). An unparsable value or a scheme other than `http:`/`https:` stops it too. The message names the setting, never the value, and the exit code is the services' startup-error code (check `runService`/`StartupError` handling). The test must be written first and must fail on the empty repo, and its output goes in the PR. Compose sets `PULSE_API_URL: http://api:3000`.
7. **`/readyz` semantics.** There are no API calls yet. Assumption: `/readyz` is `200` once the listener is up and the service is not shutting down. It does **not** check the api, so a down api does not take the console out of readiness in this item. The plan states this and leaves an API check to the later item. `/healthz` is always `200`. `/metrics` shows the kit registry with a `pulse_console_` prefix, at least the process/start metrics the other services have. The ops routes are served on the main port through `handleOps`, as status does, not on a second port.
8. **UI approach for v1.** The issue lets the plan choose. Suggested: server-rendered HTML from plain template strings with kit's `escapeHtml`, no client bundle and no new package, like status's SSR path. The reasons: one page, no interactivity yet, the strict CSP (`script-src 'self'` or `'none'`) holds without a build step, and a smaller image. A later item with forms can still add a same-origin script. A client framework (preact) is approved for pulse-website only, and the fontsource fonts for pulse-status only. Using either here would need an `approved-packages.md` change named for the owner. Assumption: system fonts and no client JS in this item.
9. **Security headers.** Use status's set on every response, ops routes included: CSP, `nosniff`, `x-frame-options: DENY`, `referrer-policy: no-referrer`. The CSP is at least as strict as status's: no inline script or style, `frame-ancestors 'none'`, `form-action 'none'` for now. Other methods than GET/HEAD get `405`, unknown paths `404`. One test asserts the headers on `/` and on `/readyz`.
10. **Pins.** Use the same pins as the services today: pulse-config `51e95b0…` (both the dev dep and the `uses:` of `check.yml`), pulse-kit `fa79ba8…` (not kit `main` `6a06ec2`, unless the plan needs something newer and says why), and the `actions/checkout` SHA from status's `docker` job. pulse-contract is not needed until the console reads API shapes. Assumption: no contract dependency in this item.
11. **`docker` CI job.** As in status: build, image holds no `*.test.ts`/`*.spec.ts` and no dev-only paths. The issue asks that "the container starts as non-root and `/readyz` answers 200; the page answers 200 with 'pulse Console'". That can be a step in this job (`docker run -d -e PULSE_API_URL=http://api.invalid …`, then `id -u` ≠ 0 and curl `/readyz` and `/`), or it can be shown in the PR only. Suggested: a CI step, so it stays checked.
12. **Compose and compose-e2e changes (api).**
    - `compose.yaml`: a `console` service with `build: https://github.com/lorenzh/pulse-console.git#main`, `image: pulse-console:local`, `PULSE_API_URL: http://api:3000`, the loopback port mapping, `healthcheck: interval: 5s` like status, and `depends_on: api: service_healthy`. It does not go into the demo profile, unless the plan says otherwise.
    - `.env.example`: a commented `# PULSE_CONSOLE_PORT=<default>`.
    - `scripts/compose-e2e.sh`: the expected service lists (regular and with demo), the running/healthy loops, a `/readyz` check of the console, and the page with "pulse Console". `docker stop` with exit code 0 should cover the console too (graceful `SIGTERM` via `runService`).
    - CI `docker` job: maybe a console port override check like the status one.
    - Docs: api `README.md:32`, `docs/install.md:33`, `docs/development.md:61`, `docs/configuration.md` (Compose variables).
13. **Meta docs (spec PR).** `README.md` lines 21, 55 and 219, `docs/architecture.md` lines 3, 11 and 16, and the `@types/bun` and `oven/bun` rows in `docs/approved-packages.md`, so that they include console.
14. **Docs in console.** `README.md` (what it is, run locally, configuration summary), `docs/configuration.md` (every setting, default, `_FILE`, errors), `docs/development.md` (commands, layout, tests), and `docs/index.md` like the other services. `AGENTS.md` adapted from status's, and `CLAUDE.md` that imports it. The existing README text ("Web console to manage checks, incidents, tokens, notify and status settings …") describes later items. It must say what works now.
15. **Performance report.** Image size (`docker image inspect`), RSS at idle (`docker stats --no-stream` after about 30 s, or `/proc/<pid>/status`), and start time (container start to the first `200` of `/readyz`). These are numbers in the PR, with no budget. The api bench covers api, probe, status and notify. Adding console to it is out of scope.
16. **Repository setup outside Factory.** Branch protection and required checks on `lorenzh/pulse-console`, and the default branch `main`, are for a person. The plan names them and does not build them.

## Assumptions

- "compose-e2e in pulse-meta (or its equivalent)" means pulse-api's `compose-e2e` job (`scripts/compose-e2e.sh`). pulse-meta has no Compose test.
- Image publishing stays as it is for the other services: a Compose build from the GitHub `main` URL. No registry and no release job.
- The console listens on `PULSE_CONSOLE_PORT` (point 2). The plan picks the default (point 3). Compose binds it to host loopback (point 4).
- The admin token setting is optional and only validated in this item (point 5). `PULSE_API_URL` is required (point 6).
- `/readyz` does not depend on the api (point 7).
- The page is server-rendered with no client JS and no new runtime package (point 8). Runtime deps are pulse-kit, plus zod only if the settings parser uses it.
- There is no bench or `bench-selftest` in console, because the shared `check.yml` does not require one.
- The page holds the text "pulse Console" in `<title>` and in a visible heading, with `lang` set and a valid HTML5 document. No accessibility test run (Playwright) is needed for a static page in this item. The plan may add one if it wants the status-style a11y job.
