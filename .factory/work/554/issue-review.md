## Open points and assumptions for the plan

1. **Chart ownership and visibility.** Define a complete matrix, for SSR and browser polling alike:
   - No components, either flag value: charts for the HTTP checks already shown by the existing fallback.
   - Components, checks hidden (the default): component-level charts derived on the server; no per-check series or identifying metadata reaches the browser.
   - Components, checks shown: retain charts for shown HTTP checks, including loose checks. The plan should state whether component charts also appear; recommended default is one component chart when members are hidden and member charts when shown, avoiding duplicate history markup.
   - Non-HTTP checks have no latency chart. A component with HTTP members but no measurements has a clear no-data message; a component without HTTP members must not imply that its other check types have HTTP latency.
   Preserve the no-components fallback; interpreting `SHOW_CHECKS=false` as a global removal of checks would expand this feature into a breaking visibility change.

2. **Component latency is a new presentation, not a recoverable pooled percentile.** The upstream supplies daily quantiles, not raw samples. Neither averaging quantiles nor weighting them by `count` produces a component percentile. Recommended status-only interpretation: per UTC day, take the maximum available member p50 and maximum available member p95, label these as the highest member daily p50/p95, and document that they are not percentiles of pooled component traffic. Use unique active HTTP members, align dates, ignore empty members, leave an all-empty day null, and omit per-check objectives in hidden component charts. If a count is exposed, define it as the sum of contributing result counts, never a member count. Membership in several components contributes independently to each component; hidden loose checks get no separate series. The plan must give a worked multi-member example and settle the exact labels/formula. True pooled percentiles would require a justified API/contract scope expansion; do not silently invent them in status.

3. **Public latency payload and validation.** The plan must define exactly what `/api/latency` returns in each visibility mode and how the poller validates it. A component projection must identify only public components and must merge member series, rather than replacing hidden IDs while leaving several distinguishable per-check histories. Reuse contract latency day types/validators where applicable; do not mislabel a component ID as a real check ID or bypass validation. A status-owned presentation projection can keep this feature in status. If a new shared wire schema is chosen instead, list contract explicitly and its dependency order. Do not add a per-check proxy route. Resolve membership server-side from raw reads, before hidden-key projection. Include all raw dependencies in answer-cache validity, following #474, and fail closed on unavailable/malformed membership. SSR's internal read must apply the same privacy policy as the HTTP route.

4. **Reason masking scope.** Assumption: “hidden-checks mode” means components exist and checks are actually hidden. Mask all automated incident reasons in that mode, both open and resolved, regardless of `HIDE_DETAILS`. Retain ordinary `HIDE_DETAILS` behavior for visible checks, including the no-components fallback. Apply the effective policy before serialization and tag creation so JSON, SSR, feed and cached answers agree. Keep operator-authored manual incident titles/updates and maintenance notes public, as the existing contract intends; the goal does not promise to redact arbitrary operator-written prose.

5. **Budget provenance and measurement.** The 250 KB number is from #378's performance section, not #381: suggested warm `/` HTML under 250 KB with 50 checks and 20 components. Status `docs/operation.md` instead records about 1.2 MB with checks shown (6,300 uptime bars) and p95 about 17 ms. This review did not reproduce that runtime measurement; dependencies are not installed in the read-only clone. Treat #554 as making the size limit a real gate, rather than grandfathering the documented excess.
   Recommended explicit unit: UTF-8 response-body bytes, at most **250,000 bytes**, before HTTP compression; not string character count, gzip size, or total JS/CSS/fonts. Preserve the 50-check/20-component fixture with full 90-day uptime and populated latency, and cover default hidden components, shown checks, and no-components fallback. Ensure the fixture renders its expected entries and histories so an empty/unavailable page cannot pass. The plan must explain how markup and daily-data access fit this budget; it must not pass by deleting charts, weakening accessibility, measuring only a tiny fixture, or changing the limit. If history is loaded on demand, preserve keyboard and no-JavaScript access and test those paths. Measure the full browser asset transfer separately if useful; no total-page asset budget was specified here.

6. **Rendered-page cache versus upstream caches.** `/` must serve a retained page snapshot, not run a new poller and render for every visit. Recommended design is a bounded, per-instance snapshot refreshed by the service poll lifecycle, with one render per published state, shared by `/` and `/index.html`. Define startup before the first successful poll, concurrent refreshes, failure/recovery, shutdown, and when relative times/the no-JS render timestamp advance. A successful snapshot is published atomically. On failure, show the established unavailable/stale-data banner semantics instead of presenting old operational state as current; optional latency failure must not take the page down. Readiness/wire-version behavior must remain deliberate rather than becoming accidentally dependent on optional latency. The plan must also reconcile `PULSE_STATUS_CACHE_MS=0` with the documented cache-off behavior, explicitly stating which snapshot behavior remains and updating docs if semantics change. Keep a bounded freshness interval and avoid overlapping poll/render work. Retain HTML `no-cache` unless a justified replacement is specified.

7. **Static cache policy.** “Cache header present” alone could pass with `no-store` and save no work. Specify usable caching for `/client.js`, `/theme-init.js`, `/page.css`, `/theme.css`, the served source-module JS, kit/contract JS and reachable zod JS. Recommended policy for unversioned URLs: `Cache-Control: public, max-age=0, must-revalidate` with content validators and bodyless matching 304s; alternatively choose a documented finite TTL. Reserve long-lived `immutable` for versioned/content-addressed resources. Cover generated theme CSS changing on restart and asset bytes changing on deploy. Keep CSP, MIME types, path allow-lists and traversal rejection. Fonts already cache; local logo policy can be stated explicitly but is not a new required optimization. Errors must not acquire a successful-asset cache policy.

8. **Manual incidents on component badges.** Reuse the page's impact/state precedence: open includes monitoring; `minor` implies degraded, `major`/`critical` down, `none` no override, resolved incidents no effect, and a worse check-derived state still wins. Uptime remains check-derived. Read manual incidents through the same filtered/cache path and include them in the resulting badge/tag dependencies. Specify older-API 404 behavior consistently with the page (retain last known manual list, empty before first success) and generic 503 for other unusable required answers. Preserve check-badge privacy and existing label validation/CSP/cache behavior.

9. **Documentation and contract upgrade.** Scope is status by default; no new API latency computation, shared tooling change, new setting, runtime dependency, or work on notify's separate old pin. Pin status to full contract main SHA `ebcbbb613328494185833f7133f1242910986948` and regenerate `bun.lock`; a newer main pin at implementation time must be explicitly reviewed. Verify both server and browser validation after upgrading, including HTTP(S) positive cases and non-HTTP URL rejection. Correct development docs using actual module imports, and reconcile the browser-import conventions in status `AGENTS.md` where they still claim no relative runtime imports. Update status README, operation/configuration/proxy docs where latency, reason visibility, caching and performance claims change. Meta README also currently says latency needs `SHOW_CHECKS=true`; correct that description as part of the approved spec work or explicitly assign its follow-up.

## Derived acceptance check

Use a local stub API and the real status HTTP server, deterministic data/clock/timers, and distinctive hidden ID/name/host/IP sentinels. At least the five regressions requested by the issue must demonstrably fail on status `2e3067d`; page snapshot reuse needs its own regression too. Additional negative controls need not each fail on baseline. Do not claim product CI was run during this issue review.

1. **Default latency and privacy:** with both visibility settings unset, HTTP history appears in SSR/no-JS HTML and in the browser, without components and with components. `/api/latency` returns exactly the displayed kind of data. Test shown checks and loose checks, multiple HTTP members with different quantiles/counts, mixed check types, empty days, and no-data cases. In component-hidden mode under both `HIDE_DETAILS` values, scan HTML, the latency JSON, all allow-listed JSON, feed and badges for hidden sentinels; no per-check history/identity is served. A failed membership read cannot fall back to raw latency. Membership changes invalidate the projected cached answer.
2. **Size:** a CI test obtains the real UTF-8 `/` response for the agreed 50-check/20-component, 90-day fixture, verifies meaningful content, and fails over 250,000 bytes. Cover the visibility/fallback cases in point 5 and exercise any deferred history access. Record before/after byte counts; do not substitute compressed transfer size. Record warm request p95 separately without a flaky timing assertion in unit tests.
3. **Reasons:** with configured components, `SHOW_CHECKS=false`, `HIDE_DETAILS=false`, automated open/resolved incident `reason` is null and its sentinel host/IP is absent from JSON, SSR and Atom. Repeat after cache hits/conditional requests. Positive control: a shown check with details enabled retains a sanitized reason; details hidden still masks it. Public manual incident text remains available.
4. **Assets:** representative successful responses from every CSS/JS route family carry the selected usable cache policy; validate conditional requests when that policy uses ETags (matching 304 has no body and retains cache/security headers; changed bytes get a new response). Retain font policy and rejection tests. Include generated theme CSS and transitive dependency modules, not only `/client.js`.
5. **Page snapshot:** repeated and concurrent `/` and `/index.html` requests within a published state reuse the rendered snapshot; they do not repeat upstream reads or render work. Advancing the injected poll lifecycle publishes changed state/time once. Startup, failure and recovery produce the documented view, cache-off mode follows the chosen semantics, server instances/settings do not mix, and shutdown stops refresh work. Use counters/injected effects rather than elapsed-time assertions.
6. **Badges:** an otherwise-up component with an open major manual incident returns a `down` component SVG consistent with the page; minor gives degraded, resolved/none do not override, and worse check state wins. After manual incident creation/resolution and refresh, its body/ETag change appropriately without changing uptime. Retain 404 compatibility, error behavior and hidden/unknown check-badge equivalence.
7. **Pin/docs:** manifest and lockfile agree on the reviewed full contract SHA; exercise the installed server and browser validation path for the stricter URL rule and keep the served import graph resolvable. Developer docs reference real files and accurately explain runtime imports; operator docs describe the new visibility, component-chart statistic, cache/freshness behavior and measured size.
8. **Completion:** status `bun run check` and `bun run check:a11y`, plus required CI `check`, both Docker architectures and `a11y`, are green. Extend Chromium coverage beyond its current `showChecks: true` setup to defaults, both component/fallback layouts, light/dark and 360/1280 px. Preserve contrast, text equivalents, keyboard access to daily values, focus/open-details across polls, quiet unchanged polls, live regions and no-JS behavior. Run the service once with `bun start` and exercise the changed behavior before implementation handoff, as status `AGENTS.md` requires.
