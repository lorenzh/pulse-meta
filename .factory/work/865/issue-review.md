## Open points and planning assumptions

Retain coverage for existing `validateAdminCheckInput`, `validateAdminCheckView` and both admin-config check lists. Responses containing only IDs, state summaries or header-name arrays do not need an unrelated validation redesign.
2. **Reserved-name policy.** Reuse the existing exact reserved-name rule. Do not broaden this into case folding of the reserved name, a ban on other prototype-related names, schema replacement, object sanitization or a change to unrelated unknown-field rules. Ownness is intentional: inherited properties and accessor handling keep their existing semantics. An own reserved key must be rejected without consulting its value, including a non-enumerable own key.
3. **Malformed-value coverage.** Use a table spanning null, non-string scalars, arrays, malformed objects, missing/invalid environment-reference fields and malformed keep-like objects. Also include otherwise valid literal/reference values under the reserved name: the policy rejects the name, not just values that happen to crash probe. Include a descriptor/accessor case with a read counter; do not execute its getter. The exact fixtures are an implementation choice, not a question for the user.
4. **Helper placement.** Share the existing admin guard with the public path where practical. `validate-admin.ts` already imports `validate.ts`; importing the admin module back from the public validator would create a cycle. An internal helper in `validate-core.ts` is a small viable option. Preserve admin checks and use public exports for tests; add no package-level export solely for testing.
