# Issue review: #348 pulse website

Verdict: specifiable. No blocking question. The points below go into the plan.

## Inspected
- `design/website/` (README, 4 pages, tokens, canvas), `docs/approved-packages.md`, `.factory/config.yaml` (target `website` exists, context lists all repos), `.repos/config` (pulse-config: Biome, ESLint, tsconfig base, lefthook, `check.yml`, Node >=24), `.repos/website` (only README, LICENSE).
- Docs in the clones: api (concepts, configuration, development, index, install, operation, rest-api, troubleshooting), probe, status (incl. theming), notify (incl. `channels/*.md`), contract (index), kit (index).

## Open points (not blocking)
1. **Packages not approved.** react, react-dom, preact and a Markdown renderer are not in `docs/approved-packages.md`. Only the two fontsource packages (5.3.0, exact) are. A separate PR in this repo must add them (licence, maintenance, runtime deps, why not own code) before the website build depends on them. Plan: that PR comes first; website build `dependsOn` it or the plan states the order. Also needed: a build tool (esbuild or similar), axe (`@axe-core/playwright` or `axe-core`), Playwright/Chromium. These are dev dependencies; the approved list covers runtime deps only, so say so in the plan. Prefer a small own Markdown renderer or a single dependency-light one (e.g. `marked`); the plan decides and justifies.
2. **Targets/dependsOn.** The work lives in one target (`website`); the approved-packages PR is in `meta`, outside `targets.json`. `targets.json` has only `website`.
3. **Node 24 vs Bun.** Default is Node 24 plus pulse-config. The plan must check that the reusable `check.yml` can run extra jobs (build, link check, a11y with Chromium). If not, add a second workflow in the website repo.
4. **Design sidebar vs real docs.** `Docs.dc.html` lists pages that have no source file with a clear 1:1 mapping: "Check states", "Quorum and incidents", "Maintenance windows", "Heartbeats", "checks.json", "tokens.json", "Metrics", "Upgrades and backup", "Install without Docker", and a "Search the docs" box. Search is a non-goal: omit the box or render it disabled. The plan must map each sidebar entry to an actual file in the clones (e.g. api `concepts.md`, `configuration.md`, `operation.md`, probe `configuration.md`) and drop or rename entries with no source. Sidebar groups follow the design; entries follow the files. Also needed: where probe, status, notify, contract and kit docs sit (the design shows only api-shaped groups); suggested group or per-repo sections.
5. **"Quick start" source.** The design cites api `docs/install.md` as its source. Confirm the page content comes from that file, not hand-written. `Overview` likely maps to api `index.md`. Slug scheme must avoid collisions (every repo has `index.md`, `install.md`, `configuration.md`): use `/docs/<repo>/<page>/` or similar. Default route `/docs/` shows the quick start.
6. **Link resolution.** Relative links between docs files, links into other repos (`../../status/...`), anchors, and `channels/*.md` subfolder. Rules: published file → site URL; other file → `https://github.com/lorenzh/pulse-<repo>/blob/<sha>/...` at the pinned SHA. The back-link "Back to the developer documentation" style links to `index.md` in meta-like docs must resolve too. Heading ids must match GitHub-style anchors so `#anchor` links keep working; the build fails on a dangling anchor.
7. **Pinning.** One config file (e.g. `docs.config.json`) with repo → SHA; a bump script resolves `main` HEAD via the GitHub API or `git ls-remote`. Fetch via `raw.githubusercontent.com` or tarball at build time (the build is the only place with network; the runtime has none). Tests and CI should use a cache or fixtures so the build works offline in unit tests. Decide whether fetched Markdown is committed (a snapshot) or only cached; default: fetched at build, cache dir ignored. Docs repos are public (assumption); if any is private the token handling needs defining.
8. **Content truth on home/hosted.** Facts must be checked against code: check types (HTTP, TLS, cron/heartbeat), channels (Slack, Teams, email, webhook, file: the design text lists four, notify has `file` too), endpoints, env vars, `checks.json` example (must validate against current schema in pulse-contract/probe docs), quick start commands, and the "one Docker Compose file" claim and ports (`localhost:8080`). The plan lists each fact with its source file.
9. **Hosted page placeholders.** The design shows concrete prices (Free, €9/€29/€149, yearly €7/€24, "about 20 %"), "4 regions", 14-day trial, open-source Team plan, status.losoft.dev, data location. All become `[PRICE]`, `[REGIONS]`, `[TRIAL]`, `[STATUS_URL]`, `[DATA_LOCATION]`, `[OSS_TERMS]` etc., visibly marked. Keep what is true now: self-hosted is free and MIT. Plan names for tiers and the monthly/yearly toggle: toggle is an island; with placeholder prices it adds nothing, so the plan decides (keep it, labelled, or drop). Plans/limits comparison rows that state numbers also become placeholders. Add a test that fails if a digit-price or `€` remains on the hosted page.
10. **Waitlist form.** Renders, fields disabled, with visible text "Sign-up is not open yet", no `action`, no network call; test asserts no `fetch`/form submission.
11. **Islands.** Likely: theme toggle, mobile menu, docs nav toggle, copy buttons (optional). Each needs a no-JS fallback (the menu as a `details` or a plain link list; theme follows `prefers-color-scheme` with an optional override stored in `localStorage`; no flash of wrong theme, needs a tiny inline script, which the CSP/size budget must allow). Tokens: light and dark come from `losoft-tokens.json`; fluid sizes (`--fs-*`) from the design.
12. **Budgets and checks.** Size budget numbers are not given. Assumption: HTML ≤ 60 kB, JS ≤ 30 kB gzip per page, fonts excluded and listed. The plan fixes the numbers and the budget file. "No external requests at runtime": a test greps the built output for `http(s)://` in `src`/`href` of resources other than GitHub links (anchors only), and Playwright blocks the network and asserts zero failed requests.
13. **Missing pieces.** Favicon, OG image (self-made static SVG/PNG, or none: `og:image` optional), canonical base URL unknown (no domain yet). `sitemap.xml` and canonical/OG URLs need a base URL: use a config value `SITE_URL` with a placeholder default, and say so. `robots.txt` allow-all with the sitemap line; plan notes that no deployment exists yet.
14. **Fonts.** Approved at exact `5.3.0`; the website pins exactly. Subset to latin to keep the weight low.
15. **Docs-repo drift.** Markdown can contain raw HTML, tables, task lists, admonitions, code fences with languages (json, yaml, bash, ts). The renderer must escape or sanitize raw HTML (docs are trusted but pinned third-party content); syntax highlighting without a runtime dependency: a small own tokenizer or none (the design uses `--syn-*` tokens for the `checks.json` sample only).
16. **a11y.** axe WCAG 2.2 AA on every page in light and dark, 360 px and desktop width; keyboard tests: skip link, menu, docs nav, focus visible, 44 px targets (target size check is partly manual: assert min-size in a test). Tables scroll regions are focusable (`tabindex=0`, design does this).
17. **AGENTS.md/README/CLAUDE.md.** CLAUDE.md contains the one-liner pointing to AGENTS.md as in sibling repos.
18. **Per-repo conventions of the siblings.** Read `.repos/status/AGENTS.md` and `.repos/config/AGENTS.md` for the test runner (`node --test`), 80 % coverage gate, `engines`, lefthook; the plan follows them rather than adding Vitest.

## Assumptions
- Docs repos are public and branch `main`.
- The design is the visual truth where it does not conflict with the code or docs; text there that claims facts is verified, not copied.
- No domain: `SITE_URL` is configurable; default placeholder.
- Dev-only tooling (build, test, a11y) does not need to be on the runtime approved list, but is named and justified in the plan; runtime (browser-shipped) deps are only preact (+ compat) and fonts.
- One feature, one target PR (plus the separate meta PR for approved packages).

## Acceptance check (derived)
In a fresh clone of pulse-website on Node 24:
1. `npm ci && npm run check` passes: lint (Biome, ESLint), typecheck, tests (coverage gate), build, link check, a11y check, size budget.
2. `npm run build` produces `dist/` with `/`, `/hosted/`, `/docs/…` (every published `docs/*.md` of api, probe, status, notify, contract, kit incl. REST API at its own page), `404.html`, `sitemap.xml`, `robots.txt`; every page has title, description, Open Graph tags.
3. With JavaScript disabled every page renders fully and navigates; with JavaScript only islands are hydrated; the page has no request to any other origin.
4. Docs pages show sidebar, "On this page", previous/next, "Edit this page on GitHub" (to the pinned source file) and "Generated from <file> in <repo>"; relative links resolve to site URLs or GitHub; no dangling links or anchors.
5. The pinned SHAs live in one file; the bump script updates them; the build reads only those SHAs.
6. The hosted page has no real price, region, trial, data location, OSS terms or status URL, only marked placeholders; the waitlist form is disabled and sends nothing.
7. Home facts (check types, channels, endpoints, env vars, commands) each match a named source in the pulse repos.
8. axe reports no WCAG 2.2 AA violation in light and dark; keyboard paths work; targets ≥ 44 px; light/dark colours come from `losoft-tokens.json`.
9. README, AGENTS.md and CLAUDE.md exist with commands, layout, conventions and the docs pinning; CI workflow uses the shared `check.yml`.
