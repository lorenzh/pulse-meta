# Issue review: #527 Release images to ghcr.io with SemVer tags and provenance

State `issue-review`, workflow `spec`. Checked against `main` of config, api, probe, status, notify and console (clones under `.repos/`), and against #460 (decision 8), #528 and #529.

Verdict: the feature can be specified. No question blocks the spec. The open points below have a stated default that the plan may take or override with a reason.

## What `main` has today (verified)

- **config**: `.github/workflows/check.yml` is a reusable workflow (`workflow_call`, input `build`) that runs install, lint, typecheck, optional build, and test on `ubuntu-24.04` with `contents: read`. The README documents the pin rule: the SHA in `package.json` and the `uses:` SHA in each target's `ci.yml` change together. No release workflow exists.
- **api, probe, status, notify, console**: each `ci.yml` calls `lorenzh/pulse-config/.github/workflows/check.yml@51e95b0…` and has a `docker` job that runs `docker build` (amd64 only) and checks the image. Nothing is pushed. Repo-specific extra jobs: api has `bench-selftest` and `compose-e2e`, status has `a11y`, and console has a container smoke test in `docker`.
- All five Dockerfiles use `oven/bun:1.4.0-alpine@sha256:07235578…`. I queried Docker Hub: this digest is a multi-arch **index** with `linux/amd64` and `linux/arm64`. So the digest pin does not block an arm64 build. The build stage runs `apk add git` and `bun install` with `github:` dependencies (pulse-contract and pulse-kit are public), so the build needs network access but no secret.
- Every `package.json` has `"version": "0.0.0"` and `"license": "MIT"`. No service reports its version at run time.
- `docs/development.md` exists in all five services. None mentions releases. The READMEs name only local tags (`pulse-<svc>:local`).
- `api/compose.yaml` builds probe, status and notify from `https://github.com/lorenzh/pulse-<svc>.git#main` and api from `.`. Console is not in it on `main` yet (#520/#525 are in flight).
- `lorenzh` is a **user** account, not an organisation. Package API paths and settings are under the user.
- `docs/approved-packages.md` (meta), section "Runtime and CI", lists the CI actions that may be used. Today it has only `oven-sh/setup-bun`, `actions/checkout`, `actions/setup-node`, `actions/upload-pages-artifact`, `actions/deploy-pages` and the `oven/bun` image. No `docker/*` action and no `actions/attest-build-provenance` is approved. Side note: the `actions/checkout` row says `fbc6f39…` (v5.1.0), but the targets use `3d3c42e…` (v7.0.1).

## Scope clarifications (assumptions)

1. **No Compose change in this feature.** The intro quotes decision 8 ("Compose uses tags instead of `git#main`"), but the required behavior does not ask for it, and #528 owns the Compose setups with digest-pinned images. `api/compose.yaml`, `compose.e2e.yaml` and `compose/` stay unchanged. `compose-e2e` keeps building from `main`. The images that this feature publishes are what #528 consumes.
2. **Order of targets:** `config` first. api, probe, status, notify and console each `dependsOn: ["config"]`, because each calls the new reusable workflow pinned by the merged config SHA. The five services do not depend on each other.
3. **Approving the new actions belongs in the spec PR.** Meta is not a listed target, but earlier spec PRs (#520, #369) updated `docs/approved-packages.md` themselves. The plan adds every new action (for example `docker/setup-buildx-action`, `docker/setup-qemu-action`, `docker/login-action`, `docker/metadata-action`, `docker/build-push-action`, `actions/attest-build-provenance`, whichever the plan picks) to "Runtime and CI", each with its version and full commit SHA. The plan may use fewer actions, for example plain `docker buildx` and `docker login --password-stdin` in `run:` steps.
4. **Pin rule:** a service's release caller pins `release.yml` (or whatever the plan names it) at the same pulse-config SHA as `check.yml` and `package.json`. The config README pin procedure gets the new file. Each service PR moves all three pins to the merged config SHA, in the same change.
5. **Who creates the tags: the owner (a person),** both the test pre-release tag and `v0.1.0` in all five repos. Reasons: the Factory delivers PRs and does not push tags. A tag pushed with a job's `GITHUB_TOKEN` does not start workflows. Cutting a release is a decision a person makes. The PRs and the feature issue list the commands (`git tag v0.1.0 <sha> && git push origin v0.1.0`).
6. **Who makes the packages public: the owner, once per package.** Pushing from the repository's workflow with `GITHUB_TOKEN` and setting the `org.opencontainers.image.source` label links the package to its repository. A new container package under a user account can still start out private, and its visibility can only be changed in the package settings UI (there is no REST endpoint). This is a manual step after the first push. The docs say so, and the anonymous `docker pull` in the acceptance check proves it.
7. **`main` publishes nothing (recommended default).** Nothing consumes an `edge` tag: #528 pins released versions by digest, and its `dev` setup builds from sibling checkouts. Pushing on every merge would also give `packages: write` to every `main` run. The plan may choose `edge` instead, but must say who uses it.
8. **Tags:** on `vX.Y.Z`, push `X.Y.Z`, `X.Y` and `X`, as the issue says (so `0.1.0`, `0.1` and `0` for the first release). On a pre-release tag `vX.Y.Z-<pre>`, push only the exact `X.Y.Z-<pre>`, never `X.Y`, `X` or `latest`. No `latest` before 1.0. Reject any other tag shape with no push. `docker/metadata-action` behaves this way for `type=semver`, apart from the reject. Note for the plan: under SemVer a `0` tag moves across breaking 0.x minors. The issue asks for it, so it stays unless the plan argues otherwise.
9. **Provenance: `actions/attest-build-provenance`** (with `push-to-registry: true`) on the pushed index digest. The acceptance check uses `gh attestation verify`, which verifies GitHub artifact attestations, not the in-toto manifests that buildx attaches. Whether to also keep the buildx `provenance`/`sbom` attestations (they show up as `unknown/unknown` entries in `imagetools inspect`) is left to the plan.
10. **The release gate is `check.yml` (lint, typecheck, test).** The publish job `needs` it, and any failed or skipped check means no push. The repo-specific image checks that already run in `ci.yml` (no test files or dev paths in the image; the console smoke test) are cheap and also guard the published image, so the plan should say whether they gate the release too. api `compose-e2e` builds the other services from their `main`, so it does not gate an api release. status `a11y` is the plan's choice.
11. **The tag, not `package.json`, is the version source.** `package.json` stays `0.0.0`. The OCI `version` label and the image tags come from the git tag. The plan may add a check that the tag matches `package.json` instead, but then each release needs a version-bump PR first. The plan says which.
12. **OCI labels:** `org.opencontainers.image.source` (repo URL), `.revision` (commit SHA), `.version` (tag without `v`), `.licenses` = `MIT`. `.title`, `.description` and `.created` are optional. Labels go on the index and on each platform manifest, or at least where `imagetools inspect` shows them. The plan names which, because a multi-arch label shown by `imagetools inspect --format '{{json .Image}}'` sits on the platform config, while index annotations need `annotations:`.
13. **Permissions:** workflow level `contents: read`. The check job stays read-only. Only the publish job gets `packages: write`, `id-token: write` (attestation signing) and `attestations: write`. A called reusable workflow cannot raise permissions, so each service's calling job grants exactly these. `actions/checkout` uses `persist-credentials: false`. Every action is pinned by full SHA with a version comment. No PAT and no registry secret: login uses `GITHUB_TOKEN`.
14. **Concurrency:** one group per tag, with no cancel-in-progress for releases.

## Open points for the plan (not blocking)

- **How to build arm64.** One option is QEMU emulation on an amd64 runner (simple, slower; Bun has had trouble under QEMU in the past). The other is native `ubuntu-24.04-arm` runners (free for public repos), one job per platform, pushed by digest and then merged into one index with `docker buildx imagetools create`. Native runners need more workflow code but avoid emulation risk. The plan picks one and reports the duration it expects. The issue asks to report the real duration after the first release.
- **Proving "a red check publishes nothing" before merge.** A Factory implement run cannot push tags. Possible evidence: (a) structure, where publish `needs: check` and the build is not reachable on failure; (b) a test in config, where config CI calls the reusable release workflow with a `push: false` dry-run input on a fixture, plus a case that fails its check; (c) after merge, the owner pushes a pre-release tag on a throwaway branch with a failing test and shows the publish job skipped. The plan picks the evidence. (c) is a manual step after merge.
- **Dry-run builds in PR CI.** If the reusable workflow takes a `push` input, a service's `ci.yml` could build both platforms on PRs without pushing. That catches arm64 breakage early but adds CI time. The plan decides. The existing amd64 `docker` jobs stay in any case.
- **Where a tag may point.** The plan decides whether a release tag must point to a commit on `main`, with pre-releases exempt so the throwaway-branch test still works. A `v*` tag ruleset limited to the owner is a repo setting (manual, documented, not done by the Factory).
- **Re-pushing a tag** overwrites the image. The plan decides whether the workflow refuses when that version already exists in the registry, or only documents "never move a release tag".
- **Cleaning up the test tag.** The issue asks to delete the pre-release git tag afterwards. The plan states whether the `0.0.0-rc.1` package version is also deleted (owner, in the package settings or with `gh api -X DELETE /user/packages/container/pulse-<svc>/versions/<id>`).
- **Docs per service.** `docs/development.md` gets a "Releasing" section: tag format, the workflow, the gate, where the image appears, the one-time visibility step, and how to verify with `gh attestation verify oci://ghcr.io/lorenzh/pulse-<svc>:<tag> --owner lorenzh`. README names `ghcr.io/lorenzh/pulse-<svc>` and may show a `docker run` with a version tag. The config README documents the reusable workflow, its inputs, and the permissions the caller must grant.
- **Meta docs** (in the spec PR, optional): the meta README or `docs/architecture.md` may mention the published images. The Compose section stays as it is until #528.

## Derived acceptance check

Done when, after the six PRs are merged and the owner has pushed a test tag `v0.0.0-rc.1` on one service (then deleted it) and `v0.1.0` on all five:

1. `docker pull ghcr.io/lorenzh/pulse-<svc>:0.1.0`, logged out, succeeds for api, probe, status, notify and console on `linux/amd64` and `linux/arm64` (`--platform`). The tags `0.1` and `0` exist, and no `latest` exists.
2. `docker buildx imagetools inspect ghcr.io/lorenzh/pulse-<svc>:0.1.0` lists both platforms. The labels show `org.opencontainers.image.source=https://github.com/lorenzh/pulse-<svc>`, `revision=<tagged SHA>`, `version=0.1.0` and `licenses=MIT`.
3. `gh attestation verify oci://ghcr.io/lorenzh/pulse-<svc>:0.1.0 --owner lorenzh` succeeds.
4. The pre-release tag published only `0.0.0-rc.1` (no `0.0`, `0` or `latest`).
5. A tagged commit with a failing test produces no push: the publish job is skipped or failed, and no new image version appears (demonstrated as the plan chooses, see above).
6. A push to `main` publishes nothing (or only `edge`, if the plan chooses it).
7. Each package page shows "public" and links its repository. Each release workflow pins every action by SHA and grants write permissions only to the publish job.
8. CI is green in config, api, probe, status, notify and console. The release workflow duration is reported in the feature issue.
