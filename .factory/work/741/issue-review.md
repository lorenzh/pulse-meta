## Verified behavior

1. `console/src/account-pages.ts` imports `plainDocument as layout`. `securityPage`, `sessionsPage`, `signOutAllPage` and `newCodesPage` each return complete standalone documents. Their handlers in `src/account-routes.ts` send them directly. The two confirmation URLs are `/account/sessions/sign-out-all` and `/account/recovery-codes`; the latter is the password confirmation, not the successful response containing the ten new codes. Neither confirmation currently has Cancel.
2. `src/shell.ts` already provides the instance header, user name and email, role, sign-out POST, skip link, main navigation and one page heading. `server.ts:signedInPage` supplies the current user's role, CSRF and a separate sign-out form token. `http-context.ts` already supplies account routes with their gated current session and form tokens. The existing shell can be reused without rewriting account authorization or mutations.
3. `src/navigation.ts` exposes Overview to every role and Team to Admin/Owner. Other registry entries remain unavailable. There is no account navigation ID. Account pages should not enable unavailable screens or mark Overview as the current page merely to provide a return link.
4. The shell 404 in `server.ts:sendNotFound` passes title `Page not found` and `notFoundState()`. The latter renders the same text in an `h2` and only the Overview link. This explains the visible duplicate. Signed-out and non-GET/HEAD unknown-path behavior is separate and must remain unchanged.
5. `src/api-failure.ts` already gives timeout its own `5 seconds` sentence and network a different sentence. `overview-read.ts` maps contract errors to those variants, and existing `overview-read.test.ts` and `server.overview.test.ts` cover a closed port and an injected timeout. However, the network variant discards the cause, so connection refusal and other network errors cannot have distinct visible wording. The pinned contract already returns a network error with a `cause`; only a fired deadline produces its timeout variant. Source inspection alone does not reproduce the screenshot's false timeout. Establish that behavior through the live request path before attributing it to any particular module.
6. `src/styles.ts` colors `nav a`, but has no common normal/visited link styling for the header or account content. Its `.actions` gap applies within one action group; it does not space separate adjacent forms. Authenticator and factor pages have consecutive forms. The broad `overflow-wrap: anywhere` rule and the header's flex layout allow the email text in `.account` to split internally.
7. `e2e/run.ts` already uses Chromium at 390 and 1280 px, checks document width without hiding root overflow, runs axe, checks keyboard focus/CSP, and exercises confirmations without JavaScript. It visits synthetic API state routes and the real 404, but has no layout assertions for the four account pages or the rendered email. Its fixture owner is `owner@example.com`, so the issue's hyphenated address needs a deliberate fixture. The Overview case called unreachable currently uses HTTP 503, not a refused socket.

## Open points and assumptions for the plan

- **Scope of account adoption:** the four named pages are mandatory. Their ordinary validation/expired-form re-renders must retain the shell, navigation and return links too. Do not migrate only successful GETs. Other account surfaces exist: password change, authenticator replacement/enrolment, and the once-only recovery-code result. Treat them as regression surfaces and style the named links/buttons there; they are not additional mandatory shell migrations. If a shared renderer also supplies a shell to a full-session variant, describe that explicitly in the plan and keep the page's content and flow intact. Password-only factor and enrolment stages must not gain a full signed-in shell or access by implication.
- **Return destinations:** use the existing navigation's visible Overview link to `/` as the universal way back. Put an ordinary Cancel/back anchor in the same action group as each confirmation's primary button: sign-out-all returns to `/account/sessions`, new recovery codes to `/account/security`. It performs no POST and requires no JavaScript. The successful recovery-code result keeps its existing safe Continue destination; Cancel must not be offered as though generated codes could be undone.
- **Layout integration:** render one HTML document with one page `h1`, the normal shell assets and the role-filtered navigation. Avoid nested standalone documents, duplicate headings and accidentally duplicated sign-out forms when reusing page bodies. Any rendered POST form keeps its correctly bound CSRF and single-use token. Reusing the generic confirmation component must not introduce its hidden revision field or different confirmation semantics into these account actions.
- **API diagnosis:** expose understandable timeout, connection-refused, other network-error, and HTTP-status wording. Exact copy is a spec choice; only a deadline that actually expired may say `5 seconds`. Classify a known refusal from structured transport information, with a generic network fallback when the runtime supplies no reliable code. Never guess refusal from elapsed time or print raw exception messages, upstream bodies, tokens or full request URLs. Preserve the current safe origin-only convention and Retry action. Preserve special token-rejected, wire-version and invalid-response behavior. HTTP-status failures must identify the status; do not turn an HTTP 503 response into a timeout.
- **Transport boundary:** the contract already preserves the network cause; no contract/API change, package addition or dependency repin is expected. The plan must establish whether the observed false timeout is reproducible on the pinned runtime. If the live refused read already has correct non-timeout wording, record that as an existing positive control and add the missing refusal category and browser coverage. Do not claim a reproduced bug or rewrite the transport without evidence. Setup's separate `connection-test.ts` also has distinct timeout/network text; preserve that distinction if shared presentation helpers change.
- **Styling:** use the existing `/console.css` and shell palette for header Account security, account links, Continue and confirmation Cancel/back, with deliberate normal/visited/focus treatment. Space adjacent form/action blocks on authenticator and two-factor sign-in screens. Choose a consistent positive gap in the plan; no redesign, new dependency, inline style or additional script is needed. Preserve keyboard affordances and readable contrast.
- **Mobile email:** moving the whole address onto another line is acceptable. Truncation is also allowed if the full address remains available in the DOM and can be obtained with pointer, keyboard and touch. Prefer whole-address wrapping for the supplied example. Very long addresses still must fit without horizontal scrolling. Do not satisfy the width check by hiding/clipping document overflow or hiding the identity.
- **Security and content:** retain all gates, roles, cookies, single-use tokens, POST validation order, race guards, status codes, redirects, throttles and one-time code disclosure. Keep the existing CSP, the single `/console.js` on shell pages, referrer policy and `no-store` behavior. Limit account copy changes to the requested wording/links/layout. No storage/schema, security policy, API, deploy or shared tooling change is required. Update the relevant console documentation as its instructions require, without broad unrelated edits.
