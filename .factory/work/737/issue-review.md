## Verified behavior and defect mechanism

1. `notify/src/api.ts` defines `ManualIncidentsResult` with accepted `incidents`, `rejected`, and `isAbsent`. `fetchManualIncidents` drops any raw item for which the contract's `isPublicManualIncident` returns false before calling the validator. No identity of a filtered item reaches the result. The guard in `contract/src/manual-incident-public.ts` accepts missing privacy fields for older APIs and rejects internal, unpublished, malformed, and accessor-defined privacy values without executing getters.
2. `notify/src/notifier.ts` builds `#visibleManual` exclusively from `manualResult.incidents` on a successful non-404 read. It preserves that set after a failed read or 404. This conflates eligibility for public delivery with presence in the upstream feed.
3. At the first successful automatic-incident poll, then at most hourly, `#pruneLedger` passes that set to `Ledger.prune`. `notify/src/ledger.ts` keeps manual keys if their incident ID is in that set, or if the set is undefined before a good manual read. Otherwise old settled keys are eligible for deletion. Pending entries are never pruned. A filtered incident therefore looks absent even while its raw item is still listed. Deleting its delivered key makes republication detectable as an unhandled event.
4. The guard applies to `/manual-incidents`, not automatic `/incidents`. Manual opened, update, and resolved keys share the `manual:<id>:` namespace, so presence protection must cover existing keys for the incident, not only its opened key.
5. Current source and README use SQLite ledger format **4** (`LEDGER_VERSION = 4`), despite the older format-3 summary in notify `AGENTS.md`. The existing `prune` API already accepts a presence set; no storage-format change is evidently needed.
6. Existing tests provide the necessary patterns: `test/manual-incidents.test.ts` supplies raw private feed items, awaits `tick()` and `idle()`, checks catch-all/component routing, draft publication, and restart; `test/prune.test.ts` injects the clock into both notifier and ledger; `test/feeds.test.ts` verifies that failed manual reads preserve keys across pruning. `src/api.ts` already has a descriptor-based `safeId` reader and a separate `listedIds` precedent for component-feed presence.

## Open points and working assumptions for the plan

These points have sufficient defaults to specify without a hold.

- **Scope and dependency:** implement notify fetch-result/presence plumbing, focused tests, and relevant notify documentation. Build on the merged #734/PR #45 behavior and existing contract helpers. No API, contract, status, deploy, routing-policy, package, or configuration change is required by this request. #568 need not finish its other children before this notify-only follow-up can proceed.
- **Presence versus eligibility:** carry numeric IDs of filtered raw manual incidents to pruning independently of the validated public incidents. Only public validated projections may reach seeding, event detection, routing, or notification payloads. Tracking an ID must not create a seeded/delivered key or mark an unseen draft as handled. A draft first encountered privately must still be announced normally when later published.
- **Identity validation:** use a safe numeric own data-property ID without coercion or getter execution; ignore missing or unusable IDs. Private items need not satisfy the public incident validator to protect an already-known ID. Never inspect or retain private titles, messages, notes, drafts, or other payload fields merely to obtain presence. Reuse the existing safe-ID convention where appropriate.
- **Which IDs the result carries:** the plan should choose either all safely identified raw listed items (the component-feed precedent) or accepted public IDs plus safely identified guard-filtered IDs. Both cover the request. If it chooses all raw IDs, explicitly describe the conservative additional retention of malformed public items with usable IDs; their existing rejection/logging/metric behavior must remain. Do not turn this into a general rewrite of automatic-incident validation or pruning.
- **Meaning of “exists in the feed”:** protection applies to an ID actually returned in a successful feed array, even when filtered out of delivery. It cannot cover a private row the API omits entirely. Keep existing last-good-read semantics for failures and 404; a successful empty array establishes absence. After actual absence and sufficient age, settled entries must again be prunable. This is bounded by ordinary retention semantics, not permanent tombstones.
- **Privacy and normal behavior:** preserve the contract guard and public projection. Filtered items must remain absent from `rejected`, malformed-item logs and counters, first-start seed counts, and channel output. No new private-item metric or log is needed. Legacy public feed items without visibility/publication metadata still pass. New public events still send normally; existing public keys, channel filters, and first-start behavior retain their meaning.
- **Delivery scope:** this hardens retention of existing deduplication records. It does not add recall, purge queued/pending payloads, change retry or manual-resend semantics, or provide exactly-once delivery across a crash. Decision 6 of #568 remains the supported publication policy.
- **Storage:** default to keeping ledger format 4, existing key formats, timestamps, and pruning cadence. A presence set supplied during polling should suffice. If the plan finds a storage change necessary, justify it explicitly, as the issue requires.

## Derived acceptance check

1. **Regression that fails for the reported reason:** through the real notifier and a local fake API, inject the same clock into notifier and ledger and use a short configured retention (for example one day). First poll a successful empty manual array to establish channel/manual initialization. Add a public manual incident with a fixed ID and fixed public event data; await `tick()` and `idle()` and assert exactly one `manual:<id>:opened` delivery. Serve the same raw ID with `visibility: "internal"`, advance beyond both retention and the hourly prune interval, and poll while the automatic feed succeeds so pruning actually runs. Assert its delivered key still exists. Restore the identical public event data and poll again: each eligible channel must still contain exactly one opened delivery in total. Include an old absent control key that is pruned to prove the pruning path ran. With unchanged test assertions against notify main at the recorded SHA, demonstrate a lost key and/or duplicate-delivery assertion failure; with the fix, demonstrate success. A coverage-only failure does not establish the regression.
2. **Draft and event-key coverage:** repeat retention protection with `publishedAt: null` rather than internal visibility. Verify existing manual opened/update/resolved keys are retained by incident identity where present; republication of unchanged events must not redeliver any of those events. Do not use changed update text/timestamps as the duplicate oracle, since those can represent new events.
3. **Public behavior and privacy:** retain or extend the existing catch-all and component-filtered channel cases. Private-only polls send nothing and do not increase skipped-item metrics or emit private-item logs; a public positive control is delivered and a malformed public control still exercises rejection reporting. Existing note/draft-field stripping remains covered. A draft with no previous public delivery, including one seen at first start, sends once on publication and remains deduplicated after restart. An older-API item without privacy fields still sends as before.
4. **Retention boundaries and persistence:** once the raw ID is truly absent from a successful manual feed read and the key is old enough, an eligible hourly prune removes the settled key. Failed/404 manual reads preserve the last good presence information; before any good read manual keys remain protected. Pending entries remain unpruned. Reopen the same ledger after a private poll beyond retention and verify that republication of the previously delivered unchanged event still sends no duplicate.
5. **Fetch-result boundary:** assert filtered usable IDs reach only presence metadata while accepted incidents remain public projections and filtered items are not rejected. Include a private item lacking required public payload fields but carrying a usable ID, plus an unusable-ID control, to ensure the protection does not rely on validating private content or inventing identities. Define and test any deliberate malformed-public retention policy chosen above.
6. **Implementation evidence:** run notify's required `bun run check` without weakening lint, typecheck, or coverage, and retain the failing-before/passing-after regression evidence. Follow notify's required local service smoke procedure with a fake API and file channels; use an injected clock for the automated retention test, not a real-time retention wait. Update README/operation retention wording to explain presence protection for filtered IDs without promising delivery of private content or protection for items omitted from the feed.
