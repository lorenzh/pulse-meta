## Open points and assumptions for the spec

1. **Design coverage and copy.** The local export is version 28. `Main.dc.html` supplies the Components and Feed and badges cards (around lines 288–297), but lacks CDN-ready caching, Hot backups, console architecture, the two new Home bands, and their previews. `Docs.dc.html` lacks the Coming soon group; `Hosted.dc.html` lacks the console card/row. Treat the issue as the authoritative additive scope. Use the existing design tokens, components and page patterns; a newer canvas export is not a prerequisite. The plan must write down exact new copy and placement before implementation instead of leaving implementers to find a missing design.

2. **Card order and truthful scope.** Add Components and Feed and badges after White-label status page and before Incident updates, matching the export. Add CDN-ready caching and Hot backups in a stated position; assume after Checks API and before Notifications. The resulting feature grid has 15 cards, retaining all 11 existing ones. Components means grouping checks into user-facing components; feed means Atom, not RSS. Caching copy must describe ETags, revalidation and cacheable feed/badges without promising that every response can be publicly cached. Hot backups means the existing operator-run API backup command while serving traffic, not scheduled off-site backups or a hosted guarantee.

3. **Component preview copy.** Replace “Every check” with “Every component” in the status section and make surrounding prose coherent with the component view. Keep names, states written as words, privacy qualification and theming facts accurate; do not mechanically replace every occurrence of “check” across Home. Existing `StatusMock` is explicitly an example; distinguish any illustrated check-only view from the default component presentation.

4. **Optional fifth service.** Extend the architecture text, SVG, accessible title/description and service list consistently for optional pulse-console. Distinguish its admin role from status/notify reads and from deployment tooling. Explain that console management is in progress; a connection labelled as planned must not imply implemented management operations. Update “Four”/“All four” wording consistently without making the console mandatory. Recheck any statement that all services share pulse-contract against their packages, rather than extrapolating from the old diagram.

5. **Roadmap versus implementation/release.** Retain the requested “Coming next” band, console “in progress”, and pulse-deploy CLI “coming soon” presentation, with no date. Qualify the CLI as forthcoming release/availability while acknowledging its existing source and guide; do not say the wizard has not been implemented or leave a fake download link. Console previews of future management need an explicit “Preview”/“Planned” indication. Recheck availability at planning/build time and disclose any wording adjustment required by newly published releases; do not expand this issue into console/CLI implementation.

6. **Previews and destinations.** No screenshot assets, recording, public demo URL or console endpoint were supplied. Assume three local static illustrations/mockups with captions: status page, CLI wizard and console. They form a distinct “See it in action” section; the existing status preview alone does not fulfill it. Reuse suitable HTML/SVG/CSS and the status mock where useful, with no iframe, external runtime fetch, credentials, executable demo or interactive terminal. Give any links real generated docs destinations; use no placeholder `href="#"` or invented hosted URL. Existing animation may be reused within its reduced-motion/visibility rules; new motion is not required.

7. **Docs readiness and Coming soon semantics.** The condition “once they have docs” is already met for both repositories. Add `console` and `deploy` to `DOC_REPOS`, then generate their config entries with targeted `docs:bump` invocations; include all three console files and deploy `docs/cli.md` at verified main pins. Avoid an unrelated bump of all six existing sources. Assume “Coming soon” is a roadmap grouping, not a claim that all documentation is absent: make existing docs usable and keep product progress labels separate. The spec should place a console overview and CLI guide in that group with appropriate progress labels, and place the other console files in suitable groups, each exactly once. If it chooses non-link forthcoming entries as well, those entries must be explicitly modelled and excluded from published-file validation and the pager; never invent unpublished Markdown paths to satisfy a label.

8. **Pinning and routes.** No upstream documentation edits are needed. Generated console routes follow the current convention: `/docs/console/`, `/docs/console/configuration/`, `/docs/console/development/`; deploy has `/docs/deploy/cli/`, not an assumed `/docs/deploy/` index. Preserve source attribution, Markdown links/anchors, navigation coverage and previous/next behavior. Update the README's six-repository description. New product facts need named upstream sources and appropriate independently copied fixtures under the existing facts discipline. The outdated hero Compose example is outside this request unless a necessary fact/pin change directly affects it.
