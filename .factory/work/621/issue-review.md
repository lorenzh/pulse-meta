## Gaps, open points and planning assumptions

1. **The manual-write baseline has changed.** Deploy's current "Manual incidents" step (around lines 483–489) accepts either 401 or 403 for the probe token and prints that allowance. Missing credentials must still produce exactly 401. Once the API pin contains #617, tighten the probe assertion to exactly 403 and update its diagnostic and success output. Keeping the dual-status allowance would miss a broken or unimported probe credential.

2. **The acceptance wording needs an honest red baseline.** The issue's historical 401-only assertion fails against the new API, but the inspected deploy main accepts both and therefore need not fail there. Do not claim the unchanged current script reproduces that failure. Demonstrate the historical 401-only check against the same qualifying image in an isolated temporary test variant or equivalent focused reproduction, record the actual 403, then run the final strict assertion and complete e2e successfully. Identify the baseline and commands in the PR. The full unmodified current script may be useful context but cannot supply this particular red proof.

3. **Release selection is an implementation prerequisite.** The requested transition belongs with the API image bump to a published release containing #617. The plan must verify the release's source commit includes that implementation and select its immutable version/digest, using `scripts/bump-images.sh`; all pins remain solely in `common/services.yaml`. Do not invent a version or infer release contents from API `package.json` (currently `0.0.0`) or from a main checkout. A release not yet published delays implementation/acceptance, not specification. State the dependency on #617 and the release explicitly; native "blocked by" linkage belongs to Factory/provider orchestration, and this review changes no provider metadata. Do not merge new-route checks against the old published API or hide missing routes behind conditional skips.

4. **Port all of API T6's compose checklist.** There is currently no "Tokens and audit" step or call to `/admin/tokens*` or `/admin/audit*` in deploy's script. Add that step after "Checks via the admin API and hot reload", adapting paths and helpers to deploy. The e2e admin bootstrap config already names its token `e2e`; the existing check-create scenario supplies `e2e-api`. Reuse that audit event even though the check is later deleted: the audit must persist independently of the current checks file. No new API or contract implementation is requested.

5. **Make scope rejection independent of revision/body errors.** The `['read','checks']` credential must attempt a valid check create with the current `If-Match` revision and a valid, unused check ID, so 403 proves missing mutation scope rather than a malformed or conflicting request. Existing `cfg_code` always uses the bootstrap admin credential; planning must provide a way to send the tested credential. Ensure the denied request introduces no check or unexpected successful-write metric change.

6. **Rotation is an isolated credential lifecycle.** Create a separate probe token for `e2e-rotated`, authenticate it on `/probe/checks`, rotate it, verify both old and new credentials during the ten-minute overlap, then revoke that token ID and verify both fail with 401. Do not rotate or revoke the running stack's bootstrap probe/admin tokens. No ten-minute sleep, clock manipulation, expiry-boundary integration test, or restarting the running probe with the rotated credential is required by T6; those behaviors are already API test concerns.

7. **Audit and secret assertions must be meaningful.** Query `action=check.create` and assert an entry with target ID `e2e-api` and actor name `e2e`. Check the NDJSON export one JSON object per line with `jq`, require a nonempty successful response, and inspect both query and export for leaked credentials. Collect every secret returned by create/rotate, plus the bootstrap e2e admin credential, for fixed-string checks against audit output and compose logs. Failures and PR evidence must identify the failed rule without printing credentials or complete secret-bearing responses. Preserve the script's existing checks for header/body secret leakage. Check logs late enough to include the new routes and restart, before containers are removed; down/up discards earlier container logs, so inspect/capture both phases as needed.

8. **Extend the existing persistence step.** It currently checks volumes, incident persistence and service health after `docker compose down` / `up -d`. Also assert that the same bootstrap admin credential still gets 200 on `/admin/config` and that the identified `e2e-api` audit event is still present. Preserve the database volume during this step and retain final teardown. Existing probe, status and notify scenarios continue to prove imported bootstrap credentials work across the run.

9. **Header-binding coverage is partly complete and has a probe dependency.** The owner's comment says to cover #552 once an API release contains it; actual binding enforcement belongs to the probe. Deploy's overlay already supplies `PULSE_PROBE_HEADER_HOSTS: '{"PULSE_HEADER_SVC_TOKEN":["e2e-target"]}'`, and `e2e-post` addresses `http://e2e-target:8000/svc` with that env header. The target accepts only the expected authenticated request, and the script already waits for this check to be up and to recover after controlled failures. Retain this fixture; do not add it twice. To claim live binding coverage, verify that the probe image used for acceptance contains #552's enforcement, bumping its published pin if necessary with the same release verification discipline. An older probe ignores the setting, so a green run on it proves only fixture compatibility. Spec #552 behavior 13 explicitly says not to add a new denial scenario to compose e2e because a persistent down check would alter incident/notify expectations; assume the owner's reference retains that scope. Denial remains covered by probe tests. Record the enforcing probe release used as acceptance evidence.

10. **Bounded target and verification scope.** Assume only deploy changes: e2e script/helpers as needed, image pins, and relevant README coverage description. API/probe clones supply read-only context. Keep the published-image full-stack path and CI's existing `full` job; do not substitute builds from main as the final release acceptance, introduce runtime packages, change user setups, or expand this into all token/audit unit tests. Deploy instructions require all checks of touched CI jobs: shellcheck and shell syntax, relevant helper/static checks, pin verification and the full job's readiness/measurement and compose e2e.
