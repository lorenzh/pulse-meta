# Spec: TCP, DNS and domain-expiry checks (#382, F9)

## Goal
Three check types next to `http`, `tls`, `heartbeat`: `tcp` (a port accepts connections), `dns` (a record resolves to the expected values), `domain` (the registration does not expire soon). Rollout stays on `WIRE_VERSION` 1.

## Scope
contract (schemas, validator, docs), probe (runners), api (checks file, storage, migrations, serving, compose, docs), status (render, privacy filter). Not changed: notify, config, kit, website.

## Non-goals
No WHOIS (RDAP only), ICMP, UDP, TLS on TCP checks, DNSSEC, browser checks, check editing through the api (F7), public-suffix-list validation (needs a dependency), migration framework or package.

## Observed on main (verified in the clones)
- contract `schema.ts`: `httpCheckSchema`, `tlsCheckSchema` (no `retries`/`retryDelayMs`), `heartbeatCheckSchema`; `validate.ts` `checkBase` switches on `type` and answers `must be "http", "tls" or "heartbeat"` for others. `certDaysLeft` exists on results and on state fields.
- probe `client.ts` `loadChecks`: validates each item and, on failure, logs `skipping invalid check<id>: <error>` and continues. So an old probe skips an unknown type per check, with a log line, and runs the rest. This confirms the issue's rollout assumption; no api-side capability filter is needed.
- probe `check.ts`: `runCheck` has TLS branch `runTlsCheck` (`DAY_MS`, `daysLeft = floor((validTo-now)/DAY_MS)`, expired -> down "certificate expired", `daysLeft <= warnDays` -> **down**). Deps are injected (`tlsConnect`, `now`, `monotonic`); retries loop only for HTTP.
- api `db.ts`: `CREATE TABLE IF NOT EXISTS` schema, `checks.url TEXT NOT NULL`, columns `host`, `port`, `warn_days`, no `user_version`. `docs/operation.md` line 23 says "no upgrade path". `config.ts` parses by type with `type !== "http"|"tls"|"heartbeat"` rejection and strict keys; `service.ts` `toCheck`, upsert (line ~240), `withPlaceholders` and `isFull` (probe listing) vs public listing.
- status `api-filter.ts` `cleanTarget` (hidden => no target; `tls` => host/port only when not hidden; unknown type => `{}`), `render.ts` shows days left only for `type === "tls"`.
- api has no `bench/` directory in `main`.

## Decisions (made by the plan)
1. **Domain state rule.** The issue's acceptance says "degraded within `warnDays`, down when expired". Today's TLS check goes `down` within `warnDays`; the issue wording ("follows the TLS rule") and its acceptance differ. Decision: `domain` follows the acceptance: `up` when `daysLeft > warnDays`; `degraded` when `0 <= daysLeft <= warnDays` (reason `domain expires in N days`); `down` when expired (`expiry <= now`, reason `domain expired`) or expiry unknown after retries. The TLS check is not changed. Docs state the difference.
2. **Days left.** `domain` reuses `certDaysLeft` (floored whole days, negative when expired, null when unread). Contract field comments and docs (`concepts.md`, `configuration.md`, status docs) say "TLS and domain checks". No new field, no wire change. The api and status treat `type === "domain"` like `tls` wherever `certDaysLeft` is stored, served or shown.
3. **Common fields.** `tcp`, `dns`, `domain` all carry `id`, `name`, `intervalMs`, optional `timeoutMs`, `retries` (0..10), `retryDelayMs` (0..60000) and reject the HTTP-only fields (`method`, `headers`, `body`, `expectedStatus`, `jsonAssert`, `keyword`, `latencyObjectiveMs`, `url`) via `z.never().optional()`. Default `retries` 0, `retryDelayMs` 1000, served resolved like HTTP.
4. **Field shapes.**
   - `tcp`: `host` (non-empty), `port` 1..65535.
   - `dns`: `dnsName` (non-empty hostname), `recordType` in `A|AAAA|CNAME|MX|TXT|NS` (case-sensitive upper), `expected` optional non-empty array (1..20) of non-empty strings, `resolver` optional IPv4/IPv6 literal (no port, no hostname).
   - `domain`: `domain` lowercase hostname with at least two labels, no scheme/port/path; `warnDays` integer >= 0; `intervalMs` >= 3 600 000 (superRefine error `must be at least 3600000 (1 hour) for a domain check`). `intervalMs` is required for `domain`; no default.
   - Timers are `timerMs` (max 2^31-1) as today. Exported constant `MIN_DOMAIN_INTERVAL_MS = 3_600_000`.
5. **DNS comparison.** Names (CNAME, NS, MX exchange) lowercased, trailing dot stripped. MX values are `"<priority> <exchange>"`. TXT records: chunks of one record joined. A/AAAA compared in canonical form (IPv6 lowercased, compressed via `node:net`/`URL` normalization). Up when every `expected` value is in the answer (superset allowed). Without `expected`: up when `dnsName` resolves with at least one record.
6. **RDAP.** Bootstrap `https://data.iana.org/rdap/dns.json`, parsed to a TLD -> first https service URL map (keep nothing else), cached in memory for 24 h by the monotonic clock; on refresh failure the stale map is used. The lookup TLD is the last label of the domain. Request `<service>/domain/<domain>` with `accept: application/rdap+json`, `fetch` with the check's timeout and the shutdown signal, at most 3 redirects, body capped at 1 MiB (bootstrap cap 2 MiB). Expiry is the event with `eventAction: "expiration"`; no such event or an unparsable date is "unknown": down with reason `expiry date not found in RDAP answer` after retries. HTTP errors give down with `RDAP <status>`.
7. **Older probes.** `WIRE_VERSION` stays 1 (owner, 30 Oct). Docs in probe and api: a new check type needs every probe location updated; until then the check stays `unknown` at old locations and the old probe logs `skipping invalid check`. Rollout order in api docs: update contract users (probes, status), then add the check to the file.
8. **Migrations (api).** `PRAGMA user_version` numbered steps, details under the api section.
9. **Privacy.** `host`, `port` (of tcp), dns `dnsName`, `expected`, `resolver`, and `domain` are check targets: private by default like `url`. The api serves them in `GET /probe/checks` (full) always; in `GET /checks` (public listing) they follow exactly the redaction rule that `host`/`port` of tls and `url` follow today (read in `server.ts`/`service.ts` in the api task; reuse the same switch, do not invent a new setting). Status passes them to the browser only when its existing settings that allow tls `host`/`port` and http `url` allow them. Reasons are filtered by the existing `cleanReason` hiding.
10. DNS hostname field is `dnsName` (not `name`, which is every check's display name); decided during review of contract#34.

## Performance impact
`bench/budgets.json` does not exist in `main` of the api, so the kinds of metric are named.
- Probe CPU and RSS at steady state (probe is not in api's budgets but is the code that changes): `tcp` = one socket per interval, closed at once; `dns` = one `Resolver` query per interval; `domain` = at most one RDAP request per domain per interval (>= 1 h) and one bootstrap fetch per day. Expected: negligible CPU rise (microseconds per check, dominated by network wait); no timers beyond the existing per-check scheduler and per-attempt timeout.
- Memory: DNS `Resolver` objects are created per attempt and released (no pool; `cancel()` on timeout/shutdown). The bootstrap cache holds only a TLD -> URL map (a few KB, not the ~100 KB raw file), parsed from a body capped at 2 MiB, then dropped. RDAP bodies capped at 1 MiB, freed after the expiry event is read. Expected peak RSS change under 1 MB; the implementer reports probe RSS before and after with a local run with 100 mixed checks.
- api: startup CPU and wall-clock startup can rise by one read of `PRAGMA user_version` and, on first start after upgrade, one table rebuild (milliseconds to a few hundred ms for large `checks`; `results` is not touched). Load CPU, p95 latency, requests/s, image size: none expected (a few extra string fields per check row and two more `if` branches in `toCheck`). Test CPU and build CPU: slightly up from new tests (< 5 %).
- Measure: api `bun test` timing and a startup timing A/B of the old and new commit on a database of the production-like size (1 000 checks, 1 M results) using whatever `bench/run.ts` exists at the start of the task (`bun bench/run.ts --a <ref> --b <ref>` if present); otherwise a documented `time` comparison in the PR.

## Risks
- Table rebuild on a large `checks` table: small (checks are tens or hundreds of rows), but the transaction must also keep FKs valid; covered by test.
- `RENAME` with FKs: SQLite rewrites references only with `legacy_alter_table` off; the test with results/incidents rows proves it, fall back to copy-into-existing-name if it fails.
- Domain state differs from TLS (degraded vs down); documented in decision 1.
- RDAP servers vary (rate limits, missing events); handled as unknown with a clear reason; the 1 h minimum limits load.
- Public `GET /checks` leaks if redaction is wrongly copied: privacy tests in api and status.
- Public-suffix domains like `example.co.uk`: the bootstrap lookup uses the last label (`uk`), the RDAP service gets the full name; registries that do not serve RDAP yield "unknown" down. Documented.
