## Decisions to carry forward from earlier runs

These are the prior design baseline reported in the comments. The planner must write them into the new spec and recheck its exact settings, schema and file list against the inspected sources.

1. **Ownership and scope.** Notify owns a separate durable SQLite subscriptions database and all subscriber sends. Status owns the public subscribe, confirm and unsubscribe pages and forwards bounded lifecycle operations to a private bearer-authenticated notify listener (previously port 9300). Contract owns shared request/response validation, address normalization and token formats. Deploy supplies secret wiring, operator setup and compose-e2e coverage. API and console do not change. Expected target order remains contract, then status and notify, then deploy depending on both.
2. **Mail scope.** Subscriptions cover public manual incident publication, published updates and resolution. Automatic check incidents, reminders, warnings, internal notes, draft incidents, unpublished draft updates and internal-only incidents are excluded. There is no new per-update “Notify subscribers” toggle in this issue. The previous plan deliberately narrowed the original broad incident wording to information safely available in the public manual feed.
3. **Enrollment boundary.** Double opt-in is mandatory. “An unconfirmed address gets nothing” means **no incident mail**: the requested confirmation message is the necessary exception. Only events first detected after confirmation are eligible, measured on notify's clock; first activation seeds existing incidents quietly. Re-subscription creates a fresh consent generation and must not revive historical eligibility.
4. **Tokens and actions.** Confirmation tokens are random, stored hashed and expire after 24 hours. Unsubscribe links are HMAC-authenticated and valid for the subscription's lifetime. GET/HEAD only show forms; state changes require POST. Every subscriber message, including confirmation messages, offers unsubscribe. Old-generation links must not delete a later subscription.
5. **Public response secrecy.** Every syntactically valid public subscribe request receives the same generic 200 page, regardless of existing/confirmed/pending membership, refusal under a limit, private-service error, redirect, invalid response, timeout or local private-call saturation. Notify answers valid subscribe requests with generic 202 and silently declines unavailable work. Do not restore the earlier 429 or membership-dependent public pages. Invalid input may have a fixed validation response independent of membership.
6. **Root hosting.** Retain the previously reviewed option explicitly allowed by the manager: subscriptions require root hosting. With subscriptions enabled, both `PULSE_STATUS_PUBLIC_URL` and notify's subscription status URL must reject a non-root path, with exit 2 and a fixed setting-naming error before opening subscription files. Root origins work. With subscriptions disabled, preserve existing URL validation; this does not claim the existing status assets support path-prefix hosting.
7. **Visitor notice and retention.** Require an operator contact setting, previously `PULSE_STATUS_SUBSCRIPTIONS_CONTACT`, accepting a validated email address or HTTPS URL. Show what is stored (including consent/token/delivery records and queued/in-flight mail), retention, deletion method and contact. Carry forward the 24-hour unconfirmed lifetime plus independent cleanup at least hourly, giving a 25-hour live-service bound. Confirmed records remain until unsubscribe. Explain backup/sent-mail exclusions and the in-flight boundary truthfully.
8. **Queue deletion and erasure (D19).** Unsubscribe, expiry cleanup, and row deletion/replacement remove waiting confirmation jobs immediately after the database write, before answering, without waiting for a blocked sender. Confirmation also cancels waiting confirmation jobs. A cancelled retry wait must stop. Workers revalidate existence, consent state, expiry and token generation before each attempt. Incident pages retain ids rather than batches of addresses. Subscriber attempts use `min(PULSE_NOTIFY_TIMEOUT_MS, 60000)` as their whole-attempt timeout. Deletion includes delivery rows and the documented live database/WAL cleanup, plus an offline operator deletion command while notify is stopped.
9. **Shared send coordination (D20, to strengthen).** The last plan used an in-memory guard keyed by subscription row id, shared by confirmation and incident workers. This solves concurrent sends for one row but **does not meet the latest mailbox requirement** after unsubscribe and re-subscribe. Keep the one-email notice only after replacing this guard as described below, or use the manager's explicit alternative and weaken the notice consistently.
10. **Late completion writes (D21).** Every terminal delivery insert must atomically require the original subscription id still to exist; event finalization builds remaining failures from current subscriptions in the same transaction that closes the event. Completing an old send after deletion must write no subscription/delivery record, even if the same address has re-subscribed under another id. Deleted recipients cannot cause retries or keep the event pending. SMTP outcome counters still reflect the actual result.
11. **Durable bounded retries.** Persist event `passes` and `next_pass_at`; commit a pass count before its first attempt. Recovery cannot reset the maximum passes. A restart inside the final allowed pass closes its remaining recipients without new attempts; a restart during backoff waits only its remainder. Preserve ordering and progress to later events. Do not promise exactly-once SMTP delivery across a crash after acceptance but before recording it.
12. **Token exception.** The only token-bearing HTTP answer is the validated, escaped request token once in the hidden form field of a successful confirmation/unsubscribe GET/HEAD page (HEAD has the same representation headers and no body). Those pages are no-store and no-referrer. Invalid pages, POST results, notify responses, logs and metrics contain no token. The generic prohibition and this exception must agree everywhere.
13. **Secrets.** Keep subscriptions disabled by default and new settings in environment variables, independent of #570. Provision the bearer token and HMAC key through the subscription secrets switch. Support an operator-provided optional host SMTP password file, mode 0600, validated before writes and copied as 0400/1000:1000 to notify's secrets volume. Never generate an SMTP password. Missing input removes a stale output; switch off ignores the input. Password/username pairing and transport rules apply. Production override docs must describe the usable path end to end.
14. **Earlier acceptance corrections.** An overlay with total capacity 5 must explicitly set compatible pending capacity 5. Privacy checks must allow the required `privacy@e2e.invalid` contact while forbidding submitted visitor addresses and other unintended mailbox echoes. Compose secret checks must permit the required `/run/pulse/subscriptions-smtp-password` path and check actual sentinel secret contents, forbidden literal-secret keys and misplaced `_FILE` paths, rather than forbidding the word `password` everywhere.

## Open points and working assumptions for the new spec

### A. Mailbox coordination across subscription generations

Recommended assumption: retain the visitor notice's promise, strengthened to at most one in-flight **subscriber** send per normalized address, across both workers and all subscription generations. This does not make claims about independently configured operator-channel mail to that mailbox.

- Define one canonical address rule in contract and use it for uniqueness, lookup, deletion and send coordination. Do not infer mailbox equivalence from provider-specific dots, plus aliases or external DNS. Case/whitespace variants considered equal by that rule must share the guard.
- Key the shared guard by stable normalized mailbox identity, or an equivalent stable digest, not by subscription id, confirmation token or event id. Its lifetime follows the actual in-flight send, so deleting the row, cancelling queued work, confirming or re-subscribing cannot remove or replace it early.
- Acquire it in the same synchronous critical section as the last current-row/eligibility check and the send invocation. Waiters must not keep stale addresses or eligibility snapshots. After waiting they re-read the exact generation, token and consent state; stale jobs do not borrow a new generation's consent. Apply this to new-generation confirmation mail as well as incident mail.
- Release on success, permanent/temporary failure, timeout, cancellation and shutdown, with safe ownership so an old completion cannot release a later owner's guard. No send begins after stop. Specify the single-active-process ownership/lock that makes an in-memory guard sufficient; do not imply it coordinates independent notify processes.
- Keep the deletion notice truthful: at deletion, queued old-generation mail is removed and at most the already-started subscriber attempt may finish. A subsequent explicit re-subscribe can request a new confirmation after that attempt settles. Any short-lived guard/attempt state retained after deletion must match the stated in-flight retention bound.
- A digest guard avoids retaining a second raw address, but does not alone establish the whole privacy promise: queue entries, closures, retry waits, store writes and shutdown must also obey it.

The manager also allows weakening the visitor notice to the real bound. If chosen, name that choice in the plan and revise every literal notice, retention statement and test together. Do not leave a per-row algorithm under a per-mailbox promise. The existing one-email text can be kept with the mailbox guard, so no decision from a person is needed now.

### B. Response timing and limits

Equal status/body does not prevent an existence-dependent early return or wait. Define a **single deterministic response-release policy** for valid subscribe requests, including known confirmed, known pending and unknown addresses. State its injected scheduler/deadline behavior and which work may occur before release. A nominal delay, random jitter, or wall-clock tolerance test alone is insufficient.

The earlier comments name limits L0-L8 but do not reproduce all definitions. The planner must enumerate every actual limit and its precedence from the new design: total/pending row capacity, resend cooldown, request/admission rate windows, confirmation queue and event/backlog caps where they affect subscribe, status's private-call concurrency cap (previously 8), and any additional overload/failure path. Every valid-address early return must be covered. Uniform global overload is allowed; address-dependent observable treatment is not.

Tests need the same response-timing class both below limits and at each limit, in both request orders. Hold SMTP and fan-out unresolved throughout the timing checks and prove requests still finish on the documented release schedule. Cover private success, immediate refusal/error, redirect, malformed reply, timeout and local no-call admission refusal without exposing membership through which branch waits. Bound resource use without awaiting SMTP or recipient fan-out on the public path. The spec should distinguish this deterministic timing-class guarantee from an unsupported promise of identical network/OS timing.

### C. Remaining lifecycle and integration details

- Finalize exact address syntax/length, token syntax/entropy, resend cooldown, all queue/rate capacities and precedence, body/time limits, error shapes and headers. A duplicate confirmed request must not de-confirm or extend consent; rotation/expiry must invalidate old confirmation jobs. An unsubscribe must remain usable when subscribe capacity/queue limits are full.
- Specify protection for public form POSTs (method, content type, size, duplicate fields and origin policy) and private calls (bearer checking, no redirects, bounded I/O). Build mail URLs from configured canonical origins, never Host or forwarded headers. Use same-origin forms without broadening status's CSP unnecessarily. Preserve keyboard, accessible labels and no-JavaScript operation.
- Carry forward privacy defenses when feeding subscriber detection: consume only public manual data, strip notes/drafts, and fail closed on hostile or malformed publication/visibility fields. Define detection/confirmation ties and restart seeding so neither history nor private feed material leaks into messages.
- Define enabled-only startup validation and resource shutdown, cleanup operation while API polls fail, offline-delete lock ownership, storage permissions and realistic backup/restore limitations. Do not assert a 25-hour elapsed-time deletion guarantee while notify is stopped; document restart cleanup before new sends.
- Preserve existing channels, failed-event CLI and ledger format. #570 is a separate in-flight settings feature, not an assumed dependency. If the planner newly needs its implementation, name the dependency and require native GitHub blocking linkage rather than silently rebuilding it.
- Use contract's next additive minor version after inspected `2.4.0` (previous proposal `2.5.0`), keep wire version 1 for additive shapes, rebuild committed `dist/`, and update consumer SHA pins only after the contract merge. Recheck versions at plan time.
- The notify `Files:` list must include every production, test, docs and manifest path the tasks will name. In particular include `test/index.test.ts` and `test/metrics.test.ts` when their integration/metrics checks are assigned. Regenerate all tasks after revising the spec, including deploy; mechanically compare task paths with the per-target file inventory. Do not merely repeat the earlier count of 72 paths.
- The plan needs its required security and performance sections: public PII intake, authentication/tokens, erasure and bounded mail/admission work make security impact yes. State storage/queue caps, fan-out work, HTTP response scheduling, timer/shutdown costs and feature-off behavior with measurable checks rather than asserting no overhead without evidence.

## Derived acceptance checks

These checks are requirements for the next spec/build states, not results from this review. Unit and service checks use injected clocks/schedulers, gated mailers and local peers; no external mailbox or real-time sleeps are required.

1. **Contract and configuration.** Validate shared subscribe/confirm/unsubscribe shapes, normalized-address equivalence, token limits and generic private responses. Check committed build/export/type fixtures. Missing/invalid enabled settings exit 2 without secret-bearing text or premature file opening. Disabled settings preserve current behavior. Check total=5 with missing/incompatible pending cap is rejected, while both caps at 5 are accepted.

2. **Double opt-in.** Submit an address and observe only a confirmation message with confirmation and unsubscribe links. Publish an incident and settle processing: zero incident messages for the pending address. GET/HEAD on the confirmation link changes nothing; valid POST confirms once. New public publication/update/resolution detected afterward each sends the expected one-recipient message. Expired, wrong, reused and rotated tokens cannot authorize a new action; repeated subscribe cannot remove confirmation or cause unrestricted resend.

3. **Incident privacy and history.** Exercise an unpublished draft, internal incident, saved unpublished update and internal note, each with unique sentinels. After detection and fan-out have settled, none of their content or messages exists in mail. Publishing the public draft/update starts eligibility exactly once. First activation/restart, old events, malformed/private upstream fields and feed errors do not replay history or leak excluded data. Automatic check alerts/reminders/warnings produce no subscriber mail under the retained scope.

4. **Unsubscribe and deletion.** Unsubscribe from both confirmation and incident messages via POST; GET/HEAD is safe. Subsequent incident processing sends nothing to that generation. Repeated/invalid unsubscribe is handled safely, and an old link cannot delete a new generation. Check database subscription/delivery rows, pending jobs and retry waits are gone. An operator can delete an address while notify is stopped; refuse a competing deletion process. Expired pending records disappear under independent cleanup even while API polls fail, within the documented live-service bound; restart cleans overdue work before sending.

5. **No enumeration: response bytes.** At status and the private subscribe handler, compare confirmed, pending and unknown addresses below limits and at every enumerated limit, in both orders and at each boundary. Compare status, body and all relevant headers (only nondeterministic Date excluded); no membership-dependent retry/remaining headers, reflected address, token or redirect. At full total capacity, specifically compare known and unknown and prove the capacity refusal was reached through private counters/state. Repeat for private backend failure/timeout, invalid reply and status's saturated call gate. Counters/log labels must not expose addresses.

6. **No enumeration: deterministic timing.** Under the same fixture load, record each confirmed/pending/unknown request's injected release time and scheduler steps at normal load, total capacity, pending cap, cooldown, every rate window, every queue cap and local concurrency saturation. Require the same documented timing class, both request orders, just below and at the limit. Hold SMTP/fan-out promises unresolved so they cannot provide an accidental barrier. Cover immediate private replies versus errors/redirects/malformed replies/timeouts and the no-private-call path. Tests must fail for a deliberately early return of a known address or an existence-dependent timer; timing tests may not merely compare bytes.

7. **Root and prefixed deployments.** Run the full subscribe, confirm and unsubscribe/mail-link flow on a root canonical origin. Submit forged Host and X-Forwarded-Host and verify all absolute links still use that origin. For `/pulse` origins, exercise enabled startup of both services and assert the documented root-hosting refusal, including the setting name and exit 2 before subscription files open. With subscriptions disabled, retain existing URL parsing. If the planner instead implements prefix support, it must replace the rejection acceptance with successful prefixed forms/actions and mail links throughout, as well as root checks.

8. **Visitor information.** Inspect the rendered form or its directly linked notice for all stored data classes, pending and confirmed retention, deletion/unsubscribe instructions, backup/sent-mail and in-flight exclusions, and the configured contact. Check escaped email/HTTPS contacts, invalid contact startup and no-JavaScript access. Keep the exact “One email that is being sent at that moment can still arrive” sentence only if acceptance 10 establishes its mailbox bound. In the e2e response comparison permit the required `privacy@e2e.invalid` contact link, forbid the submitted visitor addresses/local parts case-insensitively, and forbid other unexpected addresses after removing that link. Matcher fixtures must reject an uppercase visitor address, missing contact and an extra mailbox alongside the contact.

9. **Cancellation behind blocked sends (D19).** Gate A's confirmation send without advancing or resolving it; queue B and C behind it. Unsubscribe B or expire it via cleanup and assert its job/address is removed immediately while A still has exactly one unresolved call. Cover row rotation, confirmation, expiry exactly at its boundary without relying on cleanup, and cancellation during a retry wait. A removed/stale job never sends once A is released. Check whole-attempt timeout at both 60000 and a smaller configured value, and complete cleanup on stop.

10. **Two workers and re-subscription generations (strengthened D20).** Deterministically gate an old generation's send to normalized mailbox M. Confirm while its confirmation attempt remains unresolved, detect an incident, unsubscribe, then re-subscribe M under a new id using an equivalent case/whitespace spelling. Exercise confirmation and incident workers together, allowing the new generation to confirm if its token is known to the fixture. Assert the mailer-observed maximum simultaneous sends for M is **1**, not merely one per row; no new-generation send starts until the old attempt settles. Old jobs remain cancelled, current-generation eligibility is re-read, and another mailbox can progress. Run the mirrored case with an old incident attempt held while a new confirmation is queued. Release with success, permanent/temporary failure, timeout and stop; no leaked guard or stale-owner release. Retain the simpler confirm-during-retry, confirm-without-unsubscribe and wait-interrupted-by-stop cases. If choosing the permitted weaker notice instead, explicitly replace this bound and every notice expectation with the actual bound.

11. **Late incident completion (D21).** Hold an incident send, unsubscribe its row, optionally re-subscribe the same address under a new id, then finish the old attempt by success, SMTP 550, temporary failure or timeout. Each case leaves zero old subscription/delivery rows, creates no old delivery for the new id, performs no retry, settles the old event at its existing pass count, and advances to the next event. Check zero orphan deliveries after each case and the documented live DB/WAL erasure. Confirmation completion after deletion performs no store mutation. Keep the guard held until attempt settlement while avoiding post-delete completion writes.

12. **Retry recovery.** Persist pass consumption before sending. For a finite budget such as N=3, restart before and inside the last pass and during backoff; repeated restarts cannot obtain additional passes, and remaining delay is preserved. Confirm pending queue/sends cannot hold later events indefinitely beyond the documented bounds, permanent errors stop promptly, and stop releases waits/resources. SMTP ambiguity may duplicate a message after a crash, but must not reset the durable retry budget or revive deleted consent.

13. **Compose and secrets.** Add real mailpit-backed subscription checks to `compose-e2e`, mandatory on the dev build with `ok: email subscriptions`. An unsupported published-image run may report the explicit documented skip; dev must fail if it skips. Read real messages to follow confirm/unsubscribe links and check one-recipient envelopes, publication/update/resolution delivery, unconfirmed/draft/internal exclusions, root links, notice and saturation response comparisons. Set total/pending caps compatibly. Use a **post-write completed-detection barrier** plus zero pending fan-out, exact mail success increments and no unexpected failure increment before negative assertions. With serial detection, the prior proposal was a post-detection counter increase of 2, then zero pending work, followed by negative reads repeated across another detection. Do not substitute another recipient's mail, feed order, a pre-detection poll counter or a restart. Restart only after settlement; unit-test the barrier helper against fixed metric texts.

    Provision distinct bearer/HMAC secrets and optional SMTP password through `secrets-init`. Test host symlink/type/mode refusals, invalid password contents, 512-character boundary, input inequality, all-input validation before writes, exact output bytes/mode/owner, missing-password stale-output removal and off-switch behavior. Verify init never generates the SMTP password. Render the production override against temporary sentinel host secrets: actual password/token/key contents never appear in output or environment, literal-secret keys are absent, and secret `_FILE` paths are under `/run/pulse/`. Explicitly allow only the required password-file path rather than rejecting its filename. Keep mailpit loopback-only and pins in common services; document the approval-list expansion and operator setup.

14. **Security, integration and spec completeness.** Real status/notify server tests exercise method/origin/body limits, private bearer authentication, disabled routes, bounded upstream failure paths, safe generic responses and token exceptions. Inspect logs/metrics/errors with address and token sentinels; successful token-form GET is the sole response exception. Preserve existing status privacy, channels, ledger recovery and failed CLI checks. Run each target's required checks and relevant browser/accessibility or deploy script/static checks during build. Verify the notify `Files:` inventory and tasks agree exactly, including `test/index.test.ts` and `test/metrics.test.ts`; regenerate dependent tasks after spec changes. Require green integrated dev mail acceptance, not only unit tests.
