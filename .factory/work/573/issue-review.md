## Scope and assumptions

1. **Meaning of “unconfirmed gets nothing”.** An unconfirmed address receives the requested confirmation email only, with bounded resend behavior. It receives zero incident mail until it confirms. Reading the criterion as zero email of any kind would contradict double opt-in. “Every message” includes a cancellation/unsubscribe path in confirmation mail as well as incident mail.
2. **One public page, installation-wide subscriptions.** Subscribe to the installation's public status page, without a Console account. No component selection, multiple/private pages, SMS, digest, marketing mail, hosted tenant model or subscriber-management dashboard is implied.
3. **Eligible events.** Assume public automatic incident opening/resolution and public manual incident publication, subsequent published updates and resolution. Automatic incidents do not acquire manual updates. Private notes, an unpublished incident, a saved draft update, an internal incident (including its publication/resolution), reminders and budget/expiry warnings do not generate subscriber mail. Preserve existing operator-channel behavior.
4. **Automatic notification policy.** Every eligible publication is notified when subscriptions are configured. The Composer “Notify subscribers” label is context, not an explicit requirement for a per-publication opt-out toggle. No Console change or #569 dependency is needed under this assumption. If the planner includes a toggle, it must first define durable send/suppress semantics in the incident API and include the Console/API/contract scope; a client-only checkbox cannot control a polling notifier reliably.
5. **Future events only.** Confirmation starts eligibility for subsequent events; it does not replay incident history or previously queued incident mail. A later update/resolution of an incident that was already open at confirmation is eligible. Re-subscription after cancellation requires fresh double opt-in and must not restore old queued messages.
6. **Optional capability.** Existing installations without subscriber SMTP/configuration continue to start and monitor normally. Enable the public Subscribe action only when the capability is configured; show a useful unavailable/retry state for runtime backend failure. Mail belongs in notify with its own validated settings and env/file secret references. No SMTP password or service credential reaches the browser, status JSON, repository or Console database.
7. **Public information only.** Subscriber content must not expose more incident/check detail than the public page permits. In particular, do not reuse the operator email sender's optional reason field unchecked. Specify the relationship to status hide-details/show-checks/component presentation and use a safe public projection; do not imply that a UI visibility option already creates private checks in the API.

## Nonblocking points the plan must settle

### Storage, protocol and target scope

The issue's `(status, notify)` names describe the user-facing behavior, not a constraint against the supporting targets. Recommend API-owned durable subscriptions and delivery work, status-owned public forms/link handling, and notify-owned SMTP sending. API SQLite provides one authority for confirmation/cancellation, and contract defines the HTTP schemas. A notify-owned store with a private HTTP interface is another possible design, but needs equivalent persistence, authentication, deployment and race semantics. Do not share a SQLite file between services or have one service import another's source.

Choose one owner before breakdown. Expect `contract`, `api`, `status`, `notify` and `deploy` under the recommended design, plus a narrow meta approved-use documentation change for Mailpit. Declare target dependencies and merged full-SHA pins; a service change may depend on contract/API availability without circular status/notify/API build dependencies. Do not add Console, probe or a runtime package without a concrete need. Reuse approved nodemailer and built-in crypto/SQLite.

Write exact routes, methods, bodies, byte/count limits, responses, wire validators/version compatibility, capability detection and private service permissions. Separate anonymous subscribe/confirmation/unsubscribe operations from recipient enumeration and queue/ack/resend operations. A general read token must not inadvertently gain access to email addresses. Specify how credentials reach status/notify using deploy's secret-volume model, including disabled/older peers and fail-closed authentication behavior.

### Subscription lifecycle and link behavior

Define pending/confirmed/cancelled state, durable timestamps and a consent generation/identity. Pick email validation, length limits and normalization consistently; reject CR/LF, multiple recipients and header injection. Repeated subscribe must not create duplicate recipients or cancel an existing confirmed subscription. Use a generic response for valid addresses to avoid exposing existing subscriber state.

Specify cryptographically random bearer tokens, hashed storage, bounded confirmation lifetime (24 hours is a reasonable default), single-use confirmation, resend cooldown and pending-record cleanup. Cancellation must work without login from every message, including expired confirmation messages; do not make cancellation depend on the confirmation token still being usable. Replayed confirmation must never re-enable a cancelled subscription. Old consent tokens/queue work cannot activate a fresh subscription generation. Define harmless repeated unsubscribe and invalid/expired-token states.

Use a configured canonical public URL, not request Host/forwarded headers or user-supplied return URLs, for links. Decide path-prefix support and how test clients follow that origin. A landing page plus explicit same-origin POST is a reasonable scanner-safe default for confirmation/cancellation. Specify exactly which request commits the change; GET previews or HEAD must not accidentally activate subscriptions. No account, cookies from Console or new mail-unsubscribe standard is required to satisfy this issue.

Anonymous subscribe is a mail-sending entry point: bound body size, requests by address/source, confirmation retries and stored pending records; avoid trusting arbitrary proxy headers for client IP. Use no-store and suitable referrer policy on token pages and redact addresses/tokens from logs, errors and metric labels. Specify Origin/content-type checks for the public forms and keep the status CSP and proxy allow-list intact. This warrants `Security impact: yes` in the plan.

### Delivery, privacy and failure semantics

Choose a durable event cursor/outbox or equivalent bounded catch-up model. Current manual reads retain only bounded resolved history, and new-channel seeding deliberately suppresses old events. Simply editing a static email channel's recipients or repeatedly reseeding it cannot establish per-subscriber consent and future-only delivery. Define the behavior of events produced during notifier/API/SMTP outage, polling gaps, queue retention and first enablement; do not promise unlimited catch-up from a bounded public feed.

Track progress by event and subscriber generation. Sending to one address must not mark every subscriber delivered; one failed address must not block the others. Send separate messages with recipient-specific links and no other subscribers in To/Cc/body. A stable per-event/per-subscription Message-ID and persisted progress can avoid routine duplicates, but SMTP acceptance followed by a crash before acknowledgement can still redeliver; document at-least-once delivery rather than promising transactional exactly-once SMTP.

Check that a subscription is still confirmed at each send attempt, recovered job and manual resend. Cancellation suppresses queued work and future retries even if detection occurred earlier; on eligibility lookup failure, fail closed. Mail already accepted by SMTP cannot be recalled. Specify the send/cancel ordering so a successful unsubscribe guarantees no subsequent send starts, allowing an already in-flight send to finish. Expired, cancelled or never-confirmed recipients must not be reactivated by queue recovery or CLI resend.

Preserve #568's public filtering and projections. Do not read the private admin timeline to obtain subscriber text; do not derive keys/content from private notes or draft updates. Keep normal restart dedupe, including when an upstream incident temporarily carries explicit private flags. Reuse content-based manual update identities; do not reintroduce an update-position key assumption.

### Operations, performance and Compose evidence

Document enable/disable behavior, SMTP credentials and TLS, canonical URL, persistence/backup/restore, cleanup limits and meaningful delivery failure states. Bound recipient pagination, fan-out, workers/queue memory and retries rather than spawning an unbounded promise per subscriber or allowing the subscription queue to stall operator notifications. Measure relevant API startup/latency/RSS/CPU and notify fan-out under a representative subscriber count in the plan; keep existing budgets and CI gates.

Extend deploy's test-only overlay with the existing centrally pinned Mailpit service, SMTP config and loopback-only API/UI access. The regular stack's exact service-list check should still pass. Update cleanup/port checks/docs and the approved Mailpit use description where needed. Candidate acceptance must use the actual modified service revisions via the dev path or explicitly identified candidate images. A green run against unchanged published `0.1.0` images, or a skipped subscription scenario, does not prove this feature. If full-mode compatibility needs a capability skip for older pins, the candidate/dev CI gate must require a subscription success marker.

## Derived acceptance check

**Observable done condition:** through the public status page, a visitor requests and confirms a subscription, receives subsequent public incident emails in Mailpit with working unsubscribe links, then cancels and receives no further incident emails; a second unconfirmed address receives no incident email, and draft/internal activity produces no subscriber email.

Prove it with behavioral tests and the actual Compose stack:

1. **Request and opt-in.** With subscriptions enabled, the public page has an accessible email form and pending/confirmation states usable by keyboard, on a narrow screen and without JavaScript. Submit address A and leave B pending. Mailpit contains each requested confirmation with a valid canonical URL and cancellation link, and no incident mail yet. Repeating a request obeys the resend limit and produces no duplicate subscription.
2. **Positive delivery and pending exclusion.** Follow A's confirmation flow. Publish a new public manual incident, append a public update and resolve it; each yields the expected separate mail to A with the correct public text and unsubscribe link. B gets zero incident mail. Also cover automatic open/resolve events; reminders and warning events stay outside subscriber delivery under the scope above. Unit tests with an injected clock prove no backfill at confirmation and correct later updates to an already-open incident.
3. **Private activity with positive controls.** Successfully create/read an unpublished draft and a published internal incident through their authorized API, and save a draft update/private note on a public incident. Use unique private markers. After confirmed successful notify polls/work completion, Mailpit has no new subscriber message for those operations and no private marker anywhere in subscriber mail. Publish the public draft/draft update and verify it now sends exactly the corresponding public event. Publishing or resolving the internal incident still sends nothing. Existing public operator-channel and privacy checks continue to pass.
4. **Cancellation from mail.** Use A's incident-email unsubscribe flow with no account. Publish another public update/incident; A receives zero subsequent mail. Repeating cancellation is harmless. Cancel B through its confirmation email, then follow B's old confirmation: it cannot activate B. Every generated subscriber message kind includes a usable cancellation path.
5. **Queued work and restart.** Behavioral tests gate a transient SMTP failure, unsubscribe before retry, then release the retry: zero SMTP sends to the cancelled generation. Repeat with process restart/recovered pending work and explicit failed resend. Confirmed subscription state and delivery progress survive restart; healthy repolls/restarts do not normally resend completed events. New subscriptions after cancellation require new confirmation and receive only new eligible events. Test the defined in-flight cancellation exception separately.
6. **Trust boundaries and failures.** Reject malformed/oversized addresses, duplicate fields/header injection, invalid/expired/replayed confirmation and forged tokens without activation. Check generic duplicate-request responses, rate/cap limits, no public recipient listing, denied private service operations, fail-closed backend/auth errors, canonical-link handling and absence of raw tokens/emails in logs/metrics. Verify that subscriber mail contains no peer recipient address or hidden reason/details.
7. **Compose proof.** Run `E2E_SETUP=dev bash e2e/compose-e2e.sh` against recorded candidate checkout SHAs, or the equivalent explicitly recorded candidate-image run. Read actual Mailpit recipients/body and follow links through status; ledger rows or JSONL alone are insufficient. Use bounded waits for positive mail/control events and successful poll/worker barriers before negative assertions, rather than a single early empty inbox check. Preserve all existing scenarios and require the new scenario's success marker in candidate CI. Record the tested revisions and command result; do not treat a skip as a pass.
8. **Target gates.** Each changed code target passes its prescribed `bun run check`, contract build/committed-dist checks where applicable, real HTTP boundary tests and normal CI. New behavior tests fail meaningfully on the recorded pre-feature baseline. Run the real services once as their instructions require; deploy runs its affected shell/Compose checks. Do not weaken lint, coverage, performance budgets or CI to pass.
