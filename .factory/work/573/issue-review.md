## Prior decisions to carry forward

The supplied comments establish the following baseline. Preserve it unless the new plan explicitly explains an adjustment required by the manager additions.

- Notify owns subscriptions in a separate SQLite file and sends all subscriber mail. Keep the existing delivery ledger format independent, including any #570 migration; do not build #570's settings/Console/resend work again.
- Status owns public subscribe, confirmation and unsubscribe pages. It calls a private, bearer-protected notify listener (previously proposed port 9300). Shared request/response shapes, address rules and token formats belong in contract. API and Console changes are outside this feature's baseline scope.
- Subscribers receive **manual public incident** publication, published updates and resolution only. No automatic check incidents, reminders, budget/expiry warnings, draft messages or internal notes. This is the explicit scope narrowing in the prior plan comments, superseding broader interpretations of “incident updates.” No Composer notification toggle is required by the supplied decisions.
- Eligibility is based on events detected after confirmation on notify's clock. First enable quietly records existing incident history. Define equal-time ordering so clock ties cannot leak historical events or omit a later detection unpredictably.
- Confirmation and unsubscribe GET/HEAD requests only render a form; only POST mutates state. Confirmation tokens are stored hashed and expire after 24 hours. Unsubscribe uses an HMAC-signed link valid for the lifetime of that subscription; unsubscribing deletes it.
- New settings are environment-controlled, off by default. The prior proposal adds two secrets through secrets-init behind `PULSE_SECRETS_SUBSCRIPTIONS`. Keep secrets scoped to their consumers; the exact validated settings and transport source must be specified.
- Recovery must retain the prior review fixes: durable `passes`/`next_pass_at` or equivalent; commit a pass before its first send; a restart cannot reset the N-pass bound. When the final allowed pass was already started, recovery closes its remaining deliveries without further sends. Persist remaining backoff across restart. State the resulting loss/duplicate tradeoff honestly; SMTP cannot promise exactly-once delivery across a crash.
- Negative mail checks require a completed post-write detection and settled fan-out with exact positive counts and unchanged failure counts. Another recipient's mail, feed order, a fixed sleep, or a restart cannot establish that an unwanted send did not happen.
- Retain the narrow token exception from prior review: a successful confirmation/unsubscribe form may hold its own pattern-checked, escaped token once in a hidden field, with no-store and no-referrer. HEAD has the corresponding headers and no body. No token in other answers, invalid-token error pages, POST result pages, notify replies, logs or metrics.

## Open points and working assumptions for the plan

### 1. No address enumeration, including every limit

The manager's requirement applies to the **public** subscribe response, including the HTML form flow, not just a private notify success result. Define one fixed status/body for syntactically valid submissions irrespective of absent, pending or confirmed membership. A suitable default is a generic accepted response saying that instructions will be sent if the request can be processed; it must not promise a mail when admission was declined.

Apply the same public response below and at subscription capacity, pending capacity, per-address cooldown, requester/global rate limits, confirmation-mail queue saturation and incident queue saturation. Rejecting only unknown addresses with a “full” response while known addresses succeed is forbidden. Internally refusing work is compatible with returning the generic response; it must still enforce storage and mail bounds. Retries by a confirmed address must neither reveal membership nor revoke its existing consent.

Specify validation/admission order, all finite limits, eviction/expiry rules and which work is synchronous. A limiter before lookup may return a different status only if it is independent of membership and known/unknown comparisons under identical conditions are equal; using the single generic reply for all membership-dependent refusal paths is simpler. Malformed input may have a fixed validation error unrelated to membership. Upstream timeout/unavailability must not turn into a membership-dependent public result.

Compare response headers as well as required status/body: no membership-specific Location, Retry-After, cookies, content length, error detail or token. Do not wait for SMTP in the public request or intentionally expose lookup/admission results through response timing. Do not claim constant-time network responses without evidence. No public subscription lookup/list/count endpoint is needed. Operational failure diagnostics stay aggregate and contain no address labels.

### 2. URL prefix and canonical origin

The plan must explicitly select and document one of the manager's permitted hosting contracts:

- Preserve a configured external prefix, such as `https://status.example.test/pulse`, in subscribe entry links, confirmation/unsubscribe email URLs, form actions, redirects and return links. Define whether the service receives the prefix or a reverse proxy strips it. Test through that mapping; a bare upstream handler test does not prove external prefix support. Account for styles/scripts and CSP if the new pages use them, and the status-page entry link. Avoid accidental prefix removal by resolving `/subscribe/confirm` against a base URL. Test root hosting as well, including trailing-slash normalization.
- Or explicitly require root hosting for subscriptions, validate that requirement when enabling the feature, document the limitation and reject a prefixed configuration with a fixed setting error. Acceptance must exercise that prefix rejection and a complete successful root flow. Do not silently accept a prefix then send broken links. Preserve existing feature-off URL behavior unless a wider change is justified, since current tests accept a prefixed public URL.

Prefix preservation is preferable when it can be implemented within the feature; root-only is explicitly allowed by the issue and needs no hold. Do not claim that the existing public URL parser already solves hosting. All mail origins come from trusted operator configuration, never Host/forwarded headers or a visitor-supplied return URL. Status and notify must agree on the canonical public base.

### 3. Visitor notice, retention and operator contact

Before submission, show a plain-language notice on the form or via a usable link. It must say what is stored, why, how long, how to delete it, and whom to contact. Add a validated operator contact setting and specify its type, bounds, escaping, rendering and Compose plumbing. Recommended default: enabling subscriptions requires a nonempty operator contact; a disabled installation needs none. Do not substitute the SMTP sender for a contact setting without an explicit decision.

Make the notice true of the implementation, not aspirational. Inventory the email address, consent/creation timestamps, confirmation-token hash/expiry, subscription identifier and delivery/rate-limit metadata actually retained. Define bounded expiry **and cleanup** for unconfirmed records: a token's 24-hour expiry alone does not delete an address. Recommended: pending records expire after 24 hours with a documented maximum cleanup delay; confirmed records persist until unsubscribe/deletion. Define retention of deduplication, terminal deliveries, queued work and address-derived rate-limit entries separately. Avoid retaining raw addresses in delivery history when an opaque subscription id suffices.

Unsubscribe deletes active subscription data and prevents future queued/retry sends; stale links cannot affect a later re-subscription with a fresh identity. Explain how a visitor requests deletion without a usable link through the configured contact, and document an operator procedure that can actually carry it out. Specify treatment of SQLite WAL/free pages, backups and SMTP provider/mailbox copies; do not promise immediate physical erasure of those copies from deleting a live row. Operator-controlled backup retention and any data kept outside Pulse need clear documentation consistent with the visitor notice. This review proposes product behavior, not a claim of jurisdiction-specific legal compliance.

### 4. Consent lifecycle and abuse controls

“An unconfirmed address gets nothing” means **no incident mail**; the requested double opt-in necessarily sends a confirmation message. Every subscriber-facing message, including confirmation, needs a usable unsubscribe/cancel link. Pending cancellation must work without first confirming.

Specify a single-mailbox input format and canonicalization at the shared contract boundary: trimming, length, domain normalization and treatment of local-part case. Reject display-name lists, CR/LF and extra recipients. Do not invent provider-specific dot/plus aliases. Duplicate submits must be bounded and idempotent, and must not invalidate a still-usable link without an explicit resend policy. Define expired, malformed, forged, replayed and already-used token results and concurrent confirm/unsubscribe ordering. Confirmation must require possession of an unguessable token and no browser authentication session. Do not log the request body/query or propagate transport errors containing addresses/secrets.

Persist tokens only as hashes where applicable; use cryptographically random identities/tokens and constant-time signature checks. Sign unsubscribe links against a subscription generation so an old link cannot delete a newly created subscription. Document key rotation/loss and the effect of turning subscriptions off and on. Existing channel SMTP settings are operator notification destinations, not permission to add visitors to a channel's To list. Send one recipient per message so subscribers never see each other's addresses.

### 5. Event boundaries, privacy and delivery recovery

Use the existing public manual-incident feed/filter/projection, not admin credentials. Draft updates on a previously published incident must remain silent until published. Notes and internal incidents must remain silent on creation, update and resolution. Test filtering defensively with an upstream response containing private fields, not only an API that already hides them. Keep legacy public incidents without the newer visibility metadata compatible with the current contract helper.

Define new-subscriber cutoff, initial quiet seeding, deduplication and recovery in one durable model. Existing event keys can identify public updates; they do not by themselves encode subscription eligibility or deletion. Freeze or otherwise define each event's recipients, then recheck current consent immediately before every new send/retry. Distinguish a send already handed to SMTP from unsent work; document the in-flight boundary instead of promising recall.

Bound recipient fan-out, queue/storage growth, per-event retry passes and shutdown time. Preserve progress across restart, isolate a failing recipient so later events can progress, and define permanent/transient SMTP outcomes and store-write failure behavior. Never send before committing admission/progress that recovery needs. Define overload behavior for incident events independently from public subscribe responses; do not silently promise guaranteed incident delivery if the policy drops events. Deduplication/pruning cannot cause an old public update to replay after a new confirmation.

### 6. Target boundaries and coexistence

Expected target order remains contract, then status and notify, then deploy after both consumers. Contract must expose additive validators/types and built `dist`, keep wire version 1 for compatible additions, choose the next available minor release from its actual main and pin consumers to the merged SHA. Do not reuse a stale release number from the absent prior plan. Search current contract exports and planned names for collisions.

Keep the private notify listener bounded, authenticated, off by default and unexposed on host ports. Specify body limits, timeout/no-redirect client behavior, fixed errors, authorization on every operation and shutdown/lock ownership of the new database. State how startup handles partial/mismatched status/notify configuration; failures cannot create a partially functioning consent flow or leak membership.

#570 already has a plan and some shared contract shapes on current main, while this notify clone still writes ledger format 4. Do not assume #570's eventual format 5, runtime listener or live configuration exists. Use env-controlled feature settings and separate storage as previously decided, collision-check private ports/settings/paths, and document how the changes coexist when #570 lands. No dependency on an unmerged feature is needed on the available evidence. If the new plan introduces one, name what it consumes and arrange the native blocked-by relationship rather than relying on issue text alone.

Deploy must specify persistent data mounts, opt-in settings/contact/public base/SMTP wiring, restricted secrets, startup order and test-only Mailpit plumbing without changing normal deployments' service/port exposure. Preserve existing published-image tests and ensure dev CI cannot silently skip the new feature. Reuse the single image pin in `common/services.yaml`; do not add a pin to the overlay or scripts.

## Derived acceptance checks

These are checks the plan and tasks must make concrete. They have not been executed by this issue review.

1. **Double opt-in through real HTTP and SMTP.** Enable subscriptions with valid contact/public URL/SMTP configuration. Submit A and B using status's public form and inspect Mailpit in `compose-e2e`. Both get only the bounded confirmation mail. GET/HEAD of A's link leaves A unconfirmed; POST confirms A. Publish a uniquely marked manual public incident, a published update and its resolution. A receives one message per event in a controlled successful run; pending B receives zero incident messages. Every mail has an individual recipient and a usable unsubscribe/cancel link. Confirm B later: no historical replay, and subsequent public events arrive.

2. **No membership oracle below or at limits.** Through the public status endpoint, compare a confirmed, a pending and an unknown syntactically valid address under equivalent limiter state. Below capacity and at full subscription capacity, require byte-identical status/body for known versus unknown. Repeat independently at pending capacity, per-address resend/rate limits, per-requester/global rate limits and full confirmation/event queues, covering any other limits the plan introduces. Control fixture state so the first request cannot make the second incomparable; test both request orders. Compare observable headers and verify no address/token/membership hint. Internally assert capacity/queue bounds and consent preservation; generic success must not bypass limits. Test timeouts/outages with equivalent known/unknown outcomes. Compare HTML results as well as any public JSON surface. Deterministic tests may fill stores/fake bounded queues; include at least the below-capacity/full-capacity response comparison in the integrated HTTP scenario.

3. **Deletion and cancellation.** Unsubscribe GET/HEAD changes nothing. POST from A's mail removes active subscription state; repeat safely. Queue a later event or retry, unsubscribe before its SMTP send begins, and prove it is not sent. Pending B can cancel from its confirmation mail. Re-subscribe A, confirm it, and prove an old unsubscribe token cannot delete the new subscription. After completed deletion and settled fan-out, new public events yield no mail to the deleted address. Verify the documented operator deletion path and fake-clock cleanup/retention boundaries.

4. **Only published public content.** Create an unpublished public draft and a published internal incident; update and resolve the internal incident, add a private note to a public incident, and save an unpublished update on a published public incident. After each write and the settle barrier, assert zero prohibited mail and no private sentinel in any captured mail. Publish the saved public update and observe exactly the intended mail. Include automatic check incidents/reminders/warnings as zero-subscriber-mail cases per the retained scope. Unit/HTTP fixtures containing explicit private/unpublished upstream items prove fail-closed filtering and no private fields in payloads/logs.

5. **Root and prefix hosting.** Run the complete confirmation/unsubscribe flow with a root public URL. For a prefix-capable plan, repeat through the documented proxy/mount at `/pulse`, extracting actual mail links and HTML form actions; all navigation, POSTs, redirects and return links stay under the prefix, with no duplicated prefix or jump to root. For a root-only plan, assert that enabling with `/pulse` is explicitly refused before serving/sending and that docs identify root hosting as required. Cover trailing slashes and reject credential/query/fragment origins. A forged Host/forwarded header never changes mail destinations or link origin.

6. **Visitor information.** Fetch the subscribe form without JavaScript; inspect the inline or linked notice. Assert visible text describing the actual stored data, pending and confirmed retention, deletion/unsubscribe instructions and configured operator contact. Check keyboard access, labels, escaping and contact validation, including missing contact when enabling. Compare retention claims with fake-clock cleanup tests and documented operator/backup behavior. Verify the notice and all its links remain usable under the chosen root/prefix hosting contract.

7. **Bounded recovery and security.** Exercise malformed/expired/forged/replayed tokens, invalid or multiple addresses, CR/LF, oversized bodies, wrong/missing private bearer token, upstream failure and SMTP failure with fixed safe responses. Verify the precise hidden-field token exception and no-store/no-referrer; scan responses, errors, logs and metric labels for test address/token/secret sentinels. Restart during backoff, immediately before the last allowed pass and inside it; the N-pass bound never resets (include N=3 and repeated restarts), delivered recipients are not deliberately resent, unsent unsubscribed recipients stay excluded and later events progress. Verify persistence across ordinary restart, private file permissions and cleanup on startup failure/shutdown. Document the unavoidable crash-after-SMTP uncertainty.

8. **Mail assertions cannot pass early.** After the last API mutation of each phase, observe completed subscriber detection against a post-write feed read and no subscriber work in flight, due or waiting. The earlier spec's proposed completed-detection counter (advance by two from a sample taken after the write), pending-events gauge, exact per-phase incident-mail success deltas and unchanged failure counter are a valid approach if their update semantics are defined. The existing `pulse_notify_polls_total` alone is insufficient: it increments before detection. Read every forbidden-mail count twice with a further completed detection between reads; do not use another recipient/event as a barrier. Settle before restart. Test the barrier helper against delayed detection/send and wrong positive/failure counts, so a leak delayed behind another recipient fails the scenario.

9. **Deployment and regression gate.** `E2E_SETUP=dev bash e2e/compose-e2e.sh` must read real captured SMTP mail and emit an exact required `ok: email subscriptions` marker checked by dev CI. Published-image runs may emit an explicit skip until images contain the feature; a dev run must not. Run all checks required by each changed repository's AGENTS.md, contract build/dist checks, status accessibility checks for the new forms, deploy static/secrets/helper checks and the integrated mail scenario. With subscriptions disabled, existing status routes, configured notify channels, ledger compatibility and normal Compose exposure continue to pass. No mock sender alone satisfies the mail-catcher criterion.
