### Existing behavior that constrains the change

1. **Contract:** `ManualIncident` is separate from automatic `Incident`. Its updates are `{at, status, message}`, with no update id or draft/note/visibility fields. The creation message is update 0. Updates must be nonempty and ordered; the final update determines the incident status and resolution time. Limits are 200 title characters, 2,000 message characters, 100 updates, 50 component ids and a 16 KiB write body. Wire version is 1. API, status and notify currently pin contract `7ce23aaf3fa3e038f65ecfed755188b83bde143f`, rather than the inspected contract HEAD.
2. **API:** `GET /manual-incidents` and `GET /manual-incidents/:id` are unauthenticated. List reads expose open incidents plus up to 50 incidents resolved within 14 days, with `open|resolved|all` filters. Writes need both `admin` and `incidents` scopes, use the shared auth throttle and commit audit records with the mutation. Before admin bootstrap, reads are empty and writes unavailable. Creation immediately inserts an incident and its initial update; every subsequent update immediately changes incident status, including resolution. There are no draft-edit, publish or note operations. Resolved incidents reject updates and a second resolution. Public reads currently return all stored updates.
3. **Storage:** manual incidents and numbered updates live in separate SQLite tables, with `(incident_id, n)` as the update key and cascading delete. Both status and message are required on every update row. Existing numbered migrations are in `src/migrations.ts`; add a step rather than editing a released one. Creation/resolution callbacks currently count those operations. `hasOpenIncidentFor` considers all unresolved manual incidents when protecting component removal.
4. **Status:** the exact public proxy allow-list includes `/api/manual-incidents`, not its detail path or arbitrary queries. `cleanManualIncident` copies all messages but drops unlisted fields; therefore adding visibility fields alone would discard their meaning while still exposing the text. The poller, SSR/rendering and Atom/component-badge paths consume this public data. Open manual incidents affect component display state through `componentsWithIncidents`; API `/components` itself does not apply manual incidents. Atom emits one entry per update, with ids based on the update's array position. `hide-details` deliberately does not hide manual text. Some consumers retain a prior manual list on upstream 404.
5. **Notify:** polls unauthenticated `/manual-incidents`, validates incidents, then routes by component include/exclude filters; check filters do not restrict manual incidents. It derives opened/update/resolved events from the entire updates array. Open/resolved keys use the manual incident id; update keys hash `(at, status, message)`, rather than using array position. Initial successful reads seed history without sending it. Pending non-reminder notifications replay at startup from stored payloads, and `failed resend` returns failed entries to pending. Filtering only a sender's final message would be too late to prevent private events from entering this pipeline.
6. **Integration harness:** the current `compose-e2e` script is `pulse-deploy/e2e/compose-e2e.sh`, invoked by deploy CI's `full` job. It tests API reads, the status proxy and Atom, notification file outputs, routing and restart behavior for #340. It uses published images, not builds of these fresh target checkouts. API CI has no current `compose-e2e` job. The older #340 plan's API-owned Compose instructions are historical and must not be copied into this plan.

## Open points and planning assumptions

### Scope and lifecycle

1. **Which incidents?** Assume drafts, notes and internal-only visibility extend `ManualIncident`, based on #340 and the operator composer context. Automatic probe incidents continue to open and resolve from check results. Adding notes/visibility controls to automatic incidents would require an explicit additional design in the plan; do not silently combine the two id namespaces or change automatic detection.
2. **Draft is independent of operational status and audience.** An unpublished incident may be intended for either public or internal-only publication. Draft updates may target an already published incident. A draft resolving update must not resolve that incident, set its public `resolvedAt`, change its latest published message, or alter component state until publication. Internal notes must likewise leave operational status unchanged. Define legal combinations and transitions separately from `investigating|identified|monitoring|resolved`.
3. **Saving must be useful after the response.** Specify authenticated list/detail access to saved incident and update drafts, edit/save, discard/delete and explicit publication, with exact bodies, responses and error codes. Decide whether multiple drafts per incident are allowed and how an update is addressed. Recommended minimum: durable drafts with stable identities, mutable before publication, and published updates remaining append-only. Full autosave, incomplete form persistence, scheduling, approvals, notifications of draft saves, Console screens and new agent roles are not assumed requirements. Requiring the existing complete fields on draft save is acceptable if the plan states it.
4. **Publishing:** define first publication versus draft creation timestamps, atomic status application, publication order when several drafts exist, and repeat/concurrent publish behavior. A repeated publish must not append duplicate published updates or generate another logical notification. Validate component references and current incident state again at publication, since they can change after saving. Specify whether resolved incidents can retain drafts or receive notes; preserve the existing no-reopen rule unless the spec explicitly changes it. Discarded drafts must never later publish accidentally.
5. **Notes:** define a separate entry kind or equivalent private representation, its identity, author/time fields and whether edits/deletion are supported. A note is not a public update with a hidden message: neither its text nor a placeholder event, status change or timestamp should reach status or notify. Recommend no automatic conversion of a note to a public update; publishing an explicit separate update avoids accidental disclosure. Notes remain visible through authorized internal timeline reads, including for public incidents.
6. **Internal-only visibility:** state whether audience is fixed at creation or can change after publication. Recommended initial scope is choosing it on creation and editing it while still a draft; post-publication audience changes are not required by the issue. If changes are supported, specify cache expiry, retained snapshots, notification queues/retries/resends, reappearance/backfill behavior and the fact that already delivered messages cannot be recalled. Internal-only incidents and drafts must not influence public component summaries or component badges through their manual impact; actual check failures remain real public state.

### Privacy, contract and storage boundaries

7. **Public versus privileged reads:** recommend treating internal-only content as private at the API boundary as well as on the status page. Keep existing anonymous routes as a public projection containing only published public incidents and published public updates. Unknown and private ids should be indistinguishable to anonymous detail readers, normally `404`. Put private list/detail/timeline reads behind an explicit authenticated route/permission; an anonymous query parameter or guessed id cannot enable them. The plan must define whether private reads use existing `admin` + `incidents` permission or another existing scope combination, and preserve bootstrap, throttle, audit and secret-free logging behavior. New draft-only agent permissions are not implied merely by the design's title.
8. **Contract invariants and identities:** decide the public versus admin shapes and validators, exports and any new audit actions. A draft or note cannot satisfy the current rule that the final timeline row sets status; invariants should apply to the appropriate published updates. Avoid weakening existing public validation to accept inconsistent incident status/resolution. Filtering/inserting/discarding private rows must not renumber previously public Atom entries. Define stable public update identities or preserve a separate append-only public numbering; account for notify's content-hash keys when draft content/times change. Existing published content must not be redelivered merely because another entry is saved or published.
9. **Persistence and compatibility:** add a numbered migration that preserves existing incidents as published and public, their message order/timestamps, resolution and event/feed identities. Define defaults for old request/response shapes and whether legacy callers still publish immediately (recommended yes). Bound draft/note storage and specify how existing count/body/text limits apply, cleanup/retention, deletion cascades and component-removal checks. Draft/note operations must not inflate published creation/resolution counters. Audit writes must stay atomic and avoid storing message bodies in audit/log metadata. Update contract pins and lockfiles only after its change is merged; regenerate committed contract `dist/`. Decide wire-version compatibility from the actual shapes, rather than automatically bumping it or assuming every consumer can read an incompatible shape.

### Status, notification routing and delivery

10. **Status filtering:** the API's public projection is the primary boundary, but status must also handle explicitly private entries in an upstream response without exposing them. Inspect visibility before its allow-list strips metadata, then use the filtered projection consistently for `/api/manual-incidents`, SSR, browser refresh, open/resolved history, Atom and component state/badges. Cover both `hide-details` settings; that setting is not an authorization boundary. Define malformed visibility handling and older-API behavior. Do not add an admin feed, credentials or write routes to the public status proxy.
11. **Internal-only notifications:** the issue leaves this choice to the plan. Recommended minimal policy: suppress all internal-only incidents from all notification channels, as for drafts; public published events retain current component routing. This avoids giving the notifier private read credentials or making existing catch-all channels recipients of internal content. If the plan instead supports internal notifications, specify an authenticated notification projection, explicit channel opt-in defaulting off, interaction with component filters and stored routing fingerprints, and tests that no existing public/catch-all channel receives them. Internal notes and drafts must be excluded even from opted-in internal channels.
12. **Detection and replay:** apply exclusion before event derivation, seeding, payload creation, ledger insertion and channel output, not just during rendering. Preserve first-start history seeding and restart deduplication. A draft created before notifier startup but published after initialization should become a new eligible event at publication; a draft resolution should produce no event until then. If post-publication visibility changes are supported, new-poll filtering alone cannot stop already queued, pending or failed-resend payloads; the plan must define eligibility checks for those paths and behavior during API failures. Current delivery is at-least-once: require stable logical keys and no duplicate successful redetection, not an unsupported exactly-once delivery guarantee across crashes.

### Target ownership and verification

13. **Targets and order:** contract, api, status and notify need explicit sections. Prefer compatible public shapes so probe and other consumers do not need unrelated work. Consumers wait for the merged contract SHA; deploy integration waits for the relevant service changes/releases. Decide rollout order with the status metadata-stripping risk in mind. New privacy-enabled API storage must not feed private content to an older status/notify consumer.
14. **Compose ownership:** recommend adding a `deploy` target for the acceptance scenario in the existing harness, with service/image dependencies and concrete image versions/digests. If the plan retains only the four requested product targets, it must still name an executable way to run the updated stack and where the new cross-service assertions live. Running unchanged published images cannot establish this feature. Do not add product implementation in meta or assume API still owns the Compose harness.

## Derived acceptance check

Use distinct text/id sentinels for a public incident, an incident draft, an update draft, an internal note and a published internal-only incident. Establish a healthy notification poll before creating new eligible events. Read protected resources back successfully before asserting their absence elsewhere, so a rejected write or empty/unavailable feed cannot pass a privacy test.

1. **Draft incident:** save a draft affecting a configured component with major impact. An authorized internal read returns it, and it survives API restart. Anonymous lists (including status filters) omit it, direct anonymous detail does not reveal it, and the status proxy, rendered page/browser state, Atom and component badge contain no draft content or impact. Successful notify polls produce no draft event/payload/output. Edit and discard work as specified without publication.
2. **Publication:** publish a saved public incident draft after notify initialization. It becomes visible in public reads, status and Atom with its published content and expected component impact; notify emits its opened event to the correct channels. A repeated publication produces no additional public update or logical notification. Repeat with a draft saved before notifier startup and published after its initial seed, proving draft creation time does not suppress a new publication.
3. **Draft update:** on a visible public incident, save an update draft with a different message and proposed `resolved` status. Authorized reads confirm persistence; public status/message/updates/resolution time, feed entries and component impact remain at their previous published values, and notify output gains no event. Publish it: the new public update becomes visible, resolution takes effect and the expected single logical resolved event is detected. Repeated polls and a normal restart do not redeliver successful events.
4. **Internal note:** append a note with a unique private sentinel to a public incident. Authorized timeline reads show it, including after restart. Anonymous detail/list JSON, status proxy/SSR/browser rendering, resolved history and Atom expose neither the note nor a placeholder. Notify generates no note event and no channel payload contains it. The previous published status, resolution time and component display state are unchanged. Publish another public update afterwards and prove it still works without moving old feed ids or replaying old notifications.
5. **Internal-only incident:** save/publish one with an unmistakable title, message and component impact. Authorized reads show it. Anonymous API and all status surfaces omit it; no impact appears in public component summary/badge. Verify open and resolved states. Under the recommended suppress-all policy, all notify channels remain silent for this incident. If the plan chooses internal routing, prove only explicit internal recipients receive its published updates, with drafts/notes absent from every channel.
6. **Access and failures:** missing, invalid, revoked and insufficient-scope credentials cannot read or mutate private entries. Exercise the chosen behavior for private detail ids, invalid transitions, resolved parents, duplicate publish, malformed audience/kind values and text/body/count limits. Public parameters cannot bypass privacy. Failed validation/publication/audit writes leave stored/public state unchanged. Add replay/cache-transition checks if the plan permits post-publication audience changes.
7. **Backward compatibility:** migrate a database holding existing public manual incidents and verify unchanged public content, status, ordering and stable identities; legacy publish-immediately requests still work if retained. Automatic incidents and existing public manual incident create/update/resolve, routing, first-start seeding and restart behavior continue to pass. Consumer tests include upstream responses with explicit private flags to catch status stripping those flags before filtering or notify deriving events from hidden entries.
8. **Evidence:** implementation PRs demonstrate meaningful regression tests failing on their recorded pre-change main snapshot and passing with the change. An absence assertion must have a successful private-save/read control and a visible public control; do not claim the requirement is tested merely because an unsupported route returned an error. Run each affected target's `bun run check` (including contract build/dist checks), relevant HTTP tests and CI without weakening thresholds. Run the deploy `compose-e2e` scenario against the feature's actual service artifacts, with bounded positive polling barriers before negative notification assertions and a restart/deduplication check; record image/revision identities and results. Extend the existing #340 scenario rather than replacing its public controls.
