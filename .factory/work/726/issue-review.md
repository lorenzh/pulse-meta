## Current behavior and concrete gaps

1. Deploy `e2e/console-setup.sh:65` defines `form_token_args` without an action argument. It applies a whole-line greedy `sed` expression and takes the first matching line from the response body. It does not associate the token with a form. Consequently, which token it selects also depends on line layout when multiple fields share a line.
2. Step 11 (`e2e/console-setup.sh:289`) selects jar A, gets `/account/sessions`, checks `This browser`, extracts CSRF and a form token from that body, then posts to `/account/sessions/sign-out-all`. PR #9 renders a `/sign-out` form on the sessions page. Its separate `GET /account/sessions/sign-out-all` renders the form whose action is `/account/sessions/sign-out-all`. The script never gets that confirmation page.
3. Other token consumers include setup and owner setup (including returned form bodies), password sign-in, factor sign-in, and both authenticator actions. Authenticated account pages can contain a separate sign-out form. Merely adding the missing GET at step 11 would leave the general token-selection requirement unresolved.
4. Both flows' spent-setup checks (step 7) get `/sign-in` and then post to `/setup`, currently forwarding the sign-in token. This is a deliberate 404 check after setup has closed, not a successful form submission. Console main's `postSetupCode` returns 404 when the setup gate is absent before form-token validation. The script must preserve this check without submitting a token for `/sign-in` to `/setup`.
5. The legacy branch caches the successful sign-in arguments and replays that identical POST at step 8b only when a form token was present. It expects 409 and `Already submitted`; the tokenless branch prints the existing skipped line. This intentional replay is distinct from accidental reuse for another path.
6. The request refers to an existing stubbed harness for this script. An explicit search of deploy's tracked files, `e2e/`, `scripts/`, `cli/`, and `.github/` found no console-setup-specific harness or test invocation at the inspected SHA. Existing tests such as `e2e/published-port.test.sh` and `scripts/wait-ready.test.sh` do provide shell-function and PATH-stub patterns. Deploy CI runs those tests individually in its `lint` job; `bun run test` covers CLI tests only.

## Open points and working assumptions for the plan

These are implementation choices with sufficient defaults to specify now.

- **Scope:** implement only the deploy script, its regression tests, and any deploy-only test wiring/documentation required to make the test reproducible. Do not change console source, token validation, console CI, image pins, or other targets. This builds on #563's already-present deploy two-factor flow and PR #11's optional tokens; it does not rebuild either feature.
- **Select by exact POST action:** give extraction the intended POST path and select `form_token` only inside the form posting to that path. Do not fall back to the first token on the page, a similarly prefixed action, or a token in a later unrelated form. Cover the console's actual generated HTML, including both newline-separated forms and multiple forms on one line. No general-purpose HTML parser or new runtime package is required by the issue; the plan may choose a small bounded parser using existing script tools.
- **Fetch the real confirmation:** retain the sessions-list assertion, then in jar A get `/account/sessions/sign-out-all`, expect 200, and extract CSRF and the matching form token from that response before the POST. Keep Origin and cookie handling. Do not reuse the earlier sessions-page token.
- **Apply the rule throughout:** audit every POST and every refresh of `ftok`, including form responses after wrong setup code and connection test, shared sign-in helpers, factor and authenticator calls. Preserve the intentional cached same-path replay. For step 7, use the existing sign-in-page CSRF but omit `form_token` because there is no form for `/setup` on that page; retain the existing 404 assertion and `ok:` line. Do not invent a GET /setup success or borrow another form's token to satisfy that negative check.
- **Optional tokens:** reset the token argument array on each selection. If the matching form has no token, send no `form_token` argument, including when another form on the page does have one. Never send an empty field or retain a previous token. Fully tokenless legacy pages must keep working, and step 8b must remain skipped there.
- **Test harness availability:** reuse a console-setup harness if one has landed by implementation time. Otherwise add a focused stubbed script test (for example `e2e/console-setup.test.sh`) following the existing shell-test patterns and wire its command into deploy's script-test CI. The acceptance is behavioral, independent of that filename. It must exercise the actual script/helper and POST arguments, not a duplicate implementation of extraction. Use deterministic fake Docker/HTTP/TOTP behavior where needed, with no live stack or wall-clock TOTP waits in the regression suite.
- **Dependency and rollout:** #726 must not wait for #722 or all of #563 to merge; #722 is waiting for this fix. Develop the regression against fixtures reproducing PR #9's forms, and validate integration against PR #9's checkout. The console CI job checks out deploy main, so its final green evidence follows merging the deploy fix and rerunning that job. No console commit or CI edit is needed to rerun it. Record the deploy/console SHAs used for that proof.
- **Output compatibility:** preserve the existing `ok:` text for steps 1–10 in both flows, including replay success/skip lines as applicable. New confirmation GET checks can remain silent. Error messages may identify a step/path/status but must never interpolate response HTML, submitted fields, setup codes, passwords, setup keys, TOTP/recovery codes, CSRF tokens, or form tokens.

## Derived acceptance check

1. **Regression that detects the old bug:** render an unrelated `/sign-out` form before the desired POST form, with distinct synthetic tokens. Assert the actual outgoing POST uses only the token inside the form for its exact action. Include an authenticated account-page case and the sign-out-all confirmation; fail if the request omits the required token, uses the decoy, or skips the confirmation GET. Exercise the relevant multiline layout and a same-line layout. Keep this test unchanged, restore the old script in an isolated writable copy, and show an assertion failure caused by wrong token selection or the missing confirmation request. With the fix, show the test passing. Do not count a missing helper, syntax failure, or a fixture that accepts any token as the required regression proof.
2. **Step 11 sequence and effect:** in the two-factor flow, keep jar A for `GET /account/sessions` and the subsequent `GET /account/sessions/sign-out-all` (200), then POST the latter form's CSRF and path-matching token to `/account/sessions/sign-out-all`. Expect 303 to `/account/sessions?signed-out=others`. Existing assertions must still show B and C redirected to `/sign-in?next=%2F` and A receiving 200 with `Signed in as`.
3. **All POSTs:** tests must reject a token bound to another action for successful setup, owner test/complete, password sign-in, factor sign-in, and authenticator new/confirm submissions. Refresh tokens from the intended form response where the script currently refreshes them. Both spent-setup probes must still return 404 and must not send a sign-in token to `/setup`. The legacy replay must resend the original sign-in arguments to `/sign-in` and expect 409 `Already submitted`.
4. **Compatibility:** run the stubbed legacy flow with form tokens and without any form tokens. The latter sends no `form_token` fields anywhere and prints `ok: 8b replay check skipped: console without form_token`; the former retains the existing replay-success line. Also test a token-bearing unrelated form beside a tokenless target form, and consecutive selections where a token-bearing page is followed by a tokenless page, proving no fallback or stale token. Compare existing steps 1–10 `ok:` lines with the baseline for each corresponding flow.
5. **No secret output:** capture stdout and stderr on success and a relevant failure, assert that none of the fixture secret values is printed, and report only safe assertions/statuses. Real-stack evidence must redact secrets and never dump page bodies or POST arguments.
6. **Deploy checks:** run the regression command, shellcheck and Bash syntax checks from the deploy root, plus the required checks for the deploy CI job touched by test wiring and any relevant helper checks. Do not weaken coverage, script checks, or workflow policy. Document the test command if newly introduced.
7. **Integration and final rollout evidence:** on a fresh dev stack built with console PR #9 (or its merged equivalent), after readiness, run `E2E_CONSOLE_FLOW=two-factor bash e2e/console-setup.sh dev/compose.yaml`. Require exit 0 through steps 11–13, not only the step-11 POST. After the deploy fix reaches main, rerun PR #9's existing `deploy-dev` job and verify success. A deploy-main run against the current legacy console main alone cannot establish this acceptance. Keep premerge local evidence and postmerge job evidence distinct.
