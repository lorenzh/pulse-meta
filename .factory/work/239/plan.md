# Spec #239: Slack, Teams and email channels with reminders and signed webhooks

## Goal
pulse-notify sends native Slack, Microsoft Teams and email messages, routes per check with include, pattern and exclude, re-sends "still down" reminders for open incidents, and signs webhooks with an HMAC.

## Scope
Only `notify` changes. The contract has no tags and no status page URL, and no contract change is needed. Existing `webhook` and `file` configs keep working unchanged.

## Non-goals
No contract change, no tags, no PagerDuty/Opsgenie, no SMS, no inbound actions, no `Retry-After` handling, no secret reload on change, no signing for Slack/Teams.

## Decisions
1. **Routing.** Tags are not available (not in the contract); document it. `checks` stays the include list; each entry is an exact id or a glob where `*` matches any characters (an id without `*` matches exactly, so old configs behave the same). New `excludeChecks` (same entry syntax) wins over `checks`. Applies to all channel types and to reminders.
2. **Secrets.** Secrets and credential URLs come only from env or files: `urlEnv`/`urlFile` (slack, teams), `passwordEnv`/`passwordFile` (email), `secretEnv`/`secretFile` (webhook signing). Exactly one of each pair. A file is read at startup, a trailing newline is trimmed, and a missing or empty file or env var fails fast with a `ConfigError` naming the channel id and key, never the value. Slack/Teams have no inline `url`. The webhook keeps its inline `url`. Errors and logs never contain URLs; the Slack/Teams/webhook senders throw errors with the status only, and `errorFields` output is checked not to leak a URL (fetch error causes are reduced to a generic text for these channels).
3. **URL scheme.** Slack/Teams require `https:` (loopback `127.0.0.1`/`localhost` exempt for tests), else `ConfigError`. A webhook with `http:` to a non-loopback host logs one warning at startup via the logger, naming the channel id only; it is not rejected.
4. **Signing.** MAC over the raw body only, as specified: `X-Pulse-Signature: sha256=<hex HMAC-SHA256(secret, body)>`. `X-Pulse-Timestamp` is Unix seconds at send time of each attempt (injected `now`), is not covered by the MAC and is advisory; replay protection is the existing `Idempotency-Key`. Docs state this limit and give a Node verification snippet using `timingSafeEqual`. Without a secret neither header is sent and the request is byte-identical to today.
5. **Message.** Chat/email render: check name, state (DOWN, RESOLVED, STILL DOWN), reason unless `hideReason: true`, time (UTC ISO; for reminders also how long the incident has been open), and the status link when `statusUrl` (per channel, `http(s)` URL) is set; the link is the base URL, and it is omitted when unset. `hideReason` applies to slack, teams and email only; the webhook/file payload is unchanged. Reason text is untrusted: truncated to 300 characters, control characters removed; Slack text escapes `& < >` (blocks `<!channel>` mentions), Teams escapes markdown characters, email subject and headers reject/strip CR/LF.
6. **Slack payload** `{"text": "..."}` (mrkdwn). **Teams payload** is a message with one Adaptive Card attachment, which the Workflows URL accepts (document that the retired Office 365 connector card is not used). Success is any 2xx (Teams may answer 202); `redirect: "manual"`; everything else, including 429 and 5xx, is an ordinary failure retried as for webhooks.
7. **Email.** No new dependency: a minimal own SMTP client on `node:net`/`node:tls` (`src/channels/smtp.ts`) supporting EHLO, STARTTLS, AUTH PLAIN and LOGIN, MAIL FROM, RCPT TO, DATA with dot-stuffing, QUIT; single-line and multiline replies. Justification: nodemailer is large for this use, the repo has no runtime dependencies, and a lockfile or Docker change is avoided. Config: `smtp: {host, port, tls: "starttls" (default) | "tls" | "none", username?, passwordEnv|passwordFile}`, `from`, `to` (non-empty array), optional `subjectPrefix`. Certificate verification stays on. `none` is allowed only if set explicitly, and AUTH is refused over `none` to a non-loopback host. Connect and each command honor the timeout and the abort signal. Any non-2xx/3xx reply or socket failure rejects (4xx and 5xx both retry as for webhooks). `Message-ID` derives from the notification key (`<key-hash@host>`) so receivers can deduplicate. CR/LF in `from`, `to`, subject is rejected at config time. Plain text body, UTF-8 with quoted-printable or 8bit-safe encoding (use base64 body to stay simple).
8. **Reminders.** Opt-in per channel `remindEverySeconds` (integer, at least 60; applies to all channel types incl. webhook/file). New `NotificationEvent` value `reminder` (webhook/file receivers only see it if the operator enables it; documented). Key `<incidentId>:reminder:<n>` with `n = floor((now - openedAt) / interval)`, n ≥ 1. The detector gets an injected `now` and for each open incident whose n ≥ 1 and whose key is not handled yields only the latest n (no catch-up for missed intervals). Restarts are stable because n is derived, and the ledger holds the key. When a channel is new (seeding) existing open incidents are seeded with the current n, so reminders start from the next interval. A resolved incident gets no reminder; a reminder still queued or retrying when its incident resolves is dropped before send (delivery checks a `isStale` hook, the key is recorded as dropped without a send) so `resolved` is not preceded by a late reminder. `notification.time` = reminder time, `timeMs` likewise, plus a new `openedMs` field for the age (added to Notification; for opened/resolved it is also set). Ledger format stays `version: 1`; the stored pending payload gains the new event value. Reminder keys of each incident older than the latest n are pruned from the ledger when a newer one is recorded. No new metric; reminders count as deliveries.
9. **Wiring.** Replace the ternary in `Notifier` with a `createSender(config, deps)` function in `src/channels/factory.ts`, using an exhaustive switch. Split `parseChannel` in `config.ts` per type to keep complexity ≤ 15. `#findEvent` handles reminder keys or is not used for them (payload always present).

## Risks
- A secret or URL leaks through fetch error text, logs or `/metrics`: tests grep logs and `/metrics` for the secret strings.
- Hand-written SMTP client bugs: tested against a local stub in plain and TLS modes (self-signed test certificate generated into the test's temp directory via a fixture; if STARTTLS cannot be tested, document the gap in the PR).
- Reminder duplication or flood after restart or outage: derived keys plus latest-n-only.
- Old receivers meeting `event: "reminder"`: opt-in and documented.
