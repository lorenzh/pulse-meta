# Spec #325: HTTP checks with method, headers, body, expected status and JSON assertions

## Goal
HTTP checks can send a method, headers and a body, judge the final status against `expectedStatus` instead of "any 2xx", and assert JSON values in the response body. Secrets (header values, bodies) never reach the public status page, logs, metrics, results or reasons.

## Scope
Repositories: contract (schemas, docs), probe (request, judgement, secret resolution), status (allow-list, optional details), api (checks file, db, probe-only endpoint, docs, `compose-e2e`). `config`, `kit` and `notify` are unchanged (notify reads `GET /checks` and does not validate check fields; the implementer confirms by grep and leaves them alone).

## Non-goals
No scripting, no multi-step checks, no TLS client certificates, no `exists: false`, no JSONPath. Heartbeat and TLS checks reject every new field (`z.never`, like `keyword`).

## Decisions (resolve the open points of the issue review)
1. **Delivery channel and trust model.** `GET /checks` stays public and unauthenticated. The api adds `GET /probe/checks`, which needs the probe Bearer token (same token file and `authenticate()` as `POST /results`). It serves the checks including `headers` and `body` exactly as written in the checks file. A header value is a literal string or `{"env": "NAME"}`; the api never resolves env references. The **probe resolves `{env}` from its own process environment when it loads the checks**, so a secret lives in the probe env, never in the api env. A reference whose variable is unset or empty makes that check invalid for the probe: it logs `skipping check <id>: header <Name> env NAME is not set` (names only, never values), and does not run it. A literal value or a `body` in the checks file is stored in the api database at rest and served to every authenticated probe; the docs say to use `env` for secrets and treat the checks file, the database and the probe tokens as sensitive. Probe locations each need the env variable set. Rationale: this satisfies "resolved by the probe" and "never served in `GET /checks`".
2. **Public `GET /checks` serves** `method` and `expectedStatus` only when set to a non-default value, and never `headers` (neither names nor env names), `body` or `jsonAssert`. The api drops them in the service output; status drops them again unless allow-listed.
3. **Contract limits.**
   - `method`: upper-case enum GET, HEAD, POST, PUT, PATCH, DELETE, OPTIONS; default GET; case-sensitive.
   - `headers`: object, at most 20 entries; name is an RFC 9110 token, 1..256 bytes; forbidden names `host`, `content-length`, `transfer-encoding`, `connection`, `user-agent` (it stays the probe's); names unique case-insensitively; value is a string of 0..4096 visible ASCII/obs-text bytes without CR/LF, or `{env: string}` with `env` matching `^[A-Za-z_][A-Za-z0-9_]{0,127}$`; total of names and literal values at most 16 KiB.
   - `body`: string, at most 65536 bytes (UTF-8); rejected with GET and HEAD (effective method). No default `Content-Type`; the user sets it via `headers`.
   - `expectedStatus`: non-empty array, at most 20 entries, each an integer 100..599 or a string `"lo-hi"` (`^\d{3}-\d{3}$`, `100 <= lo <= hi <= 599`). Absent means `200-299`. The probe judges the final status after redirects, as today.
   - `jsonAssert`: non-empty array, at most 10 items, each `{pointer, equals}` or `{pointer, exists: true}`. `pointer` is an RFC 6901 JSON pointer (`""` is the whole document; invalid escapes rejected; at most 256 bytes). `equals` is any JSON value (deep, strict type equality); `exists` only `true`; exactly one of the two. Rejected with HEAD. `keyword` is also rejected with HEAD.
   - Contract exports the types, the schemas, helpers `matchesStatus(code, expectedStatus)` and `evaluatePointer(doc, pointer)` only if they stay pure; otherwise probe implements them. The wire version stays 1 (additive fields). Package version bump is minor.
4. **Body and reasons.** One read of the response body, capped at 1 MiB (`MAX_KEYWORD_BODY_BYTES`, reused), is shared by `keyword` and `jsonAssert`; it is read only when the status is accepted and one of them is set. A body over the cap or not valid JSON gives `json: invalid body`. Reasons, in precedence order: `HTTP <code> not in <expectedStatus joined with ", ">` (default `200-299`; for a default check the reason is `HTTP 503 not in 200-299`), then `keyword "<k>" not found`, then `json: invalid body`, then `json <pointer>: expected <JSON>, got <JSON>` (`got` is `missing` when absent), `json <pointer>: missing` for `exists`. Quoted response values are truncated to 80 chars with `…`. Only response data is quoted, never request data. The first failing assertion decides. Status code goes in `statusCode` as today.
5. **No secrets in output.** The probe never logs header values, env values or bodies, and never puts them in results, reasons or metrics (also not in error messages from fetch failures: those use the error code only, as today).
6. **Compatibility.** Rollout: contract, then probe and status, then api. A new probe falls back to `GET /checks` when `/probe/checks` answers 404 (old api), and retries on any other failure. Old probes keep calling public `GET /checks`: because the api serves non-default `method` and `expectedStatus` there, an old probe would misjudge them; docs tell operators to upgrade all probes before adding the new fields to the checks file, and the api docs state this. Header, body and assertion fields never appear on the public endpoint.

## Required behavior (summary per repository below)
Acceptance evidence: see the last section.

## Risks
- A secret leaks through reason text, a log line, `/metrics` or the status proxy: covered by sentinel tests in every repo.
- Env-referenced secret missing in one probe location: the check is skipped there and a log names the variable (not the value).
- ReDoS or huge input: limits above bound count, size and body read.

## Repository: contract
Files: `src/schema.ts` (extend `httpCheckSchema`, add `httpMethodSchema`, `headerValueSchema`, `expectedStatusSchema`, `jsonAssertSchema`; `tlsCheckSchema` and `heartbeatCheckSchema` get the new keys as `z.never`), `src/index.ts` (exports and types `HttpMethod`, `HeaderValue`, `ExpectedStatus`, `JsonAssertion`), optional pure helpers, `docs/index.md`, `README.md` if it lists fields, `test/` for each option.
Behavior: limits and rules of decision 3 with precise error messages by path; rule "body not allowed with GET/HEAD" and "jsonAssert/keyword not allowed with HEAD" via `superRefine`/`refine` with the path of the offending field; docs for header value forms, the trust model (decision 1) and the reason formats (decision 4); `dist` is rebuilt as the repo does.
Checks: `npm run check`-equivalent from the repo's AGENTS.md. Tests: every method, bad method, header name/forbidden/duplicate/count/size, `{env}` form and bad env name, body limit and GET/HEAD rejection, status ranges (`lo>hi`, 99, 600, bad strings, empty list, default), pointers (`""`, `/a~1b`, bad escape), equals vs exists exclusivity, rejection on tls and heartbeat; each fails on the old schema.
Done when: all tests pass and the package exports the new schemas and types.

## Repository: probe
Files: `src/client.ts` (fetch `GET /probe/checks` with the probe Bearer token, 404 falls back to `/checks`; `toCheck` copies the new fields; resolve `{env}` header values from `process.env`-like injected `env` map; skip with a log when unset), `src/check.ts` (send `method`, `headers` plus `user-agent`, `body`; judge with `expectedStatus`; shared body read; `jsonAssert`; reasons of decision 4; truncation), `src/main.ts` for wiring the env, `docs/`, README; tests beside the sources.
Behavior: redirect, timeout, retry and 1 MiB cap rules unchanged. Retries apply to any `down`. `latencyObjectiveMs` applies to `up` results. `keyword` and `jsonAssert` combine (keyword first, then assertions, same body read). HEAD never reads a body. Nothing secret is logged, put in results, reasons, or `/metrics`.
Checks: repo AGENTS.md commands. Tests: each method and body and header sent (fake fetch records the request), env resolution and the unset case, `expectedStatus` list and range (`HTTP 503 not in 200-299`, redirects judged on final status), each json reason (`json /status: expected "ok", got "degraded"`, `json: invalid body`, missing, exists, equals with number/null/object), truncation, keyword+json combination, fallback to `/checks` on 404, auth header on `/probe/checks`, and a sentinel test that greps logs, results, reasons and `/metrics` for a header secret and a body. Each fails on the old code.
Done when: tests pass and the probe docs describe the env reference, the endpoint and the failure modes.

## Repository: status
Files: `src/api-filter.ts` (allow-list in `cleanTarget`: `method` and `expectedStatus` only when not hidden and non-default; `headers`, `body`, `jsonAssert`, env names stay dropped and are dropped even when hidden is false), `src/render.ts` (with details shown, a `method` span for non-GET and an `expectedStatus` span for non-default values; nothing new by default or when details are hidden), `docs/`, tests.
Behavior: by default (`PULSE_STATUS_HIDE_DETAILS` true) the page and proxy output are unchanged. Values rendered are HTML-escaped as other details.
Checks: repo AGENTS.md commands. Tests: allow-list keeps `method` and `expectedStatus` only with details shown; sentinel header secret, env name, body and jsonAssert in an upstream `/api/checks` payload never appear in proxy output nor in rendered HTML (hidden or not); default checks render as before; each fails on the old code.
Done when: tests pass and docs state the allow-list.

## Repository: api
Files: `src/config.ts` (checks file accepts the new fields with the contract schemas; tls and heartbeat reject them), `src/db.ts` (columns `method`, `headers_json`, `body`, `expected_status_json`, `json_assert_json` through `addCheckColumn`), `src/service.ts` (upsert and clearing for checks removed from the file or whose fields are removed, as for `keyword`; `listChecks` public output drops `headers`, `body`, `jsonAssert` and defaults; a probe listing includes the full request), `src/server.ts` (`GET /probe/checks`: Bearer probe token, 401 without; same body shape plus state fields as `GET /checks` is not required: checks only), `checks.example.json`, `compose.yaml` and `compose/` (`compose-e2e`), `docs/` (checks file, REST API, trust model, rollout order, secret handling), README, tests.
Behavior: decisions 1, 2 and 6. `GET /checks`, `/metrics`, logs and error messages (config validation errors name the field path, never the value) never contain header values, env names, bodies or assertions. Config reload keeps working with changed fields.
`compose-e2e`: add a local target service (extend the existing compose test target or a small node service) and one check with `method: POST`, a JSON `body`, `headers` with `{"Authorization": {"env": "SVC_TOKEN"}}` and `Content-Type`, `expectedStatus: [200]`, and `jsonAssert` `/status equals "ok"`; the probe service gets `SVC_TOKEN`; the target answers 200 `{"status":"ok"}` only when the method, header and body match. The CI workflow runs it and asserts the check is up and that the sentinel token and body are absent from `GET /checks`, `/metrics` and container logs.
Checks: repo AGENTS.md commands, `compose-e2e` locally in CI. Tests: config accepts/rejects each option and field combination, db round trip and clearing, `GET /checks` omits secrets (sentinel for a literal header, an env name and a body), `GET /probe/checks` auth (401 with no or a wrong token, 200 with a valid one) and content, metrics and log grep, non-default `method` and `expectedStatus` served publicly; each fails on the old code.
Done when: tests and `compose-e2e` pass and the docs describe the new fields, the trust model and the rollout order.

## Acceptance evidence
Run `compose-e2e` with the POST/Authorization-from-env/`/status equals "ok"` check: up with `{"status":"ok"}`; with `{"status":"degraded"}` down with `json /status: expected "ok", got "degraded"`; with 503 down with `HTTP 503 not in 200`; with a non-JSON body down with `json: invalid body`. The token and body sentinel appear in no log, `/metrics`, `GET /checks`, status proxy output or status HTML; status with details shows at most the method and expected status. Tests in contract, probe, status and api cover every option and the secret handling.
