## Open points and proposed assumptions for the plan

### 1. Scope semantics and authorization

The issue names `read`, `checks`, `incidents`, `admin` and `probe`, but gives no permission matrix. In particular, allowing a `checks`-only credential to write checks would contradict the explicit acceptance criterion that a token without `admin` cannot write checks.

A coherent conservative default is to treat `admin` as a required mutation capability, combined with resource capabilities: `admin` + `checks` for config writes (including components and maintenance), `admin` + `incidents` for manual-incident writes, and `admin` for token administration and audit access. Import legacy admin credentials with all four non-probe scopes so they retain their current access. Give `read` an explicit protected-read meaning, including the behavior of `GET /admin/config`; do not silently introduce authentication on existing public read routes. The plan may choose another coherent matrix, but must preserve the literal no-`admin`, no-check-write requirement and explain what every scope permits.

Keep probe credentials separate: recommend `probe` as their only scope, with a required location and no administrative privileges. Non-probe credentials must not gain `/probe/checks` access implicitly through `read` or `admin`. Define missing/unknown/expired/revoked authentication failures versus an authenticated credential lacking permissions. Existing config routes return 403 for probe credentials, while manual writes currently return 401; document intentional changes and update the contract's status descriptions and tests.

### 2. Store and token-management API

Specify stable token/credential ids, name bounds and duplicate-name policy, scopes, location, created/last-used/expiry/revocation times, and rotation linkage/deadline. Names are display labels, not primary keys; retaining duplicate legacy names avoids an unnecessary migration failure. Audit attribution should preserve the actor name at write time and preferably a stable id even after revocation or rotation.

Define protected routes for creation, metadata listing/detail, revocation and rotation. Creation and rotation generate high-entropy credentials on the server and reveal the new plaintext once; list/detail/audit/error responses must contain neither plaintext nor digests. Do not create a general plaintext-import endpoint merely to support the legacy-file migration. Specify request limits, validation, status codes, unknown scopes, invalid expiry and unknown ids. Recommend `Cache-Control: no-store` on secret-bearing responses.

Choose the random-byte count, token encoding and hash algorithm explicitly using runtime built-ins or approved packages. Persist only the digest, never encrypted/recoverable credentials. Legacy valid credentials must remain usable even if they do not match the new generated format. Retain timing-safe verification. Last-used time should mean successful authentication, with a stated persistence precision and restart behavior; decide whether writes may be coalesced to protect ingest performance without delaying expiry/revocation enforcement.

### 3. Upgrade, bootstrap and startup

There is tension between “files remain only to bootstrap the first admin” and “upgrade from file tokens keeps existing tokens working,” including existing probe tokens. Resolve it as an explicit one-time compatibility import followed by database authority, not ongoing file authentication:

- Import every valid legacy admin and probe credential as a hash, preserving admin names, probe locations and current privileges. Assign deterministic metadata/names where the probe file lacks a name. Imported creation time can be the import time, with no expiry unless the plan states otherwise.
- Record durable import state in the same transaction as the import, validate before committing, and do not leave half an import on failure. Define separate states for a probe-only installation and a later first-admin bootstrap, so starting without an admin file does not permanently prevent adding the first admin.
- Never re-import or revive revoked, expired or rotated credentials on restart merely because their old files are still mounted. File edits after import must not become a second source of credentials. Removing files after import must not prevent startup or disable DB-backed admin/manual-incident routes.
- State fresh-install behavior: how existing Compose probe files seed the first probe, how the first admin is seeded, whether probe-only operation remains supported, and errors for missing/invalid bootstrap files. Do not require inventing a new out-of-band CLI for this issue.
- If all admins are revoked/expired, do not automatically reopen bootstrap based on “zero active admins”; that would resurrect file credentials. Document the lockout/recovery policy, and whether last-admin revocation is refused. Operator-controlled database restore can remain the recovery path; a recovery product is outside scope.

This exception for legacy probe import is necessary for the requested upgrade check and existing deployments. After initialization, files serve bootstrap purposes only and are not consulted on each request.

### 4. Rotation, expiry and revocation

Recommend a fixed 10-minute overlap, stated as an API/server guarantee in the plan and docs. The new credential works immediately; the old one works only while `now < overlapDeadline`, capped by its original expiry. Test the exact deadline using an injected clock. Persist the deadline so a restart does not reset or extend it.

Define whether metadata belongs to a logical token with credential generations or to linked token rows. Rotation must preserve scopes and probe location, avoid privilege escalation, and return the new credential once. State repeated/concurrent rotation behavior (recommend refusing another rotation during an active overlap), rotation of an expired/revoked token, and immediate revocation semantics for every still-valid generation. Revocation must override overlap. Define the replacement credential's expiry; it must not silently become immortal when the original had a finite lifetime. Updating an operator's probe env/file and restarting that probe during the overlap is sufficient; automatic distribution and probe token hot reload are not required.

### 5. Audit coverage, secrecy and durability

“Every admin write” must cover all existing config mutations, all four manual-incident actions, and new token create/rotate/revoke mutations. Automatic result ingest, heartbeat pings, file reloads and retention jobs are not actor-token admin writes. Recommend recording committed writes, with rejected attempts continuing through the existing auth/error logs; if attempts are included in the database, give them an explicit outcome so they cannot look like successful changes.

Use an allow-list of audit fields: stable entry id, actor name (and preferably id), action, typed target/id and timestamp. Do not store arbitrary request bodies, titles/messages, header/body values, heartbeat secrets, Bearer credentials, token hashes, or raw request URLs/query strings. Snapshot names rather than joining against mutable/deleted token records. Keep audit entries after their target or actor is revoked/deleted. For maintenance, whose current address is an array index, include enough revision/target context to identify the change after indices shift without storing config contents.

Audit must be durable before a write is acknowledged. Put DB-only mutations and their audit inserts in one transaction, and move manual-incident acknowledgement after commit. For file-backed config writes, the plan must describe an intent/recovery or equivalent protocol across file replacement and SQLite; a best-effort insert after `writer.apply` leaves successful file changes unaudited after crashes. State how a stored-but-not-applied file is represented and recovered, and how audit-storage failure is handled before any irreversible file step. Do not promise filesystem/SQLite atomicity that the existing writer cannot provide.

Assume append-only entries with no audit delete/edit HTTP routes and no automatic audit expiry in this issue. Existing result/manual-incident retention must not delete audit records. Document disk growth; tamper-proof external storage and a new retention product are outside scope.

### 6. Query and JSON-lines export

Choose exact protected routes (for example `/admin/audit` and `/admin/audit/export`), response envelopes, filters, limits and cursor semantics. Recommend actor/action/target/time filters, deterministic ordering with an entry-id tie breaker, bounded pages and parameter validation. Export must return one contract-valid entry per newline with an appropriate content type, use the same authorization/filters, and stream or iterate in bounded memory. Define whether export covers the full matching range rather than just one query page and how new writes during pagination/export affect the result. Do not expose audit data through the status proxy/public read routes.

### 7. Contract and target boundaries

Primary targets are contract, then api depending on the merged contract change. Contract should define token metadata, scopes, create/rotate response secrets separately from metadata, management requests/responses and audit entries/query shapes with schemas/validators and exports. Hashes are an internal storage detail, not a public token field. Build and commit `dist/`, extend type fixtures, and use an additive package update without a wire-version bump if existing response shapes remain compatible.

No console screens, account roles, multi-tenant model, check-storage redesign from #460 decision 4, or probe credential-distribution feature belongs here. Retaining existing probe routes/Bearer syntax and location rules should avoid a probe code target. Update api docs, examples, startup tests, benchmark fixtures and its existing Compose test as needed. Check #528's landing state before the plan chooses integration-test paths: if the move has landed, a narrowly scoped deploy section may be needed for bootstrap/e2e compatibility; otherwise use api's actual files. Do not build on unmerged #528 code or assume it supplies a dependency this feature needs.

## Derived acceptance check

Use real HTTP on loopback with port 0, temporary database/files and injected time. The build must demonstrate one independent regression test for each of the four issue criteria, plus the upgrade test, and record their expected failures against pre-feature main before showing them pass on the implementation. The following expands their observable checks rather than replacing them:

1. **Hash-only storage and one-time disclosure:** create a named token over the management route; its returned credential authenticates, but persisted token rows contain only a digest. Closing/reopening the DB preserves authentication. Metadata reads, audit query/export and logs contain neither the credential nor the digest. Rotation has the same disclosure rule. Inspect token storage specifically: existing check data can legitimately contain unrelated secrets, so “the entire database contains no secret strings” is not the criterion.
2. **Scope enforcement:** a valid `read` token and a valid `checks`-only token cannot write checks, and no check/file/state/audit-success change occurs. A fully privileged admin succeeds. Exercise the plan's full matrix, including components/maintenance, manual incidents, token management, audit access, and denial of probe-only credentials on admin routes. Public reads retain their current behavior.
3. **Rotation without outage:** rotate admin and probe credentials; both generations authenticate before the stated overlap deadline, and only the new one at/after it. Restart midway and repeat. Verify scope/location preservation, original expiry cap, immediate revocation during overlap, and the specified repeated-rotation behavior. Probe generations must work for both checks retrieval and result ingest while rejecting spoofed locations.
4. **Durable, secret-free audit:** perform a config write with distinct secret sentinels, query its actor/action/target/time, and find the same entry in parsed JSON-lines export after restart. Cover every config/manual-incident/token mutation category, including deletes and rotation. Confirm no body/header/heartbeat/token/hash sentinel enters audit storage, returned entries or logs. Verify paging/filter/order and export beyond one page, plus forbidden audit reads. Inject audit failure for DB writes and exercise the file-write recovery protocol; an acknowledged or recovered committed change must not disappear from the audit trail.
5. **Upgrade compatibility:** start with a pre-feature database and legacy files containing multiple admins, multiple probe locations and multiple credentials for one location. Upgrade once; existing admin credentials can still administer, probes can retrieve checks and post results, and spoofed locations remain denied. Restart with files removed; stored tokens and manual incidents still work. Revoke/rotate an imported credential, restart with its unchanged old file still mounted, and prove it is not resurrected. Cover a probe-only installation followed by first-admin bootstrap, malformed import rollback and fresh bootstrap.
6. **Lifecycle/contract:** expiry/revocation reject credentials immediately, creation/last-used times satisfy the documented semantics, invalid scope/location/expiry inputs fail without secret leakage, and contract validators/type fixtures accept valid shapes and reject malformed ones. Existing auth failure metrics/logging continue with bounded, secret-free labels.
7. **Integration and performance:** contract and api `bun run check` pass with generated contract artifacts current. Run api `bun run bench:selftest`, the existing A/B bench (`bun bench/run.ts --a <before-ref> --b <implementation-ref> --out <dir>`) under its current CPU/memory budgets, and the actual `compose-e2e` job/script at implementation time. Include bootstrap of mounted file credentials, restart with persisted DB, and continued probe/status/notify operation. Bench self-tests alone do not establish that DB-backed auth and last-used writes meet performance budgets. Do not relax CI or budgets to make the feature pass.

These are implementation acceptance requirements, not checks claimed to have run during this review. This state changes only this review artifact.
