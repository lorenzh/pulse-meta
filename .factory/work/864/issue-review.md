## Open points and assumptions for the spec

These are implementation choices the planner can settle from the issue and repository evidence; none blocks specifying the feature.

1. **Compression policy.** The issue allows rejection or bounded decoding. Recommend rejecting non-identity Content-Encoding rather than adding decoders. The plan must define accepted absent/identity headers and fail closed for unsupported, unknown or combined encodings. An Accept-Encoding preference alone is insufficient. Suppress Bun's eager automatic decompression on the request before the response arrives, including responses discarded for HTTP or wire errors. Use a narrowly typed optional fetch-init extension, without adding a public option, runtime dependency or Node/Bun runtime import to browser code. Preserve Node and browser imports and ordinary identity JSON reads; verify the behavior with their native fetch implementations where relevant. Do not claim that rejecting a header after fetch resolves, by itself, bounds all runtimes' internal buffers.
2. **Existing failure shapes.** Unsupported encodings need an explicitly documented existing result variant. Recommend a `network` failure with a fixed local Error cause, without copying the encoding value or response text. Do not add an error-union member, require exhaustive consumer-switch changes, or report a small encoded body as exceeding `maxBytes`. Preserve HTTP and wire precedence wherever those failures already determine the result. The plan must spell out treatment of non-2xx encoded write responses, which normally return an `http` error without a message when no safe body can be read.
3. **Shared write paths.** Apply the runtime decompression protection to `requestJson` as well as GETs; otherwise the same eager allocation remains through another export in the same module. Shared parser and wire-error sanitization naturally apply to both. Keep writes' existing redirect restriction, no retries, methods, ETag/status metadata, empty/204 success, and bounded optional `ErrorResponse.error` behavior for supported bodies. This is a shared helper hardening change, not a redesign of write outcomes.
4. **Meaning of fixed errors.** Use a fixed invalid-JSON message independent of parser/runtime exception text. Fix the source in `checkWireVersion` so its mismatch error contains only local constants such as the expected version. Cover nested `http.wire.error` and `requestJson.response.wire.error`, not just the top-level GET mismatch message. Preserve header comparison semantics, `WIRE_VERSION === 1` and the existing result shapes. The requirement concerns invalid-JSON and wire-version diagnostic text; it does not remove the documented write `http.message`, caller abort reason, transport cause or validator diagnostics.
5. **Redirect result.** Prefer `redirect: "manual"` for GETs, consistent with writes and consumer wrappers. All redirect destinations, including same-origin, must receive zero follow-up requests. A visible 3xx becomes the existing `http` failure. Browser manual redirects can produce an opaque response with status 0; document and test a failure outcome without requiring browser access to a hidden Location or status. A runtime rejection must likewise remain a typed failure. No new redirect configuration is needed.
6. **Resource regression design.** A synthetic stream or fetch-init assertion is useful but cannot prove memory safety. Add a real local encoded-response test with native Bun fetch in an isolated process, measuring peak memory against a warmed/identity baseline. Use a modest bounded fixture, a fixed budget, process timeout and cleanup; do not require a multi-GiB allocation or risk killing the test runner. The plan must choose an explicit budget with enough room for runtime noise but below the old decoded-size growth, and show that the regression fails against the reviewed main. Include early-discard responses because they can allocate before any reader runs. If supporting a decoder instead, demonstrate that decoded bytes are bounded before full expansion; a final `too-large` result alone is not sufficient evidence.
7. **Compatibility and docs.** Retain the default 5 MiB cap, custom `maxBytes`, web API public signatures, missing-wire tolerance/callback behavior, timeout covering headers and body, caller abort and first-interruption semantics. Keep cancellation nonblocking. Update README and `docs/index.md` with the encoding policy, failure mapping, redirect policy and fixed diagnostics. Regenerate committed dist with the normal build; do not hand-edit it. Mark the spec's security impact as yes.
