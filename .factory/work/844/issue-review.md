## Open points resolved by assumptions and earlier decisions

1. **What the bound measures.** Timestamp the invocation of fetch for `PUT /service/status/report`, not report completion, requested timer delay, or api receive time. Count failed/timed-out attempts too. A successful response cannot be promised during an api outage. The bound applies while running with a service token, under the existing 5000 ms per-request timeout and a progressing event loop. Arbitrarily stalled JavaScript, synchronous callbacks or clock discontinuities cannot have an absolute timer guarantee; do not claim such a guarantee or weaken the issue's HTTP-latency requirement because of that physical limit.

2. **Deadline choice.** Carry forward the reviewed D1 design from the comments: record tick/read start and actual report start. Let `REPORT_LEAD_MS = SETTINGS_TIMEOUT_MS + 1000 = 6000`. After a token-bearing cycle, arm for `max(0, due - now)`, where `due = min(tickStart + min(pollMs, 60000), reportStart + 60000 - REPORT_LEAD_MS)`. A cycle that sends no report uses its tick start as the report-anchor fallback to avoid an overdue-anchor tight loop. Without a token, preserve `min(pollMs, 60000)` local polling with a tick-start deadline. No new report-content or wire fields are needed.

   Merely replacing the completion-relative delay with a tick-relative 60000 ms delay is insufficient for varying read latency: an instant read followed by a 4000 ms read can move adjacent report starts 64000 ms apart. The report-anchor lead accommodates the next read, not just the previous requests. With request durations bounded by the existing timeout, the reviewed design gives a report-start bound of 59000 ms, inside the issue's literal 60000 ms limit.

3. **Two distinct time bounds.** For token-bearing normal cycles, the report anchor schedules the next read at most 54000 ms after the previous report starts. This is not a 54000 ms read-to-read promise. At long intervals, read-start spacing is `min(pollMs, 60000, 54000 + previous read duration)`. For `pollMs=60000`, previous reads of 0, 1000, 4000 and timeout-at-5000 yield 54000, 55000, 58000 and 59000 ms. At 120000 with a 4000 ms read, spacing is 58000 ms. At 55000 with a 4000 ms read, spacing is 55000 ms and the next read starts 51000 ms after the previous report. Keep these distinctions in source comments, documentation and task acceptance.

4. **Rate wording.** Above 54000 ms the poller **can be faster** than configured; it is not always faster. The 55000/4000 example preserves the configured rate, while instant reads at 55000 run every 54000 ms. The earlier comments' 1.111x and 2.222x figures at 60000 and 120000 are upper limits reached with instant reads. For normal timer cycles with `pollMs <= 54000`, reads do not run faster than configured; a slow in-flight cycle can postpone the next start.

5. **One lane, bounded pending work.** Serialize timer polls and `pollNow()` together, covering the read, local resolution/apply and report. At most one poll waits; concurrent manual requests can share that pending poll's completion rather than creating an unbounded queue. A due timer must skip or wait while busy. Preserve the meaning that `pollNow()` resolves after its requested/coalesced cycle and report finish; settle pending callers on stop. Do not add parallel heartbeat requests or a catch-up burst.

6. **Shutdown.** Preserve synchronous, idempotent `stop()`. Use a controller owned by the whole cycle for the read and report; cancel the timer and active request, and guard continuation after awaits. No post-stop local read, apply, report, queued/manual poll or timer re-arm is allowed. A cancelled request's asynchronous settlement must still be observed. No changes to `start.ts` or `main.ts` are needed for this design.

7. **Settings/report semantics.** Retain immediate startup, no-token readiness/local reload, ETag/304 behavior, old-api 404 behavior, last-good file/database state, precedence, rejected-state reporting, authentication, manual redirects and timeout/body limits. Report generation and existing public responses stay unchanged except ordinary time-dependent values. The no-token path must never start remote requests, and must not lose the existing 60000 ms polling cap.

8. **Scope and documentation.** The plan and the single coupled implementation task should list exactly these files in `Files:`: `src/settings-poll.ts`, new `src/settings-poll.heartbeat.test.ts`, `README.md`, and `docs/configuration.md`. Keep existing semantic tests intact. README must state that report starts stay at most 60 seconds apart regardless of HTTP time within the request timeout. Explain the long-interval read scheduling consistently in both docs: 54–59 s read-start spacing above 54000 ms under the bounded-read assumptions, never exceeding the configured interval, and it **can be faster** than configured. Do not promise reads “every 54 s”, “about 54 s” or “at most 54 s apart”. Docs must distinguish the 54 s report-to-next-read deadline from read-to-read spacing, and must not say long-interval reads are always faster.
