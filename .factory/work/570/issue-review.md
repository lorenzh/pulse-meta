## Open points and working assumptions

### 1. Settings inventory and boundaries

The plan needs a finite field inventory with type, bounds, default, file/env representation, DB representation, source metadata and observable effect for **every** editable field. Do not use “branding” or “routes” as untestable catch-all tasks.

- **Status branding:** assume name, logo and the existing validated theme tokens (light/dark colours, fonts and radii), reusing current validation and shipped theme defaults. Define which tokens the form exposes. Existing local logos/theme files remain operator-managed; no upload, arbitrary CSS, remote font installation or new asset store is implied. A DB logo can use a validated public HTTPS URL; whether a pre-provisioned local logo reference is offered must be explicit, without letting an API edit read arbitrary status files. Escape names and logo attributes and preserve the appropriate CSP for changed logo origins.
- **Component order:** a status presentation preference using existing component IDs, not component CRUD or rewriting `checks.json`/API component definitions. Define group ordering and order within groups, because `components-view.ts` currently groups by first appearance. Recommended: ordered known IDs, reject duplicates, preserve grouping with a documented rule, append components omitted from the preference in their upstream order, and tolerate later removed IDs without breaking the page. Decide the save-time response to unknown IDs and define clear/reset behavior. Never change component membership, incident targeting or global API order as a side effect.
- **Visibility:** independent booleans for show checks, show latency and show SLOs, plus hide details. Preserve current defaults/semantics for show checks (`false`, effective when components exist) and hide details (`true`); latency and SLO display default to their current enabled behavior. “SLOs” means presentation of existing API objectives, not changing availability targets, SLO calculations or warning thresholds. Define whether latency includes the current latency label, chart and daily table; recommended: all latency presentation. With checks hidden, component latency still follows the latency switch. Without components, preserve today's check-list behavior unless the plan explicitly explains a required change.
- **Notify routes:** use the existing per-channel routing vocabulary: `checks`, `excludeChecks`, `components`, `excludeComponents`, `alerts`, `sendIncidents`, and `remindEverySeconds`. A separate priority/escalation rule engine or routing resource is not required. Retain opt-in budget/TLS/domain warning semantics now present in source; do not reimplement #571. Include existing per-channel message/transport options where needed for usable channel CRUD (SMTP host/port/TLS/username, from/to, subject prefix, status link, hide reason, etc.). Operational knobs such as retry scheduling, state paths, ports and polling intervals need not all become Console settings.
- **Resend UI:** a bounded list of failed deliveries with channel ID, opaque event key, failure time, event kind and resendability is sufficient to identify a delivery and offer a button. No general delivery-history dashboard, test-notification button, bulk resend, subscriber mail (#573), new transports, status password/IP allow-list or hosted/multi-organisation model is implied. Use existing event variants, including manual incidents and warnings, rather than assuming all keys are numeric incident IDs.

### 2. Source precedence, omission and reset

Explicit **environment > service file > database > built-in default** is the recommended status precedence. The owner requires file/env to win over DB but does not specify ties between local sources; preserve existing env behavior and make the tie rule explicit. Preserve whether a field was actually set: parsing a default `false`/`true` must not turn an absent env setting into a permanent override. Theme-file precedence should apply to explicitly supplied tokens, not lock the complete merged default palette.

Notify uses **whole-channel ID** precedence, including that channel's routing/options. Never merge a file channel's secret reference with a DB channel's destination/routing. DB records survive shadowing. Follow the checks model: reject new DB IDs that already belong to the known file set; if a file later gains a DB ID, show both origins and mark the DB copy shadowed, with safe removal of the DB copy only. Do not silently discard DB data. Define server-side handling of forged edits to read-only/shadowed records and the behavior when the service report is stale.

The status service currently lacks a general settings file and a local source for the new order/visibility controls. The plan must define a backward-compatible local representation for these controls so file-over-DB acceptance is possible; extending the theme format or adding a settings file is an implementation choice. It must preserve existing env/theme options. Notify needs a supported **DB-only / zero-channel** configuration mode: an obligatory non-empty file otherwise makes creating the first channel in the Console impossible. Distinguish intentionally absent/empty local config from an explicitly configured file that is invalid or unreadable. Saving/deleting a DB setting must never rewrite a service file or environment.

Define clear/reset separately from empty/false values: clearing a DB override returns to the next source/default; removing a valid local override reveals the retained DB value. Environment changes normally require process replacement; live reload here must apply **DB changes without restart**, and the plan should also specify file polling/reload behavior. Do not promise mutation of a running process's inherited environment through the Console.

### 3. Runtime distribution and observed application

The API owns durable DB settings; status/notify consume them over HTTP. The Console continues to talk **only to the API**, as #460 requires. The API cannot infer status/notify file/env values from `checks.json`: the services must report sanitized local provenance/effective state (or supply it over a bounded API-mediated query). Specify this feedback path, its authentication, staleness and instance identity. Do not mount service files into the Console/API to fake provenance, or treat “not reported” as “no overrides.” Assume one status and one notify instance per self-hosted stack; any multi-instance reporting/claim semantics must be explicit if supported.

Pick and document a bounded reload interval and request timeout, revision/ETag behavior, and the point at which a valid configuration becomes active. Separate **stored**, **applied**, **shadowed**, **rejected** and **service unavailable/stale** states. A successful DB save alone is not evidence that the service applied it. Reject invalid edits at the API; resolve/validate runtime-only secret references on notify. Apply a valid snapshot atomically and retain the last good snapshot on malformed/oversized/incompatible responses, missing secrets, file errors or API outage; report the rejection safely, keep retrying, and do not partially install channels. Define cold start when the API is unavailable (local config and any deliberately persisted last-good snapshot, or explicit not-ready), without erasing durable DB settings or silently enabling less-private status output.

Status must use the same effective snapshot for SSR, browser updates, CSS/logo/CSP, proxy filtering and cache keys/ETags. On visibility changes invalidate or version filtered answers, including in-flight reads, so an old permissive answer cannot be served under new privacy settings. A page already open should converge on changed settings on a bounded refresh/poll, not keep startup `data-show-checks` forever. Hiding details affects public JSON/SSR, not merely hidden DOM text; retain current hidden-check ID/name protections when components exist. State exactly which latency/SLO data is filtered from public responses when display is disabled and test the chosen behavior. A browser cannot retract data it already received; verify subsequent responses and rendered state.

### 4. Secrets and service authority

Only unresolved reference **names/paths**, never resolved values, cross notify's boundary. The API/Console must not read an env variable or a referenced secret file to validate its value. The UI offers variable names; if file references are editable, offer the reference path/approved selector with clear instructions that it is on notify. Persist refs as refs, including backups, reports, audit and errors. Reject inline passwords/signing secrets and credential URLs in DB requests, even when a forged form bypasses the UI. Trusted local files with existing supported shapes remain compatible; sanitize their reports.

The webhook schema currently requires a literal `url`, whereas Slack/Teams use `urlEnv`/`urlFile`. Reconcile that mismatch explicitly: recommended DB transport schemas use URL refs for webhook too, adding notify support while retaining legacy local webhook configuration. Do not store a purportedly non-secret webhook URL that contains userinfo, query tokens or a secret path. Public `statusUrl` is a message link, not a credential URL; keep its purpose distinct.

Reference selection is also a concrete trust boundary: a remote DB edit must not name an unrelated notify credential (for example an API authentication token) and combine it with an attacker-selected destination or expose it through a file channel. Specify a service-local allow-list/binding policy for remotely selectable env/file refs and writable file-channel destinations, or an equivalent restriction that the API cannot widen. Keep transport validation (Slack/Teams HTTPS, SMTP TLS rules), and do not return resolved destinations or secrets in failed-delivery metadata. This is part of implementing remote configuration safely, not a request for a new secret-management product.

### 5. Notify reload and delivery lifecycle

Build new senders/workers only after complete validation. Reconcile workers by stable channel ID under the existing ledger owner; no service restart, second poller or second ledger writer. The plan must define the transition for added/changed/deleted/shadowed/unshadowed channels, running sends, retry timers and stored pending/failed jobs. Recommended: serialize per-channel replacement, quiesce the prior worker before activating its replacement, keep pending/failed state and recipient progress, and refuse resend while its effective channel is unavailable. Define whether changed destinations apply to previously pending events; do not leave the old and new worker racing to send the same key.

Preserve current quiet seeding of historical automatic/manual incidents for new channels, quiet seeding when routing widens, reminder enable/re-enable baselines, warning suppression, one active send per channel, independent retries and stale-reminder drops. A settings save, shadow/unshadow or worker rebuild must not reset deduplication and flood old events. Deleting a DB channel need not delete delivery history; define what happens if its ID is recreated and whether changing transport type with stored recipient progress is allowed. Do not revive the old #255 JSON ledger/batched-write design: current ledger mutations are SQLite transactions.

### 6. Live failed-delivery resend

Use the running notify process's ledger and scheduler. The plan may choose an authenticated API-to-notify command path or API-persisted commands polled/acknowledged by notify; either must keep the Console API-only and must not expose mutations on the unauthenticated health endpoint. If using commands, define durable command identity, claim/ack, retention, timeout and result readback. If proxying, define bounded network failures and ambiguous outcomes. Do not run the offline CLI as a web subprocess.

Identity is **(channel ID, opaque event key)**; the same key may be failed in two channels. Atomically admit a resend only from a failed entry with retained payload, mark it pending and enqueue it immediately/within the stated command interval. Preserve the notification's key and payload and successful SMTP recipients; clear only refused recipients as current `Ledger.resend` does. Do not report “delivered” merely because it was accepted. Pending/in-flight/delivered/seeded/dropped entries must not create another job. Define response/result states for unknown/pruned key, legacy no-payload entry, missing channel, stale reminder, concurrent clicks and a second request after completion. The UI's one-use form token is helpful but is not sufficient deduplication for network retries/concurrent clients; the live command admission must be idempotent as well.

“Delivers once” is a controlled successful-resend acceptance check, not a new distributed exactly-once guarantee. Notify already promises **at least once**: a crash or uncertain remote acknowledgement can duplicate a send. Retain the receiver idempotency key, durable pending recovery, retry rules and this documented limit. A still-failing receiver can yield failed again; explicit later resend is allowed. Prevent replay of the *same command* from authorizing another attempt after a response is lost.

### 7. API contract, permissions, concurrency and UI

Add contract schemas/validators for durable settings, origin/effective reports, channel refs and failed-delivery/resend requests/results before consumers, with a compatibility/deployment order and explicit unsupported-version behavior. Do not copy notify-private resolved types or raw ledger payloads into the API. Use append-only migrations in the API DB; no second authoritative settings store in the Console DB. Choose per-resource revisions or deliberately extend existing ones; define stale-write `If-Match` behavior without breaking existing check/maintenance consumers or cross-resource concurrency.

Status/notify settings are **Owner-only** (`settings.edit`). Recommended for new failed-delivery list/resend routes: Owner too, because no existing permission row assigns them; record that assumption rather than inheriting Viewer access from overview. Enforce every route on the server, with tests for allowed and denied roles and role/session change during awaited reads. Keep API token scopes distinct from Console roles: current `config-write` is `admin+checks`, not a generic runtime-settings permission. Specify the new routes' required scopes and service-only read/report/command authority, without making notify/status carry an unnecessarily broad Console admin credential or exposing refs publicly. Reuse hashed-token/auth throttling and audit patterns as applicable; no need to add a role or scope without explaining it.

Reuse the protected shell, escaped SSR forms, fixed Origin/size/content-type/CSRF order, replay-resistant form tokens, safe return paths and conflicts preserving input. Mark file/env settings read-only with origin and show shadowed DB channels distinctly. Provide first-use/zero-channel, invalid-input, stale-save, token-rejected, old-API, offline-service and apply-rejected states. Preserve desktop-first usability and keyboard access; use ordinary move controls for component order so drag-only interaction is not required. Add People-log actions/targets and API audit events for saves/deletes/resend admission using IDs and fixed metadata, never config/secret values; distinguish remote success from failure to record a local audit row, using established Console write patterns.

### 8. Target split and rollout

At minimum expect **contract → api → status/notify → console**, with explicit consumer pins and integration dependencies; status and notify implementations can be separate parts, and resend can be a distinct notify/API/Console task group. Do not create conflicting duplicate sections/child issues for the same target. Add deploy if new credentials/mounts, DB-only setup or cross-service tests require it. Full/dev's explicit show-checks env override must be documented as intentionally read-only; test an unlocked configuration as well as an override fixture. Update relevant READMEs/configuration/operation docs for file schemas, refs, precedence, polling/failure behavior and offline CLI compatibility. Publish/pin dependent versions only through the established release/deploy workflow, never assume an in-flight feature is on main. Existing auth/roles/checks and warning/seeding code are present in these clones and should be reused, not rebuilt from older review artifacts.

## Derived acceptance check

The spec should turn the following into named tests and one integrated check. Use temporary API DB/notify ledger/files, injected clocks/schedules, HTTP servers on loopback port 0 and fake receivers; no external notifications. Each target runs its required `bun run check`, and Console changes run the applicable browser checks. This review did not run product tests because it changes only this artifact.

1. **Per-field live matrix.** Enumerate every status field/theme token and every exposed notify transport/routing/message field. With services already running and a setting absent locally, submit a real authorized Console form, verify its API DB/ref representation, advance the documented reload interval and observe the actual service effect. Record unchanged process identities/listeners and reload revisions. Status assertions include title/logo/CSS, grouped order, check visibility/privacy, latency labels/charts/tables and check/component SLOs, through SSR and an already-open browser. Notify assertions use new events and matching/nonmatching checks/components/warning kinds and inspect the chosen receiver/payload. For every boolean exercise both directions and distinguish omitted from explicitly false.
2. **Precedence and reset per setting.** For each matrix entry set a conflicting explicit local file value and DB value: the service uses the file value and the Console shows origin/read-only. Repeat for applicable env overrides, including an env value equal to the shipped default. A file channel shadows the *whole* same-ID DB channel; no option/secret mixing. Removing a valid file override reveals the retained DB value live; clearing a DB value restores the next source/default. Test disjoint theme tokens so a partial theme file does not suppress unrelated DB tokens. Assert no Console/API write changed a status/notify file. Test file-owned ID create rejection, later shadow/unshadow, and forged edits to read-only rows.
3. **First use and durability.** Start in documented DB-only mode with zero channels, create the first through the Console and observe delivery without a service restart. Delete the last DB channel cleanly. Restart API/status/notify after successful saves to prove DB settings, channel refs and delivery/seeding state persist; local precedence still wins. Migrate an existing API DB without losing checks, tokens, incidents or windows; unchanged local-only installations retain behavior.
4. **Bad input and outage recovery.** Invalid settings/order/refs and stale revisions are refused without partial DB changes. Missing/empty runtime secrets, unreadable/invalid local files, oversized/malformed/version-incompatible settings responses and API loss retain the last good effective snapshot; show safe rejected/stale state and recover on the next good poll. Test service-down provenance as unknown/stale, not editable by assumed absence. Verify cold-start policy separately. Turn hide-details/show-checks toward the private setting during a cached/in-flight read and confirm subsequent public JSON, SSR and browser state cannot reuse the permissive answer; test CSS/logo/ETag convergence too.
5. **Notify reconciliation.** Add/change/delete and shadow/unshadow channels while events and retry timers exist: no duplicate worker, burst of old incidents, loss of pending/failed payloads, reset of warning/reminder baselines, or repeat to already-delivered SMTP recipients. Routing widening quietly seeds historical incidents; a new matching event delivers. A slow/retrying channel still leaves others and polling responsive. Exercise the specified policy for changed destination/type, deleted/recreated IDs and unresolved pending jobs.
6. **One successful live resend.** While notify holds its normal ledger lock, make a controlled event fail permanently, list it through API/Console, repair the receiver, click Resend once and observe exactly **one additional successful receiver delivery** within the command bound. The event key/payload and webhook idempotency header stay identical; the ledger becomes delivered, the UI reflects completion, and later polls/restart send nothing again. Send duplicate/concurrent/retried commands, including replay after completion, and prove one admitted job. Two channels sharing a key remain independent. Partial SMTP failure retries only previously unsuccessful recipients. Also cover a manual incident/warning key, no-payload legacy entry, pruned/unknown key, non-failed key, unavailable channel, stale reminder and another genuine delivery failure.
7. **Auth and secrets.** Owner may save/delete/resend; Admin/Member/Viewer, unauthenticated callers, invalid Origin/CSRF/form tokens and insufficient API/service tokens cannot perform those writes. Verify denied direct routes, not just hidden buttons. Service credentials/config refs never enter browser credentials, public status proxy/ops routes or arbitrary upstream paths. Sentinel secret values resolved only by notify are absent from API/Console DBs, response bodies, logs, metrics, audits and errors; refs remain usable. Forged inline credentials and unapproved env/file refs or output paths are rejected without reading/writing/sending them. Existing local CLI still refuses while notify owns the lock, and offline list/resend still works when stopped.
8. **Integrated observable completion.** In a documented dev/Compose or equivalent multi-process harness, sign in as Owner, save unlocked status branding/visibility/order and notify channel/routing settings, observe the public status page and actual fake receiver without restarting services, apply a conflicting file value and see the read-only override, then resend one deliberately failed event through the button with the same key exactly once in the controlled successful run. Include status/notify service feedback and failure recovery so the check cannot pass by verifying DB writes or a fake Console API alone. Keep the at-least-once crash limitation explicit in documentation.
