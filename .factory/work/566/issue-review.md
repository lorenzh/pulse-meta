- Console already has local accounts, mandatory admin/owner second factors, live role checks, the shared shell, confirmation pages and single-use form tokens. `/tokens` and `/probes` are registered as unavailable navigation entries with minimum role `admin`; neither screen is implemented. The permission matrix already assigns `token.write` and `probe.write` to admin and owner. Copy buttons already work through the single same-origin script with a selectable-text fallback.
- Console's contract pin is the inspected contract HEAD. Token input, metadata, list and secret-response types/validators already exist. `TokenMetadata` contains ID, name, scopes, location, source, creation/last-use/expiry/revocation/rotation times and overlap deadline, with no secret or digest. Probe scope is exclusive and requires a location; admin-side tokens cannot have one.
- API has list/get/create/rotate/revoke under `/admin/tokens`. Create returns `201` with `{token, secret, previousValidUntil: null}`; rotate returns `200` with a new secret. Rotation retains the logical token ID, scopes and location. The old secret works for 600000 ms, capped by token expiry; another rotation during overlap returns `409`. Revocation invalidates both generations immediately. Listing retains revoked tokens. Successful authentication updates last use; persistence is coalesced over 60 seconds, so crash recovery can lag.
- Token routes require `admin`. Creation and mutation additionally enforce the grant rule: every target scope must be held by the caller, with target `probe` mapped to caller `checks`. Thus a Console token with only `read,admin` cannot mint probe or Full access credentials. Last active admin revocation is refused by API with `409`.
- **`GET /admin/tokens/self` is missing.** Today `self` matches the ordinary ID position and is rejected as an unknown ID. Setup currently tests `/admin/config`, then lists `/admin/tokens` to prove admin scope; it accepts a `404` on that second call for old APIs. #562 explicitly defers switching to `/self` to #566.
- `GET /locations` returns observed locations only: `{name, lastResultAt, state: reporting|silent}`. A newly minted probe token does not register a reporting location. There is no durable location create/delete API or version field. Locations can have multiple token IDs, especially imported credentials. Revoking a credential does not delete historical results or the observed location.
- Probe reads `PULSE_API_URL`, `PULSE_LOCATION` and exactly one of `PULSE_PROBE_TOKEN` / `PULSE_PROBE_TOKEN_FILE` at startup. Rotation requires replacing the credential and restarting the probe within overlap. Every probe runs every eligible check; per-check location selection is not part of v1. A new check's initial scheduling delay is below `min(intervalMs, 1000)`; execution and posting still take time.
- Compose e2e lives in **deploy**, not API. The full stack does not publish the API; dev and the e2e overlay publish it on loopback. An internal URL such as `http://api:3000` is reachable on the stack network, not from an arbitrary remote Docker host. Published image pins currently remain at `0.1.0`; dev builds current source. New API/Console behavior cannot be accepted solely against those old published images.

## Scope and nonblocking points for the plan

### 1. Targets, prerequisite and delivery order

Expected targets are **api, console and deploy**: API adds the decided self-metadata route; Console builds the screens and updates setup's connection test; deploy owns the runnable-snippet acceptance scenario. Existing contract exports can describe `/self` as `TokenMetadata`, so no contract implementation change appears necessary. No probe implementation change is justified after the version deferral. Confirm this during planning rather than adding speculative targets.

Name #561 as the completed prerequisite and preserve its semantics. Use the existing #562/#563/#564 and shell foundations; they are already present. Recheck main when planning/building. Arrange API before Console consumption of `/self`, and deploy's integration coverage after both, with native dependencies through Factory's normal workflow. This review changes no provider metadata. Release/pin updates, if assigned, follow deploy's bump procedure; do not substitute unpublished tags into production setups.

### 2. Token UI and own-token protection

The owner's section 3 specifies **presets only**, rather than arbitrary scope checkboxes: Read = `[read]`; Manage checks = `[read, checks, admin]`; Post incidents = `[read, incidents, admin]`; Full access = `[read, checks, incidents, admin]`. Probe credentials belong to Probes. Presets containing admin must explain that they can also manage tokens with the same or fewer scopes and read the audit log. Preserve actual API scope values and grant restrictions; the Console user's role is an additional gate, not a replacement.

List metadata including last use (`Never` for null), source (created in pulse-api/imported from a token file), scopes and lifecycle state. Include imported tokens, and make the treatment of expired/revoked rows explicit. Do not invent token creator, IP address, agent access or a second API-key store. Recommend identifying credentials by immutable ID even when names repeat.

Include rotation for admin-side tokens too: it is explicitly decided in #460 despite being omitted from #566's abbreviated first bullet. Display the returned `previousValidUntil` as a 10-minute countdown and an absolute deadline; without JavaScript the deadline and instructions must remain useful. Expiry may shorten overlap. Do not infer a fresh ten minutes on every page load.

Specify `/admin/tokens/self` before the generic ID branch, reuse the metadata validator, retain normal admin authentication/throttling and document statuses/methods. Recommend the same `admin` permission as the other token reads: setup already requires it on modern API. Metadata must identify the same logical row with either credential during overlap. Update setup's second call to `/self` without sending its configured secret to the browser. Decide and test compatibility explicitly: an older API may still support setup's existing not-checked fallback, but Tokens/Probes must fail closed for mutation when self identity cannot be established.

Mark the Console's own token row and forbid its rotate/revoke actions **on the server as well as in the UI**; rotating it without changing the operator-managed environment/file would disable the Console after overlap. Never identify it by name, source or by hashing/comparing browser input. Re-read self and relevant metadata before mutations rather than trusting hidden IDs or a stale list. When self lookup fails, explain the API prerequisite and disable mutations, rather than guess.

Disable revoke on the last active admin and retain API's authoritative race-safe `409`. The owner also forbids assigning expiry to that last admin. The present API has create-time expiry only, with no expiry-edit endpoint. Do not silently add expiry editing to meet an imagined screen requirement. If optional create-time expiry is offered, specify its validation and this invariant; keep existing expiry visible and warn if the last admin already expires. No expiry-change or rename API is implied by this issue.

### 3. Meaning of a probe location and its actions

Recommend a view joining location-bound probe token metadata with `/locations` by exact location name. This shows newly created, never-reporting credentials immediately, historical observed locations without a live credential, and reporting/silent state with last-result time. Token last use is not a substitute for last result. Define a clear `Awaiting first result` state and distinguish revoked access from a silent probe. Do not delete history when revoking access or show a successful token create as proof a probe is connected.

An add operation creates a `[probe]` token bound to the supplied location through the existing token API, then shows its deployment instructions. Apply API limits (trimmed location 1–64 characters, token name 1–100, distinct scopes) and choose a conservative safe UI validation for control characters. API does not guarantee unique location names or token names. The plan must state duplicate-add behavior and expose all existing credentials rather than collapsing multiple IDs into one mutable row.

Rotation targets a particular token ID; imported locations may have several. State clearly whether revoke is per credential or location-wide. Recommended minimum is an explicit per-credential action, labelled accordingly, with other active credentials visible; if offering `Revoke location`, it must revoke all its active token IDs and report partial failure without claiming the location is disabled. Use typed-name confirmation for revoke, as section 14 requires. Define the confirmation snapshot from stable lifecycle fields; last-use updates must not make every confirmation stale. No GET performs a mutation.

### 4. Snippets that can actually run

Both the `docker run` and Compose forms need the same location binding, a usable API base URL, a probe image and the returned credential via a documented env/file mechanism. The plan must choose one concrete deployment mode and show any required token-file creation, network attachment and cleanup instructions, rather than output a fragment with missing prerequisites. Do not give probes the Console's admin credential.

Do not silently copy the Console container's internal API URL into remote-host instructions. Allow an operator-supplied reachable probe API URL or explain attachment to the existing Docker network for same-host snippets. Keep full-stack API exposure unchanged; a remote probe needs operator-provided network access. A loopback host address inside an ordinary container does not point to the API host. Document which URL/network the acceptance scenario uses.

Include `PULSE_PROBE_BLOCK_PRIVATE_RANGES` with its self-hosted default off and an explanation, per #460 section 7. Do not add a Console runtime toggle or host-binding editor. Existing env-header checks still require operator-provided variables/host bindings. Quote shell words through the existing POSIX quoting helper, escape HTML separately, and serialize YAML so quotes, newlines and Compose `$` interpolation cannot change URL, name or secret values. Container/service identifiers need their own safe generation; location text is not a container name.

Choose an image selection strategy consistent with pinned SemVer/digest releases and deploy's sole pin source `common/services.yaml`; do not hard-code a second floating production image pin in Console code. Acceptance may use dev-built candidate images with the test identity supplied explicitly. State how release deployment obtains an approved image identity and how old API/Console versions remain supported during rollout.

### 5. Show once, failures, permissions and audit

Define show-once as one successful creation/rotation response to the initiating authenticated admin session, with copy/selectable text and a clear save-now instruction. Never persist returned secrets in Console SQLite, People log, URL/query strings, cookies, logs, metrics or browser storage. Ordinary list/detail/reopen requests cannot retrieve one. Recommended minimum is direct no-store POST success rendering with existing single-use form tokens; a refresh/replayed POST must not recreate, rotate or redisplay a credential. Specify browser Back/forward handling for secret-bearing DOM, including restored-page behavior, rather than assuming HTTP no-store alone removes it. Snippet copies of a secret follow the same lifetime as the standalone value; later snippet views can contain placeholders only.

Writes are never retried automatically. If API committed a create/rotate but its answer was lost or invalid, report the uncertain outcome, allow metadata inspection and explain recovery (revoke an identified unwanted credential or rotate again once allowed); do not promise secret recovery, announce that nothing changed, or mint another token implicitly. Handle `401` rejected Console credential, `403` scope/grant denial, `404` missing token/unsupported API, `409` overlap/expiry/revocation/last-admin conflicts, `429`, timeouts and malformed/wrong-version responses through the existing shell patterns. A successfully committed write with a failed local People log is not a refused API write.

Use `ProtectedRoute`, `routeRole`, the established Origin/content-type/body/CSRF checks and single-use form-token boundary. Admin/owner can view and mutate; viewer/member cannot use the endpoints directly even when forging a form. Recheck live session/role immediately before the outbound mutation as current check writes do. Escape all upstream names/messages. Use the existing script/CSP and preserve no-JavaScript operation.

Append secret-free Console-person events using the existing People store for create/rotate/revoke, with API action names and stable token IDs/location labels. The API already records token audit events under its caller token; do not add on-behalf-of fields or implement the Activity page here. Define the independent-HTTP-write/local-log failure behavior explicitly.

## Derived acceptance check

1. **API self identity:** a real-server test that fails on current API main proves an admin credential receives exactly its `TokenMetadata` from `/admin/tokens/self`, validated by contract, without secret/digest. Both overlap generations identify the same row. Missing/invalid/inactive credentials, insufficient scope, disabled admin routes and wrong methods retain the chosen documented statuses and throttling; literal `self` is not treated as an arbitrary ID. Console setup tests use this route and cover the stated old-API compatibility policy.
2. **Tokens through the real Console:** admin and owner can list, create with each permitted preset, copy the one-time value, rotate and revoke with typed-name confirmation. Assert outbound scopes exactly match the presets and caller limits. Null last use shows `Never`; a successful authenticated use advances metadata. Imported/expired/revoked rows and source labels render correctly. `/self` marks the own row; forged rotate/revoke requests for it make no API write. Last-active-admin revoke is disabled and an API `409` race is displayed without false success. Member/viewer direct GET/POST attempts are denied.
3. **Show-once and boundary tests:** replay a successful POST, refresh/reopen, navigate away and Back/forward, use another session, and sign out/in. No fresh response or restored active page reveals the earlier secret or repeats the API write. Verify no returned secret appears in Console DB, People/API audit data, logs, metrics, URLs or browser storage. Include JavaScript-disabled create/revoke and selectable snippet text, invalid CSRF/Origin, mismatched confirmation, lost-response and upstream-failure cases. Use injected clocks for overlap/countdown boundaries and live session/role changes before writes.
4. **Probe management:** creating a bound credential shows `Awaiting first result`; an observed result changes the row to reporting with the API's last-result time. Cover silent, historical-only and multiple-token locations. Rotate shows the actual deadline and replacement instructions; both credentials authenticate during overlap and only the replacement afterward (existing API clock tests can supply expiry-boundary evidence). Revoke invalidates both generations for that ID. Tests prove the chosen per-credential/location-wide semantics and preserve history. No probe version/results-per-minute claim is rendered.
5. **Requested browser evidence:** extend the existing automated browser suite with create/show-once/revoke flows for Tokens and Probes, and exercise those changed flows with `agent-browser` against a running Console. Record commands and secret-free outcomes in the implementation PR. Cover copying where clipboard is available, typed-name confirmation, own-token protection, usable layout at 390 px and desktop, keyboard access and unchanged CSP. Existing Playwright/axe coverage complements, rather than replaces, the specifically requested agent-browser check.
6. **Runnable snippets in deploy compose-e2e:** use an isolated authenticated Console and real API, create a new location through the Console flow, and execute the actual generated deployment text. Test both docker-run and Compose variants with distinct locations (or explain a shared exact renderer plus runtime coverage of each). All non-secret network/image substitutions must be explicit and identical to the selected UI mode; do not hand-build a different command in the test. With a fast reachable non-heartbeat check already configured, pre-pull/build the image, record start time, launch the probe and assert a newly accepted result for that exact location within **one configured check interval**. Choose a fixture interval comfortably above the initial <1 s jitter plus fast execution/posting, and state the clock origin; do not reuse the unrelated 90 s global first-result timeout as proof. Assert reporting and last-result advancement, then exercise replacement/revoke and keep all secrets out of output. Clean up added containers/networks/temporary files on failure too.
7. **Delivery checks:** API and Console `bun run check`, Console `bun run check:browser`, and the deploy checks required by its touched scripts/workflows pass. Run candidate-source `E2E_SETUP=dev bash e2e/compose-e2e.sh` for these new behaviors, retaining the existing stack checks. If published pins are updated, run the published-image suite too and record qualifying immutable identities. Do not claim new-screen acceptance from old `0.1.0` images or fake-API browser fixtures alone. Update the owning API/Console/deploy docs for endpoints, screen semantics, snippets, rotation and compatibility.
