Notify already has important delivery semantics to extend: a per-channel SQLite ledger (format 3), lease locking, persisted pending/failed payloads, retries and explicit resend. It quietly seeds existing incident keys for new channels and when routing widens. Its retention logic protects keys of visible automatic/manual incidents; arbitrary new warning keys do not automatically receive that protection. Chat/email rendering currently assumes incident events. These are implementation constraints, not evidence that the requested warnings already exist.

## Open points and working assumptions

1. **“Burn rate” versus remaining budget.** The concrete requirement and design label describe a low remaining-budget alert. Use existing `slo.budgetRemaining` in percentage points, with a default threshold of **25**, strict `<` (25 itself does not alert), including zero and negative budgets. A missing SLO or null budget does not alert. Preserve the API's existing availability formula/window. Multi-window burn-rate ratios, new SLO CRUD and recovery notifications are outside scope. The plan should name the operator setting, its scope and valid range if making the threshold configurable; a notify-wide default is sufficient without per-SLO rule CRUD.

2. **Which SLOs and their identity.** “Per SLO” includes both current check and component SLOs, each identified by `(subject kind, subject id)`. A check and component with the same id must not share suppression state. Route check SLOs using check include/exclude filters and component SLOs using component include/exclude filters. A component budget produces one component event, not one duplicate per member. Subjects without an `availabilityTarget` are skipped. Do not invent a third independent SLO resource.

3. **Meaning of once per day.** Assume at least **24 elapsed hours** between newly generated low-budget events for the same SLO. The next successful evaluation after that boundary may alert again if still below threshold; recovery and another drop during the same interval cannot bypass suppression. This avoids two alerts a few seconds apart across midnight. The planner must state this choice explicitly; UTC calendar-day bucketing is another plausible reading, but must not be left implicit. Detection uses injected time and must not manufacture a burst for days missed during downtime. Suppression is per SLO event; each selected channel may deliver that same event once, and channels cannot consume each other's delivery state.

4. **Expiry coverage and time semantics.** Cover existing `tls` checks and `domain` checks. Ordinary HTTP checks do not currently report certificate expiry. Use the published whole-day count rather than parse reason text; the warning milestones are fixed at 14 and 3 independently of a check's `warnDays`, status and incident history. Preserve current probe degradation/down and incident behavior. A valid observation at 15 does not warn, at 14 enters the first warning band, and at 3 enters the urgent band. `0` means less than a whole day left and may warn; negative counts are expired and do not create a new advance-warning event. Null/missing counts and failed reads must not act as zero, reset deduplication or rearm a cycle.

5. **Polling gaps and first observation.** Equality-only comparisons can miss an entire milestone during downtime. Prefer first observation in a due band: 14..4 sends the 14-day warning; 3..0 sends the 3-day warning. If the first good observation is already at 2 days, send only the urgent warning and record the earlier milestone as superseded; do not send two warnings together. A jump from 15 to 13 must send the 14-day warning once; a jump from 13 to 2 must send the 3-day warning once. This is a proposed catch-up policy; the plan must spell it out and test it.

6. **“Not again”, renewal and data limits.** Expiry suppression is per check and warning milestone for an expiry cycle, not per polling day or per result timestamp. Persist it across restart, failed delivery and ledger pruning. A later renewal must allow the next cycle's warnings. Current integers cannot identify exact expiry: `result.timestamp + certDaysLeft * dayMs` drifts within a day, so it must not be used directly as an idempotency key. To stay within notify/api, an acceptable documented policy is an observed warning episode, rearmed only by a newer valid observation above 14 days after an earlier warning episode. Small increases, location variation, reordered results and null gaps must not rearm it. That policy cannot recognize every replacement/renewal that remains within 14 days. If the spec promises once per actual certificate/registration expiry, it must instead add stable observation identity or exact expiry through contract, probe and API, and include those target sections/dependencies. Do not silently promise that precision from the current wire data.

7. **Freshness and multiple locations.** API `service.ts` picks `certDaysLeft` from the newest per-location result. Use one documented current observation per check, and its observation time; do not generate one warning per location or count down the same stale integer again on every wall-clock day. The plan must define a freshness cutoff relative to the check interval, tie handling, and rejection of older results. Prefer existing newest-result semantics with a bounded freshness allowance. An unreachable API or stale/null data leaves suppression state intact and lets unrelated incident/event feeds continue.

8. **Routable events and compatibility.** Required routing must distinguish low budget, TLS expiry and domain expiry, as well as subject filters. Add explicit warning event kinds and channel selection semantics; exact names/config shape belong in the plan after collision checks. Assume warning subscriptions are opt-in so unchanged channel files keep their current incident behavior. A warning subscription must work without incident reminders. The planner must define first subscription/filter-change behavior: recommended default is to evaluate current due warnings once, while preserving quiet seeding of old incidents. No Console UI work, route-management API or dynamic configuration reload is implied.

9. **Payloads and all senders.** Warnings have no incident id. Define warning payloads as appropriate discriminated variants rather than fake incidents or overloaded incident identifiers. Include stable event key, event time, subject kind/id/name and budget threshold/value or expiry kind/days/milestone as applicable. Keep old incident payloads compatible. Update webhook/file output, chat/email summaries, signing/idempotency, failed list/resend and persisted pending-payload handling. Respect existing text cleaning and secret-redaction behavior. A recipient failure retries the same key; it is not a new daily/milestone event. Physical exactly-once delivery across a receiver-success/sender-crash boundary is not guaranteed by the existing transport; receivers can use the stable webhook idempotency key.

10. **State ownership, retention and edits.** The plan must choose one evaluator/suppression owner rather than competing API and notify schedulers. Existing API read models plus notify polling/durable state are sufficient for budget evaluation; API work must identify a concrete missing behavior or be scoped to documentation/verification. Do not add a durable API event feed only to justify a target. Keep detection/suppression records distinct from prunable delivery history where necessary, and define subject removal/recreation, threshold edits and subscription changes. Those edits must not reset a live SLO's 24-hour limit or replay a live expiry episode. Use the existing lock and transactional persistence; do not require shared state across independent notify installations.

11. **Target scope and rollout.** Likely product scope is notify and API, with contract/probe only if the chosen wire requirements need them. A service-to-service field/route must live in contract; do not copy a new wire type into notify. Existing state/component validators may avoid a contract change. Notify's contract dependency is currently older than inspected contract main, so the plan must verify its needed exports and pin an appropriate merged full SHA. Handle old API responses/new optional fields explicitly; a warning feed failure must not disable incident delivery. Deploy may need an acceptance/fixture task, but Console/status changes and published image pin bumps are not automatically necessary.

12. **Compose evidence.** “CI and compose-e2e green” must refer to the changed implementations. Deploy's existing published-image run alone cannot validate an unshipped API/notifier. The plan must assign an integration owner, arrange temporary candidate image overrides in a writable scratch checkout, and record API and notify SHAs/images. Keep committed production pins unchanged unless a pin update is explicitly part of the approved plan. Do not wait real days or introduce a production clock-control endpoint to test the timing rules.

## Derived acceptance check

Expected thresholds, counts and boundaries below are literals from the request or the assumptions above, not values read back from the implementation under test. The final plan must adopt or explicitly revise each timing/startup/renewal assumption before implementation.

1. **Budget red/green regression:** with injected time and a configured check SLO at 25%, observe zero budget events. Change to 24% and observe exactly one logical event delivered once to each of two matching channels. Repeated polls, recovery followed by another drop, and reopening the same state database before 24 hours produce zero additional events. At `first event time + 24h - 1ms`, none; at `+24h`, a still-low budget produces exactly one additional event. A second SLO can alert independently. Cover component SLOs, a check/component id collision, no target, null budget, zero and negative budget. Record a behavior assertion failing against inspected main and passing after the change.

2. **Expiry red/green regression:** for each of TLS and domain, feed newer valid observations with literal counts `15, 14, 14, 13, 4, 3, 3, 2, 0, -1`. The episode yields exactly two logical warning events, milestones `[14, 3]`, never one per day/poll. Restart at a repeated milestone and run delivery-history pruning with a short retention: counts remain two. New observations above 14 rearm the documented episode policy; a later `14, 3` yields exactly two more. Null observations, duplicates, stale/reordered data and a small increase while still in the episode do not rearm it. Separately cover `15 -> 13`, `13 -> 2`, and first observation `2` with the catch-up expectations above. Record failing-before/passing-after assertions for both milestone behavior and suppression.

3. **Routing and delivery:** a warning-only channel receives selected kinds/subjects and no incident events; exclusions win. TLS and domain can route separately. Component SLO routing does not expand to member checks. An unrelated channel receives no warning; old config retains incident behavior. Verify a warning does not need an open incident and does not create one. Exercise webhook/file plus chat/email formatting, the same idempotency key through retry/restart, independent channel outcomes, and failed list/resend. Existing automatic/manual incidents, reminders and ledger migrations retain their behavior.

4. **API and trust boundaries:** use actual HTTP tests for every changed/new response and for notify reading the relevant state, with contract validation. Verify the budget matches the API's existing SLO computation and no synthetic incident is needed for a warning. Invalid/null/stale warning observations cannot generate alerts or reset suppression; an unavailable optional/older feed does not stop healthy incident feeds. If wire fields are added, test old producers/consumers and update committed contract `dist/` as required.

5. **Implementation handoff:** run target `bun run check` and their required CI/image checks; API `bun run bench:selftest` and any performance checks warranted by API changes. Start changed services using their documented start commands and exercise a warning through real HTTP with local fixtures. Run deploy `bash e2e/compose-e2e.sh` to completion against the candidate API and notifier images and preserve command, SHAs and results. Timing-boundary proof belongs in deterministic fake-time tests; Compose proves stack compatibility and routing/delivery without a multi-day wait. These are future build acceptance requirements, not checks claimed as run during issue review.
