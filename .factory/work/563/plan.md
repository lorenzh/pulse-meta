# Spec #563: console TOTP, recovery codes, sessions

## Goal

The owner of a self-hosted pulse-console must prove a second factor before the console grants
any protected page. The second factor is a TOTP authenticator app (RFC 6238) or one of ten
single-use recovery codes. TOTP seeds are encrypted at rest with a key that pulse-deploy
provisions. The owner sees the list of their sessions. "Sign out all" ends every other session,
and the current one stays. The plain "Sign out" ends only the current one. The rule "who must
have a second factor" is one function, so #564 can extend it from the owner to every admin.

The console on `main` already has setup, password sign-in, sessions and throttling from #562.
This spec builds on that code (console clone at `edefdbeaa152d602d724a3c19cc3ca3ad760aa6b`) and
does not redo it. Owner recovery after a lost owner password belongs to #564.

Engineering choices made here (the issue review lists them as open points; none needs a hold):

1. **Three session stages.** A session row has a stage: `factor` (password proven, a second
   factor is pending), `enrol` (password proven, the user must enrol and has no authenticator)
   or `full`. Only `full` opens protected pages. Partial stages expire 15 minutes after their
   creation and are never extended.
2. **One access gate.** Every app route declares the stage it needs in the route table. One
   check in the request path enforces it before the handler runs. Navigation and the password
   POST do not enforce anything on their own. The gate runs only after setup; before setup the
   #562 redirects to `/setup` stay as they are.
3. **Legacy sessions end.** The migration to schema 2 deletes every session row. A schema-1
   session never had a second factor, so it must not count as one. The owner, the password hash
   and the saved API URL stay.
4. **Missing key.** `PULSE_CONSOLE_SECRET_KEY_FILE` is optional at start, like the admin token.
   Without it, the console starts and logs a warning, but enrolment and TOTP sign-in answer
   `503`. So the owner gets no protected access without it. Recovery codes still work, because
   they are hashed, not encrypted. A malformed key file stops the start (exit 2). A missing
   key never opens a protected page: the owner stays in the `enrol` or `factor` stage.
5. **No acknowledgement state.** The response that confirms the authenticator shows the ten
   recovery codes and also starts the full session. If that response is lost, the owner makes a
   new set on `/account/recovery-codes`. An extra "I saved them" state would add a stage
   without adding security: the hashes are already stored.
6. **Re-authentication.** Replacing the authenticator and making new recovery codes from a
   `full` session need the current password. A stolen session cookie alone cannot plant a new
   second factor.
7. **Sign out all keeps this browser.** The button label is "Sign out all other sessions". The
   action deletes every other session row of the user, in every stage (pending authenticators of
   those sessions go with them). The current session row stays unchanged: same cookie, same CSRF
   token. Then it redirects back to the session list. The plain "Sign out" (`POST /sign-out`,
   #562) still ends only the current session. A password change follows the same rule: it ends
   every other session of the user and keeps the current one. The console has no password change
   today (console `main` has no route or store function that updates `password_hash`; checked in
   `src/server.ts:69-75` and `src/account-store.ts`), and this spec adds none. So the spec gives
   the one store function `deleteOtherSessions(userId, keepSessionId)`. Sign out all uses it, and
   a later password change (#564) must call it in the same transaction that writes the new hash.
8. **Separate factor throttle.** Second-factor attempts (TOTP, recovery code, enrolment
   confirmation) have their own limiter, with an account key per user and a client key. A
   correct password does not clear it. Only a successful second factor clears the account key.
9. **Manual setup key.** The enrolment page shows the setup key as text, and the `otpauth://`
   URI as text. There is no QR code: that would need a package or a weaker CSP.
10. **Deploy first, with an e2e for both console flows.** deploy's daily `dev` job builds console
    `main` and runs `e2e/console-setup.sh`, which today expects the #562 flow
    (`e2e/console-setup.sh:111` expects `Location: /sign-in?setup=done`). So deploy merges first:
    it provisions the key (the #562 console ignores it) and its e2e picks the flow from the
    `Location` of Finish setup. Console merges second; its PR gets a CI job `deploy-dev` that runs
    deploy `main`'s `dev` setup and e2e against the console under test with
    `E2E_CONSOLE_FLOW=two-factor`. So the console PR cannot turn green unless deploy's `dev` job
    will pass after the merge, and no merge leaves a consumer failing (see Rollout order).

## Scope

- console: schema 2, the access gate and stages, the second-factor policy predicate, TOTP,
  seed encryption, recovery codes, the enrolment, sign-in factor, recovery-code, account
  security and session pages, sign out all, the key setting, metrics, logs, docs and tests.
- deploy: provisioning of the console secret key in `full`, `dev`, `demo` and CLI installs,
  the setup e2e extended with a two-factor flow (enrol, TOTP, recovery code, sign out all) next
  to the #562 flow it runs today, and docs.
- console CI: a `deploy-dev` job that runs deploy `main`'s `dev` e2e against the console under
  test.

## Non-goals

- Passkeys and WebAuthn (#563b), and any change to `docs/approved-packages.md`.
- Roles, admins, members, viewers, invitations, managed 2FA or password resets, ownership
  transfer, the organisation-wide "require 2FA" switch, owner recovery after a lost password
  (all #564).
- An activity log (item C) or an app shell rebuild (item A).
- Per-session revocation, device names, IP addresses or locations in the session list (the
  console stores none of them).
- Key rotation, a key-management service, or a QR code.
- Any change to pulse-api, contract, kit, config or the other services.
- A console image release or a pin bump in deploy.
- Removing the `legacy` flow from `e2e/console-setup.sh`. That is a later deploy cleanup, once
  console `main` has this feature; until then the flow keeps the `dev` job green.

## Required behavior

### Second-factor policy

- `src/two-factor-policy.ts` exports `isSecondFactorRequired(user: { role: User["role"] }):
  boolean`. Today it returns `true` for `role === "owner"`. It is the only place that decides
  whether a user must have a second factor. #564 widens the role union and this function.
- The same module exports a pure `signInStage(view: { isRequired: boolean; hasAuthenticator:
  boolean }): "factor" | "enrol" | "full"`:
  - `hasAuthenticator` true: `factor`;
  - required and no authenticator: `enrol`;
  - not required and no authenticator: `full`. No user reaches this branch today; it is the
    seam for optional members and viewers in #564. A unit test covers it.

### Session stages and the access gate

- Session rows get a `stage` (`factor`, `enrol`, `full`) and an optional `next_path`.
- A `full` session is live until 30 days after its last use, as today, with the 60-second touch.
- A `factor` or `enrol` session is live while `now < created_at + 900000` ms. It is never
  touched, and its cookie has `Max-Age=900`.
- The effective stage of a request:
  - no cookie, an unknown cookie, an expired row, or a missing user: anonymous;
  - a `full` row whose user is required to have a second factor but has no confirmed
    authenticator: `enrol`. This cannot happen after the migration, but it makes the gate hold
    when #564 makes an existing user required;
  - otherwise the row's stage.
- The route table gains an access column. The gate runs after route, method, phase and the
  loopback `Host`, and before `Origin` and the body. It runs only after setup (an `instance` row
  exists); before setup no request reaches it (see "Before setup" below). When the stage does
  not match:
  - anonymous on a route that a `full` session may open (this includes
    `/account/authenticator`): `303` to `/sign-in?next=<encoded path>`, encoded as today
    (`/` gives `/sign-in?next=%2F`);
  - anonymous on `/sign-in/factor`: `303` to `/sign-in`;
  - `factor` on any other protected route: `303` to `/sign-in/factor`;
  - `enrol` on any other protected route: `303` to `/account/authenticator`;
  - `full` on `/sign-in/factor`: `303` to `/`.
  - A POST refused by the gate reads no body and changes nothing.
- Before setup (no `instance` row), each route keeps or gets exactly this answer, and the gate
  does not run:
  - `GET` and `HEAD /`: `303` to `/setup`, unchanged from #562 (`sendLanding`,
    `src/server.ts:241-245` on console `main`; tested at `src/server.test.ts:105-110`; the
    `docker` CI step `ci.yml:76-80` follows it with `curl -L` to the setup page).
  - `GET` and `HEAD /sign-in`: `303` to `/setup`, unchanged (`sendSignInForm`,
    `src/server.ts:303-307`).
  - `POST /sign-in`: `404`, unchanged (`isClosedInPhase`, `src/server.ts:618-622`).
  - `POST /sign-out`: unchanged; without a live session it answers `303` to `/sign-in`
    (`src/server.ts:525-530`).
  - `/setup`, `/setup/owner` and `/console.css`: unchanged.
  - The new routes `/sign-in/factor`, `/account/authenticator`, `/account/security`,
    `/account/recovery-codes`, `/account/sessions` and `/account/sessions/sign-out-all`: `404`
    for every allowed method, as a phase rule beside `POST /sign-in` (a method that is not
    allowed still answers `405` first, as for every route).
- Routes after setup:

| Route | Methods | Access |
| --- | --- | --- |
| `/` | GET, HEAD | `full` |
| `/sign-in` | GET, HEAD, POST | any; GET with a `full` session redirects to `/` |
| `/sign-in/factor` | GET, HEAD, POST | `factor` |
| `/sign-out` | POST | any session stage (unchanged) |
| `/account/authenticator` | GET, HEAD, POST | `enrol` or `full` |
| `/account/security` | GET, HEAD | `full` |
| `/account/recovery-codes` | GET, HEAD, POST | `full` |
| `/account/sessions` | GET, HEAD | `full` |
| `/account/sessions/sign-out-all` | GET, HEAD, POST | `full` |

- The landing page gets a link "Account security" to `/account/security`.

### Setup step "Secure the owner account"

- Finish setup saves the owner and the URL as today. Then, in the same request, it starts an
  `enrol` session for the new owner (new id and CSRF token) and redirects `303` to
  `/account/authenticator`. The password was just set in this request, which is the proof.
- If enrolment is interrupted (tab closed, 15 minutes passed, restart), the owner signs in with
  the password and gets an `enrol` session again. Setup stays closed.

### Password sign-in

- `POST /sign-in` keeps its validation, throttle (account by email and client) and timing. On a
  correct password it computes the stage with `signInStage`, starts a session of that stage
  (rotation as today: the old row of this browser goes, a new id and CSRF token are made), stores
  `safeNext(next)` as `next_path` in a partial stage, and redirects `303`:
  - `factor`: to `/sign-in/factor`;
  - `enrol`: to `/account/authenticator`;
  - `full`: to `next`.
- A correct password clears the password account failures, as today. It does not touch the
  factor throttle.

### TOTP

- RFC 6238 with HMAC-SHA-1, 6 digits, a 30-second period and T0 = 0: step
  `c = floor(nowMs / 30000)`; the code is the RFC 4226 dynamic truncation modulo 10^6, left-padded
  with zeros to 6 digits.
- Accepted steps: `c - 1`, `c` and `c + 1`, and only steps greater than the stored `last_step`
  of that authenticator. The lowest accepted matching step is used. Success stores it as the new
  `last_step` in the same transaction that completes the sign-in, with
  `UPDATE … SET last_step = ? WHERE user_id = ? AND last_step < ?`; zero changed rows is a
  failure. So a code works once, also across browsers, concurrent requests, restarts and a clock
  that goes back.
- Input: the field is trimmed and spaces (U+0020) are removed. It must then be exactly 6 ASCII
  digits; anything else answers `422` and does not count.
- Seed: 20 random bytes per authenticator. The setup key is its RFC 4648 base32 text, upper
  case, no padding (32 characters), shown in groups of 4 separated by spaces in an element with
  `id="totp-secret"`. The page also shows the parameters (SHA-1, 6 digits, 30 seconds) and the
  URI `otpauth://totp/pulse%20Console:<url-encoded email>?secret=<key>&issuer=pulse%20Console&algorithm=SHA1&digits=6&period=30`
  as text. No QR code and no script.

### Seed encryption

- Key: `PULSE_CONSOLE_SECRET_KEY_FILE`, read once at start. The content, after dropping exactly
  one trailing `\n`, must be exactly 64 lowercase hex characters (`^[0-9a-f]{64}$`), which give
  the 32 key bytes. It must differ from the admin token value. The value never appears in a log,
  an error, a response or the database.
- Start errors (exit 2, one stderr line, checked after the admin token):
  - `PULSE_CONSOLE_SECRET_KEY_FILE=<path>: cannot read (<code>)`;
  - `PULSE_CONSOLE_SECRET_KEY_FILE=<path>: must hold 64 lowercase hex characters`;
  - `PULSE_CONSOLE_SECRET_KEY_FILE=<path>: must differ from the admin token`.
- Unset: the start logs `warn`
  `PULSE_CONSOLE_SECRET_KEY_FILE is not set: authenticator enrolment and TOTP sign-in are unavailable`.
  The start log line `pulse-console listening` gains `hasSecretKey` (`true` or `false`).
- AES-256-GCM, a fresh 12-byte random nonce per encryption, a 16-byte tag, and the additional
  data `pulse-console:totp:v1:user:<user id>` (UTF-8), which binds the ciphertext to the account.
  Stored envelope (TEXT): `v1:<nonce>:<ciphertext>:<tag>`, each part base64url without padding.
- Decryption that fails (wrong key, changed ciphertext, another user's row, unknown version)
  returns a typed failure. The plaintext is discarded. It never falls back to password-only
  access and never replaces the stored seed. The request answers `500` with the page text
  `The authenticator secret cannot be read. Sign in with a recovery code.`, releases the
  throttle reservation (it is not a failed guess) and logs `error`
  `authenticator secret cannot be decrypted` with `userId`.
- The key is not in SQLite, not derived from a password or the api token, and never rotated by
  the console. Backup means the database file and the key file together. A lost key makes the
  stored seeds unreadable; the owner then signs in with a recovery code and replaces the
  authenticator, which encrypts the new seed with the new key.

### Recovery codes

- A set is 10 distinct codes. Each code is 16 random bytes as 32 lowercase hex characters, shown
  as 8 groups of 4 joined by `-`. A repeated value is drawn again.
- Stored: only the SHA-256 hex digest of the 32 normalised hex characters, one row per code, with
  `used_at` (NULL while unused). Never the plain code, never in a cookie.
- Input normalisation: trim, remove spaces and `-`, lowercase. It must then be exactly 32 hex
  characters; anything else answers `422` and does not count.
- A recovery code replaces only the TOTP step after the password. It never replaces the
  password, the setup code or a reset link.
- Use, all inside the `BEGIN IMMEDIATE` transaction that completes the sign-in (see "Second factor
  at sign-in"):
  1. The candidate digest is the 32-byte SHA-256 of the normalised input.
  2. Look up the user's unused codes:
     `SELECT id, digest FROM recovery_codes WHERE user_id = ? AND used_at IS NULL`. The SQL never
     filters on the digest, so the database does no comparison of secret-derived values.
  3. Compare in `src/recovery-codes.ts` with the pure `matchRecoveryCode(candidate, rows)`:
     - every row is compared, with no early exit;
     - a stored digest must match `^[0-9a-f]{64}$`, which decodes to 32 bytes; another value
       never matches and is never passed to `timingSafeEqual`;
     - each comparison is `crypto.timingSafeEqual(storedBytes, candidate)` on two 32-byte
       buffers, so it cannot throw on a length mismatch;
     - the result is the `id` of the matching row, or none.
  4. No match: the transaction rolls back and the answer is `401` (counts).
  5. Consume: `UPDATE recovery_codes SET used_at = ? WHERE id = ? AND used_at IS NULL`. It must
     change exactly 1 row; with 0 the transaction rolls back and the answer is `401`.
  The lookup, the comparison and the update run under one write lock (`BEGIN IMMEDIATE` takes it
  at the start). So a second request with the same code, in this process or another one on the
  same file, sees `used_at` set and fails. The conditional update is a second guard. A code works
  once, also with parallel requests and after a restart.
- The codes are shown only in the `200` response that created them, in
  `<ol id="recovery-codes">` with one `<li><code>…</code></li>` per code. A later GET shows only
  the count of unused codes ("<n> of 10 recovery codes left").
- A new set replaces the whole old set in one transaction (delete all rows of the user, insert
  10). The old codes stop working at once.

### Enrolment and replacement: `/account/authenticator`

- A pending authenticator is a row bound to one session (`session_digest`), with an encrypted
  seed and `created_at`. It is live while `now < created_at + 900000`. It is deleted with its
  session (foreign key cascade). It never replaces the confirmed authenticator before
  confirmation. Parallel tabs of one browser share it; another browser has its own.
- `GET` without the key: `503` page
  `Two-factor setup needs PULSE_CONSOLE_SECRET_KEY_FILE. Ask the operator to set it.`
- `GET` with a live pending row of this session: `200` with the setup key, the URI, and a form
  `action=confirm` with the field `code`.
- `GET` without a live pending row:
  - `enrol` stage: `200` with a form `action=new` ("Create a setup key").
  - `full` stage: `200` with the enrolment date of the current authenticator (never its seed) and
    a form `action=new` with a `password` field ("Replace authenticator"). The text says that
    replacing ends every other session and makes new recovery codes.
- `POST action=new`:
  - In the `full` stage the `password` must be correct. Empty or over 128 code points: `422`.
    The password throttle (account by email, client) applies: `429` with `Retry-After`; a wrong
    password answers `401` and counts.
  - Without the key: `503`.
  - It creates or replaces the pending row of this session with a new seed and redirects `303`
    to `/account/authenticator`.
- `POST action=confirm` with `code`:
  - Format (`422`), then the key (`503`), then the factor throttle (`429`), then a live pending
    row of this session (else `409` with the text `The setup key expired. Create a new one.`
    and the `action=new` form; the reservation is released).
  - The code is checked against the pending seed with the TOTP window. Wrong: `401`, counts.
  - Success, in one `BEGIN IMMEDIATE` transaction: delete the pending row; replace the user's
    authenticator with the pending envelope, `last_step` = the matched step and `confirmed_at`;
    replace the recovery codes with a new set; delete every session row of the user; insert a
    new `full` session (new id and CSRF token). So every other session ends, and this browser
    goes on with a rotated session: it stays signed in, and the stage change gets a new id, as at
    any sign-in. This is the same rule as sign out all and a password change. The factor throttle
    succeeds (clears the account key). The response is `200` with the 10 codes, `Set-Cookie` for the new session, and a link
    "Continue" to the stored `next_path` (`/` when none).
  - `POST action` with another value: `422`.

### Second factor at sign-in: `/sign-in/factor`

- `GET`: `200` with two forms on one page: the field `code` (TOTP, `autocomplete="one-time-code"`,
  `inputmode="numeric"`) and the field `recovery_code`. Both post to `/sign-in/factor` with the
  session's CSRF token. A "Cancel" button posts to `/sign-out`.
- `POST` fields `code`, `recovery_code`, `csrf`. Exactly one of `code` and `recovery_code` must be
  non-empty, else `422` with `Enter the code from your authenticator app or a recovery code.`
- Order after CSRF: format (`422`), the key for a TOTP code (`503`), the factor throttle (`429`
  with `Retry-After`), verification (`401`, counts, page text `Wrong code.`), decryption failure
  (`500`, released), commit.
- Commit, in one `BEGIN IMMEDIATE` transaction:
  `DELETE FROM sessions WHERE id_digest = ? AND stage = 'factor'` must change 1 row; then the
  `last_step` update must change 1 row (TOTP), or the recovery-code lookup, timing-safe match and
  `UPDATE … WHERE id = ? AND used_at IS NULL` of "Recovery codes" must find and change 1 row
  (recovery code); then insert a new `full` session. If the delete changes 0 rows (the session
  was signed out, expired or already used), the transaction rolls back, the reservation is
  released and the answer is `303` to `/sign-in`. If the factor step fails (TOTP: the `last_step`
  update changes 0 rows, a replay; recovery code: no unused row matches, or the update changes 0
  rows), the transaction rolls back and the answer is `401` (counts). For a recovery code the
  verification is this step: the match runs only inside the transaction, never before it.
- Success: the factor throttle succeeds, the response sets the new session cookie and redirects
  `303` to `safeNext(next_path)`. Log `info` `signed in` with `userId` and `factor`
  (`totp` or `recovery-code`); for a recovery code also `remaining`.
- A new password sign-in from the same browser replaces the `factor` row (rotation) but not the
  factor failures.

### Account security page

- `GET /account/security` (`full`): the authenticator enrolment date, "<n> of 10 recovery codes
  left", and links to `/account/authenticator` ("Replace authenticator"),
  `/account/recovery-codes` ("New recovery codes") and `/account/sessions` ("Sessions").

### New recovery codes: `/account/recovery-codes`

- `GET` (`full`): the count left and a plain confirmation form: the `password` field and the button
  "Create new recovery codes", with the text `Your current recovery codes stop working.`
- `POST`: password rules and the password throttle as for `action=new`. Success: replace the set
  and answer `200` with the 10 codes. Log `info` `recovery codes created` with `userId`.

### Sessions: `/account/sessions` and sign out all

- `GET /account/sessions` (`full`): one row per live `full` session of this user, newest last use
  first, with "Signed in" (`created_at`) and "Last used" (`last_seen_at`), both as
  `YYYY-MM-DD HH:MM UTC`, and the marker "This browser" on the current one. Partial sessions are
  not listed. No session id, digest or CSRF token of another session is in the HTML. Expired rows
  are deleted before the list is read. A link "Sign out all other sessions" goes to the
  confirmation. The page also has the existing "Sign out" form (`POST /sign-out`), which ends
  only this browser.
- `GET /account/sessions/sign-out-all` (`full`): the confirmation page
  `Sign out all other sessions? This browser stays signed in.` with a form that holds only the
  CSRF field and the button "Sign out all other sessions".
- `POST /account/sessions/sign-out-all`: the CSRF token of the current session is required
  (`403` without changes otherwise). Success calls `deleteOtherSessions(userId, currentId)` in
  `src/account-store.ts`: one statement
  `DELETE FROM sessions WHERE user_id = ? AND id_digest <> ?` (the digest of the current
  session). It deletes every other session row of the user in every stage (`full`, `factor`,
  `enrol`; their pending authenticators go with them by the foreign key cascade). The current row,
  its cookie, its CSRF token and its pending authenticator stay unchanged; no `Set-Cookie` is
  sent. The answer is `303` to `/account/sessions?signed-out=others`, where the page shows
  `All other sessions are signed out.` and lists only this browser. Log `info`
  `signed out other sessions` with `userId` and `sessions` (the count of deleted rows).
- `POST /sign-out` stays as in #562 (`src/server.ts:525-536`): it deletes only the current row and
  the cookie and redirects `303` to `/sign-in`. Other sessions of the user stay.
- Password change: the console has none (see decision 7). The rule for any later one is that it
  calls `deleteOtherSessions` in the transaction that writes the new hash; the current session
  stays. `src/account-store.test.ts` tests `deleteOtherSessions` directly, so #564 can rely on it.
- A touch is `UPDATE … WHERE id_digest = ?` and never inserts, so a revoked row is never
  recreated. A request that read a row before the delete may finish; its next request fails.

### Schema 2

- `SCHEMA_VERSION` becomes 2. Migration 1 stays as it is. Migration 2, in one immediate
  transaction, runs on version 1 (and right after migration 1 on a new file):
  - drops the table `sessions` (all rows go) and creates it again with the columns `id_digest`,
    `user_id`, `csrf_token`, `created_at`, `last_seen_at`, `stage` (NOT NULL, one of `factor`,
    `enrol`, `full`), `next_path` (nullable), and an index on `user_id`;
  - creates `authenticators` (`user_id` primary key, references `users` on delete cascade,
    `secret` TEXT, `last_step` INTEGER, `confirmed_at` INTEGER);
  - creates `pending_authenticators` (`session_digest` primary key, references
    `sessions(id_digest)` on delete cascade, `user_id` references `users`, `secret`, `created_at`);
  - creates `recovery_codes` (`id` INTEGER PRIMARY KEY, as `users.id`; `user_id` NOT NULL
    references `users` on delete cascade; `digest` TEXT NOT NULL, 64 lowercase hex; `used_at`
    INTEGER, nullable; UNIQUE `(user_id, digest)`; an index on `user_id`);
  - sets `PRAGMA user_version = 2`.
- `instance` and `users` rows are unchanged. The start error for a newer schema names `(2)`.
- Start and every session creation delete expired rows: `full` after 30 days idle, partial rows
  and pending authenticators 900000 ms after creation.

### HTTP rules for the new routes

- Every new POST follows the documented order: route and method (`404`, `405`); phase (`404`
  before setup); the loopback `Host` (`421`); the access gate (`303`); `Origin` (`403`); content
  type (`415`); body over 8192 bytes (`413`); a repeated known field (`400`); the CSRF token of
  the current session (`403`); field format (`422`); the key (`503`); the throttle (`429`);
  verification (`401`); state (`409`); commit (`200`, `303` or `500`).
- Every new form carries the session's CSRF token. Every page is `no-store`, uses the existing
  CSP and works without JavaScript. Each code field is at most 64 characters (`422` above).
- Pages for sign-in, `/sign-in/factor`, `/account/authenticator` and the recovery-code page have
  no horizontal scroll at 390 px; the setup key and the codes wrap.
- Metrics: the `path` label gains the 6 new routes. `pulse_console_auth_attempts_total` `kind`
  gains `totp`, `recovery-code`, `enrolment` and `password-confirm`. `sign-in` keeps counting the
  password step.
- Logs never hold a seed, a setup key, a TOTP code, a recovery code, the secret key, a session id
  or a CSRF token. New lines: `info` `password accepted` (`userId`, `stage`); `warn`
  `second factor failed` (`client`, `kind`, `reason` `credentials` or `throttled`); `info`
  `authenticator confirmed` (`userId`); `info` `recovery codes created`; `info` `signed in`
  (`userId`, `factor`); `info` `signed out other sessions` (`userId`, `sessions`); `error`
  `authenticator secret cannot be decrypted`.

### Intended disclosures

The setup key and the `otpauth://` URI appear only in `GET /account/authenticator` responses
while a pending row is live. The ten codes appear only in the `200` response that created them.
Neither appears in a `Location`, a cookie, a log, a metric or an error. Tests that scan for
sentinels cut these responses out first.

## Risks

- **Lost key.** Stored seeds become unreadable. Recovery codes still work; the owner replaces
  the authenticator. With the key and all codes lost, the only way back is the destructive reset
  (delete the database), until #564 adds owner recovery. The docs say so.
- **Lost response with the codes.** The session is already `full`; the owner makes a new set.
- **Clock skew.** A server or phone clock more than about 30 seconds off fails the window. The
  docs name NTP.
- **Factor lockout as denial of service.** Someone who knows the password can lock the owner's
  second factor for 15 minutes. The password is the barrier; this is the decided rule.
- **Throttle state in memory.** A restart clears it, as in #562 (a documented limit).
- **A copied current cookie survives sign out all.** Sign out all keeps the current session as it
  is, as the issue asks. Someone who holds a copy of this browser's own cookie keeps access until
  the owner also uses "Sign out" here, or until the 30-day idle expiry. The sessions page puts the
  "Sign out" form next to "Sign out all other sessions", and the README says to use both after a
  suspected cookie theft.
- **The two-factor e2e flow first runs in the console PR.** deploy merges first, when no console
  has the new flow, so deploy CI proves only the `legacy` flow and the static checks of the new
  one. The console PR's `deploy-dev` job is the first real run. If it fails because of the deploy
  script, the console child holds with `needs-input` and names the step; a person fixes deploy
  through a feature issue before console merges. `main` of both repositories stays green
  meanwhile, because console does not merge red. The literals of the e2e steps come from this
  spec, so each side is checked against the same text.
- **Factor tests that hit the throttle by accident.** The client key of the factor throttle is
  not cleared by a success (like the sign-in client key, `src/auth-throttle.ts:143-145`), so five
  wrong factors from one test client in 15 minutes lock it, across accounts and successes. The
  tests isolate their failures (see the fixture rules in Acceptance evidence).

## Security impact

Security impact: yes. The change is authentication: a second factor, session stages, encryption
at rest, a new secret file in Compose and the CLI, and new form parsing at a trust boundary.

Checklist items that apply:

- **Secrets in errors, logs and responses.** Seeds, setup keys, TOTP and recovery codes, the
  secret key, session ids and CSRF tokens never appear in a log, a metric, an error, a
  `Location` or a cookie other than their own; the setup key and the codes appear only in their
  intended disclosures. Start errors for the key name the path and the rule only. deploy scripts
  never print the key.
- **Auth order and status codes.** The gate runs before the body is read; partial stages reach
  only their own routes; the POST order above; `303` for a wrong stage, `401` for a wrong factor,
  `429` before verification, `503` without the key, `500` for an unreadable seed. The challenge is
  a `factor` session row, consumed in the same transaction as the step or code, and replaced by a
  new full session id (no fixation). Legacy sessions are deleted by the migration. Sign out all
  deletes every other session of the user in every stage and keeps only the current row; the
  plain sign-out deletes only the current row.
- **Secret comparison.** A recovery code is found by user and unused state only, and its digest
  is compared with `crypto.timingSafeEqual` on two 32-byte buffers, over every unused row, inside
  the consuming `BEGIN IMMEDIATE` transaction. SQL never compares a secret-derived value. This is
  the pattern of `src/setup-code.ts:51` and `src/request-guard.ts:44` on console `main`.
- **Body and size limits.** Forms stay capped at 8192 bytes; code fields at 64 characters; the
  password at 128 code points; throttle tables at 10000 keys.
- **Input validation.** TOTP and recovery-code formats, `action`, the password, `next`, and the
  key file format at start and in deploy.
- **Atomic, path-safe writes.** Every factor change is one `BEGIN IMMEDIATE` transaction with
  conditional updates. deploy writes the key with `mktemp`, mode `0600`, never over an existing
  file; `secrets-init` writes through a temp file and a rename, `1000:1000`, `0400`.
- **Dependency pins.** No new package. `node:crypto` and `bun:sqlite` only. The new console CI
  job `deploy-dev` uses only the approved `actions/checkout` pin with
  `persist-credentials: false` and `permissions: contents: read`; it checks out public `main`
  branches, builds them locally and generates its secrets with deploy's `init-secrets.sh`, so no
  repository secret is used or printed. It runs on `pull_request`, never `pull_request_target`.

Not applicable: SSRF and redirects (no new outbound request), accessor execution (form fields are
read with `URLSearchParams`), the probe HTTP client, Dockerfiles (unchanged).

## Counterexamples

- **TOTP window** (step `c = floor(now / 30000)`):
  - At `now = 59000` the code `287082` (step 1) is accepted; at `now = 90000` (step 3) the
    code for step 1 is refused (`c - 2`).
  - The code for step `c + 2` is refused.
  - At `now = 29999` the step is 0; at `now = 30000` it is 1. A wrong implementation that rounds
    gets the boundary wrong.
- **Replay:** after a success at step `s`, the same code at the same time answers `401`; a code
  for step `s - 1` (still in the window) answers `401`, because `s - 1 <= last_step`.
  The code for `s + 1` answers `303`. After the clock goes back 120 s, step `s - 4` is refused.
  A wrong implementation that keeps a list of used code strings would also refuse the same six
  digits at a much later step, which must be accepted.
- **TOTP input:** `081804` accepted (leading zero kept); `81804` → `422`; `081 804` accepted;
  `0818040` → `422`; `08180a` → `422`; `٠٨١٨٠٤` (Arabic-Indic digits) → `422`; both fields
  filled → `422`; none → `422`. None of them counts.
- **Recovery input:** `ABCD-…` upper case accepted after lowercasing; the code without `-`
  accepted; 31 hex characters → `422`; a `g` inside → `422`; the code with one changed hex
  digit → `401` (counts).
- **One budget:** 3 wrong TOTP codes and 2 wrong recovery codes → the 6th factor attempt `429`.
  A correct password in between does not reset it.
- **Client key after a success:** on one server, 3 wrong codes, a correct code (`303`; the account
  key is cleared), then a new password sign-in and 2 wrong codes: the next attempt answers `429`,
  because the client key still holds 5 live failures. A wrong implementation that clears both keys
  on success would answer `401` or `303`.
- **Lock boundary:** the lock set by the 5th failure at `t5` refuses at `t5 + 899999`
  (`Retry-After: 1`) and admits at `t5 + 900000`; each of those checks needs a fresh password
  sign-in, because the partial session from before `t5` has expired.
- **Partial expiry:** a `factor` session created at `t` works at `t + 899999` and is anonymous at
  `t + 900000` (a factor POST then answers `303` to `/sign-in`); a request at `t + 600000` does
  not extend it. A pending replacement of a `full` session (the session lives 30 days) created at
  `t`: confirm with a correct code at `t + 899999` → `200`; another one confirmed at
  `t + 900000` → `409`. In the `enrol` stage the session is never younger than its pending row,
  so at the pending row's `t + 900000` the session has expired too: confirm → `303` to
  `/sign-in?next=%2Faccount%2Fauthenticator`, not `409`. A wrong implementation that checks the
  pending row before the gate would answer `409` there.
- **Gate:** `POST /account/recovery-codes` with an `enrol` session and a valid CSRF token → `303`,
  no new codes. `GET /sign-in/factor` with a `full` session → `303` to `/`. `GET
  /account/authenticator` with a `factor` session → `303` to `/sign-in/factor`.
- **Gate before setup:** on an empty database, `GET /` without a cookie → `303` to `/setup`. A
  wrong implementation that runs the gate before the phase check answers `303` to
  `/sign-in?next=%2F`, which breaks `src/server.test.ts:105-110` and the `docker` CI step at
  `ci.yml:76-80`. A wrong implementation that closes every route before setup answers `404`.
  `GET /account/security` before setup → `404`, not `303` to `/sign-in?next=…` or `/setup`.
- **Re-authentication:** `POST /account/recovery-codes` from a `full` session with a wrong password
  → `401`, old codes still work; empty password → `422`.
- **Replacement:** a confirmed replacement makes the old authenticator's code fail (`401`), ends
  every other session of the user, and makes the old recovery codes fail.
- **Key format:** `0123…` (64 lowercase hex, one trailing `\n`) accepted; the same in upper case,
  63 characters, 65 characters, `\n\n` at the end, a leading space, `\r\n` at the end → refused
  with the "must hold 64 lowercase hex characters" text.
- **Envelope:** `v2:…`, three parts, a 11-byte nonce, a tag of 15 bytes → typed failure.
- **Sign out all:** the CSRF token of another session of the same user → `403`, nothing deleted.
  A wrong implementation that deletes every row of the user (the earlier reading of the label)
  makes A's own cookie answer `303` to `/sign-in?next=%2F`; the spec requires `200`. One that
  deletes only `full` rows leaves C's `factor` session, which then completes with a correct code
  (`303` to its `next_path`) instead of `303` to `/sign-in`. One that rotates the current session sends
  `Set-Cookie`; the spec sends none. `POST /sign-out` that ends every session of the user makes
  B's `GET /` answer `303`; the spec requires `200`.
- **Recovery-code lookup:** a code that is 32 hex characters, the right format, but in no row →
  `401`, no row changes. A wrong implementation that compares with `===` or with `digest = ?` in
  SQL passes this test too, so the check is also static: `src/recovery-codes.ts` calls
  `timingSafeEqual`, and no SQL in `src` filters `recovery_codes` by `digest` (Checks of
  Repository: console). A stored digest of 63 characters must give no match; a wrong
  implementation that passes it to `timingSafeEqual` throws (`500`). Two parallel uses of one code:
  a wrong implementation that matches before `BEGIN IMMEDIATE` and updates without
  `AND used_at IS NULL` gives two `303`; the spec requires one `303` and one `401`.
- **Statistics:** this spec defines none (no percentile, average or rate).
