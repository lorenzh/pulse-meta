## Current implementation and implications

**Console authentication exists.** `src/database.ts` creates schema version 1 with `instance`, `users` and `sessions`. `src/account-store.ts` exposes owner lookup, transactional initial setup, and session create/read/touch/delete/expiry operations. Its `User` type and row conversion expose only `role: "owner"`; the database has a unique owner index. There are no TOTP seeds, recovery codes, enrolment state or session factor markers.

`src/server.ts` verifies the password and immediately calls `startSession`, then permits `/` through `signedInOf`. The only protected application page today is that landing page; there are no admin management pages to test yet. Sessions store a SHA-256 digest of the random cookie ID, CSRF token, creation and last-use timestamps. They survive restarts, expire after thirty days idle, refresh after sixty seconds and support signing out the current browser. There is no list or account-wide revocation operation, and no stored browser, IP, geography or identity-provider metadata. Existing authenticated sessions must not silently count as second-factor-verified after migration.

`src/auth-throttle.ts` already implements bounded account/client tables, in-flight reservations and the decided five-failure lockout. Sign-in currently clears account failures after password success. With a second stage, password success must not clear a second-factor failure budget or mint unrestricted authentication. `src/main.ts` injects clock, random source, verifier and store; the new behavior can retain that testable structure.

`src/pages.ts` renders HTML forms with kit escaping. The server already applies no-store responses, CSP, exact raw-path routing, Origin/Host checks and the documented POST validation order. Preserve these on every new endpoint. Existing real-server tests cover setup, sign-in, cookies, security and restart behavior; extend them for the new states instead of discarding those guarantees.

**Key provisioning is missing in deploy.** `scripts/init-secrets.sh` creates probe and admin tokens. `scripts/secrets-init.mjs` distributes the admin token in files mode and creates/keeps it in demo generate mode. Neither provisions a console encryption key. `full/compose.yaml`, `demo/compose.yaml` and `dev/compose.yaml` already mount durable `console-data` and read-only `console-secrets`; the console receives the admin-token file and public URL. `cli/render-compose.ts` generates the same arrangement, while CLI secret generation and preservation live in `cli/init.ts`, `render-files.ts`, `tokens.ts` and `write-install.ts`. The generated helper embeds `scripts/secrets-init.mjs` through `cli/services.ts`.

Deploy's `e2e/console-setup.sh` assumes password success gives immediate landing-page access, so mandatory enrolment will require updating that test. Published console pins in `common/services.yaml` are still `0.1.0`; deploy documentation explicitly says these predate #562. Do not confuse console main with the released image or invent a future image digest.

## Open points the plan must settle

These are engineering choices, not unanswered owner decisions. The defaults below are assumptions/recommendations for planning, not claims that the issue already specified them.

1. **Authentication states and enrolment.** Define anonymous, password-proven/enrolment-only, password-proven/factor-challenge, and fully authenticated states, with their allowed routes. New setup must include “Secure the owner account”, confirm a generated seed with a valid TOTP, and present recovery codes before completing the user-facing flow. Persisting the existing owner/instance transaction before enrolment is acceptable only if it grants no administrative access and interrupted enrolment can resume after proving the password. Define cancellation, refresh, parallel tabs, restart and expiry. Pending seeds must not replace an active seed before confirmation.

2. **Upgrade and the policy gate.** Migrate schema 1 without losing the owner, password hash or API URL or reopening setup. Require the existing owner to enrol; previously issued password-only sessions cannot open `/` or future administrative handlers. Recommend expiring or downgrading legacy sessions and using one server-side access gate plus one required-factor predicate that #564 can extend. Avoid enforcement only in navigation or the password POST. Explicitly allow only the minimal enrolment/challenge/sign-out routes until requirements are met; retain public ops routes and static assets.

3. **TOTP parameters and replay.** Recommend six decimal digits, HMAC-SHA-1, a thirty-second period, Unix epoch start, a random per-user seed of at least twenty bytes, and a fixed small drift window such as current step ±1. Specify parameters, input format and exact boundaries, and test against independent known vectors. Persist an atomically advanced last-accepted counter (or equivalent durable replay protection), including for the enrolment confirmation. No replay across browsers, concurrent requests or restarts; a clock rollback must not resurrect a consumed step. A later legitimate occurrence of the same decimal value is not permanently blacklisted. [RFC 6238 sections 4–6 and Appendix B](https://datatracker.ietf.org/doc/html/rfc6238) define the algorithm, bounded clock drift and rejection of a second use within an accepted step. These concrete parameter defaults are planning choices.

4. **Provisioning UI.** Show a manual authenticator setup key with issuer/account identification and clear confirmation instructions. Manual entry is a sufficient baseline under the no-new-package rule. Settle whether a provisioning URI is also displayed; QR generation is not an issue requirement and must not introduce an unapproved runtime library, remote service or weaker CSP. A confirmed seed must not be shown again by an ordinary security-page GET. Protect even an unconfirmed seed while stored; keep secrets out of URLs and browser storage.

5. **Encryption-key contract and lifecycle.** Specify `PULSE_CONSOLE_SECRET_KEY_FILE` format (recommend exactly thirty-two random bytes encoded as sixty-four hex characters with an optional terminal newline), validation, startup behavior and safe error messages. Use AES-256-GCM with a fresh nonce and authenticated ciphertext; document its storage envelope and binding to the account. Do not derive the key from a password or API token or put it in SQLite. The [node:crypto authenticated-decryption documentation](https://nodejs.org/api/crypto.html#deciphersetauthtagbuffer-encoding) requires discarding plaintext when authentication fails. Missing/unreadable/malformed keys, wrong keys and tampered seeds must never fall back to password-only access or silently replace the seed. Explain backup/restore of the database together with the separate key. Automatic rotation and a key-management service are not required; regenerating a lost key is not account recovery.

6. **Second-stage challenge and throttling.** Bind a short-lived, unguessable challenge to the password-proven account, browser and safe return path; it cannot be a general session. Define its expiry, one-use completion, restart behavior, cancellation and cookie flags. Reuse the account/client limiter appropriately for TOTP, recovery and enrolment verification, including concurrent attempts. A fresh challenge or another correct password cannot reset factor failures. Only completed authentication records sign-in success. Keep socket-peer client identity and existing forwarding-header rules. Use a fresh full session ID/CSRF token after factor success to prevent fixation.

7. **Recovery-code lifecycle.** Generate exactly ten distinct, high-entropy random codes (recommend at least 128 bits each), define display groups/normalisation and store only hashes. A recovery code supplements the password; it is neither a setup code nor a password-reset link. Consume it atomically with the successful authentication transition so concurrent uses yield at most one success. Settle one-time display and acknowledgement, interrupted-response handling, remaining count and safe regeneration. Recommend a confirmed regeneration action protected by recent password/factor proof that replaces the whole set atomically. Never redisplay stored codes or keep a plaintext set in a signed client cookie. A user who signs in with recovery must have a safe way to replace a lost authenticator without removing the required-factor gate.

8. **Own-factor management.** Provide enough own-account security UI to inspect enrolment, enrol/replace an authenticator and obtain replacement recovery codes. Owner-required protection cannot be disabled. Replacement must require appropriate existing credential proof, confirm the new factor before discarding the old one, invalidate the old recovery set and settle effects on existing sessions/challenges. Do not expose an unauthenticated “lost device” bypass. Define the shared own-factor operations so #564 can later use them for optional member/viewer enrolment and managed resets without implementing those roles here.

9. **Session list and sign out all.** Default to the caller's live full sessions only, showing creation/last-use times and which is current; expire/prune stale rows. Do not invent devices, IP locations or provider sessions absent from current storage. Recommend interpreting the literal label “Sign out all” as revoking all the caller's sessions including the current one, then redirecting to sign-in; the issue's required observable result is that other browsers stop working. The spec must explicitly choose caller behavior and cover pending challenges so an old challenge cannot restore access after account-wide revocation. Use a plain confirmation and CSRF-protected POST, with no side effect on GET or other accounts and no raw session credential or digest exposed in list HTML. Define concurrent revocation/touch/completion behavior so a revoked row is never recreated by a touch.

10. **Target boundaries and rollout.** Expect console plus a narrowly scoped deploy target: durable key provisioning in full/dev/demo and CLI-generated installs, matching setting/path, secret permissions, stable reruns and backup instructions. Minimal without console must keep working. Check the CLI's preservation rules separately: token validity rules are too broad for a fixed-length encryption key, and an invalid existing encryption key must not be silently replaced. Specify a compatible merge/rollout order. For example, key plumbing can precede console because old console ignores the new setting; if console lands first, explicitly define safe behavior without the key and account for deploy's daily dev-from-main job. Missing provisioning must never grant admin access. Coordinate the updated e2e flow with the console change. No API or shared wire-contract change is indicated for local account storage and browser forms. Pin bumps must use an actually released image through the existing bump process.

11. **HTTP details, documentation and verification.** The plan must name routes, methods/statuses, field limits, validation order, CSRF authority for partial states, error/expired notices, safe-next handling and metrics with bounded labels. Never log seed, OTP, recovery code, challenge, session credential or encryption key. Confirmations for new recovery codes and sign out all work without JavaScript. Update console README/configuration and affected deploy/CLI documentation. Keep 390 px sign-in/2FA usable without horizontal scroll. This is authentication work: task/security review should cover replay, concurrency, partial authentication, migration and revocation, rather than only happy-path pages.

## Derived acceptance check

Done when a fresh self-hosted owner and an upgraded #562 owner can complete mandatory TOTP enrolment and retain recovery codes, password alone cannot grant administrative access, a second factor completes sign-in, each recovery code works once, and sign out all invalidates other browsers, with encrypted seeds and a stable separately provisioned key after restart.

Implementation must add tests that fail before the corresponding change, then pass against real HTTP/store behavior:

1. **Mandatory owner gate:** after fresh owner creation, correct password alone permits only security completion; direct GET/HEAD of `/` and every introduced protected action cannot reach protected content/effects. Confirm TOTP and acknowledge recovery codes to gain access. Repeat with a schema-1 database and an old live session; account/API URL survive, setup stays closed, old authentication cannot bypass enrolment. Test the central owner-required predicate for #564's extension seam without creating admin accounts here.
2. **Sign-in challenge:** an enrolled owner supplies password then valid TOTP to get a rotated full session and safe return path. Wrong, expired, missing, fabricated, cross-browser and already-completed challenges cannot authenticate. Direct factor POST without password proof fails. A valid password/challenge restart does not reset five-factor-failure lockout; account/client enforcement and fifteen-minute recovery use injected time.
3. **TOTP correctness and one use:** independent RFC-compatible vectors, leading zeroes, chosen drift boundaries and malformed input; the accepted step cannot authenticate again, even concurrently or after reopening the database. Advance fake time between enrolment confirmation and later sign-in. Verify a new eligible step works and backward time cannot replay an old one.
4. **Encrypted persistence:** confirmed and any persisted pending seeds are encrypted. The same key can decrypt after restart; wrong key/tampered ciphertext cannot authenticate. Missing/bad key behavior matches the spec and grants no administrative access. Inspect database rows and relevant file/log outputs for seed/key/plain-code sentinels while allowing only the intended secret presentation responses.
5. **Ten recovery codes:** exactly ten distinct values are presented at enrolment; only hashes persist. After password proof, one unused code authenticates, its second use fails, concurrent uses have at most one success, and consumption survives restart. Regeneration invalidates the previous set and does not disclose it. Losing TOTP can lead through authenticated replacement while the owner remains subject to mandatory 2FA; recovery codes do not replace the password.
6. **Sessions:** authenticate two independent clients, see their live sessions with a correct current marker, reject missing/wrong CSRF on sign out all without revocation, then confirm the action. Every other old cookie fails on its next protected request, including after restart. Assert the chosen current-client behavior and pending-challenge revocation. Store isolation can use fixtures for a second user without building team flows. Keep thirty-day idle expiry and bounded touch behavior.
7. **Browser check replacing WebAuthn acceptance:** exercise setup, manual-key TOTP enrolment, recovery-code display, password-plus-code sign-in, invalid-code feedback and session revocation in a browser. Check the 2FA sign-in at 390 px and confirmations with JavaScript disabled. No virtual authenticator is required because passkeys are deferred. The plan must choose tooling allowed by the package policy rather than assuming console already has Playwright.
8. **Deploy integration:** key has the specified format and restricted permissions, is readable by the console user through the read-only secrets mount and absent from source/output/database. First provisioning works for static full/dev/demo and CLI installs; reruns/container recreation preserve the same key and allow TOTP sign-in. Invalid existing key is refused, not replaced. Update the real console setup e2e to enrol and challenge; keep no-console installs working. Use released pins or dev builds honestly.

Console implementation must pass its required `bun run check` and local service exercise; deploy must pass the checks for the scripts, CLI/rendering and Compose paths it changes. This issue-review state performs source/document review only: it adds this artifact, changes no target code, and does not claim the future acceptance checks have run.
