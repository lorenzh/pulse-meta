# Issue review: #7 TLS certificate expiry check

Verdict: specifiable. No blocking questions; open points have proposed defaults.

## Current state (inspected in .repos/*)
- contract: `Check` is `{id, name, url, intervalMs, timeoutMs?}`, HTTP only. `Result` has `status: "up"|"down"`, `statusCode`, `latencyMs`, `reason`, `location`. `CheckWithState` carries `state`, `consecutiveDown`, `lastResultAt`, `lastReason`, `locations`, `maintenance?`. No type or field for check kind or certificate days. `dist/` is committed build output.
- api: `config.ts` `parseChecks` requires `url` (http/https) and `intervalMs` for every check, so a `tls` check (host/port) is rejected today. `state.ts` `applyResult` is pure: 3 consecutive downs open an incident (`DOWNS_TO_OPEN`), an up resolves it. Checks are served by `GET /checks`, and the probe consumes the same endpoint.
- probe: `check.ts` `runCheck` only does `fetch(check.url)`. `client.ts` `fetchChecks` rebuilds each `Check` from only `id,name,url,intervalMs,timeoutMs`, so new fields would be dropped. The probe pins an older contract SHA (23f8830) than api/status (7b1c48c).
- status: `render.ts` `renderChecks` shows state, name, url, maintenance note and `lastReason`. There is no per-check detail field. It would show a TLS check's `url` as empty or undefined.
- Conventions (AGENTS.md): strict TS, node:test, injectable clock, network tests only against local servers started in the test.

## Open points (non-blocking, with proposed defaults)
1. **Check shape and discriminator.** Propose `Check` becomes a union or gets an optional `type?: "http" | "tls"` (absent means `http`, so existing config and API data stay valid). TLS fields: `host` (required), `port` (default 443), `warnDays` (default 14). Spec must choose between a discriminated union (cleaner, but `url` becomes optional for TLS and every consumer needs narrowing) and flat optional fields. Recommend a discriminated union on `type`, with the HTTP variant keeping `type` optional.
2. **Config validation (api).** `parseChecks` must branch by type: for `tls`, require non-empty `host`, `port` an integer 1–65535, `warnDays` a positive integer (or non-negative; decide whether 0 is allowed, since "at or below" 0 means only expired), and `intervalMs`/`timeoutMs` as for HTTP. A `tls` check must not need `url`. Reject an unknown `type`. Reject `host` containing a scheme or path.
3. **`url` for TLS checks.** The status page and `GET /checks` rely on `url`. Propose the status page shows `host:port` for TLS checks. Do not synthesise a fake `https://` URL.
4. **How the probe reads the certificate.** Use `node:tls` `connect` with `servername = host` (SNI) and read `getPeerCertificate().valid_to`. Key decision: validation. The test requirement uses generated (self-signed) certificates. Propose the probe connects with `rejectUnauthorized: false` and judges only expiry. Otherwise a self-signed or unknown-CA cert fails the handshake and the "up" test cannot pass without a CA option. Consequence: an untrusted or hostname-mismatched certificate is not reported. Alternative: verify the chain and reason `UNABLE_TO_VERIFY_LEAF_SIGNATURE`, with an optional CA for tests only. The issue says "handshake fails -> down with reason", which suggests verification, but then the tests must inject a CA. Default: don't verify the chain, and document it. The spec should record this as an explicit decision.
5. **Days-until-expiry arithmetic.** Propose `daysLeft = floor((validTo - now) / 86400000)`, using the injectable clock (`deps.now`), not `Date.now`. The comparison is `daysLeft <= warnDays` means down, so "at or below" holds at the boundary. Whole days, floored. Reason text: `certificate expires in N days` (N=1 gives "1 days"? Decide singular. Default: the literal "N days" for all N, since the issue gives the exact wording). Expired (`validTo <= now`): `down`, reason `certificate expired` (suggest including the date or "N days ago"). Handshake errors: `down` with the error code or message, using the same `errorReason` style as HTTP (e.g. `ECONNREFUSED`, `timeout after Nms`).
6. **Where the days value lives.** The status page must show the days next to a TLS check, and the spec must say how it gets there. Options: (a) a new optional field `Result.certDaysLeft?: number | null` that the api stores (a new SQLite column, so a schema migration), and `CheckWithState.certDaysLeft`; (b) parse it back out of `lastReason`. Default (a), because reason text only exists when down and an `up` result also needs to show its days. The api needs a migration for existing DBs (`ALTER TABLE ... ADD COLUMN`) and must handle old rows as null. The contract change must be backwards compatible (optional field), and the probe, api and status pins must be bumped.
7. **Result for the expired/failed case.** `statusCode` is null; `certDaysLeft` is null for handshake failure, and zero or negative for expired (decide: store negative days to show "expired 3 days ago" or null). Default: store the (negative) number when a certificate was read, null when none was.
8. **Incident rule.** "Same as HTTP": `applyResult` already works on `status` only, so 3 consecutive downs open an incident and one up resolves it. No state-machine change. Note the consequence: a threshold warning needs 3 consecutive probe intervals before an incident opens, so the status page shows `down` on the first result while the incident follows later. Multi-location quorum and maintenance windows (already in the clones) apply to TLS checks unchanged. Verify that the quorum logic does not depend on HTTP-only fields.
9. **Interval default for TLS.** `intervalMs` is required for HTTP. Cert expiry changes slowly, but keep it required for consistency (no new default) unless the spec says otherwise.
10. **Status page.** `renderChecks` shows e.g. `certificate expires in 5 days` or `12 days` beside the state for TLS checks (new span `.cert-days`), via `escapeHtml` and the injectable rendering, with no `url` span for TLS. Show `host:port`. HTTP rendering output must stay byte-identical for existing tests. CSS class for a down state already exists.
11. **Probe plumbing.** `fetchChecks` must pass through the new fields (it whitelists today). `runCheck` branches by `check.type`. A new `CheckDeps` member (e.g. `tlsConnect`) makes the probe testable. Tests use a real local `tls.createServer` with a generated certificate. The repos have no cert generation tooling, and the tests must not depend on the `openssl` binary being installed in CI. Options: a devDependency (e.g. `selfsigned`/`node-forge`) or a checked-in fixture. A checked-in fixture cannot have a short expiry relative to "now", but the injectable clock makes that workable (fix a long-lived fixture cert, move `now` to N days before its expiry). Default: generate with `openssl` via `child_process` in test setup only if CI images have it; otherwise a fixture cert plus an injected clock. The spec must pick. Generating fresh certs with a chosen `notAfter` needs a library or `openssl x509 -days`/`-not_after`.
12. **Delivery.** PRs to contract (types, `dist/` rebuilt and committed) first, then probe, api and status with SHA bumps (probe's pin is already behind: bump it to the new contract commit). Update the READMEs, `checks.example.json` and the meta README config example.
13. **Out of scope** (assume): chain/hostname verification reporting, multiple certificates in a chain (only the leaf is checked), STARTTLS protocols, alerting/notification, per-check config reload, IPv6 literal hosts beyond what `tls.connect` handles.

## Assumptions
- No chain verification: expiry is judged on the leaf certificate (point 4).
- `type` absent means HTTP, so old config and DB rows stay valid.
- `warnDays` default 14, `port` default 443, applied in the api config parser, so the probe gets full values.
- The injectable clock (`deps.now`) decides days left. The probe's `timeoutMs` bounds connect plus handshake.
- Whole days are floored, and `daysLeft <= warnDays` is down.
- A nullable `certDaysLeft` is added to the result and the check (point 6).

## Acceptance check
Using local servers only, no internet:
1. Generate two certificates (or one fixture plus a controlled clock): A expires in 5 days, B expires in 90 days. Start two local `tls.createServer` instances with them.
2. api config contains `{ "id": "tls-a", "type": "tls", "host": "127.0.0.1", "port": <A>, "intervalMs": ..., ... }` and `tls-b` likewise (default `warnDays` 14), plus the existing HTTP check. Start api, probe and status.
3. `GET /checks` (and the status page) shows `tls-a` as `down` with reason `certificate expires in 5 days` and 5 days next to it. `tls-b` is `up` with about 90 days shown. The HTTP check behaves exactly as before.
4. After 3 consecutive down results for `tls-a` an incident is open, and it appears in the incident list. Stopping the TLS server of `tls-b` gives `down` with a connection error reason. An expired certificate gives `down` with `certificate expired`.
5. The config edge cases are rejected with `ConfigError`: a `tls` check without `host`, a bad `port`, an unknown `type`. Defaults `port` 443 and `warnDays` 14 apply when omitted. A boundary test: a certificate with exactly `warnDays` left is `down`, and `warnDays + 1` is `up`.
6. Existing HTTP-only config, API data and the existing tests pass unchanged in contract, probe, api and status (`npm run check` in each).
