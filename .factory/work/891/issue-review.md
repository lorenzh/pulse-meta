## Open points and resolved assumptions

- **Meaning of “held request”:** preserve the existing D22 release boundary, the manually held 2,000 ms response timer. The driver's valid form request is sent completely; the self-check is not currently holding an incomplete incoming body. The required observation is client data while release has not fired. There is no reason to change production body handling or write a new partial-body scenario for this issue.
- **Where to synchronize:** waiting after `driveSubscribe` returns is too late: it cannot change the already captured `bytesBeforeRelease`. Waiting for fake-notify finish, server write completion, or more fixed turns is also insufficient. Observe the raw client's received bytes before the snapshot and release.
- **How much data:** positive length is sufficient for this self-check; it proves an early response became observable. Preserve existing full-response and timing assertions; do not replace them with the new condition.
- **Failure behavior:** waits must remain bounded and fail with an identifiable condition when no data arrives. Never fire the release to make the positive-data condition true. Keep manual clocks and resource cleanup; add no real timers, sleeps, production changes, dependency changes, config changes, or new test files.

- **Names and tooling:** any new local hook/gate names need scoped collision searches where the plan contract requires them; historical searches are not substitutes for current evidence.
