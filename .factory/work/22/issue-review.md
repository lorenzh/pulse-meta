# Issue review: CI workflow for every pulse repository

## Current state (checked in the clones)
- contract, probe, api and status each already have `.github/workflows/ci.yml`, identical: triggers `push: [main]` and `pull_request`; one job `check` on `ubuntu-24.04`; `actions/checkout@v5`, `actions/setup-node@v6` with `node-version: 24` and no `cache`; `npm ci`; `npm run check`.
- Missing versus the issue: npm cache, separate lint/typecheck/test steps, `permissions: contents: read`, `concurrency` cancel-in-progress, a named dist-freshness step in contract, README badges (no README has one).
- **No lint exists anywhere.** No repo has a `lint` script, ESLint, Biome or any config. Scripts today: `typecheck` (`tsc --noEmit`), `test` (`node --test`), `check` (typecheck + test; contract's also runs `build` first). TypeScript is `^7.0.2`, strict, ESM, `erasableSyntaxOnly`.
- contract commits `dist/` (`index.js`, `index.d.ts`). `test/smoke.test.ts` already has "dist matches a fresh build of src", so `npm test` in contract already goes red when dist is stale. Note `npm run check` runs `build` first, which would regenerate dist and hide staleness in a CI that only used `check`; the CI must not call `check` (and must not build before the freshness step in a way that masks it).
- api, probe and status depend on contract via a Git dependency pinned to a commit; `npm ci` needs GitHub access, which a public repo gives without secrets. If the contract repository is private, `npm ci` in the other three would need a token (see open point 6).
- Repo conventions (AGENTS.md): npm only, `npm ci`, Node 24. Each repo's `.gitignore` covers `node_modules/` (api also `checks.json`, `pulse.db*`).

## Open points (none block the spec)
1. **Lint tool is not chosen.** The issue demands a lint step but no linter exists. Assumption: each repo gets a `lint` script and a dev dependency. Choice for the spec: ESLint with typescript-eslint (flat config), or Biome. Spec should pick one and use it in all four repos for consistency; check that it works with TypeScript 7 (typescript-eslint peer range may not accept TS 7; Biome has no TypeScript dependency, so it is the safer assumption). Adding it must keep existing code passing (fix or configure rules, do not mass-rewrite). The lockfile changes with it, so `npm ci` must stay consistent. A new dev dependency does not conflict with "keep using npm".
2. **Scope of the change.** The issue says "has a workflow", yet one exists. Assumption: replace/extend the existing `ci.yml` in place (same file name, workflow name `CI`) rather than add a second workflow, so the badge and any required status check keep working.
3. **Job and step layout.** Assumption: one job `check` (keep the name), steps `Install` (`npm ci`), `Lint`, `Typecheck`, `Test`, each its own `run`, using `npm run lint`, `npm run typecheck`, `npm test`. Do not call `npm run check` in CI. Keep `check` scripts in package.json (unchanged, or add `lint` to them in the spec's discretion).
4. **Node 24 and cache.** `actions/setup-node` with `node-version: 24` and `cache: npm` (lockfiles exist in all repos). Keep `ubuntu-24.04` and the action major versions already used.
5. **Concurrency.** Assumption: `concurrency: { group: ci-${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: true }`. On pushes to `main` this would also cancel an older main run; acceptable, or restrict cancellation to pull requests (`cancel-in-progress: ${{ github.event_name == 'pull_request' }}`). Assumption: cancel on any ref, per the issue wording "same branch".
6. **Private contract dependency (risk).** If `lorenzh/pulse-contract` is private, `npm ci` in probe/api/status fails without a token, contradicting "no secrets". Not verifiable from the clones. Assumption: the repositories are public (the READMEs link to them with plain URLs). The spec should state this assumption.
7. **Contract dist check.** Assumption: a separate step `Check dist is up to date` after install: `npm run build` then `git diff --exit-code -- dist` (also fail on untracked files in dist via `git status --porcelain dist`). Red-on-stale is then provided twice (this step and the smoke test), which is fine. Order matters: the Test step must run on the committed state or the check step must come first/last consistently; spec should put the freshness step so a stale dist is reported by name. Rebuilding in CI uses the same TypeScript from the lockfile, so output is deterministic.
8. **Badge.** Assumption: `[![CI](https://github.com/lorenzh/pulse-<name>/actions/workflows/ci.yml/badge.svg)](https://github.com/lorenzh/pulse-<name>/actions/workflows/ci.yml)` directly under the README title in the four repos. The meta repo has no CI target and is not listed; it gets no badge or workflow.
9. **Permissions.** `permissions: contents: read` at workflow level; no secrets, no `GITHUB_TOKEN` write use.
10. **"Green run" is verified only on GitHub.** Locally the implementation can verify that each script exits 0 and that the YAML parses; the green/red PR runs need real CI. The contract red case can be simulated locally by editing `src` without building and running the freshness step.
11. **Cross-repo order.** Independent per repo, except that a lint dependency choice should be identical. No ordering dependency between repos; contract's pin in the other repos is untouched.

## Assumptions to carry into the spec
All of the above; in particular: public repos, in-place edit of `ci.yml`, one linter for all four repos (prefer Biome unless typescript-eslint supports TS 7), `cache: npm`, workflow-level concurrency cancel, badge under each README title.

## Derived acceptance check
1. In each of contract, probe, api, status, `.github/workflows/ci.yml` triggers on `pull_request` and `push` to `main`, sets `permissions: contents: read`, has `concurrency` with `cancel-in-progress`, uses no secrets, uses `actions/setup-node` with Node 24 and `cache: npm`, runs `npm ci`, then separate steps for lint, typecheck and test.
2. Each repo has a working `npm run lint` that exits 0 on the current code, alongside `npm run typecheck` and `npm test`; `npm ci` succeeds with the updated lockfile; no non-npm package manager appears.
3. contract's workflow has a dist-freshness step that exits 0 on the committed state and non-zero after a change to `src` without a rebuild.
4. Each README shows a CI badge linking to its `ci.yml` workflow runs.
5. On GitHub: a pull request in each repo shows a green CI run listing Lint, Typecheck and Test steps; a contract PR changing `src` without rebuilding `dist` shows a red run.
