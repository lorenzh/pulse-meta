# Spec #619: contract: restore a fast path for plain JSON in validate-core

## Goal

Make the shared validator core fast again for plain JSON input. Plain JSON here means plain objects and dense arrays that hold only own data properties, as `JSON.parse` returns them. Such input must validate as fast as it did before PR #44 (lorenzh/pulse-contract#44, merge `41dfbc8`) without giving up any own-data protection: inherited elements and fields, holes and accessors stay rejected or count as absent, as they do today. A plain-JSON input skips the own-data copy and is parsed directly. Every other input still takes the copy path. This fixes the CPU regression in api result ingest, status history polling and notify polling (issue comment on #605). Those services get the fix when they update their contract pin.

- **What Zod 4.6.7 reads from the input it parses** (read in the zod 4.6.7 package that `bun install --frozen-lockfile` installs for `7ce23aa`, files `v4/core/schemas.js` and `v4/core/util.js`). For an object schema it reads only the declared keys (`input[key]`, `schemas.js:1072`, and `key in input` in `handlePropertyResult`, :894). A strict object also runs a `for … in` key loop (`handleCatchall`, :960) and does not read the values of unknown keys. For an array it reads `length` and the indexes (:870-871). Object and union parses test the input only with `typeof`/`Array.isArray` (`util.js:215-217`). The record parse is the exception: it runs `util.isPlainObject(input)` (`schemas.js:1725`, `util.js:236-254`). That reads `input.constructor` through the prototype chain, then `ctor.prototype` if that is a function, then `Object.prototype.hasOwnProperty` and its `call` (through `Function.prototype.call`), which it calls to test whether `ctor.prototype` has an own `isPrototypeOf` (`util.js:250`). If that own property is missing, `isPlainObject` returns false and the record fails with its type error. On the copy path a record value is the null-prototype `recordView` copy, so `constructor` reads as `undefined` and none of the later reads happen. For a `z.string()` key type, the record parse then loops over `Reflect.ownKeys(input)`, calls `Object.prototype.propertyIsEnumerable` for each key (:1811-1814) and reads `input[key]` (:1857). It does this on the copy as well, so a getter on `Object.prototype.propertyIsEnumerable` already runs on `7ce23aa` (2 calls for a 2-key `headers`, planning run, the same count against the historical walk). That is an existing limit of the copy path, not a fast-path issue (Non-goals). Refinements run on Zod's output object, not on the input.

## Scope

- One repository: `contract`. The change goes in `src/validate-core.ts` (fast path), `src/validate.ts` (`arrayProblem` own-data element read), the tests, a CPU A/B script, docs, the patch version and the regenerated `dist/`.

## Non-goals

- Proxy inputs. A fast path cannot portably tell a Proxy whose traps disagree from a plain object. `node:util` `types.isProxy` is not an option: the contract must stay importable in a browser (`docs/index.md`, "API client": "uses web APIs only"). A Proxy never comes from `JSON.parse` or an HTTP body, so it cannot cross a service's trust boundary. Validators must still never throw on a Proxy, including one with throwing traps.
- No consumer pin updates (api, status, notify, probe). Each consumer gets the gain with its next contract pin bump, which is not part of this spec.
- No new public API, no caller trust flag, no schema, type, wire or `WIRE_VERSION` change, and no change to `bench/budgets.json` in the api.
- Do not redo #561/#616 (tokens, audit) or #596 (header secrets). Their own-data tests stay as they are.
- Getters on `Object.prototype` methods that Zod calls on the copy, such as `propertyIsEnumerable` in the record key loop (Verified state). They already run on `7ce23aa` with the copy, and the fast path must not add calls, but this spec does not remove them. The same goes for the `lookupGetter.call` read per element in the top-level `arrayProblem` accessor check (`src/validate.ts:72`), which stays as it is. The PR lists both under known limits.
- A fast path for records. Records always take the copy path (required behavior 2). No hot path has one.

## Required behavior

1. **Fast path.** `problem(schema, value, path)` parses `value` directly when a schema-driven walk of `value` certifies that parsing the original gives the same result as parsing `ownView(schema, value)`: same `ok`, and on failure the same error text. Otherwise it parses the copy, as today. The walk builds no copy of the input: it creates no object or array that holds input values, and no per-object view. It reads precompiled key lists and uses indexed loops. It allocates nothing per value except as the allocation rule below allows. The history workloads (`uptimeDaySchema`, `checkUptimeSchema`, `latencyDaySchema`, `checkLatencySchema`, `src/schema.ts:638-712` on `7ce23aa`) hold only objects, arrays and scalars. The walk runs no getter. The parse of a certified value runs no getter either, and it calls no function found on the input or on a prototype that the copy path would not call. This is why records always take the copy path (item 2).
   **No code from a prototype or a mutable built-in.** The walk runs no function except the built-ins it captured in module-level constants at module load (`Object.getPrototypeOf`, `Object.hasOwn`, `Object.getOwnPropertyDescriptor`, `Array.isArray`, `__lookupGetter__`, `__lookupSetter__`, the `Object.prototype`, `Array.prototype` and `Function.prototype` references, and whatever else it needs). It never calls `Object.x(...)` or `Array.x(...)` through the global at run time. A method that needs a receiver is invoked in one of two allowed ways:
   - **A. Descriptors.** Read each declared field and each index with the captured `Object.getOwnPropertyDescriptor`, and treat it as own data only when the captured `Object.hasOwn(descriptor, "value")` is true. Not `"value" in descriptor`: that also sees an inherited `Object.prototype.value`, so an accessor would pass as data. The walk passes no descriptor to Zod, and Zod parses the original input.
   - **B. `lookupGetter.call` behind a call integrity check.** Use `hasOwn(value, key)` plus `lookupGetter.call(value, key) === undefined` and `lookupSetter.call(value, key) === undefined`. `ebcbbb6` used `lookupGetter.call` alone, which misses a setter-only accessor (counterexample 10). This is allowed only after a **call integrity check** of this `problem` call has passed: `Function.prototype` has an own data property `call` identical to the `Function.prototype.call` captured at module load, and each of the captured `lookupGetter` and `lookupSetter` has the captured `Function.prototype` as its prototype and no own `call` property. The check reads descriptors and prototypes only, once per `problem` call, before the walk. If it fails, the input takes the copy path.
   - Not allowed: a run-time `x.call(...)` or `x.apply(...)` without the call integrity check. `Function.prototype.call.bind(...)` and `Reflect.apply(...)` are allowed but cost about 3x the walk time in Bun 1.4.0 (Verified state), which puts the 10% bound at risk.
   **Allocation.** With technique B the walk allocates nothing per value. With technique A the only per-value allocation is the descriptor object that `Object.getOwnPropertyDescriptor` returns, which is dropped at once. Neither creates a copy of the input or anything the parse reads.
2. **What the walk certifies**, level by level along the schema (wrappers `optional`, `nullable`, `default` and `readonly` unwrap as in `ownView`):
   - **object schema, value an object (not an array):** the prototype is `Object.prototype` or `null`. Each declared key is either an own data property, read with no getter and no setter (an own accessor of either kind fails the walk), or absent with no inherited property of that name (`key in value` is false). Each declared own value passes its field's walk.
   - **array schema, value an array:** the prototype is `Array.prototype`. Every index `0..length-1` is an own data property: no hole, no inherited element, no accessor. Each element passes the element walk.
   - **record schema, value a non-array object (`isObject`, any prototype including `null`):** fails the walk, always. The whole input then takes the copy path (`recordView`), which is today's behavior. Zod's record parse runs `isPlainObject` on the value it gets, and that function reads `constructor`, `ctor.prototype`, `Object.prototype.hasOwnProperty`, `Function.prototype.call` and the own `isPrototypeOf` of `ctor.prototype` (Verified state). The null-prototype copy reaches none of these. A walk that certified a record would have to reproduce every one of these preconditions, so it does not try. A record value that is not such an object (absent, `undefined`, a primitive, an array) passes, because `ownView` passes it through unchanged (`src/validate-core.ts:264-266` on `7ce23aa` copies only when `isObject(value)`). No record is on the history or result workloads (Verified state), so this does not affect the CPU A/B. The walk compiler needs no record-specific code beyond this rule, and the walk calls neither `Object.keys` nor `Reflect.ownKeys`.
   - **union schema:** with exactly one object option (`onlyObjectOption`), an object value passes when it passes that option's walk, and a non-object value passes. With zero or several object options, an object value fails the walk, so the copy path (`dataView`) still decides. A non-object value passes.
   - **lazy schema** (recursive JSON value): an object or function value fails the walk (copy path). A primitive passes.
   - **any value that the schema branch does not copy** (a primitive, a function where an object is expected, an array where an object is expected): passes, because `ownView` passes it through unchanged too.
   - **inherited enumerable keys:** when `Object.prototype` has any enumerable string key, every object at an object schema fails the walk. This keeps item 1 true for Zod's `for … in` strict-key check. The check is cheap enough to run once per `problem` call.
3. **Top-level array elements are own data.** `arrayProblem` (`src/validate.ts:63-81`) passes `ownValue(value, i)` to the item check instead of `value[i]`. A hole or an inherited element at index `i` reaches the item check as `undefined` and fails with the item check's usual text. For an object item that text is `<path>[<i>]: must be an object`, the same as a top-level hole today. An accessor element still fails first with `<path>[<i>]: is required` (line 72-74). This covers every array validator built on `arrayProblem`: checks, results, incidents, maintenance, latency, uptime, locations, components, components uptime, manual incidents.
4. **Unchanged:** on success, validators return the same object (`verdict`). They never throw: a throwing trap or getter is caught by `verdict` and gives `<path>: is not a valid value`. Error formats, paths and texts of every non-Proxy case stay the same, as do the schemas, the exported names and types, `WIRE_VERSION`, and `zod` 4.6.7 as the only runtime dependency.
5. **Proxy test and comment.** Rewrite the comment on `problem` (`src/validate-core.ts:288-292`): plain own-data input is parsed directly once the walk certifies it, and Proxy inputs are out of scope because a Proxy whose traps disagree can pass the walk. Replace the test `a Proxy whose get differs from its own data descriptor is judged by the descriptor` (`test/tokens.test.ts:313-338`). The new test asserts only that each of those validator calls returns a `Validation` (`typeof result.ok === "boolean"`) and does not throw. Change no other Proxy test. The hostile-trap tests (`test/validate.test.ts` "hostile proxies … never throw", `test/admin.test.ts` cyclic prototype) must pass unchanged.

## Risks

- **A walk that is too permissive brings back an own-data hole.** The `ebcbbb6` walk accepted inherited array elements (see Verified state) and treated all multi-option unions as `alwaysOwn`. Mitigation: required behavior 2, plus counterexamples 1-4, 9, 11, 13 and 14 as red tests (each fails on current `main` or against the historical walk), and counterexamples 5-8, 10 and 12 as guards, all through exported validators.
- **The walk diverges from the copy in its verdict or error text, or in which code the parse runs.** Mitigation: item 1 states the invariant. Counterexamples 9, 10, 13 and 14 cover the known divergences: Zod's `for … in` key check, a setter-only accessor, the record's `isPlainObject` reads of `constructor`, `prototype`, `hasOwnProperty` and `isPrototypeOf` (avoided because records always take the copy), and the walk's own reads of `Function.prototype.call` (avoided by captured built-ins and the call integrity check, required behavior 1). Verified state lists every read that Zod 4.6.7 makes on the input. A future zod bump must re-check that list; this spec changes no zod pin.
- **CPU above the threshold.** The added per-element own-data and prototype checks cost more than `ebcbbb6`'s walk. If B exceeds 1.10 x A, keep the checks and make the walk cheaper. Cheaper means indexed loops, precompiled key lists, technique B instead of technique A (item 1), no bound functions or `Reflect.apply` per property, and one `Object.prototype` and call integrity check per `problem` call. The 10% bound is not relaxed.
- **Cognitive complexity.** The walk compilers must stay under SonarJS cognitive complexity 15 per function. Split them per schema kind, as `ebcbbb6` did (`compileObjectWalk`, `compileRecordWalk`, `compileWalk`).

## Security impact

Security impact: yes. The change edits the own-data validators at the contract trust boundary, which parse every JSON body and API response.

Checklist items that apply:
- **Input validation:** inherited elements and fields, holes, symbol or non-enumerable record keys, multi-option unions and recursive JSON values must still be rejected, or count as absent, exactly as on the copy path. Top-level inherited elements are newly rejected (required behavior 3).
- **Accessor execution:** neither the walk nor the parse may run a getter on the fast path. This includes the getters and functions that Zod's record plainness test would reach through `Object.prototype` (`constructor`, `prototype`, `hasOwnProperty`, counterexample 13; records always take the copy) and a getter on `Function.prototype.call` (counterexample 14; the walk uses captured built-ins and, with technique B, the call integrity check). Every getter counter in the existing tests stays 0.
- **Secrets in errors, logs and responses:** error texts must not change. No input value is added to any error.
- Not applicable: auth, body or size limits (unchanged, enforced by services), SSRF, file writes, dependencies (none added), Dockerfiles, CI.

Hostile inputs for the security state: the counterexamples below, plus polluted `Object.prototype` and `Array.prototype` getters and data values (including `Object.prototype.constructor`, `Object.prototype.prototype`, `Object.prototype.hasOwnProperty` and a deleted `Object.prototype.isPrototypeOf`, at every validator that reaches a record), getters on `Function.prototype.call`, `Function.prototype.apply`, `Object.hasOwn` and `Object.getPrototypeOf` at the history validators, a record value with an own `constructor` key, a frozen array, an array subclass instance (`class A extends Array`), a null-prototype object, and the hostile-trap Proxies of the existing tests (they must never throw). For every polluted global, a validator on the PR head must give the same verdict and text as on `7ce23aa` and run no more getter calls than there.

## Rollout order

One repository: only `contract` changes. Every consumer (api, status, notify, probe) pins contract by SHA (`7ce23aa`). They keep working unchanged on the old pin. On a new pin they get the same validator API and types, the same results for plain JSON, and less CPU. The only new rejection is a top-level array element that is not own data. `JSON.parse` never produces one, so no service response or request that works today starts failing. The package version goes from `1.7.0` to `1.7.1` (semver patch, `docs/index.md` "The package version … follows semver").

## Counterexamples

Every case runs through an exported validator. `item` is a valid `CheckUptime` with 90 own days. `litem` is a valid `CheckLatency`.

Each case has one of three labels. The label says where the case is red, so the test can be shown to fail:

- **R-main**: fails on current `main` `7ce23aa` as it is. These are cases 1 and 2. Both exercise the top-level `arrayProblem` read at `src/validate.ts:75`.
- **R-walk**: passes on `7ce23aa` but fails against the **historical walk**. These are cases 3, 4, 9, 11, 13 and 14. On `7ce23aa`, nested elements are already read with `ownValue` (`src/validate-core.ts:88-95`, `arrayView`), so 3 and 4 are rejected there. On `7ce23aa`, a record is always parsed as a null-prototype copy, so 13 runs no getter and keeps `ok: true` there. On `7ce23aa`, the copy path of a single object never reads `Function.prototype.call`, so 14 counts 0 there. The tests of case 11 already exist (listed in case 11). The historical walk is a throwaway local change of `7ce23aa`: copy the `ebcbbb6` lines 189-312 of `src/validate.ts` (`type Walk` through `isOwnData`, fetched with `gh api "repos/lorenzh/pulse-contract/contents/src/validate.ts?ref=ebcbbb613328494185833f7133f1242910986948" --jq .content | base64 -d`) into `src/validate-core.ts` just above `problem`. Leave out lines 195-197, the `lookupGetter` declaration, because `7ce23aa` already exports the same function at `src/validate-core.ts:282-286`, and a second declaration does not compile. Then make `problem` call `schema.safeParse(isOwnData(schema, value) ? value : ownView(schema, value))` (line 316 there). Leave `arrayProblem` as it is. Cases 1 and 2 also fail there. Never commit that change.
- **Guard**: passes on `7ce23aa` and against the historical walk. Guards are cases 5, 6, 7, 8, 10 and 12. They are mutation guards: they fail only for a wrong fast path, for example one that caches trust per input (8), skips the prototype or `key in value` check (7), or treats a setter-only accessor as data (10). The implementer does not have to show a guard red.

1. **Top-level mixed own and inherited (R-main).** `a = [item]; a.length = 2; Object.setPrototypeOf(a, [item, item])`. `validateUptimeResponse(a)` → `{ ok: false, error: "uptime[1]: must be an object" }`. The same goes for `validateLatencyResponse` with `litem` (`latency[1]: must be an object`).
2. **Top-level all inherited (R-main).** `a = new Array(2); Object.setPrototypeOf(a, [item, item])` → `uptime[0]: must be an object`.
3. **Nested inherited day (R-walk: rejected on `7ce23aa`, accepted by the historical walk).** `days = item.days.slice(0, 89); days.length = 90; Object.setPrototypeOf(days, item.days)`. `validateUptimeResponse([{ ...item, days }])` → `uptime[0].days[89]: is required`. The same holds for latency, and for `validateCheckUptime` (`uptime.days[89]: is required`).
