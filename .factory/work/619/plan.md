# Spec #619: contract: proven-equal fast path for plain JSON in validate-core

## Goal

Make the shared validator core fast again for plain JSON input. Plain JSON here means plain objects and dense arrays that hold only own data properties, as `JSON.parse` returns them. Such input must validate as fast as it did before PR #44 (lorenzh/pulse-contract#44, merge `41dfbc8`) without giving up any own-data protection: inherited elements and fields, holes and accessors stay rejected or count as absent, as they do today. A plain-JSON input skips the own-data copy and is parsed directly. Every other input still takes the copy path. This fixes the CPU regression in api result ingest, status history polling and notify polling (issue comment on #605). Those services get the fix when they update their contract pin.

"Proven equal" means a differential test suite runs the new code and a frozen copy of the pre-change copy path (`7ce23aa`) on the same inputs and requires the same verdict and the same error text (required behavior 6). The guarantee has exactly two exceptions, and nothing else may differ:

1. **Inherited or missing top-level array elements** change from accepted to rejected (required behavior 3). The reference accepts them; the new code rejects them with a literal text.
2. **Proxy inputs** are out of scope (#619 "Proxy inputs remain out of scope"). The suite contains no Proxy input. Validators must still never throw on one.

Deep nesting is not a third exception. Every depth that the suite tests requires the same verdict and text on both sides. The suite tests only depths where the reference gives the same result on every call (counterexample 15 g). Between about 5,000 and 10,000 levels, the reference's own result for one and the same input changes from call to call with the engine's remaining stack (Verified state), so the reference defines no single result there. The suite makes no assertion at those depths, for the candidate or for the reference, and accepts no outcome there in place of the reference's. The candidate gets no extra allowance at any depth.

## Non-goals

- Proxy inputs (exception 2 of the equivalence guarantee). A fast path cannot portably tell a Proxy whose traps disagree from a plain object. `node:util` `types.isProxy` is not an option: the contract must stay importable in a browser (`docs/index.md`, "API client": "uses web APIs only"). A Proxy never comes from `JSON.parse` or an HTTP body, so it cannot cross a service's trust boundary. Validators must still never throw on a Proxy, including one with throwing traps.
- No consumer pin updates (api, status, notify, probe). Each consumer gets the gain with its next contract pin bump, which is not part of this spec.
- No new public API, no caller trust flag, no schema, type, wire or `WIRE_VERSION` change, and no change to `bench/budgets.json` in the api.
- Do not redo #561/#616 (tokens, audit) or #596 (header secrets). Their own-data tests stay as they are.
- Getters on `Object.prototype` methods that Zod calls on the copy, such as `propertyIsEnumerable` in the record key loop (Verified state). They already run on `7ce23aa` with the copy, and the fast path must not add calls, but this spec does not remove them. The same goes for the `lookupGetter.call` read per element in the top-level `arrayProblem` accessor check (`src/validate.ts:72`), which stays as it is. The PR lists both under known limits.
- A fast path for records. Records always take the copy path (required behavior 2). No hot path has one.
- An exact stack-overflow depth. The contract has no depth limit, and this spec adds none (a limit would be a new rejection). Between about 5,000 and 10,000 levels the reference's own result changes from call to call (Verified state). This is not an exception of the candidate (Goal): the suite asserts nothing for either side at those depths, and at every tested depth it requires equality.

## Required behavior

1. **Fast path.** `problem(schema, value, path)` parses `value` directly when a schema-driven walk of `value` certifies that parsing the original gives the same result as parsing `ownView(schema, value)`: same `ok`, and on failure the same error text. Otherwise it parses the copy, as today. The walk builds no copy of the input: it creates no object or array that holds input values, and no per-object view. It reads precompiled key lists and uses indexed loops. It allocates nothing per value except as the allocation rule below allows. The history workloads (`uptimeDaySchema`, `checkUptimeSchema`, `latencyDaySchema`, `checkLatencySchema`, `src/schema.ts:638-712` on `7ce23aa`) hold only objects, arrays and scalars. The walk runs no getter. The parse of a certified value runs no getter either, and it calls no function found on the input or on a prototype that the copy path would not call. This is why records always take the copy path (item 2).
   **No code from a prototype or a mutable built-in.** The walk runs no function except the built-ins it captured in module-level constants at module load (`Object.getPrototypeOf`, `Object.hasOwn`, `Object.getOwnPropertyDescriptor`, `Array.isArray`, `__lookupGetter__`, `__lookupSetter__`, the `Object.prototype`, `Array.prototype` and `Function.prototype` references, and whatever else it needs). It never calls `Object.x(...)` or `Array.x(...)` through the global at run time. A method that needs a receiver is invoked in one of two allowed ways:
   - **A. Descriptors.** Read each declared field and each index with the captured `Object.getOwnPropertyDescriptor`, and treat it as own data only when the captured `Object.hasOwn(descriptor, "value")` is true. Not `"value" in descriptor`: that also sees an inherited `Object.prototype.value`, so an accessor would pass as data. The walk passes no descriptor to Zod, and Zod parses the original input.
   - **B. `lookupGetter.call` behind a call integrity check.** Use `hasOwn(value, key)` plus `lookupGetter.call(value, key) === undefined` and `lookupSetter.call(value, key) === undefined`. `ebcbbb6` used `lookupGetter.call` alone, which misses a setter-only accessor (counterexample 10). This is allowed only after a **call integrity check** of this `problem` call has passed: `Function.prototype` has an own data property `call` identical to the `Function.prototype.call` captured at module load, and each of the captured `lookupGetter` and `lookupSetter` has the captured `Function.prototype` as its prototype and no own `call` property. The check reads descriptors and prototypes only, once per `problem` call, before the walk. If it fails, the input takes the copy path.
   - Not allowed: a run-time `x.call(...)` or `x.apply(...)` without the call integrity check. `Function.prototype.call.bind(...)` and `Reflect.apply(...)` are allowed but cost about 3x the walk time in Bun 1.4.0 (Verified state), which puts the 10% bound at risk.
   **Allocation.** With technique B the walk allocates nothing per value. With technique A the only per-value allocation is the descriptor object that `Object.getOwnPropertyDescriptor` returns, which is dropped at once. Neither creates a copy of the input or anything the parse reads.
2. **What the walk certifies**, level by level along the schema (wrappers `optional`, `nullable`, `default` and `readonly` unwrap as in `ownView`):
   - **object schema, value an object (not an array):** the prototype is `Object.prototype` or `null`. Each declared key is either an own data property, read with no getter and no setter (an own accessor of either kind fails the walk), or absent with no inherited property of that name (`key in value` is false). Each declared own value passes its field's walk.
   - **array schema, value an array:** the prototype is `Array.prototype`. Every index `0..length-1` is an own data property: no hole, no inherited element, no accessor. Each element passes the element walk.
   - **record schema, value a non-array object (`isObject`, any prototype including `null`):** fails the walk, always. The whole input then takes the copy path (`recordView`), which is today's behavior. Zod's record parse runs `isPlainObject` on the value it gets, and that function reads `constructor`, `ctor.prototype`, `Object.prototype.hasOwnProperty`, `Function.prototype.call` and the own `isPrototypeOf` of `ctor.prototype` (Verified state). The null-prototype copy reaches none of these. A walk that certified a record would have to reproduce every one of these preconditions, so it does not try. A record value that is not such an object (absent, `undefined`, a primitive, an array) passes, because `ownView` passes it through unchanged (`src/validate-core.ts:264-266` on `7ce23aa` copies only when `isObject(value)`). No record is on the history or result workloads (Verified state), so this does not affect the CPU A/B. The walk compiler needs no record-specific code beyond this rule, and the walk calls neither `Object.keys` nor `Reflect.ownKeys`.
   - **union schema:** with exactly one object option (`onlyObjectOption`), an object value passes when it passes that option's walk, and a non-object value passes. With zero or several object options, an object value fails the walk, so the copy path (`dataView`) still decides. A non-object value passes.
   - **lazy schema** (recursive JSON value, `z.json()`): an object or function value fails the walk (copy path). A primitive passes. The walk never descends into a lazy value, so its own depth is bounded by the schema, not by the input.
   - **any value that the schema branch does not copy** (a primitive, a function where an object is expected, an array where an object is expected): passes, because `ownView` passes it through unchanged too.
   - **inherited enumerable keys:** when `Object.prototype` has any enumerable string key, every object at an object schema fails the walk. This keeps item 1 true for Zod's `for … in` strict-key check. The check is cheap enough to run once per `problem` call.
3. **Top-level array elements are own data** (exception 1 of the equivalence guarantee). `arrayProblem` (`src/validate.ts:63-81`) passes `ownValue(value, i)` to the item check instead of `value[i]`. A hole or an inherited element at index `i` reaches the item check as `undefined` and fails with the item check's usual text. For an object item that text is `<path>[<i>]: must be an object`, the same as a top-level hole today. An accessor element still fails first with `<path>[<i>]: is required` (line 72-74). This covers every array validator built on `arrayProblem`: checks, results, incidents, maintenance, latency, uptime, locations, components, components uptime, manual incidents.
4. **Equivalence guarantee.** For every non-Proxy input, every validator gives the same result as the frozen `7ce23aa` copy path, except exception 1 (item 3): the same `ok`; on success the same object (`verdict` returns the input); on failure the exact same error text, which includes the path and the first issue, so the order of competing errors is unchanged. Validators never throw: a throwing trap or getter, and a stack overflow on deep input, are caught by `verdict` and give `<path>: is not a valid value`. The schemas, the exported names and types, `WIRE_VERSION`, and `zod` 4.6.7 as the only runtime dependency stay as they are. Item 6 is the evidence for this item.
5. **Proxy test and comment** (exception 2). ## Risks

- **A walk that is too permissive brings back an own-data hole.** The `ebcbbb6` walk accepted inherited array elements (see Verified state) and treated all multi-option unions as `alwaysOwn`. Mitigation: required behavior 2, plus counterexamples 1-4, 9, 11, 13 and 14 as red tests (each fails on current `main` or against the historical walk), counterexamples 5-8, 10, 12 and 15 as guards, and the differential suite over all of them.
- **The walk diverges from the copy in its verdict or error text, or in which code the parse runs.** Mitigation: item 1 states the invariant, and item 6 checks it against a frozen reference. Counterexamples 9, 10, 13 and 14 cover the known divergences: Zod's `for … in` key check, a setter-only accessor, the record's `isPlainObject` reads of `constructor`, `prototype`, `hasOwnProperty` and `isPrototypeOf` (avoided because records always take the copy), and the walk's own reads of `Function.prototype.call` (avoided by captured built-ins and the call integrity check, required behavior 1). Counterexample 15 covers the input classes the owner named. Verified state lists every read that Zod 4.6.7 makes on the input. A future zod bump must re-check that list; this spec changes no zod pin.
- **A reference that is not frozen proves nothing.** If the reference imports the candidate, or is edited along with it, every comparison passes. Mitigation: item 6 forbids those imports, every entry also checks a literal on the reference, the exception entries show that the reference still accepts counterexamples 1 and 2, and the PR shows the diff of each reference file against `git show 7ce23aa:<file>`.
- **A flaky depth test.** The stack-overflow depth moves with the JIT tier (Verified state). Mitigation: counterexample 15 g compares only at fixed depths where the reference gave one result in every round under `bun test` (1,000 and 5,000 pass; 10,000 and 100,000 fail). Each depth is called 3 times per side, and every call must equal the literal. No depth between 5,000 and 10,000 is tested, and no outcome is accepted there in place of the reference's. If the reference itself does not match the literal at a tested depth on the implementer's machine, the test must fail, not be loosened. The implementer then requests a hold with the measured values.
- **CPU above the threshold.** The added per-element own-data and prototype checks cost more than `ebcbbb6`'s walk. If B exceeds 1.10 x A in task c, keep the checks and make the walk cheaper in task c, then run the full suite, including the differential suite, again. Cheaper means indexed loops, precompiled key lists, technique B instead of technique A (item 1), no bound functions or `Reflect.apply` per property, and one `Object.prototype` and call integrity check per `problem` call. The 10% bound is not relaxed.
- **Cognitive complexity.** The walk compilers must stay under SonarJS cognitive complexity 15 per function. Split them per schema kind, as `ebcbbb6` did (`compileObjectWalk`, `compileRecordWalk`, `compileWalk`).

## Security impact

Security impact: yes. The change edits the own-data validators at the contract trust boundary, which parse every JSON body and API response.

Checklist items that apply:
- **Input validation:** inherited elements and fields, holes, symbol or non-enumerable record keys, multi-option unions and recursive JSON values must still be rejected, or count as absent, exactly as on the copy path; the differential suite checks this against the frozen reference. Top-level inherited elements are newly rejected (required behavior 3).
- **Accessor execution:** neither the walk nor the parse may run a getter on the fast path. This includes the getters and functions that Zod's record plainness test would reach through `Object.prototype` (`constructor`, `prototype`, `hasOwnProperty`, counterexample 13; records always take the copy) and a getter on `Function.prototype.call` (counterexample 14; the walk uses captured built-ins and, with technique B, the call integrity check). Every getter counter in the existing tests stays 0.
- **Secrets in errors, logs and responses:** error texts must not change. No input value is added to any error.
- Not applicable: auth, body or size limits (unchanged, enforced by services), SSRF, file writes, dependencies (none added), Dockerfiles, CI.

Hostile inputs for the security state: the counterexamples below, plus polluted `Object.prototype` and `Array.prototype` getters and data values (including `Object.prototype.constructor`, `Object.prototype.prototype`, `Object.prototype.hasOwnProperty`, `Object.prototype.value` and a deleted `Object.prototype.isPrototypeOf`, at every validator that reaches a record), getters on `Function.prototype.call`, `Function.prototype.apply`, `Object.hasOwn` and `Object.getPrototypeOf` at the history validators, a record value with an own `constructor` key, a frozen array, an array subclass instance (`class A extends Array`), a null-prototype object, deep nesting beyond the stack limit, and the hostile-trap Proxies of the existing tests (they must never throw). For every polluted global, a validator on the PR head must give the same verdict and text as the frozen reference and run no more getter calls than it.

### CPU statistic (acceptance A/B)

- **Sides.** A = a worktree of `ebcbbb613328494185833f7133f1242910986948`. B = a worktree of the candidate PR head. Both run `bun install --frozen-lockfile`, on the same machine and the same Bun 1.4.0.
- **Workloads.** The two shapes of `test/validate.bench.test.ts`: 1,000 checks x 90 days, dates from 2026-01-01. Uptime has `uptime: 99.5, results: 288` per day and `uptime: 99.5` per check. Latency has `p50Ms: 120, p95Ms: 340, count: 288` per day. Each fixture is passed through `JSON.parse(JSON.stringify(...))` once, before any timing. Uptime is validated with `validateUptimeResponse` and latency with `validateLatencyResponse`, both imported from `<root>/src/index.ts`.
- **One invocation per side.** Before timing, assert `ok === true` and `value === input` for each workload. Then run 2 warmup calls and 7 measured calls per workload. Each sample is the `process.cpuUsage()` delta (user + system) around one call, in ms. The invocation median is the 4th smallest of the 7 samples.
- **Rounds.** Run 3 rounds in the order A, B, A, B, A, B, each as a fresh process. The side value for each workload is the median of its 3 invocation medians (the 2nd smallest). Do not average medians.
- **Pass.** For each workload separately, `B ≤ 1.10 × A`, compared unrounded. The PR reports values rounded to 0.01 ms and the change as `(B/A − 1) × 100` rounded to 0.1 %. The 1.10 factor comes from the issue ("within 10% of main"). A faster B passes.
