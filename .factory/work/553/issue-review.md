## Open points and proposed assumptions

### 1. Liveness lifecycle versus feed readiness

Interpret “poll loop running” as the notifier being started and not stopped/shutting down, independent of API success or delivery results. Keep the existing failed-poll threshold, reset on a good poll, and reasons on `/readyz`. Keep startup/shutdown liveness non-success while the listener can still answer. Do not introduce a new stale-loop watchdog or freshness timeout without an explicit requirement: request timeouts and the existing scheduling loop already bound ordinary feed failures.

Docker health status alone does not make Docker restart a container; some external policy must act on it. The observable requirement here is a healthy liveness check during feed failure, independent of deployment restart policy.

### 2. Meaning of the first manual-feed observation

An older API's 404 is a tolerated absence, not evidence that the manual feed has been initialized. A successful, validated array response, including `[]`, is an observation. A failed read must not consume the one-time initialization. Preserve the distinction represented by `ManualIncidentsResult.isAbsent`; currently `#pollChannel` receives only the incidents array and loses it.

Use durable per-channel initialization state, separate from “has any manual key.” Otherwise an empty first response, ledger pruning, or restart can make a later genuinely new incident disappear into repeated seeding. On the first successful manual observation, seed currently routed missing manual keys and persist initialization together before detecting manual events. Automatic events for an already known channel must continue even if manual initialization waits or fails. Preserve the existing new-channel rule that waits for both incident feeds before its initial baseline.

Initialization must be idempotent and retry on a failed persistence operation. It must not overwrite any existing `pending`, `failed`, `delivered`, or `seeded` status or payload. Metadata must survive load/flush/prune and an initialized empty feed. Do not silently reset automatic keys or reminder initialization.

An old ledger cannot prove which never-recorded manual updates were already delivered. The proposed quiet-upgrade policy baselines the first successful snapshot once, including missing historical updates in an otherwise known channel. This intentionally suppresses that snapshot, rather than promising to recover every event created during upgrade downtime. Document this tradeoff in the upgrade note, including when the snapshot is taken. Existing pending deliveries and explicit failed resends retain their established at-least-once behavior; “never resends” applies to detection/migration replay, not an exactly-once delivery guarantee.

### 3. Stable update identity and legacy positional keys

The spec must choose an exact, version-distinguishable key encoding and migration strategy. A suggested identity is incident id plus a fixed-size digest of a canonical tuple `(at, status, message)`. Array position and timestamp alone are insufficient. Keep opened/resolved key namespaces and automatic keys compatible. Define whether an edit to message/status is a new update identity; absent a wire update id, the proposed rule treats a changed tuple as new and identical tuples as the same logical update. The spec must state this limit rather than invent a persistent update id in notify.

Keep the contract's ordering validation. Arbitrary chronological reordering is invalid input and should be skipped, not accepted by relaxing shared validation. For a valid reorder fixture, swap interior updates with equal timestamps and the same status while preserving creation and terminal resolution semantics.

A reorder-only “sends nothing” test may already pass with positional keys: every occupied index is still marked handled. Strengthen it with a valid insertion before existing updates. For example, after handling `[creation, A(at=2000), B(at=3000)]`, return `[creation, X(at=1000), A(at=2000), B(at=3000)]`, with creation earlier and statuses consistent. The current code skips X at occupied index 1 and emits B again at new index 3. The required result is X once and no replay of A or B.

Legacy `manual:<id>:update:<n>` entries must not become unhandled merely because the encoding changes. Baseline compatible stable keys at the one-time migration while retaining legacy pending/failed payloads and their resend behavior. Specify compatibility for old ledgers with automatic keys only and ones that already contain manual positional keys. A persistent key-version/initialization marker must prevent repeating this migration on every restart or every new incident. Changing channel filters and their replay policy remain #559 work.

### 4. Skipping and counting malformed items

Cover all three feeds: automatic incidents, manual incidents, and checks. The malformed-item reporting path must itself be nonthrowing for JSON-reachable hostile values; safe validation alone does not solve SEC-1. Do not stringify raw ids or include unchecked raw objects in logs. Preserve valid later items and valid other feeds in the same tick.

“Counted” needs an observable definition. Proposed default: a monotonic skipped-item counter with only the finite feed name as a label, incremented for every rejected occurrence on every poll, even when its warning is deduplicated. Choose and document the exact metric name in the spec. Do not put raw ids, reasons, paths with arbitrary keys, or hashes into metric labels. A successfully fetched array containing rejected items remains a good feed read, as existing tests require. Invalid JSON or a non-array envelope remains a failed feed read.

### 5. Body-free logging

Interpret the requirement across API failure and malformed-item diagnostics, not only the JSON parse branch. Use fixed error categories and trusted feed names/statuses, with safe finite numeric identifiers only if useful; do not copy raw bodies, parser token text, unknown property names, raw ids, manual messages, or raw contract validation strings into logs or nested causes. Truncation alone still leaks a marker. Bounded diagnostic categories can replace the currently documented arbitrary validation reason text.

This does not prohibit validated manual text in the outgoing notification payload or configured file channel; those are intended notification output. Test application log lines separately from notification files. No startup config/state error hardening from the other audit findings is implied.

### 6. Redirect policy

Choose the explicitly permitted simpler policy: reject every redirect for all three API feed reads, including same-origin redirects. Apply it to the real fetch and injected fetch path without dropping timeout signals, headers, body caps, or wire checks. Treat 3xx as an ordinary feed failure, not an empty successful response or an old-API 404. Never log a Location value or redirect target. Document the policy since API URLs behind a redirect must point directly to their final endpoint.

### 7. Malformed-warning cache bound

The issue supplies no numeric bound or eviction rule. Proposed default: retain at most 1,024 malformed-warning identities per process, using fixed-size keys (for example a feed prefix plus digest), evicting the oldest when adding a new key at capacity. The planner may choose another explicit small bound with justification. Bound both entry count and retained bytes; limiting count while retaining megabyte error strings does not fix SEC-4. A generic per-feed malformed category is also acceptable if the spec explicitly chooses that coarser dedupe behavior.

Keep the one-time missing-version warning separate so cache eviction does not cause unrelated warning churn. A retained malformed identity logs once; an evicted identity may log again. Counting must remain independent of warning suppression and eviction. Existing legacy-key warnings also share `#reported`; the implementation must not leave an unbounded attacker-controlled path there after separating concerns.

### 8. Healthcheck fallback and verification ownership

Read the runtime environment inside both image healthcheck commands; do not substitute the port only at image build time. Use 9100 when unset (and consistent empty-as-unset handling). This does not change the bare-service default of no ops listener. Preserve `/healthz`, timeouts, non-root execution, and network exposure. Custom health host support and an ephemeral container port are outside this port fix.

Run the actual healthcheck from each built image with the listener at 9200 and with the default 9100. Container tests need valid notify config and probe token plus a local fake API; otherwise a startup problem can obscure the port regression. Probe's source behavior does not need alteration. The planner should choose a repeatable test/CI location without weakening the stated Dockerfile-only product scope.

## Derived acceptance check

Use concrete expected counts/statuses below, independent of helpers that generate the implementation's keys or limits. Keep a regression for each changed behavior and show its relevant failure on the cited main before implementing it. A check already passing on main is compatibility coverage, not evidence of the fix.

1. **Liveness/readiness:** start notify and drive at least five consecutive failed polls using its real notifier and a local API peer. Assert literal `/healthz` status 200 and `/readyz` status 503 at the default threshold of 5, with the failed-poll metric at least 5 and continued polling. After one fully good poll readiness returns to 200. Preserve startup/shutdown behavior and GET/HEAD behavior. Update the old health test that expects feed-driven liveness failure.
2. **Docker ports, both targets:** build notify and probe images and run each with `PULSE_HEALTH_PORT=9200`, no listener on 9100, and otherwise valid inputs. Docker's actual configured healthcheck must exit 0 and the container must reach literal `healthy`. Repeat with the default 9100; inspect the runtime status rather than asserting only that the Dockerfile contains an environment expression.
3. **Quiet manual upgrade:** load hand-written version 1 and version 2 ledgers with a known channel and automatic-only state. Serve existing open/resolved manual incidents with updates. The first successful observation produces zero manual deliveries, writes the baseline durably, and repeated polls plus reload/restart still produce zero. A later new incident/update/resolution produces exactly one corresponding event. Repeat first with manual 404, with a failed read, and with an empty successful feed, to establish the initialization distinction. A persistence failure retries without sending a historical burst. Existing statuses, payloads, reminder state, and automatic delivery remain intact.
4. **Stable updates and key migration:** start from a ledger already containing handled manual positional keys and verify that migration does not replay its current snapshot. Subsequently use the insertion fixture above: exactly one delivery for X and zero for A/B. Compare the identity of unchanged updates across position changes, and test a contract-valid equal-time reorder with zero deliveries. Two different messages at the same timestamp must each be delivered once. Persist/reload and repeat unchanged input with zero new deliveries. Check legacy pending/failed entries retain their existing retry/CLI semantics, without redesigning delivery.
5. **Malformed-item isolation/count:** after initialization, place an item with id `{"toString":null,"valueOf":null}` before a valid new incident in `/incidents`; the valid item is delivered in that tick and no poll-wide exception occurs. Repeat on `/manual-incidents` with a valid later manual item and a simultaneous automatic event; cover malformed checks followed by a valid check name. Include a deeply nested JSON id within the body limit. Each rejected occurrence increments the chosen per-feed skipped counter by literal 1 even on a repeated poll whose warning is suppressed; valid items are not counted. Rejected items alone do not degrade readiness.
6. **No response content in logs:** serve a 200 non-JSON body with an unquoted unique marker token, JSON-like text containing that token, and an error-status body with it. Also put marker text in rejected ids/unknown keys/validation inputs. Capture every serialized application log line (including cause fields), assert the marker is absent, and assert a useful fixed failure category/feed remains. Cover all three feed paths. Notification output is checked separately.
7. **No redirect follow:** local origin A returns a redirect to local origin B, which counts requests. Reading any of the three feeds must produce literal zero requests to B and a failed feed result; valid other feeds still progress. Exercise same-origin redirects too for the proposed reject-all policy. Verify the fetch option explicitly forbids following an HTTPS-to-HTTP redirect; an actual local TLS fixture can additionally prove no downgrade connection occurs without globally disabling TLS validation.
8. **Bounded dedupe:** with the adopted literal bound (proposed 1,024), feed more than twice that number of distinct malformed identities, including large strings and unknown property names. Verify retained entry count never exceeds the bound and retained key lengths have a separate explicit cap. Use a production-consumed cache abstraction if introduced, not a private-state export solely for tests. Repeated retained identities suppress warnings; oldest eviction allows a warning again; skipped-item counts include all occurrences. Do not use a noisy RSS threshold as the sole bound check.
9. **Compatibility and docs:** existing independent-feed processing, automatic keys/reminders, routing, size/timeout/wire checks, and pending/failed workflows stay green. Update notify README and relevant operation/channels docs with separate health semantics, redirect policy, count/cache behavior, stable keys, and the upgrade snapshot tradeoff. Reconcile any touched health descriptions; meta README also currently describes the old behavior and is a documentation follow-up for the spec author, not a third product target.
10. **Completion evidence:** notify and probe checks and image CI pass. Run API `scripts/compose-e2e.sh` against the candidate notify/probe images via an isolated validation checkout and explicit local build overrides, or record the green API `compose-e2e` run after both changes merge. A run that built remote old `main` proves neither candidate. Record tested commit/image identifiers, commands, and results. The read-only context clones must not be modified or used as writable e2e workspaces.
