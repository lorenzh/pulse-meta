## Confirmed current behavior

Paths below are relative to `pulse-api` at the inspected SHA.

- `bench/compose.bench.yaml:27`, `:43`, `:62`, `:87` publish api, probe, status and notify on `127.0.0.1` with an omitted host port. Docker chooses the host ports. There is no explicit port allocator or bind retry in the inspected orchestration. The issue's ephemeral-range diagnosis comes from its run logs; this review did not measure the runner's range or independently reproduce that cause.
- `bench/stack.ts:99`, `:217`, `:315`, `:347` use the fixed project `pulse-bench-${side}` for builds, load, cold and end-of-day runs. Explicit container names in Compose derive from that project. Different checkouts on one Docker daemon still collide.
- Compose image tags use only the side, and `bench/stack.ts:105` inspects those fixed tags. Unique Compose names alone would leave concurrent builds able to overwrite each other's images or inspect the wrong image.
- `bench/run.ts:56` has one `.bench` workspace per checkout. Clone fetching uses `FETCH_HEAD`, and checkout/seed/run preparation deletes fixed paths (`:157`, `:166`, `:187`, `:237`). Two invocations from one checkout can corrupt each other's work even after Docker names are fixed. `--out` also defaults to one `bench-out` directory.
- The load stack starts api first, creates runtime configuration/tokens, then starts probe, status and notify (`bench/stack.ts:222`). A later-service bind failure can therefore leave an already running api and modified database. The cold and end-of-day paths use `composeTarget`, whose `start` and `restart` issue Docker commands (`bench/cold.ts:289`). Fixing only the first `up api` misses other binding points.
- Failures currently dump stack diagnostics and attempt teardown. `runChecked` throws a generic error containing only the last 500 stderr characters (`bench/measure.ts:74`). `bench/run.ts:339` maps uncaught errors to exit 2; report verdict failures return 1 (`:329`). Preserve that distinction and retain enough command output to recognize a real bind failure before diagnostic truncation.
- `package.json` runs bench self-tests as explicitly enumerated scripts, separately from `bun run check`. New self-tests must be wired into `bench:selftest`. CI also validates `docker compose -f bench/compose.bench.yaml config --quiet` (`.github/workflows/ci.yml`, `bench-selftest` job).

## Open points and assumptions for planning

1. **Port strategy and retry wording.** The first requirement allows either probing outside the host's ephemeral range or retrying once. The final requirement explicitly asks self-tests to cover port choice and retry. Assume a bounded bind retry is required; the retry option is sufficient without also requiring a non-ephemeral allocator. The plan must choose and document one concrete allocation strategy. If it also chooses explicit ports, read the actual host range rather than assuming the usual Linux default, skip occupied candidates, coordinate concurrent allocations, bound exhaustion and handle the gap between probe and Docker bind. Probing alone cannot reserve a released socket. Do not change host sysctls or require privileged ports.
2. **Meaning of fresh ports.** Retrying the same failed container or using a new project name with the same explicit ports is insufficient. Tear down the failed attempt and request fresh host bindings; do not reuse the known failed mapping. All four published services remain on loopback. Active runs must have distinct host ports, with Docker bind failure still handled if another process wins a race.
3. **Meaning of failed side.** Apply recovery on either A or B and in every Docker phase that can bind, including cold restarts. The plan must name the retry boundary and count precisely: one additional attempt for the affected side/phase, not an unbounded loop or a new allowance at every nested helper. Retry only a Docker port-in-use failure, not arbitrary Docker failures, readiness timeouts, request failures or metric verdicts. Keep the existing end-of-day midnight retry separate and unchanged.
4. **Measurement integrity.** Before repeating an affected measurement, remove its partial containers, restore its original seed/configuration and recreate runtime tokens as needed. Discard failed-attempt samples and begin successful-attempt startup timing afresh. Do not concatenate load windows or change seeds, warm-up, idle/load durations, settle/restart order, routes, cycle counts, metric definitions or median computation. Prefer wrappers around existing procedures; where a procedure adapter must change, constrain it to lifecycle wiring and prove parity.
5. **Concurrent ownership.** Use an invocation identity that is unique across processes/checkouts, not just side, PID or a timestamp of coarse resolution. Propagate ownership consistently through projects, explicit container names, image builds/inspection and cleanup. Give mutable workspaces their own invocation directories, or provide equally safe coordination. Never tear down another invocation's containers or remove its files. Parallelism should be real; a machine-wide lock that serializes whole benches does not demonstrate concurrent operation.
6. **Output directories.** Two invocations may use explicit, distinct `--out` paths for the concurrent proof, including distinct summary destinations if configured. Document that shared output paths are not safe; changing default output layout or report schema is unnecessary. Keep the existing report filenames and contents' shape.
7. **Concurrent completion versus budgets.** The proof is that both complete their measurement rounds and produce their reports without a terminal bind error. Shared-machine metric noise may yield the existing exit 1; disclose such verdicts and exit codes, and do not alter budgets to get exit 0. Exit 2 or an incomplete measurement is not a completed proof. Controlled self-tests separately force a bind failure to prove recovery, since two lucky real runs do not prove retry behavior.
8. **Test CPU.** Interpret five interleaved runs as five samples per version: base, branch repeated five times (ten executions). Report user plus system CPU for `bun run test`, raw samples, both medians, and branch-minus-base absolute and percentage deltas. Keep this separate from the concurrent Docker proof and avoid running the CPU series simultaneously with those benches. No product CPU/RSS/build change is expected from harness-only work; allocation and cleanup cost is outside measured service work.

These are implementation choices and conservative interpretations, not reasons for a `needs-input` hold. The plan must resolve them explicitly so build and review use the same interpretation.
