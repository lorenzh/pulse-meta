## Open points for the plan

### 1. Window identity and file compatibility

The requirement for same-id file precedence cannot be exercised with today's file format: file windows have no ids. Specify how identified file windows are represented while every existing id-less single-check window keeps loading and behaving as today. An additive optional file `id` is one possible approach; a mandatory conversion of existing files is not. Do not identify a window by `checkId` alone: several windows per check are already valid.

Specify uniqueness, id syntax/bounds, legacy row identity in admin reads, stable addressing and the meaning of numeric ids versus old numeric indices. Choose whether a named file window remains single-check or gains an optional multi-check form. If any new file syntax is introduced, make its validation, snapshot and export behavior explicit without tightening legacy note or timestamp rules accidentally.

Keep ownership and time overlap separate: matching window ids shadow, while different ids may overlap on the same check. A same-id override suppresses the whole database window, including its other check ids; it must not leave a partially effective database copy. Preserve the hidden definition for later unshadowing. As with #565, recommend rejecting creation against an applied file id, refusing file-only mutations and shadowed replacements, and permitting deletion of the shadowed database copy only.

### 2. Admin operations, listing and validation

Define exact routes, request/view schemas, Location, status order, id/path matching, and whether edits are full replacement or partial. Do not silently reinterpret an old index-based request as an unrelated database id. List effective and shadowed definitions with source information sufficient for #569 to render file rows read-only and address database rows reliably. A list must expose planned, current and past windows without changing the public route's current/upcoming-only policy. `GET /admin/config` may supply this if its contract and size behavior are specified; a new listing route is a plan choice.

Specify 1..50 distinct effective check ids, unknown/inactive id rejection, id immutability, timestamp units and valid date range, `end > start`, and note length 1..500. Choose whitespace/control-character rules for new notes without changing legacy file acceptance. No separate persisted lifecycle state is needed: planned means `now < start`, current means `start <= now < end`, past means `end <= now`. Define whether past-window create/edit/delete is permitted; the issue imposes no future-only restriction.

### 3. Components and reference lifecycle

Record a definite include/omit decision and its evidence. If included, define independent component definitions, file precedence, source/shadowed views, CRUD and revision/audit behavior. Retain existing component fields, validation, state/uptime/SLO behavior and public shapes. Database components should be able to reference effective checks of either source. Keep the existing rule that a hand-written file is validated against its own checks unless a change is explicitly justified.

The window stores check ids, not component ids. Component selection should resolve to a deduplicated check-id list at save time, enforce the 50-check cap after expansion, and not silently retarget a saved window when component membership changes.

Specify what happens to database components/windows when a referenced file check is removed, when a database check is deleted, and when an override disappears. A database reference must not make an otherwise valid file reload fail indefinitely. Options include retaining definitions with missing members inactive, or projecting only live members with explicit admin diagnostics; choose a rule and test recovery when an id returns. Avoid silently rewriting stored definitions. Define whether any window reference, including a past or shadowed one, blocks check deletion. Preserve the existing refusal to delete a component named by an unresolved published manual incident, and account for shadowed component deletion and draft publication revalidation.

### 4. Durable state, revisions and failures

Add a numbered migration; do not treat old file snapshots or runtime rows as console-owned definitions. Persist new definitions, ordering and any required file identity metadata, including compatibility with snapshots written before this feature. On restart, rebuild the same effective set and shadowed views. Maintain #565's snapshot fallback when a running or restarting API sees a broken file; no-snapshot startup behavior need not change.

Use a shared configuration revision across checks, windows, components and applied file changes. Every successful mutation must invalidate stale revisions held for another entity kind. Preserve missing If-Match = 428, malformed/wildcard = 400, well-formed stale revision = 412. The issue's phrase "without the right revision answers 412" means stale revisions, not removal of these existing distinctions.

Commit definition, generation and audit atomically, publish runtime/cache changes only after commit, and return the new quoted ETag. Failed writes must leave all of them unchanged. A bad, unreadable, read-only or not-yet-applied disk file must not prevent a database write with a fresh revision or be overwritten by it. Keep file status and last-applied time distinct from database writes. Specify handling of outstanding legacy `audit_pending` records even if new admin file writes disappear.

### 5. Runtime projection and existing semantics

Project each effective multi-check database window into the existing single-check runtime/public shape. Preserve half-open boundaries, sorted order and earliest-start overlap selection, including a deterministic tie rule that keeps legacy file behavior. Ensure create, edit, delete, shadow and unshadow update the holder, status, heartbeat suppression, service cache and component consumers together. In particular, prime a cached response, then edit only the current window note or end with the same start and prove the new value is immediately visible.

"Silences" means today's API maintenance behavior. It does not mean stopping probes, closing pre-existing incidents, suppressing all notify reminders, hiding manual incidents, or changing uptime calculations. Retain past definitions for admin listing and timestamp-based handling of late results; do not automatically purge windows at their end. Decide explicitly how edits/deletes of past definitions affect later-arriving results; no historical replay or recomputation is requested.

### 6. Contract version and consumer rollout

A contract change is needed for identified multi-check database definitions and source/shadowing information; the existing types cannot express them. The issue requests a minor package bump. Prefer additive schemas/types/routes that preserve existing exported shapes and the unchanged public/probe wire version. A replacement of strict `AdminMaintenanceInput/View` or `AdminConfigResponse` is not automatically an additive change simply because public reads are unchanged.

Choose a compatible surface or explicitly account for every affected consumer and the requested minor-version constraint. Verify old console Checks reads/export with a non-empty new database window and component, not only an empty fixture. If a pin/schema integration change in console is necessary, give it a narrow consumer-compatibility section; leave Maintenance screens to #569. Update contract schemas, validators, exports, type fixtures, committed `dist/`, package version and documentation together. api waits for the merged contract commit and pins its full SHA.

### 7. Export and documentation

Decide how the effective-set export includes database components and multi-check windows while remaining a checks.json document. Flattening windows preserves the public single-check format but may lose identity needed for file shadowing; an id-preserving extension must specify grouping and duplicate-id validation. Test the chosen round trip and state any deliberate loss of identity. Exclude shadowed definitions and preserve existing check-secret redaction. Keep console's per-check export functional.

Update api README, configuration, operation, REST and concepts documentation for ownership, listing, references, export, revision and reload behavior. Keep the already-consistent reload statements aligned with tests; do not reintroduce restart-only semantics or claim the contradiction still exists on inspected main. If components are included, remove the now-obsolete requirement for a writable checks-file mount from relevant docs/tests. No new runtime dependency is authorized.

## Assumptions used to derive acceptance

1. #765 provides the backend prerequisite; #569 provides the screens. Existing database checks, token scopes, audit action names and public wire shapes are the baseline.
2. File ownership and precedence are per entity id. Existing id-less file windows remain supported. New database windows have independent ids and an explicit check-id list.
3. Database windows can target both file and database checks. Components selected in the future UI resolve to concrete checks, not dynamically expanding stored targets.
4. File reload remains authoritative for file content; database definitions survive it, including when shadowed or temporarily referencing a missing check, according to the plan's explicit reference policy.
5. Public maintenance remains single-check, current/upcoming-only and sorted. Past listing and ownership details are private admin concerns. Existing maintenance semantics apply equally to each projected database target.
