- `e2e/redact.sh` replaces nonempty literal needle strings. Its collector takes explicit token arguments, owner `password` and `setup_key`, and secret-file lines. An unreadable needle file suppresses input and prints a fixed marker. It has no general credential-field suppression.
- `e2e/compose-e2e.sh:80` builds those needles only inside failure cleanup. It adds the admin token, database service token and runtime status/notify token files, prints container logs through `redact`, then removes temporary state. Preserve the teardown and original failure status.
- `e2e/console-lib.sh` owns HTTP response/cookie files, CSRF selection, form-token selection and TOTP generation for console scenarios. Calls commonly run in command substitutions. An array or variable updated only inside that subshell cannot communicate accumulated needles back to the parent.
- Response files and jars are overwritten, jars are switched or deleted, and generated TOTP values change across requests. Retaining only the final response or last code is insufficient for logs accumulated during the run.
- `console_owner_signed_in` proceeds past the recovery-code response without retaining the codes. `e2e/console-setup.sh` has a separate recovery-code collection and multiple browser jars, then deletes its work directory on exit. Parent cleanup cannot rely on those files surviving.
- `e2e/runtime-settings.sh` also builds request form arguments with its own `form_args`, in addition to the shared console helpers. Cover this path when choosing collection hooks.
- Parent failure paths can print captured scenario output before the final container-log dump. The probe, incident and runtime steps have different output-scanning arrangements. Protect failure diagnostic streams before printing, while preserving success output and all existing scenario assertions.
- CI's `dev` job runs standalone `console-setup.sh` and subsequently prints raw container logs on failure (`.github/workflows/ci.yml:240`). Masking only `compose-e2e.sh` would leave a diagnostic bypass for a scenario that creates the requested credentials.
- The checked-in redaction test covers owner password, owner TOTP setup key, admin token, service token and a secret-file value. These are five existing cases, distinct from the five new categories requested here. ## Scope and assumptions for planning

1. **Target:** deploy only. Changes belong in its e2e diagnostic/collection paths, focused tests, required docs, and narrowly necessary CI diagnostic wiring. No service logger, authentication behavior, dependency, image pin or Compose service change is needed. Other target clones remain read-only.
2. **Five categories:** session cookie value; CSRF token; form token; generated TOTP code; recovery codes. A TOTP setup key is already covered and is not the current TOTP code. Include every cookie/browser and every issued value encountered during the scenario, not just the last or currently usable value: expired, rotated and consumed values can still occur in earlier diagnostics. Retain all recovery codes the scenario obtains, not only the one exercised by sign-in.
3. **Collection lifetime:** use private run-owned state that survives child processes, command substitutions, response overwrites and local scenario cleanup until the final diagnostic consumer finishes. Initialize it before credential-producing steps and record values before the next request can discard them. Never discover credentials from failure logs as the collection strategy. Prefer existing Bash/awk/sed/Node facilities; add no dependency.
4. **Uncollected values:** define a conservative suppression fallback for credential-bearing fields/records, including one-time console output that was not retained. Omitting the whole affected line is acceptable. Keep ordinary diagnostic lines visible. Known values must also be masked when embedded in otherwise unlabelled text; a field-name filter alone does not meet the collection requirement.
5. **Failure boundary:** trace all diagnostic emissions for these console e2e flows, including parent replay of failed child output and CI's standalone console-setup failure dump. Either pass those emissions through the same redactor or suppress their credential-bearing records. The planner must choose a lifecycle that also handles early failures before the registry exists. Unrelated CLI stack tests and other setup jobs are not a request for a repository-wide logging rewrite.
6. **Success compatibility:** keep scenario requests, selected form tokens, replay checks, assertion order and expected success/skip lines unchanged. Internal recording must be silent and must not corrupt HTTP-status command-substitution output. Do not redact the raw log input used by existing secret-detection assertions: those assertions must still detect leaks rather than inspect already-masked logs.
7. **Private temporary state:** credentials and needle files remain run-local, mode 0600 within private directories where applicable, and are deleted after their last diagnostic consumer on success and failure. An unavailable or failed collector must not cause raw diagnostics to be printed. Preserve the existing unreadable-needle fail-closed behavior.
8. **Disclosure:** public issue-review, plan, task evidence and PR text describe category, location, impact and fix direction. Only tests contain synthetic credential sentinels. Include no real credential, copied sensitive log line, or instructions for extracting credentials from logs. Stub evidence demonstrates a masking limitation, not that a service emits those values.
