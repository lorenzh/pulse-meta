## Open points and carried-forward decisions

These are nonblocking and must be explicit in the regenerated plan and tasks.

1. **Timer anchor.** Preserve the earlier D1: each heartbeat tick arms the next 60000 ms timer before requesting its report. Report completion never arms the heartbeat. The initial poll still supplies the startup report.
2. **Poll collisions and non-overlap.** Preserve D2's wait/coalesce choice, which is permitted by the issue. Heartbeat and poll reports share one in-flight request. All requests made while it runs share at most one follow-up; do not queue one report per missed tick. Build a follow-up body when it actually starts, using current state and `at`, rather than preserving a stale body from a missed tick.
3. **Meaning of the 60-second bound.** Measure request starts, not response completions or successful acknowledgements. For ordinary requests completing within the existing 5000 ms timeout, report starts stay at most 60000 ms apart. A report deliberately held beyond 60000 virtual ms cannot satisfy both that bound and non-overlap; preserve non-overlap, send one follow-up when it ends, and retain the heartbeat cadence. This is the earlier decision, not a blocking contradiction. Event-loop delays are outside an exact real-time guarantee.
4. **Shutdown and failure.** Preserve D3/D4: cancel the newest heartbeat and pending poll timers, discard a follow-up that has not started, await running work before releasing the ledger/lock, and schedule/start no new work after stop. A failed report releases the slot so later heartbeats still run. Preserve existing failure logging and tokenless behavior.
5. **Two missed ticks.** Preserve the accepted review correction: holding the 60000 report until 125000 crosses only one missed tick and cannot distinguish coalescing from a catch-up queue. Hold it until 185000 so both 120000 and 180000 ticks encounter it in flight.
6. **Runtime cost.** Preserve the revised performance measurement, not the earlier claim that only test CPU changes. Relative heartbeat request rate rises by `L / 60000` when latency is L: about 6.7% at 4000 ms (56.25 to 60 heartbeat requests/hour) and 8.3% at 5000 ms. These are heartbeat-only estimates; poll reports and collisions affect total counts. Measure CPU rather than treating the earlier comment's roughly 5 ms/hour estimate as established evidence.
7. **Documentation and exclusive scope.** The manager requires four files in the plan's and task's `Files:`: `src/index.ts`, new `test/report-heartbeat.test.ts`, `docs/channels.md`, and `README.md`. Both documentation files must explain that heartbeat starts stay at most 60 seconds apart under the bounded request behavior and that a longer poll interval no longer stretches the heartbeat. Explain serialization without promising overlapping requests or an impossible bound for an indefinitely held report.
8. **Scope checks must survive commits.** Record the actual notify implementation base SHA before edits. All protected-file and complete changed-file checks compare against that base. An empty working tree or `git diff --exit-code` without a base proves nothing about a committed forbidden edit. The inspected SHA above is context; refresh the implementation base if notify main advances before build.
