## Findings, open points and adopted assumptions

1. **The finding reproduces.** `src/config-fs.ts:25–76` implements `fillTemp`, `writeTemp` and `fsyncDir`; `nodeConfigFs` exposes those operations. `src/config-write.ts:44–61` defines the local `WriteFs` surface and its prepare/replace/store path calls it. Searching these two files for `writeFileAtomic` finds nothing. A production-source search locates the copied write loop and permission handling only in `config-fs.ts`; `backup.ts` has a separate backup-publication rename, which is out of scope.

2. **“Configuration files” means the existing checks-file write path.** Today `FileKind` is only `component`. Admin check and maintenance writes go to SQLite, imported token files are read rather than rewritten, and exports are HTTP responses. Preserve that division. There is one API implementation target; kit and the other services need no child task or pin change. #555 supplies the helper already merged; do not redo its timer, logger, shutdown or other-service work. There is no unmet upstream dependency.

3. **The #555 mechanical replacement is stale.** It described a simpler store routine. Current `config-write.ts:388–561` has a durable pending-audit protocol: write/fsync/close temp; sync its directory entry; insert the pending row durably; check revision again; rename; sync the directory; promote the row; adopt. Recovery uses the absolute temp path as evidence. A present temp means abort, a missing temp means rename. The resolver must sync directories after its observations before promoting candidates. Keep all of this, including lock sharing, absolute paths and the crash model.

4. **Default kit cleanup would break that protocol.** The pinned helper unlinks on a throwing `beforeRename` or failed rename. API must delete a pending row durably before removing its temp; if deletion fails, the temp must remain. A rename can also move the file and then throw: API must observe the temp and keep the pending row when the outcome is uncertain, rather than delete evidence or lose the audit entry. Existing audit tests explicitly cover both cases. A direct call with the unmodified node adapter is therefore insufficient.

   The plan must specify a small per-write `AtomicWriteSyncFs` adapter and `beforeRename` integration, using kit for the actual write loop, metadata application, file fsync, rename and post-rename directory fsync. The callback can sync the temp's directory, create the pending row and run the second revision check. Cleanup and rename wrappers can enforce API audit ordering and track uncertainty. They must also handle an insert that commits and then throws, and preserve the original mapped error. Do not copy kit's write algorithm into the adapter. Retain fault-injection cut points at equivalent completed steps; a simulated power loss must remain a crash, not be converted into an ordinary caught failure that cleans up durable evidence.

5. **Directory syncing has two responsibilities.** Remove the copied atomic writer and its old `nodeConfigFs.writeTemp`/`fsyncDir` surface. The helper owns its normal post-rename sync. API still needs the extra pre-insert sync and recovery syncs because they order filesystem evidence against SQLite. Small audit-specific open/fsync/close plumbing through the injected kit fs is necessary; the request is interpreted as eliminating the duplicate atomic-write implementation, not deleting these required durability barriers. Specify that distinction explicitly in the plan. Do not remove the first directory sync or change the resolver merely to make a text search empty.

6. **Preserve initial temp permissions too.** Local code opens a temp with `wx`, mode `0600`, then applies existing destination mode after filling it. Kit normally opens with the destination mode. The injected API adapter can keep `wx` creation at `0600` while kit still applies the final mode and owner. Test creation mode as well as final mode, preserve existing mode bits and owner-copy behavior (only EPERM tolerated), and do not unlink another writer's colliding temp. Keep `<path>.<suffix>.tmp`, suffix injection, same-directory placement, full writes, close behavior and recovery paths. Do not introduce an async gap into this synchronous protocol.

7. **Errors and application timing are invariants.** Keep the `ConfigWriteError` mapping, statuses and sanitized messages; `AtomicWriteError.code` supplies the original Node error code. A stale `ConfigWriteError` must pass through unchanged. An unsuccessful pre-rename write leaves old bytes. A failed post-rename sync leaves the new disk bytes, old applied state/revision and a recoverable pending row; do not adopt early. Promotion/apply failures, warning codes and next-write/start resolution retain their current semantics.

8. **Tests need migration, not deletion.** The four existing suites below cover real permissions, HTTP error mapping, stale writes, audit ordering and power-loss subsets. Replace old high-level fake operations with injected low-level kit fs operations, preserving assertions and fault cases. Existing `config-reload.initial.test.ts` only uses the shared adapter through spread/default operations; `server.maintenance-admin.test.ts` overrides `assertWritable` without the obsolete writer fields. `start.ts` consumes `ReloadFs & WriteFs` by type and default injection. They need no edits under this scope. New coverage must prove delegation and prevent reintroduction of the local implementation, rather than merely import an unused helper.
