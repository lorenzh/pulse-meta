# Issue review: #81 Shared tooling configuration in pulse-config

Verdict: specifiable. No blocking question; the TypeScript 6 isolation check is a planned first step with its own stop condition (see constraints in the issue).

## Findings from the clones (current state)
- `.repos/config` (pulse-config) already holds a scaffold: `biome.json` (four-repo version, `noNonNullAssertion: error`, test override), `tsconfig.json` (`include: ["src"]`), `lefthook.yml`, `.github/workflows/ci.yml`, `tools/sonarjs` (workspace, TS 6.0.3, eslint 10.13.0, sonarjs 4.2.2, parser 8.72.1), `.npmrc` (`install-strategy=nested`), a `.repos/**` ignore in its ESLint config. `config` is already in `.factory/config.yaml` and in every target's context.
- Targets differ from that scaffold:
  - `biome.json`: only status differs (`noNonNullAssertion: "off"`, no test override). Others identical.
  - `tsconfig.json`: api, contract, notify, probe have `include: ["src", "test"]`; the scaffold has `["src"]`. Status matches the scaffold. contract also has `tsconfig.build.json`.
  - `lefthook.yml`: ESLint command differs per target (`npx --no-install eslint ...` vs `node tools/sonarjs/node_modules/...`; flags `--no-warn-ignored`, `--no-error-on-unmatched-pattern`, or none). notify is identical to the scaffold.
  - `tools/sonarjs`: eslint config is written in three equivalent-looking forms (plugins object, spread of `recommended`, flat `recommended` plus `rules` merge); package names differ (`pulse-sonarjs-tools`, `@lorenzh/pulse-sonarjs-tools`, `@lorenzh/sonarjs-tooling`). Only some ignore `.repos/**`. Shared version must keep the same effective rules (recommended + `cognitive-complexity` 15 + `reportUnusedDisableDirectives: error`).
  - CI: identical except contract, which adds `Build` and `Check dist is up to date` steps. contract's `check` also runs `npm run build`; its `test` script has an extra coverage exclusion `test/**`.
  - `package.json` scripts differ (lint uses `eslint ...` in contract/api vs `node tools/sonarjs/node_modules/...`; contract and others carry `overrides` for `ts-api-utils` -> typescript 6.0.3).
- Existing pin style: `"@lorenzh/pulse-contract": "github:lorenzh/pulse-contract#<sha>"` in `dependencies`/`devDependencies`.

## Open points (for the plan, none blocking)
1. **TS 6 isolation via a Git dependency (first step, stop with `needs-input` if it fails).** npm does not install the devDependencies or workspaces of a Git dependency. The ESLint toolchain (eslint, parser, sonarjs, TS 6) therefore cannot simply come from the pulse-config package: the plan must test options such as (a) pulse-config declaring the toolchain as `dependencies` of a nested package under `tools/sonarjs` that a target installs, (b) the target keeping a thin `tools/sonarjs/package.json` that depends on `github:lorenzh/pulse-config#<sha>` (nested package, `install-strategy=nested`), (c) a `prepare`/install script in the dependency. It must show: root `typescript` stays 7 (`npx tsc -v`), the linter resolves TS 6 only, `npm ci` works from the lockfile, and the pulse-config repo itself still works. A target should keep as little as possible locally (ideally one dependency line and one-line ESLint entry).
2. **Resolution of `extends` paths into `node_modules`.** Verify each tool: Biome `extends: ["@lorenzh/pulse-config/biome.json"]` (and how `files.includes`, `vcs.useIgnoreFile` and the override globs are resolved relative to the extending project), tsconfig `extends` (`include` is relative to the file that defines it, so `include` must stay in the target), Lefthook `extends` (local path in `node_modules`; `{staged_files}` commands and `glob`). The `$schema` URL of the base is version-pinned to Biome 2.6.3, which the targets also pin.
3. **ESLint config as a shared file.** ESLint flat config is a plain JS file, not "extends"; decide how a target uses it (re-export `export { default } from "@lorenzh/pulse-config/...";` or `--config` pointing into `node_modules`). Ignore patterns like `**/dist/**` are matched relative to the config location with `--config`; verify they still apply in the target. The shared file must not contain `.repos/**` (issue comment); Factory-runner clones live under `.repos/` inside `.target`, so decide whether the target's linter run is affected (e.g. `.gitignore` already covering it; Biome uses the VCS ignore file) and where a target-local ignore, if needed, goes. Note this is a behavior risk: lint in the runner could pick up `.repos/`.
4. **Variation to normalise vs. keep per target.** `tsconfig` `include` (src vs src+test; the shared base should not set `include`, or targets override it), contract's `tsconfig.build.json`, contract's extra CI build/dist steps, contract's extra coverage exclusion. Spec must say per target what stays local. Lefthook ESLint flags: choose one shared form that works for all (staged files may be empty or ignored); must not change which files are checked.
5. **Reusable workflow.** `uses: lorenzh/pulse-config/.github/workflows/<name>.yml@<ref>`. A workflow `uses:` needs a ref (SHA or `main`); it cannot take the `package.json` pin. State whether it is pinned to the same SHA (two places updated together) and whether the workflow takes inputs (e.g. extra steps for contract's build and dist check) or contract keeps an extra job. The pulse-config repo must be public (or allow access) for cross-repo reuse; the repo's own `ci.yml` must also be kept (it dogfoods the local files and needs `workflow_call` split from it or a separate reusable file). Also check that `npm ci` of a Git dependency in CI needs no token (public repo, `.npmrc`).
6. **Pin update flow.** Pulse-config changes reach targets only via a pin update in each target (package.json + lockfile + workflow ref). Document it; Dependabot/automation is out of scope unless stated. Pin to a full SHA on `main`, as for the contract. Changing the contract pin and config pin independently must not conflict.
7. **Dependency order / fan-out.** pulse-config must be built first (`config` target with no `dependsOn`); the five targets `dependsOn: ["config"]`. A target PR cannot pass CI before the pulse-config PR is merged to `main` (the pin needs a SHA on `main`). The plan only sees `main` of pulse-config at its start; since the config scaffold exists but the shared files are partly different from the target copies, the config child must fix content (see 8) and the targets must pin the merged SHA (state how the child learns it: the unblock flow).
8. **pulse-config content and own repo.** Scaffold state is not final: needs the reusable workflow, the final SONARJS file, TS 6 toolchain packaging, the `README`/`AGENTS.md` shared text. The repo should check itself with its own files (it is the source; it is not a consumer). The scaffold `package.json` is `private: true` and name `@lorenzh/pulse-config`; a Git dependency on a private-flagged package is fine, but `files`/`exports` need to expose the config files.
9. **Status drift (given in comments).** Shared Biome = four-repo version. pulse-status must remove non-null `!` in `src/` code (reported once the rule is on) and drop its local biome rules; status has no `test` override locally so tests following the shared override apply.
10. **Docs.** Each README and the shared `AGENTS.md` paragraph (text common to all targets) says where the config lives and how a change reaches targets. Also `AGENTS.md` rule "never weaken biome.json, tsconfig.json or CI" should now refer to the shared config. Also update this repo's `README.md` listing if it names repositories (pulse-config already in context).
11. **Lockfile and `overrides`.** The `ts-api-utils -> typescript 6.0.3` override in some targets may become unnecessary or may still be required; the plan decides after step 1. Root TS 7 must stay.

## Assumptions
- `lorenzh/pulse-config` exists, is public, the bot has write access, and the Factory target `config` is configured (scaffold seen in `.repos/config`).
- "Same checks as before" means the effective Biome rules, SonarJS rules (recommended, cognitive complexity 15), coverage gate (80 lines, same exclusions), hook and CI steps; file layout and package names of the tooling may change.
- Biome version stays 2.6.3, lefthook 2.2.2 in all repos; Node 24.
- Each target still runs `npm run check` with the same script names.
- No `.factory/` in target repos; no npm publishing.

## Acceptance check (derived)
1. In each of contract, probe, api, status, notify: `biome.json`, `tsconfig.json` (base options), `lefthook.yml` and the CI workflow contain only `extends`/`uses:` plus what is specific to that target; no copy of the SonarJS rules or ESLint tooling versions; the files exist in full only in pulse-config.
2. Every target has a Git dependency on `pulse-config` pinned to a full SHA on its `main`; `npx tsc -v` at each root is 7.x; the linter runs on TS 6 only.
3. `npm ci && npm run check` passes in every target and in pulse-config; CI of each target passes via the reusable workflow.
4. Equivalence: before/after, `biome check` and ESLint report the same rule set (e.g. a cognitive complexity of 16 fails, 15 passes; an `any` fails; a `!` in `src/` fails, in `*.test.ts` passes), including pulse-status (no `!` left in `src/`).
5. Shared ESLint config does not mention `.repos/`.
6. Mutation check: change a rule in pulse-config (e.g. cognitive complexity limit), merge it, update the pin in one target, and `npm run lint` there changes its result; without the pin update it does not.
7. READMEs and the shared AGENTS.md text state where the shared config lives and how a change reaches targets.
