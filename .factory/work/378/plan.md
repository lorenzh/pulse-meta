# Spec #378: status page accessibility

Checked against `.repos/status` main (48b7cb9). Open points 1-12 of `issue-review.md` are decided below.

## Goal
The status page works with a keyboard and a screen reader while it polls: focus stays put, an uptime group is one tab stop, changes are announced once, every group is named, the page shows content without JavaScript, and every time names its zone.

## Scope
Only pulse-status (`public/`, `src/render.ts`, `src/sections.ts`, `src/components-view.ts`, `src/server.ts`, tests, CI, docs). Also a separate by-hand PR in pulse-meta (see "Meta follow-up").

## Non-goals
No visual redesign, no new page content, no api/proxy allow-list change, no website, feed or badge change, no new runtime dependency, no change to manual-incident writing.

## Decisions

### D1 In-place update (keyed patch)
- Renderers keep returning HTML strings, and `buildSections`/`showSections` keep their signatures (existing tests stay valid). `showSections` gets a new second-argument contract only in the browser: `client.js` passes a `show(id, html)` that calls a new browser module `src/patch.ts` (served like the other modules via `tsModules`): `patchHtml(container, html)`.
- `patchHtml`: if `container.innerHTML` equals the last html written for that container (kept in a `WeakMap`), do nothing. Otherwise parse `html` with a `<template>` and reconcile children recursively: match nodes by `data-key` when present, else by position and tag. Same tag + key: keep the node, sync attributes (set changed, remove missing) and recurse; text nodes: update `data` only if different; unmatched old nodes removed, new ones inserted. The active element is never replaced when its key matches. Reordered keyed children are moved with `insertBefore` (moving an element that holds focus is avoided: the focused node is not moved if its relative order is already right; otherwise moved and focus restored with `focus({preventScroll:true})`).
- Stable keys added by the renderers as `data-key`: `check:<id>`, `component:<id>`, `group:<heading>` (component group), `incident:<id>`, `maintenance:<checkId>:<start>`, `manual:<id>`, `manual-update:<id>:<at>`, `day:<date>` for bars. Incidents and checks have ids today; maintenance has none, so it uses `checkId:start`; manual updates use `at`. Fixed sections (`banner`, `summary`, `updated`) are handled by D3.
- Relative times (`<time>`) change text only (every 30 s tick and polls) and keep their node.
- No dependency. `patch.ts` is split in two: pure helpers with no DOM (`sameKeyOrder(oldKeys, newKeys)`, `diffAttributes(oldAttrs, newAttrs, keep)`, `planChildren(oldNodes, newNodes)` returning keep/insert/remove/move steps over plain `{key, tag}` descriptors) and a thin DOM layer that applies those plans. Decision on tests: `bun test` has no DOM, and no DOM library may be added, so `patch.test.ts` uses a small hand-written fake DOM (`src/patch.fake-dom.ts`, test-only, about 80 lines: element with tag, attributes, children, `data`, `insertBefore`, `removeChild`, `setAttribute`, `removeAttribute`, a call counter and an `activeElement` field; a `template` stand-in that builds the new tree from a prebuilt descriptor). Real-browser behavior (node identity with the real parser, focus, selection, scroll) is covered only in the Chromium run (D7). The unit tests assert: unchanged html makes zero fake-DOM calls (old code: `innerHTML` assigned every time, counter > 0); a same-key node keeps its object identity with changed text (old code replaced the container's children, identity lost); removed, added and reordered keyed children give the expected child order; the node that is `activeElement` is never replaced or removed while its key exists; `diffAttributes` with `keep: ["tabindex"]` leaves `tabindex` alone. Each fails on the old code because the old `show()` has no patch function: the tests run against the same `show`-level entry (`showSections` with the real `patchHtml` versus an `innerHTML` stub) and fail by identity and counter assertions.

### D2 Tab stops and uptime bars
- `renderUptime(entry, name)` (new required name argument; callers pass the check or component name) renders:
  `<div class="bars" role="group" aria-label="Checkout API, 90-day uptime 99.9 %" data-key="bars">` with days as `<span class="bar ..." role="img" data-key="day:2026-10-30" tabindex="-1" aria-label="2026-10-30 UTC: 99.9 %" title="...">`. Exactly one day has `tabindex="0"` (default: the last day). `role="img"` with `aria-label` passes axe and names the day; the text is not only a `title`. Incidents on a day, when the data has them, are appended to the label (`, 1 incident`); the day data has no incident list today, so only add when `days[].results` or equivalent already gives it, else leave it out (as today).
- Roving keys in a new browser module `src/bars.ts` (event delegation on `document`, bound once): ArrowLeft/ArrowRight (not wrapping), Home/End; moves `tabindex=0` and focus. On `focusin` of a bar it records that bar as the group's roving stop. Because the patch keeps nodes, `tabindex` of existing `.bar` elements is not taken from the new html (`diffAttributes` `keep`); the roving state lives in the DOM. The patch then repairs the stop after each reconcile of a `.bars` group (`bars.ts` exports `ensureRovingStop(group)`, called by `patchHtml` for each touched group): if the group has exactly one `tabindex="0"` bar, nothing; if zero (the day it sat on left the 90-day window) or two or more (a new day was added with the server default `0`), keep the one that is the active element, else the last existing one that held `0`, else the last bar; set all others to `-1`. New bars are inserted with `tabindex="-1"` by the patch (the server default `0` only counts on first insert of a whole group). A sliding window therefore moves the stop to the day that now holds the same date when it exists, else to the last day. When focus is on a bar that is removed, focus moves to the nearest remaining bar (the last one) with `preventScroll`.
- Relative times: remove `tabindex` from `<time>`. `<time>` renders `datetime`, visible text = the relative text (`3 min ago`, as today), `aria-label` = the exact time with zone (`Oct 30, 2026, 12:00:00 PM UTC`, screen readers read the exact time), `title` = the same exact text (hover). No new element, button, state or page content. How a sighted keyboard user reaches the exact time: for a check or component the times inside its entry (last ping, since, windows) show the exact time in the existing tooltip style (`::after { content: attr(data-exact) }`, as `.bar` tooltips do today) while keyboard focus is inside that entry (`li.check:focus-within time[data-exact]`, `li.component:focus-within time[data-exact]`), because the uptime group is the entry's one tab stop. Times outside such entries (the "Last updated" line, incident, maintenance and resolved rows) have no focusable element, so a keyboard-only sighted user cannot reveal them; that gap is accepted and written in `docs/operation.md` (pointer hover and screen readers have them). This is a CSS-only change with no new tab stop.
- Tab budget: per check or component the focusable elements are the bars group (1 stop). Manual incident entries and incident rows have no links today, so the real budget is 1 per check/component and 0 elsewhere (limit stays 3 as in the issue). Global stops: theme radios (1 group stop), the feed link if present. The Chromium test tabs from the top to the end of the page and counts stops inside each `li.check, li.component`: at most 3 and exactly 1 on default data.

### D3 Live regions
- `index.html` holds `<div id="live" role="status" aria-live="polite" aria-atomic="true" class="visually-hidden"></div>` and `<div id="alert" role="alert" class="visually-hidden"></div>`, outside every patched container, never re-created. `renderSummary`/`renderBanner` lose their `role` attributes (the visible `#summary` and `#banner` text stay for sighted users and are patched in place without a role; `aria-live` is off on them).
- `client.js` (new `src/announce.ts` browser module, pure and unit-tested): `announceSummary(prev, next)` returns the text to set in `#live` only when the full summary text (the visible text of `#summary` as `renderSummary` produces it, including any "· N incidents open" part) differs from the previous full text, else `undefined`. A state change of one check therefore reaches the polite region only if it changes that overall text (for example "All systems operational" to "Partial outage", or the open-incident count); a change that leaves the text equal writes nothing; `announceError(prev, next)` returns the alert text only when error kind goes `null → kind` or `kind → other kind`, and `""` when it goes back to `null`. Kinds are the existing `PollerErrorKind`: `unreachable`, `invalid`, `version`. Text uses the existing `bannerText`. The first draw after load sets `#live` only if the server did not already render the same text (the server renders `#live` and `#alert` empty, so the first client draw does not announce an unchanged initial state: the client seeds `prev` from the server-rendered summary text, read from `#summary`).
- Ordinary polls (same text, same kind) write nothing, so no DOM mutation and no announcement.

### D4 Names
`renderUptime` takes the name; `renderCheck`, `renderComponent` pass `check.name`/`component.name`. Checks under components use the check name. Manual incidents have no uptime bars; their list items get `aria-label`-free headings: the title is already the visible name, and the "Affects" list stays. Add `aria-labelledby` linking each manual incident `li` to its `.name` span via id `manual-name-<id>`. Format: `"<name>, 90-day uptime 99.9 %"` or `"<name>, 90-day uptime no data"`.

### D5 No-JavaScript view
- `index.html` placeholders. Each section container gets its server html in place of its current content: `<div id="banner">{{banner}}</div>`, `<div id="summary">{{summary}}</div>`, `<div id="updated">{{updated}}</div>`, `<section id="manual" ...>{{manual}}</section>`, `<div id="checks">{{checks}}</div>` (replacing the "Loading…" paragraph), `{{incidents}}`, `{{resolved}}`, `{{manualResolved}}`, `{{maintenance}}` likewise, and `{{checksTitle}}` is not needed. Directly after `</header>` goes `{{renderedLine}}`. The server replaces `{{renderedLine}}` with `<noscript><p class="no-js-note">This page does not refresh without JavaScript. Rendered <time datetime="2026-10-30T12:00:00.000Z">Oct 30, 2026, 12:00:00 PM UTC</time>.</p></noscript>`. Inside `<noscript>` the paragraph is shown only without JavaScript (browsers parse it as markup only then), so with JavaScript nothing changes and no style is needed to hide it. The ids and the live regions (D3) stay as they are. The placeholder replacements use function replacers like the existing `renderIndex` (`$` safe).
- Server: a new `src/ssr.ts` exports `renderState(ctx, options)`. It uses the existing public `createPoller(...).refresh()` of `src/poller.ts` (no refactor, no new export): it creates a poller per request with `fetch` set to an adapter over `cachedAnswer` in `server.ts` (the adapter maps the request path to `cachedAnswer(path, new URL(path, "http://localhost"), ctx)` and wraps the `ProxyAnswer` `status`, `body`, content-type and wire-version header in a `Response`; this is the same cache the `/api/*` proxy and the feed use, `cacheMs` applies, so a warm cache means no upstream traffic), `baseUrl: "/api"`, a no-op `timer`, `now: ctx.now`, `onUpdate` capturing the state, then awaits `poller.refresh()` once without `start()`. Because `refresh()` publishes when its generation is current, `onUpdate` fires exactly once. Then `buildSections(state, makeServerEnv(ctx), ...)` with the same renderers as the browser (`showChecks` from options). On a failed refresh the state has `error` set and empty lists: the same `buildSections` output as the browser's first failed poll (`renderBanner` and `renderUnavailable`); the server still answers 200. Exceptions thrown by the render are caught and the placeholders are filled with empty strings (page as today).
- Server env: `now = ctx.now()`, `formatExact` = `Intl.DateTimeFormat("en", {dateStyle:"medium", timeStyle:"medium", timeZone:"UTC", timeZoneName:"short"})` so the no-JS text names UTC explicitly. The same for `formatExactSpan`.
- Take-over without flash (open point 2): the client does not redraw on load. It seeds its patch cache from the server DOM, and the first draw happens at the first poll (a poll fires immediately at start, as today); `patchHtml` only touches nodes whose text differs. Absolute times switch from server UTC text to the visitor's zone at that first patch (accepted: the same layout, a zone label changes, one-time). Relative times stay stable because they are recomputed from `Date.now()`.
- CSP unchanged: no inline script, no inline style; the note is plain HTML.
- Escaping: all values go through the existing `escapeHtml` in the renderers.

### D6 Time zones
- `client.js` formatters get `timeZoneName: "short"` (`exactFormat`, `clockFormat`; `dayFormat` stays date only; the span's end carries the zone once). Absolute times in `data-exact`, `title` and `aria-label` therefore show the zone.
- Day labels read `2026-10-30 UTC: 99.9 %`. Add a legend line under the checks heading: `<p class="legend">Days are UTC days. Bars: ...</p>` rendered by `renderUptimeLegend()` once per section (not per entry), pulled in `renderChecks`/`renderComponents`; if the section is empty, no legend.

### D7 Automated check in CI
- Dev dependencies of status, pinned exactly like pulse-website (read its `package.json` for the versions; the website row in meta says playwright 1.64.1): `playwright`, `@axe-core/playwright`. `bun.lock` updated.
- New `e2e/a11y.test.ts` is NOT in `bun test` (`bunfig.toml` test root is set to `src`; the file lives in `e2e/` and has its own script) and `package.json` gets `"check:a11y": "bun e2e/run.ts"`. The runner starts `createStatusServer` with a stub api (in-process `http` server serving the contract JSON, mutable between polls) with a short `pollMs` (200 ms), then drives Chromium via Playwright over {light, dark} x {360, 1280} x {components, no components} (color scheme via `emulateMedia`, plus `data-theme`).
- Assertions: axe `wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa` no violations; focus on a given `day:` bar survives five polls and a state change of its check (same node: a marker property set on the element survives); Tab count per entry; `#live` and `#alert` nodes are the same elements (marker property) and their text is stable across ten polls, changes once on a summary change; the alert appears on an error, changes on a kind change, clears on recovery; every `[role=group]` bars has an accessible name containing the entry name (via `page.accessibility`/`ariaSnapshot`); with `javaScriptEnabled:false` the page shows the check, component, incident, maintenance and the note; every `time[data-exact]` and the span text contains a zone abbreviation; legend and day labels contain "UTC".
- CI: new job `a11y` in `.github/workflows/ci.yml` (separate from `check` and `docker`): checkout, setup bun at the version in `package.json`, `bun install --frozen-lockfile`, `bunx playwright install --with-deps chromium`, `bun run check:a11y`. Dockerfile installs production dependencies only (`--production`), so Playwright and the browser never reach the image; the Dockerfile copies only `package.json`, `src` and `public` (it has no `COPY . .`), so `e2e/`, `playwright` and the browser are never in the image and no Dockerfile change is needed; the `docker` job gets one added assertion that `/app/e2e` and `/app/node_modules/playwright` do not exist in the built image. New unit-test files and `patch.fake-dom.ts` live in `src/` like the existing tests and are handled as today.

## Risks
- Patch regressions that skip a needed update: mitigated by the identical-html short circuit being exact string compare and by the Chromium test.
- `role="img"` on 90 bars is noisy for screen readers browsing by element: accepted; the group name carries the summary.
- SSR adds an upstream read per page request when the cache is cold: see below.
- Playwright download in CI: flaky network; cache `~/.cache/ms-playwright`.

## Performance impact
- Client: per poll, today 10+ `innerHTML` writes re-parse and re-layout whole sections, 90 bars per entry included. With the patch, an unchanged poll costs one string compare per section and no DOM writes. Target: on an unchanged poll, zero DOM mutations (asserted with a `MutationObserver` in the Chromium test).
- Server: each page request now runs the existing cached reads (`cachedAnswer`, `cacheMs` default applies) and the renderers. Status has no written performance budget in `docs/` or `AGENTS.md`; the implementation measures a request to `/` with 50 checks and 20 components (warm cache): p95 render time and response size, and records them in `docs/operation.md` as the budget (suggested: p95 under 20 ms warm, HTML under 250 KB). A cold cache adds at most the existing upstream timeout; the page falls back to the unavailable view.
- `/` is not cacheable by clients longer than before (`cache-control` unchanged).
