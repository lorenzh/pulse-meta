# Issue review: #558 — request-target errors, admin auth throttling and token strength

## Disposition

Ready for `plan`. No question blocks the spec. The issue explicitly delegates throttle limits to the plan. The points below need explicit decisions in that plan, especially the handling of credentials imported before this change; they do not require a hold.

## Request and earlier decisions

Read [#558](https://github.com/lorenzh/pulse-meta/issues/558) and all its comments. The only comment is this run's Factory claim; there are no earlier owner decisions. Read meta `AGENTS.md`, `README.md`, the issue-review prompt, `docs/approved-packages.md`, and `audits/security/api.md`, including finding `security-api-2026-10-31-1`.

The request has three observable outcomes: malformed request targets produce an ordinary 400 without an error stack, admin credentials require at least 32 characters with a startup diagnostic and upgrade guidance, and repeated admin authentication failures are limited per client with observable throttling. Admin route relocation and implementing the hashed store are outside this feature.

- `server.ts:582` constructs `new URL(req.url ?? "/", "http://localhost")` without a guard, before ops routing or authentication. The outer handler maps unexpected exceptions to 500 and calls `logError`; `start.ts` supplies a logger that records the error stack. `routeOf` already catches URL failures and labels them `unmatched`. The admin handler also parses the URL; fixing only that handler would leave the public entry point vulnerable.
- `tokens.ts` exports the shared 16-character minimum and schema. `admin-tokens.ts` uses that schema. Startup wraps import errors with `PULSE_API_ADMIN_TOKENS_FILE` and the path, and `main.ts` handles startup failures. Current admin parser/startup fixtures contain many valid tokens shorter than 32 characters.
- `admin-auth-failures.ts` limits warning logs to one per route/status/token-kind per minute. It counts failures in `pulse_api_admin_auth_failures_total`; it neither rejects nor delays requests and has no client identity. Both admin routing and manual-incident writes use this recorder. Existing kinds include missing, unknown, inactive, probe and insufficient scope.
- The issue's `c00a375` baseline predates the now-present implementation of [#561](https://github.com/lorenzh/pulse-meta/issues/561); its approved spec is `.factory/work/561/plan.md`. Tokens are already hashed and scoped. Admin routes now also include token management and audit reads/exports. New/rotated secrets are generated from 32 random bytes as 49-character `pulse_` strings. Reuse this work rather than implementing another store or reverting to file authentication.
- `start.ts` and `token-import.ts` perform one-time imports. After the admin bootstrap, the file is never opened again, even if missing or malformed. `migrations.ts` stores a digest and timestamps in `token_secrets`, with no original secret length. Startup cannot infer whether an already-imported credential was shorter than 32 characters.
- Kit has no rate limiter in its current source or exports. Api and kit instructions require reusable infrastructure to live in kit rather than a service-local helper. An additive kit helper, followed by an api pin to its merged full SHA, is the expected approach; route selection, auth decisions, metric names and limits belong to api.
- Compose e2e moved to deploy: api CI no longer has a `compose-e2e` job. Deploy's `full` CI job runs `bash e2e/compose-e2e.sh` against published pinned images. Both its shell script and YAML default to the same **27-character** admin token, incompatible with the new minimum. The shell also expects a probe token on a manual-incident write to yield 401, whereas current api code/docs yield 403; this is pre-existing integration drift to account for when testing the candidate.
- Console's local admin-token validation and deploy's shared secret initializer still accept 16 characters. Both can pass a 32+ character credential already. Api remains the authority; coordinated validation changes in those clients are optional scope decisions, not prerequisites for enforcing the api rule. Deploy's generated/operator examples use longer random secrets already.

## Open points and assumptions for the plan

1. **Define an unparseable target narrowly.** Treat failure of the existing WHATWG URL construction as expected client input failure, with a stable generic message in the existing `ErrorResponse` shape `{error: string}`. Preserve JSON content type, security and wire-version headers. Do not expose the target, headers, credentials or URL exception. Do not catch unrelated handler errors as 400. Keep existing behavior for parseable paths, bad path escapes, query validation, methods and routing. Raw HTTP rejected by Bun before the application handler is a separate boundary; a regression must reach this URL parse. Use a raw socket or an HTTP request with an explicit path, since `fetch` may reject or normalize the target before transmission.
2. **Separate admin strength from probe strength.** The admin bootstrap file must reject 16–31 characters and accept the 32-character boundary, preserving whitespace, placeholder, public-example, duplicate and cross-role checks. Keep probe and heartbeat minimums unchanged. Use the existing string-length convention rather than silently changing character/byte semantics. Document a clear, secret-free startup error naming the entry, minimum, setting and file, with exit code 2. Cover both first startup and a first admin import on an existing probe-only database. Do not reread files after a completed import or redo #561's database migration.
3. **Cover existing database credentials explicitly.** Raising the import schema alone leaves already-imported short admin credentials usable. Recommended interpretation: startup validation applies when plaintext is actually imported; authentication must also refuse a presented short admin-side secret already in the database. Apply the rule to all non-probe scopes, not just credentials with the `admin` scope. There is no trustworthy length information for a proactive startup check of existing digests. Preserve restart with ignored/missing files, and do not guess strength from a digest or silently grandfather short admin credentials. The upgrade note must tell operators to rotate short imported admin credentials on the old version **before** upgrading, distribute the generated replacement to clients, and explain the normal rotation overlap and backup recovery. Editing the old bootstrap file after import does not rotate a token. State the treatment of an old short secret during a rotation overlap; the recommended minimum rejects it on the new version. A database already holding a suitable generated credential needs no special migration.
4. **Limit admin authentication across route families.** Assume the title's admin scope: recognized `/admin/*` endpoints (config, writes, tokens and audit) and authenticated manual-incident writes share one failure budget per client. Include evaluated 401 and 403 failures and every existing token kind. Public reads, ops, probe ingest/check retrieval, and heartbeat authentication are outside this throttle. Preserve feature-off 404 and the existing method/id checks that occur before manual-incident auth. Alternating paths, token values or failure kinds must not give a fresh budget. Body validation and writes must not run on a blocked request.
5. **Choose a complete throttle policy.** Specify threshold, interval, exact triggering request, recovery boundary, success behavior and whether requests with valid credentials are blocked during a penalty. A reasonable starting proposal is 10 failures per 60-second window starting at the first failure; the first 10 retain 401/403 and subsequent protected attempts get immediate 429 until that window ends, including a valid credential during the penalty. Do not extend the penalty on rejected attempts or hold connections asleep. Successful authentication before the penalty should not consume the failure budget. These numbers and choices are recommendations for the plan, not an owner decision already made. Tests with many intentional failures must isolate client/window state rather than disable production protection.
6. **Define client identity and bounded state.** Recommend the connection's peer IP (`req.socket.remoteAddress`), shared across connections and ports, with IPv4/mapped-IPv6 handling specified. Ignore `Forwarded` and `X-Forwarded-For`; there is no trusted-proxy configuration today. Document that clients behind a proxy/NAT can share a budget and that state is per process and resets on restart; distributed limiting and proxy trust settings are outside this request. Specify behavior when the peer address is unavailable. Give the table a fixed capacity, expiration/cleanup and an overflow policy that does not provide unlimited fresh attempts merely by evicting blocked clients. Inject time and test bounds without real timers. Keep authentication/token information out of kit.
7. **Define 429 and metrics without changing existing meanings.** Recommend `{error: "too many requests"}` plus an integer `Retry-After` in seconds, rounded up to remaining penalty time, and normal response/security headers. Add a dedicated counter such as `pulse_api_admin_auth_throttled_total` with bounded route-pattern labels (or no labels), incremented once per blocked request. Preserve the 401/403 failure counter for evaluated denials; if blocked requests skip authentication, do not fabricate an auth failure kind or double-count them there. HTTP request metrics should record 400/429 rather than 500. Preserve warning-log suppression and never emit a stack for these expected client responses. No client IP, raw path, secret, digest, authorization value or token-specific identifier belongs in metric labels.
8. **Account for support targets and verification.** Plan kit → api for the reusable limiter. Include narrowly scoped deploy work for compatible e2e fixture defaults in both locations, and explain whether matching secret-validator/docs changes are needed. No contract change is expected for existing `ErrorResponse` or `Retry-After`. No route relocation, new auth port, token-store redesign, new runtime dependency or unrelated audit remediation is required. If console validation alignment is included, inspect its instructions and define that child explicitly.
9. **Make CI, Bench and compose evidence refer to the changed api.** Api's CI runs `bun run check`, bench selftests and Docker checks. The separate Bench workflow runs `bun bench/run.ts`; passing selftests alone is not a performance result. Deploy e2e normally uses `common/services.yaml` release pins, so a green run against the unchanged published api cannot validate this feature. Specify how a candidate image is exercised in an isolated validation checkout or how the release pin/run is staged after release. Respect deploy's committed image-pin/build conventions. Record exact candidate SHAs/image identity and do not claim acceptance before the matching run is green. Account for the existing manual-incident status drift rather than weakening the api auth contract to fit an old published image.

## Derived acceptance check

The feature is accepted when the following behavior and verification are demonstrated together:

1. **URL regression, red on the inspected api baseline.** A local real server on an ephemeral loopback port receives a target accepted by the runtime HTTP parser but rejected by the application's URL parser, without credentials. It responds 400 with the ordinary typed error body and normal headers. An injected error logger receives no stack/error callback; request metrics count `unmatched`/400 without increasing 5xx. Include an ops-looking malformed target and preserve ordinary valid-route behavior and genuine server-error reporting.
2. **Admin-length regression, red on baseline.** With a pending admin bootstrap, an otherwise valid 31-character token prevents startup with the documented diagnostic and exit behavior, without printing the token or importing partial token rows. A 32-character admin token starts and authenticates; the existing 16-character probe minimum still works. Test that already-completed imports remain independent of their old files. An upgrade fixture containing a short previously imported admin secret is refused at authentication under the documented migration policy, while a generated replacement works. Retain placeholder, whitespace and token-separation coverage with appropriately sized fixtures.
3. **Throttle regression, red on baseline.** With fake time, the chosen number of repeated failures from one peer reaches the exact documented 429 boundary, returns the correct body and `Retry-After`, and increments the throttle metric exactly once per blocked request. Advance time to the precise recovery boundary and verify normal authentication resumes. Cover shared budgeting across admin config, token/audit routes and manual-incident writes; independent peers; reconnects; spoofed forwarding headers; valid-credential behavior during the penalty; capacity/expiry; and feature-off/public/probe/heartbeat behavior. Verify denied/blocked requests cannot mutate state and no sensitive values appear in logs or metrics. Use a real HTTP integration check as well as deterministic limiter tests.
4. **Operator guidance is usable.** Api README and configuration, REST and operation docs explain the separate admin minimum, startup error, throttle limits/scope, 429/retry/metric behavior, peer-IP limitations and upgrade/rotation procedure. The procedure handles both not-yet-imported files and already-imported digests without implying that editing an ignored file rotates credentials. Compose e2e's shell and YAML token defaults agree and are at least 32 characters.
5. **Required checks pass against the implementation.** Capture a failing-before/passing-after test for each of the three requested items. Run api `bun run check`, `bun run bench:selftest`, Compose bench configuration validation and applicable image checks; run kit checks/build if adding the helper, including its committed `dist` output. Obtain a green complete Bench comparison with the candidate api and existing budgets, and green deploy `bash e2e/compose-e2e.sh` against that api image, plus checks for changed deploy files. Start the changed API via `bun start` and exercise the changed behavior as required by its instructions. Link actual command/run evidence in implementation handoff; do not substitute unchanged release tests or relax checks/budgets for this security fix.
