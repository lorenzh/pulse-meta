## Nonblocking points and assumptions for the plan

1. **Scope and prior work.** Keep implementation in probe. Build on #864/#879's merged contract adoption; no new shared change, dependency update, route, field, setting, wire version or runtime package is currently necessary. Existing API reads and parser sanitization are compatibility controls. This composite feature still needs production changes for result posts and log formatting, so already-completed subrequirements do not block the spec.
2. **Meaning of direct requests.** Interpret “keep direct API requests unchanged” as preserving successful requests to the configured final API and the ordinary failure contract. It cannot prohibit the explicitly requested transport guards. Preserve monitored-target redirect rules, authentication, request bodies, URLs, timeout/abort handling, read body caps and wire behavior.
3. **Redirect outcomes.** Explicitly use manual redirects for posts and classify every 300–399 response as `retry`, including missing or unusable locations. Do not issue a destination request or fall back to a different API route. Let the existing buffer handle backoff, retention, ordering and eventual delivery; do not add a client retry loop. Cover same-origin and cross-origin redirects, including 307 and 308, and transport downgrade refusal.
4. **Encoding policy and precedence.** Posts should ask for identity encoding and disable Bun's eager decompression, as the shared client does. Define absent/identity as supported after trimming and case normalization; refuse every other coding, including unknown or combined values, before body processing or discard. Request preference alone is insufficient. Proposed outcome rule: redirects retry; an otherwise accepted 204 with unsupported encoding retries; other HTTP failures retain their ordinary status-based outcome without interpreting a response body. Thus encoded error answers still cannot be decoded, while 401/403, 404, 429 and 5xx retain their meanings. State this ordering explicitly in the spec and tests. Preserve wire diagnostics and ensure cleanup cannot strand delivery when cancellation remains pending. Do not parse result-response JSON or introduce a new public outcome variant.
5. **Fixed JSON diagnostics.** Retain the existing fixed startup message `invalid JSON: response body is not valid JSON` and require it through the reload path too. Do not interpolate raw parser text or remove useful retry/keep-current context. A local change to `toError` is optional if the inherited contract behavior already satisfies this. Do not downgrade the contract to manufacture a failing regression on this feature's base.
6. **ID presentation versus identity.** Bound only displayed IDs; preserve complete IDs in validators, checks, results and deduplication keys. Use the existing 80-unit-plus-ellipsis convention unless the plan justifies another literal bound. Apply it to invalid-record logs and audit the remaining ID interpolations in `client.ts`, including skipped header checks and result-drop logs, so those paths cannot bypass the log bound. Do not broaden this into a schema limit or unrelated service logging rewrite. IDs with the same displayed prefix must still deduplicate separately.
7. **Memory acceptance.** Carry forward #864's maximum 64 MiB isolated-process peak RSS growth as the proposed budget for result-response handling. This is a review assumption grounded in that accepted budget, not a new measurement. The plan must define the baseline/control interval, native-memory-inclusive peak measurement and tested runtime. Measure successful and failure/discard paths, including redirect and wire diagnostics. A fetch-option assertion or final JS heap measurement alone does not establish bounded memory. Keep input creation outside the measured client interval and report no construction details.
8. **Documentation and files.** Every probe `Files:` list must include `README.md`, as probe's AGENTS requires. Update `docs/configuration.md` and `docs/troubleshooting.md` where their descriptions of retryable failures and final drops would become stale. Enumerate individual source, test and helper files in the plan and tasks; protect unrelated source, dependencies, AGENTS, CI and tooling/coverage settings. Existing buffer/reloader production code should need no changes; exported integration boundaries suffice for tests.
9. **Security and performance.** The spec must say `Security impact: yes`: redirects, secrets in diagnostics, response memory/encoding, input validation, and dependency-pin preservation apply. Expect reduced peak RSS for refused responses, bounded log output, and some added test CPU. Specify measurement of that cost without relaxing checks or budgets. Runtime/tool facts in the plan need file citations and pinned shared-config verification as required by the plan prompt.
