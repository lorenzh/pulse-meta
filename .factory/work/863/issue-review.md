## Gaps, assumptions and retained decisions

1. **Scope and sequencing.** Plan one target, `probe`, unless inspection reveals a concrete missing shared protection. The current contract pin already supplies #864; no shared rewrite or dependency bump is currently justified. Preserve direct successful API requests, authorization, timeouts, body limits, wire checks and monitored-target redirect policy. No new dependency, setting, wire field or outcome variant is needed. Earlier comments disagree about redirect credential forwarding; acceptance is zero requests to the redirect target, independent of runtime forwarding behavior. Public descriptions stay at class and impact level.

2. **Post redirects.** Keep the separate post fetch. Send `redirect: "manual"`, `decompress: false`, and `accept-encoding: identity`. Every 3xx is undelivered and returns `retry`, with or without a usable Location, including same-origin redirects. No per-result redirect/drop line is added. Explicit exception: the existing wire-mismatch diagnostic remains, once for that response, even for a redirect. Preserve its current outcome-independent meaning.

3. **Encoded post responses and status precedence.** Disable eager decompression for every status. Inspect status and headers before body cleanup. A 204 is accepted only for absent/empty or identity content coding, using trimmed, case-insensitive comparison; a non-identity-coded 204 returns `retry`. Every 3xx returns `retry`. All other statuses retain their current outcome, including encoded 400/401/403/404/429/5xx and non-204 2xx. Their bodies are never decoded or read. Do not introduce a blanket rule that all encoded responses are retried. Keep wire diagnostics and authentication/drop messages, without received header values or body text. Cancel an unused body best-effort without awaiting cancellation; a pending or rejected cancellation must not delay or change delivery classification.

4. **Fixed JSON diagnostic.** Use the inherited fixed reason `invalid JSON: response body is not valid JSON` for malformed or otherwise unparseable API JSON, identically at startup and reload. Retain the surrounding startup retry and reload keep-current-checks context. No parser detail, stack or body text may appear. Interpret the manager's “unreadable or malformed API answer” as a JSON parsing failure here; preserve the separate timeout, network, size, wire and encoding errors rather than relabeling transport failures as invalid JSON. A further local parser replacement is unnecessary while the pinned shared client supplies fixed text.

5. **Bound displayed IDs only.** Use `quote` for check-ID fragments in every affected `client.ts` message: invalid records, header-resolution skip/denial lines and both result-drop paths. Cap the invalid record's validation reason with `capReason`; an ID can be echoed there too. Preserve short diagnostics. Full IDs remain in validation, returned checks, posted results and skip-deduplication keys; header-denial reasons keep their existing result semantics. Distinct IDs sharing the first 80 characters must still be distinct skip keys. Saturation, recovery and ID-less handling stay unchanged. This issue does not expand into a rewrite of all service logs.

6. **Documentation is required, including README.** The probe section's `Files:` list must explicitly include `README.md`, plus the reviewed four docs: `docs/configuration.md`, `docs/operation.md`, `docs/troubleshooting.md` and `docs/development.md`. The plan's README instructions and task's documentation acceptance must explicitly name the fixed JSON reason for both startup and reload. Put it next to the final-endpoint/redirect and encoded-answer rules, not only in a linked troubleshooting page. Explain bounded displayed IDs, the existing buffer path for redirects and encoded 204s, and unchanged status handling for other encoded answers. Update stale retry/drop descriptions. Security impact must name both changed outcomes: every 3xx becomes retry; a non-identity-coded 204 becomes retry instead of accepted. Do not claim that all 2xx outcomes are unchanged.

7. **Baseline evidence.** New fixes need regressions that actually fail on the recorded implementation base for their stated reason and pass on the branch. Existing contract protections, ordinary failure classifications, direct delivery, warning-cache behavior and target-check redirects are controls that must pass on that same base. Do not call inherited JSON/read protections new regressions merely because the tests are new. Keep the earlier M1/M2 memory requirements: each case and the whole child must exceed the 64 MiB growth budget on BASE and meet it on the branch. M2's existing retry outcome and wire diagnostic alone do not discriminate the fix. If the required memory failure cannot be established within the performance budget, adjust the fixture within that budget or hold; do not relabel the case or relax the limit.
