## Open points for the plan

1. **Keep binding authority on the probe.** An admin who can change a check must not be able to change that secret's allowed hosts through the same API. Use operator-controlled startup configuration on each probe, separate from checks and their headers. A JSON env setting such as `PULSE_PROBE_HEADER_HOSTS`, mapping variable names to host arrays, is a suitable minimal format. This proposed name has no matches in contract `src/` or the config clone. It avoids placing the policy setting itself under the `PULSE_HEADER_` secret namespace. No secret values go in the map, API, database, or Console. #460's future editing UI must preserve this trust boundary; it is not needed to specify this work.

2. **Define exact matching and parsing.** Specify hostname versus host-with-port versus origin; case, trailing dots, IDNs, IPv4, IPv6, and default ports must have one consistent normalization. Recommended minimum: exact canonical `URL.hostname` matches, with the same normalization on configuration entries, no wildcard/subdomain/suffix matching and no DNS-address expansion. State explicitly that hostname-only binding covers the host's ports and HTTP/HTTPS schemes; existing redirects still require the same origin. If the plan chooses port/origin restrictions, give their syntax and examples. Never compare with substring matching. Host binding is not a new private-network/SSRF policy.

3. **Fail closed, and report a result.** Missing setting, absent variable entry, or an empty host list must grant no destinations; no legacy allow-all fallback. An unset map can mean an empty map so probes without secret headers still start. Malformed configured JSON, invalid keys, and invalid host entries should stop startup with a bounded error that does not dump the map. Check authorization before reading the secret value. For a disallowed target, recommend aborting the whole HTTP attempt and emitting a normal `down` result, with null status code and a bounded reason identifying the denied reference/header and host, never its value. Merely skipping it during `loadChecks` leaves a gap and does not meet “the result says so.” Silently removing authentication and reporting a successful anonymous response would also be misleading. State how other unset/invalid-secret cases relate to today's skip behavior; only host denial necessarily changes it here.

4. **Carry policy through reload and redirects.** The map is read once at startup and reused when checks reload. An admin URL edit must be checked against that same map. Existing resolution erases the distinction between literals and env references, so the plan must define a probe-internal representation or execution dependency that retains enough information to report denial without adding internal fields to the wire contract. No update may leave a secret attached to an unauthorized URL. Keep #384's redirect restrictions: even when two hosts are both bound, a secret-bearing check must not gain permission to redirect between origins. Literal headers and bodies retain their existing rules.

5. **Reason bounds must cover every path.** Apply the 1000-character maximum to both result and POST request schemas. Decide explicitly whether the same bound applies to incident `reason` and check `lastReason`; those have separate schema definitions and carry copies of result reasons. Use JavaScript string length consistently with API ingestion, counting any ellipsis inside the final maximum. Share the existing `quote()` behavior where HTTP/RDAP/DNS/error fragments are quoted, and specify whether complete reasons also pass through it. A final bound after all result construction must cover every check type, retries, degraded latency reasons, and policy failures. Fixing only the four cited redirect lines misses DNS and generic error paths. A bounded string is not automatically redacted: reasons must still avoid header values and URL credentials, paths, and queries when reporting redirect/policy failures.

6. **Choose and document the warning range in both types.** Recommend integer `0..3650` days for TLS and domain warnings (ten years is a conservative operational maximum), keeping current defaults. This is a proposed range for approval through the spec, not an already approved numerical limit. The plan can choose another justified finite range but must name it literally in checks and docs. Also fix API TLS file/admin validation; a contract pin alone cannot enforce it. Current contract tests explicitly accept `warnDays: 10000` and will need an intentional expectation change. Existing configurations outside the range need a migration note; do not silently clamp warning settings.

7. **Integer latency needs an explicit compatibility policy.** Cover `Result` and `PostResultRequest`, not only the former. Define rounding of newly measured fractional durations (recommend nearest whole ms after non-negative clamping). The API's existing 86,400,000 ms ceiling also conflicts with the broad goal if the new contract accepts larger integers; either align this affected static limit or explicitly resolve that difference in the spec. Account for fractional historical rows and nested results before upgrading status. Safe options include normalizing legacy latency at API ingress/response boundaries while validating canonical integer results, or a documented producer-first rollout that drains old probes/buffers plus normalization of historical responses. If ingress normalization is chosen, validate the raw finite/non-negative/bounded number before rounding; it must not turn a negative fraction into an accepted zero. Do not hide coercion inside contract validators: their established behavior returns the input object unchanged.

8. **Make rollout operationally executable.** Distinguish contract merge/pin dependencies from service release order. At minimum: publish the contract change; migrate invalid check definitions and provision bindings at every probe location; deploy producers that cap reasons and emit integer latency against the older API; upgrade the API with the necessary validation/history handling; then upgrade strict downstream consumers. If all old probes must be retired before stricter POST validation, explicitly include draining their buffered results and a rollback procedure. Otherwise test a compatibility ingestion path for old fractional payloads. A single contract wire-version bump would make mixed-version fetch clients reject responses, so justify any bump and its transition rather than assuming one is harmless. No old probe may lose ingestion merely because a newer API was released.

9. **Include the actual integration fixture and documentation.** Add the e2e secret's allowlist to api `compose.e2e.yaml` and preserve the successful authenticated target scenario. Since api builds the probe from main, the API child may need to wait for the merged probe change to test new behavior. Conversely the new probe can make API main's existing e2e fail until its map fixture is supplied; the spec must arrange this transition (for example, provision the harmless setting before releasing enforcement). Do not claim an e2e pass on an old peer proves the new policy. Update probe settings/migration docs, contract docs and built artifacts, and API configuration/operation documentation. State that an admin token is as sensitive as every header secret it can address, even though values remain env-only. status/notify need full-SHA contract pin and lockfile updates and compatibility verification, not new UI.

10. **Keep the remaining scope bounded.** This is the follow-up to already landed #384, not a redo of its prefix/redirect implementation. No new secret store, Console UI, settings hot reload, private-network policy, or dependency is required. Pin contract's compiler alias exactly to `npm:typescript@7.0.2` and refresh its lockfile; leave unrelated toolchain pins alone. Interpret “every value” as consistency for the affected fields: authentication, known check identity, timestamps relative to the server clock, and other contextual API checks still exist. The plan should call out remaining unrelated static discrepancies rather than implying this issue removes all validation differences everywhere. Likely targets are contract, probe, api, status, notify; deploy is not required by the inspected baseline.

## Review validation and limitations

This state performed source/configuration inspection and read GitHub decisions; it did not implement product changes or run service CI. No target clone was edited. Dependencies are not installed in the inspected target clones, so full contract/probe/API tests were not executed here.

A dependency-free Bun 1.4.0 URL check confirmed that the current protocol-only rule accepts a URL with non-empty username/password, and that WHATWG parsing accepts a 2001-character protocol and a 2013-character redirect origin. This validates the long-redirect test construction without external network access. The concrete service regressions and Compose run belong to implementation and review.
