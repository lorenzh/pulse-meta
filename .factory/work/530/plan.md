# Spec #530: pulse CLI day-2 commands (token rotate, upgrade, logs)

## Goal

The `pulse` CLI of pulse-deploy (#529) gets three day-2 commands for an installation that `pulse init` wrote:

- `pulse token rotate <admin|probe>` rotates a token through the api's token store. Consumers switch to the new secret while the old one is still valid, and only the consumers that need the new secret restart. An interrupted run resumes from a journal.
- `pulse upgrade [--to <version>]` moves the installation's pinned pulse images to a newer release. It shows the change, verifies the provenance of every new image digest, applies the change with `--yes`, waits for readiness, and restores images and data if the new release does not become ready.
- `pulse logs [service] [--follow]` wraps `docker compose logs` for the guarded project.

The commands get docs, unit tests with failure injection, and live CI jobs.

## Facts the spec builds on

1. **Token store in `0.1.1`.** api `v0.1.1` has the database token store.
   - Routes (`docs/rest-api.md` "Tokens", lines 502–529): `GET /admin/tokens`, `GET /admin/tokens/self`, `GET /admin/tokens/:id`, `POST /admin/tokens` (answers `201`), `POST /admin/tokens/:id/rotate` (answers `200`) and `POST /admin/tokens/:id/revoke` (answers `200`, line 515).
   - Rotate and create answer `{token, secret, previousValidUntil}`. The `secret` is `pulse_` followed by 43 base64url characters, 49 characters in total. It is shown only in that answer and cannot be read again (line 517).
   - `TokenCreateInput` is `{name, scopes, location?, expiresAt?}`. `name` is 1 to 100 characters without control characters, and `expiresAt` must be later than now (line 516).
   - The old secret stays valid for 10 minutes. A second rotate during the overlap answers `409`. Revoked or expired tokens also answer `409`. A revoke invalidates every secret of the token at once (line 520).
   - Grant rule: a caller may create, rotate or revoke a token only when it holds every scope of that token, where `probe` counts as `checks` (line 498). Last-admin rule: revoking the last active admin answers `409` (line 500).
   - Token ids are `tok_` and 24 lower-case hex characters (`src/token-store.ts` line 23).
   - The token files are imported once and ignored afterwards (`docs/configuration.md` "Token import", lines 233–241). An imported admin token gets `["read","checks","incidents","admin"]` (line 238), so it may create, rotate and revoke probe and admin tokens. Imported probe tokens are named `probe <location> #<n>`. The admin token keeps the name from `admin-tokens.json`, which `secrets-init.mjs` writes as `admin` (line 223).
   - Admin-side secrets need 32 or more characters (`docs/operation.md` lines 94–110). The CLI-generated ones have 64.
2. **Schema versions.** api `v0.1.0` reads tokens from files: its `src/migrations.ts` has three steps, so `SCHEMA_VERSION` is 3 (line 76 at tag `v0.1.0`). `v0.1.1` has nine steps (`SCHEMA_VERSION` 9, `src/migrations.ts` line 225). The version is the SQLite `PRAGMA user_version` (`src/db.ts` lines 101–102) of `/data/pulse.db` (`Dockerfile` line 9). An older api refuses a newer schema with exit 2 (`docs/operation.md` lines 33–36).
3. **Probe cadence and stop.**
   - The probe reads `PULSE_PROBE_TOKEN_FILE` once at start and becomes ready only after `GET /probe/checks` succeeds (`src/main.ts` lines 128–155 and 249–251).
   - The first run of each check starts after a random delay below `min(intervalMs, 1000)` ms (`src/scheduler.ts` lines 36–42). After that it runs once per interval from the previous start. The result `timestamp` is the start of the run (`src/check.ts` line 149). Consecutive results of one probe are therefore one interval plus the timer lateness apart.
   - On SIGTERM the probe aborts its in-flight requests, stops the scheduler and flushes queued results (`stop()`, `src/main.ts` lines 264–271). It starts no run after the signal.
   - When the api does not take a result, the probe keeps it in a buffer and retries with a backoff from 1 s up to 30 s (`BACKOFF_START_MS` and `BACKOFF_MAX_MS`, `src/buffer.ts` lines 4–5 and 113–128). The result keeps its `timestamp`. The buffer drops results only above `bufferMaxResults` or `bufferMaxAgeMs` (`src/main.ts` lines 195–196).
   - `intervalMs` is any integer from 1 (`timerMs = intBetween(1, MAX_TIMER_MS)`, contract `src/schema.ts` line 89). Only domain checks have a higher minimum (1 hour, line 351).
   - The console reads its admin token file at start and needs at least 32 characters (`src/admin-token.ts`).
4. **How deploy hands out secrets.**
   - `secrets-init` (files mode) copies `secrets/admin-token` and `secrets/probe-token-<loc>` into the per-consumer volumes: owner 1000:1000, mode 0400, written atomically (`scripts/secrets-init.mjs` lines 162–204).
   - It also rewrites `api/tokens.json` and `api/admin-tokens.json`, which a token-store api ignores after the import.
   - The CLI's install renders `PULSE_PROBE_LOCATIONS` and `PULSE_SECRETS_ADMIN: "on"` (`cli/render-compose.ts` lines 101–118).
5. **How the CLI writes and runs Compose today.**
   - The generated `compose.yaml` writes every string double-quoted (`cli/yaml.ts` lines 1–5). Each pulse service has an `image: "ghcr.io/lorenzh/pulse-<svc>:<x.y.z>@sha256:<64 hex>"` copied from `common/services.yaml` (`cli/render-compose.ts` lines 90–99, `cli/services.ts` lines 36–48).
   - In full and demo the api port is not published (`cli/render-compose.ts` lines 156–158). Readiness already runs `docker compose exec -T <svc> bun -e <script>` inside the container (`cli/ready.ts` lines 48–77).
   - The spawn seam has stdin `ignore`, and an abort sends SIGKILL to the client process (`cli/docker.ts` lines 52–83). Killing a `docker run` client does not stop its container. A SIGKILL to the `pulse` process alone does not end its Docker client children either: a client that has not yet reached the daemon can still create and start its container after the CLI is gone (reproduced in the eighth plan review: two empty lists, then a late helper start).
   - **Create, then start** (checked in this run with Docker 29.9.2): `docker create --rm -i … -v <missing name>:/to …` exits 0 with the 64-hex id on stdout and leaves a container in state `created` that `docker ps --all --no-trunc --quiet --filter label=…` lists; a created container runs no process. It also creates the missing named volume, with labels `null`. `docker start -ai <id>` with stdin from a pipe ran the command with that stdin and exited with its code (0); `docker start -a <id>` passed the container's stdout through (3 bytes) and exited with the container's exit code 3, after which `--rm` had removed it. `docker start -a <id>` after `docker rm -f <id>` exited 1 with `Error response from daemon: No such container: <id>`. `parsePs` reads `Service`, `State`, `Health`, `ExitCode` and `Image`, no `ID` (`cli/ready.ts` lines 18–46).
   - The only lock is `.pulse-init.lock`, held by `pulse init` (`cli/write-install.ts` lines 28 and 345–400). It is an exclusive create (`openSync(lockPath, "wx", 0o600)`, line 356) with the content `pid <pid>\nnonce <hex>\n` (line 353). On `EEXIST` it refuses (lines 358–362). Nothing removes a lock that a killed process left, so after a SIGKILL every later lock holder refuses. `docs/cli.md` lines 217–219 tell a person to check for a running `pulse init` and delete the file.
   - `pulse down` runs `docker compose <prefix> down` (`cli/lifecycle.ts` lines 148–154). It only acts on Compose containers of the project, never on a container started with `docker run`.
   - Volumes carry the label `io.github.lorenzh.pulse.install` with the install id (`INSTALL_LABEL`, `cli/render-compose.ts` line 9).
   - The helper image of `secrets-init` is `oven/bun:1.4.0-alpine@sha256:0723…437eb` (`common/services.yaml` line 66). Its busybox 1.37.0 has `sync [-df] [FILE]...`. `sync -f /to` exits 0 on a directory and 1 on a missing path (checked in this run with `docker run --rm --network none` of that digest). `sync -f` calls `syncfs(2)` on the filesystem of the path; Linux 5.8 and later return writeback errors from it.
6. **Pins today.** `common/services.yaml` pins all five pulse images to `0.1.0` (lines 8, 16, 25, 35 and 44). The deploy rule is that no other file holds a version or digest of a pinned image, also not a script, test or workflow (`AGENTS.md` "Rules", first bullet). `scripts/check-setup.sh` checks the shape of each pin (line 36).
7. **How the api applies a create.**
   - Token names are not unique: `api_tokens.name` is `TEXT NOT NULL` with no unique index (api `src/migrations.ts` lines 75–85). Two creates with the same name make two tokens.
   - Creates are not serialized like rotates. A rotate meets the overlap rule (`409`, fact 1), a create meets no such rule.
   - `create` awaits the whole body (`await readText(req)`, api `src/token-routes.ts` line 232), validates it and then calls `store.create` (lines 225–259). The api reads a body when its event loop gets to that connection. Nothing orders that read against requests on other connections. So a create whose client process has already ended can still be applied after the api has answered a later request on another connection, for example the token list of a sweep. Only the end of the api process ends that possibility (decision 8 "Barrier").
   - Only the api process writes the token store, `/data/pulse.db` on the `api-data` volume (fact 8). The api runs as the container's main process (api `Dockerfile` line 19, `CMD ["bun", "--no-env-file", "src/main.ts"]`). A stopped container has no process left, including every `docker compose exec` process in it. SQLite rolls back a transaction that was not committed when the database is opened again.
   - **Auth comes first, the body later.** Admin routes authenticate the bearer when the request starts (`adminAccess`, api `src/admin-auth-throttle.ts` line 90). A failed authentication answers `401` for an unknown, expired, revoked or retired secret (`src/admin-auth-failures.ts` lines 35–38), before any route reads metadata. So a revoked or expired token's secret gets `401` also for `GET /admin/tokens/<its own id>` and for `/admin/tokens/self`. After the authentication, `create` awaits the body (`src/token-routes.ts` line 232) and then creates the token for that caller without authenticating again (lines 240–251). A revoke of the caller's token, or of any other token, that commits while the create awaits its body does not stop the create.
     - **What a `401` says about a known secret.** `authenticate` (api `src/token-store.ts` lines 322–337) answers `unknown` when the secret's digest is not in the credential index, and `inactive` when the credential is retired (a previous secret after its `previousValidUntil`, lines 330–332) or the token is expired. A revoke removes every credential of the token from the index in the same call (lines 315–318), and a restart loads only tokens with `revoked_at IS NULL` (line 164). A rotate by any caller that holds the token's scopes sets `retires_at` on the current secret (line 283), so that secret answers `401` once the overlap has ended, while the token stays active. `adminAccess` also answers `401` for a secret shorter than 32 characters (`src/admin-auth-failures.ts` lines 48–49). So a `401` for a secret that the CLI holds has four possible causes: the token was revoked, it expired, **another client rotated it and the overlap has ended**, or the text is not that token's secret. Only the first two are final. The CLI cannot tell them apart with that secret, because the api shows no metadata to it. The eleventh plan review reproduced the third cause with the real token store: the old credential answered `401`, the new one worked, and `revokedAt` and `expiresAt` were null. **So the CLI never reads a `401` as a confirmation of anything. A `401` only ever stops it** (decision 8).
     - **Revocation and expiry are final.** Nothing clears `revoked_at` (`grep -rn 'revoked_at = NULL' src` has 0 matches), and no route changes `expiresAt`. So a readback `gone` (`revokedAt` set, or `expiresAt` passed) that an authenticating, independent bearer received stays true.
   - **A pending `exec` client.** Like a `docker run` client (fact 5), a `docker compose exec` client of a killed CLI can reach the daemon after any later step, including a stop and start of the api container (reproduced in the ninth plan review). Its process then runs in the restarted container. A container's process 1 is new after each start: in this run, `docker run -d --user bun` of the pinned `oven/bun` image, then `docker exec` reading `/proc/1/stat` field 22 as uid 1000 printed `1129985`; after `docker stop` (then `State.Running` false, `State.Pid` 0) and `docker start` it printed `1130212`. `/proc/sys/kernel/random/boot_id` was the same both times. The api image runs as `USER bun` (api `Dockerfile` line 15) and the rendered api service sets no `init` (no `init:` key in deploy `cli/render-compose.ts` or `common/services.yaml`), so process 1 is the api server itself. The fence of decision 4 does not depend on that: with an init process, process 1 is still new after each start.
8. **Where the services keep their data.**
   - The images set the data paths: api `PULSE_DB=/data/pulse.db` (api `Dockerfile` line 9), notify `PULSE_NOTIFY_STATE=/data/notify-state.json` (notify `Dockerfile` line 9), console `PULSE_CONSOLE_DB=/data/console.db` (console `Dockerfile` line 9). Probe and status keep no data.
   - The CLI renders `api-data:/data` (`cli/render-compose.ts` line 153), `notify-data:/data` (line 207) and `console-data:/data` (line 220). Every other mount of a pulse service is read-only: the `*-secrets` volumes at `/run/pulse` and the `./config/*` binds (lines 153, 175, 207, 220).
   - `compose.override.yaml` may change mounts. Compose merges service volumes by target, so an override entry for `/data` replaces the rendered one while the top-level `api-data` stays declared.
   - Mounts are not only in `volumes`. Compose keeps the service keys `tmpfs`, `configs`, `secrets` and `volumes_from` apart. Checked in this run with Compose v2.40.3 (`docker compose config --format json`, base file with `api-data:/data` on `api`, plus an override):
     - `tmpfs: ["/data/"]` prints `"volumes":[{"type":"volume","source":"api-data","target":"/data","volume":{}}],"tmpfs":["/data/"]`; `tmpfs: "/data/x:size=1m"` (a string) prints `"tmpfs":["/data/x:size=1m"]`; `tmpfs: ["/data//"]` prints `"tmpfs":["/data//"]`; `tmpfs: ["/srv"]` prints `"tmpfs":["/srv"]`. Without the key it prints `"tmpfs":null`.
     - `tmpfs: ["/data"]` and `["/data:size=1m"]` fail the config call itself with `services.api.volumes[0]: target /data already mounted as services.api.tmpfs[0]` on this Compose version. The eighth plan review saw `["/data"]` kept next to the volume, so another Compose version accepts it; the CLI must not rely on Compose to refuse it.
     - `configs: ["data", {source: other, target: /data/pulse.db}]` prints `[{"source":"data"},{"source":"other","target":"/data/pulse.db"}]`: a config without `target` is mounted at `/<source>`, here `/data`. `secrets: ["data"]` prints `{"source":"data","target":"/run/secrets/data"}`. `volumes_from: ["notify"]` on `console` prints `"volumes_from":["notify"]`.
     - Which of two nested mounts wins is an engine detail: with `tmpfs: ["/data/"]` and Docker 29.9.2, `docker compose run` showed both mounts at `/data` in `/proc/mounts` and a write landed in the volume. The CLI does not rely on that order.
     - `scripts/check-setup.sh` rule 8 (lines 128–145) already checks these keys for `/run/pulse`: it reads `volumes`, `configs`, `secrets` and `tmpfs` (array or string, options after `:` cut off) and normalizes each path with `def norm` (line 131: empty and `.` parts dropped, `..` removes the previous part, `/var/run` mapped to `/run`). Its tests use `/run//pulse`, `/run/pulse/x:size=1m` and `/tmp/../run/./pulse/` (`scripts/check-setup.test.sh` lines 98–105).
   - The guard requires every top-level volume to be named `<project>_<key>` and not external (`checkNames`, `cli/docker.ts` lines 326–345). It does not look at service mounts.
   - The guard's volume step (`checkVolumes`, `cli/docker.ts` lines 413–447) inspects each declared volume and refuses one whose labels `io.github.lorenzh.pulse.install` and `com.docker.compose.project` are not this install's. A declared volume that does not exist is skipped (`no such volume` → `continue`, lines 432–434). So the guard passes after `pulse init` without `pulse up`, and after a `down` that removed the volumes.
   - `docker run -v <name>:<path>` creates a named volume that does not exist, with no labels. Checked in this run with Docker 29.9.2: `docker run --rm --network none -v <new name>:/from:ro <secrets-init image> true` exited 0, and `docker volume inspect --format '{{json .Labels}}'` of that name then printed `null` (the test volume was removed afterwards). A service that starts on such a volume sees an empty store, and the guard refuses it on the next command because its labels are missing.

- **deploy only**:

  - the three commands in `cli/`, with shared seams extracted from existing code;

## Non-goals

- `pulse backup` (a later item). The upgrade's internal safety snapshot is not a public backup command.
- Self-update of the CLI binary.
- Rotating tokens that the installation does not manage itself: remote probe tokens, the `status` and `notify` service tokens, and tokens created in the console.
- Upgrading third-party images (`oven/bun`, `alpine/openssl`, `axllent/mailpit`) and `dev` source builds.
- Downgrades through `pulse upgrade`. Prereleases are never chosen.
- Automatic resume of an upgrade that was killed hard (SIGKILL, power loss). The next run refuses and the docs give the manual steps (decision 13).
- Changes to api, probe, console or any other service.

## Decisions

1. **Supported installations.** The commands work on directories with `pulse.json` format 1 written by `pulse init`. They reuse the guard of `up`, `down` and `status` (`resolveProject`, `cli/docker.ts` lines 453–474), with the same `--dir` default `.` and the same exit codes (0 ok, 1 failed, 2 usage, 3 Docker missing, 130 interrupted). No new metadata goes into `pulse.json`.
   - The standalone repository setups (`minimal/`, `full/`, `demo/`, `dev/` with `scripts/init-secrets.sh`) are out of scope. The standalone `demo/` generates its tokens inside volumes (`PULSE_SECRETS_MODE=generate`). The docs say so.
2. **Pins.** The deploy child bumps the pins with `scripts/bump-images.sh api=0.1.1 probe=0.1.1 status=0.1.1 notify=0.1.1 console=0.1.1`. If `main` already pins `0.1.1` or later when the task starts (for example after #692), it skips the bump and records that in the PR. No other file gets a version or digest. The upgrade test does not depend on the pins (acceptance 2).
3. **One mutation lock.** `pulse init`, `pulse token rotate` and `pulse upgrade --yes` share the existing lock file `.pulse-init.lock` (exclusive create `wx` 0600, fact 5). The release rule stays: the holder removes the file only when its content is still the content it wrote.
   - The name stays, so an older CLI's `init` still excludes a running rotation or upgrade.
   - `up`, `down`, `status` and `logs` take no lock.
   - **Content.** Five lines: `pid <pid>`, `nonce <32 hex>`, `host <hostname>`, `started <identity>` and `command <init|token rotate|upgrade>`. `<hostname>` is `os.hostname()`. `<identity>` is the process identity below for the CLI's own pid.
   - **Identity.** A text that names one process for its whole life and does not depend on the environment of the reader. The lock never runs `ps` and never formats a time: `ps -o lstart=` prints local time in the reader's time zone and locale, so the same live pid gave two texts under `TZ=UTC` and `TZ=America/New_York` in this run. procps also derives that time from the boot time in wall-clock terms, so it can move when the wall clock is stepped (not tested in this run).
     - **Linux** (`process.platform === "linux"`): `linux:<boot>:<pidns>:<ticks>`.
       - `<boot>` is the content of `/proc/sys/kernel/random/boot_id`, trimmed. It must match `^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$`.
       - `<pidns>` is the decimal inode in `readlink /proc/self/ns/pid` (`pid:[4026533036]` in this run). It must match `^pid:\[([0-9]{1,20})\]$`.
       - `<ticks>` is field 22 (`starttime`, clock ticks since boot) of `/proc/<pid>/stat`, parsed by `startTicks` (Reuse; the api instance of decision 4 uses the same function). The CLI takes the text after the last `)` (the command name in field 2 may hold spaces and parentheses), splits it on single spaces and takes index 19 (field 22 minus the 3 fields up to and including the name). It must match `^[0-9]{1,20}$`. In this run the same pid gave `835098` under `TZ=UTC` and under `TZ=America/New_York` with `LC_ALL=C`, and a `node` read of its own `/proc/<pid>/stat` with index 19 gave `861731`, equal to `awk '{print $22}'` of the same file.
       - The three values come from the kernel and do not change with `TZ`, the locale, the user or a step of the wall clock. Any read or match failure makes the identity `-`.
     - **Other systems** (macOS): the identity is `-`. The CLI cannot read a start time there without `ps`, and it does not run `ps`.
     - `-` is a valid identity. It only removes the pid-reuse test below.
   - **Order.** The lock is taken first, before the guard and before the rotation journal or `upgrade.json` is read. The reconcile (decision 8), the barrier, the helper sweep (decision 13) and every recovery run only under the lock, also after a stale lock was broken.
   - **Stale lock.** On `EEXIST` the CLI reads the lock (`lstat`: a regular file, not a link, at most 1 KiB). The lock is *stale* only when it has all five lines in that order with valid shapes (`started` is `-` or the Linux form), `host` equals `os.hostname()`, and one of these rows holds. The CLI computes its own identity first; "own" below means the reader's values.

       | Lock `started` | Own identity | Stale when |
       | --- | --- | --- |
       | `linux:B:N:T` | `linux:B:N:…` (same boot, same pid namespace) | `process.kill(pid, 0)` throws `ESRCH`; or the pid runs and its `<ticks>` read now is a valid number other than `T` (the pid was reused). An unreadable `/proc/<pid>/stat` while the pid runs is not stale. |
       | `linux:B:N:T` | `linux:B:M:…` with `M` ≠ `N` | never: the holder ran in another pid namespace (for example a container), so the pid means nothing here |
       | `linux:B:…` | `linux:C:…` with `C` ≠ `B` | always: the host was rebooted since the lock was written, so its process has ended |
       | `linux:…` | `-` | never |
       | `-` | `linux:…` | never: the lock does not say which pid namespace its pid belongs to |
       | `-` | `-` (macOS, or a Linux whose `/proc` reads fail) | `process.kill(pid, 0)` throws `ESRCH`. A running pid is never stale, because reuse cannot be told apart. |

     - `EPERM` from `process.kill` means the process runs. Any doubt means "not stale".
     - The judgement reads only the lock file, `os.hostname()`, `process.kill` and the three `/proc` paths. It reads no environment variable and spawns no process. So two readers with different `TZ`, `LC_ALL` or `LANG` judge a lock the same way.
     - The reboot row relies on `host`: two machines that share one install directory under the same hostname are not supported (Risks).
   - **Break.** A stale lock is removed only under the second lock file `.pulse-init.lock.break` (`wx` 0600, content `pid` and `nonce`):
     1. Create `.pulse-init.lock.break`. `EEXIST` refuses with `another pulse command is starting in <dir> (or remove .pulse-init.lock.break if none is)`.
     2. Read `.pulse-init.lock` again. It must be byte-equal to the content that was judged stale; otherwise remove the break file and refuse as "not stale".
     3. Unlink `.pulse-init.lock`, create the own lock with `wx` (an `EEXIST` here means another command took it in between: remove the break file and refuse), fsync the directory.
     4. Remove `.pulse-init.lock.break` and print `removed a stale .pulse-init.lock (pid <pid>, <command>)`.
     - So at most one process holds the lock: every holder created it with `wx`, and a breaker only unlinks the exact content it judged stale, while it holds the break file.
   - **Refusal.** A lock that is not stale refuses with exit 1 and `another pulse command is running in <dir> (or remove .pulse-init.lock if none is)`. When the lock has the five lines, a second line names `pid <pid>, <command>, host <host>`. An old two-line lock of an older CLI is never stale; the refusal is the same.
   - **Docs.** `docs/cli.md` "A stale `.pulse-init.lock`" (lines 217–219 today, only about `pulse init`) is rewritten: the three commands that hold the lock, the automatic break with its conditions, the manual way when the CLI refuses (`ps -ef | grep -E 'pulse (init|token|upgrade)'` must print no such command for this directory, on this host and any other host that shares it; then delete `.pulse-init.lock` and a left `.pulse-init.lock.break`), and that the interrupted command is then run again: a rotation resumes from its journal, an upgrade refuses and names the recovery (decision 13).
4. **Private transport to the api.** Every api call runs `docker compose <operation prefix> exec -T api bun -e <API_SCRIPT>`.
   - `API_SCRIPT` is a constant text. Its stdin carries one JSON line `{"method","path","bearer","body"}`.
   - The script calls `http://127.0.0.1:3000<path>` with a 10 s timeout and `redirect: "error"`. It prints the status code on line 1 and the body, capped at 1 MiB, after it.
   - The script ends itself. Besides the fetch timeout it starts an `unref`'d timer that calls `process.exit(70)` 11 s after the script starts. So the process in the container ends within 11 s even when the client was killed (killing `docker compose exec` does not end it, fact 5). The end of this client process says nothing about the api server: an unanswered write is settled only by the barrier of decision 8.
   - **Instance fence.** A write must never run in an api container run other than the one the CLI checked before it (fact 7 "A pending `exec` client").
     - **Instance.** The *api instance* is `<boot>:<ticks>`: `<boot>` is `/proc/sys/kernel/random/boot_id` (trimmed, the shape of decision 3) and `<ticks>` is field 22 of `/proc/1/stat`, both read inside the api container. `<ticks>` is parsed by `startTicks(statText)`, one exported pure function in `cli/lock.ts` that decision 3 also uses (text after the last `)`, split on single spaces, index 19, `^[0-9]{1,20}$`). `API_SCRIPT` embeds its source with `String(startTicks)`, so there is one implementation. Any read or match failure gives the instance `-`.
     - **Output.** The script prints `instance <value>` as line 1, before anything else; the status code moves to line 2 and the body follows.
     - **Fence.** The stdin line gets a field `instance`. For `GET` it is `null` and ignored. For `POST` it must be a string equal to the instance that the script has just computed, and not `-`. Otherwise the script prints `instance <value>` and `fenced` and exits 71 **before any network call**. The compare runs after the script has started, so a script that a pending client starts after a restart sees the new instance and refuses.
     - **Which instance a write carries.** The instance printed by the CLI's previous api call in the same run (a capability check, readback, sweep list or the barrier's check read). The CLI never sends a `POST` without one, and a value `-` refuses the command before the first write with `cannot read the api instance; see docs/cli.md#token-recovery`.
     - **Answer class.** For a rotate or create `POST`, `fenced` (exit 71 with the line `fenced`) is classed `ambiguous` (decision 8): the CLI does not trust the line alone, so the barrier runs. For a revoke `POST` it is an unconfirmed revoke, which the readback of decision 7 step 6 decides; a revoke needs no barrier.
     - Why this closes the gap: a script runs either in the container run in which the CLI read the instance or in a later one. In the first case the barrier's stop ends it with the api (fact 7). In the second case its instance differs and it sends nothing. This holds however late the client reaches the daemon, and also across later `pulse up`, `pulse down` and upgrades.
   - No bearer, secret or digest of a secret is ever in argv, the environment, `compose.yaml`, the journal, a diagnostic or normal output.
   - The spawn seam gets an `input` option that writes the text to stdin and closes it. stdin stays `ignore` when `input` is absent.
5. **Capability detection.**
   - `GET /admin/tokens/self` with `secrets/admin-token` must answer `200` with an object whose `id` matches `^tok_[0-9a-f]{24}$` and whose `scopes` include `admin`.
   - `404` means an api without the token store. The CLI refuses with `the api has no token store (pulse-api 0.1.1 or later); run pulse upgrade first`.
   - `401`, `403` and `429` are named as such.
   - This check runs before any token changes. A resume runs it too, with the bearer that decision 8 names for the item's state, after the reconcile and after the barrier (decision 8 "Resume order").
6. **Which tokens `admin` and `probe` mean.**
   - `admin` is the token that `secrets/admin-token` authenticates as, so its id comes from `/admin/tokens/self`.
   - `probe` means every locally managed probe location. The locations are the comma list `PULSE_PROBE_LOCATIONS` of the `secrets-init` service in the resolved Compose configuration. Each location needs exactly one pulse.json service whose resolved `environment.PULSE_LOCATION` equals it (`probe` in minimal/full, `probe-<loc>` in demo) and a host file `secrets/probe-token-<loc>`. Anything else refuses.
   - A `secrets-init` whose `PULSE_SECRETS_MODE` is set and not `files` refuses.
   - For each location, the CLI reads `GET /admin/tokens`. The candidates are tokens whose `scopes` are exactly `["probe"]`, whose `location` equals the location, with `revokedAt` null and `expiresAt` null or in the future.
     - Exactly one candidate is used.
     - None refuses.
     - Several candidates refuse and list each candidate's `id` and name (the name through `shown()`), unless `--location <loc> --id <tok_…>` selects one.
     - A candidate whose `previousValidUntil` is in the future refuses: `token <id> is still in its rotation overlap until <ISO time>; run again after it`. The exception is a resume from the journal (decision 8).
   - Every refusal happens before the first api write. Rotation keeps the id, scopes, location and expiry. It never revokes and recreates the token, except for the lost answer of decision 8.
7. **Order of one rotation item.** For one token, with consumer service C (admin: `console` when present, else none; probe: the location's probe service). Each step writes its journal state (decision 8) before its first side effect, so a rerun knows where it stopped.
   1. **Preflight of the whole command.** Lock, guard, file checks (decision 9), capability, the token and candidate selection for every item, and every consumer service running and ready with exactly one container. For a probe item, the id of that one container (`docker compose ps --all --no-trunc --format json`, field `ID`) is recorded as `oldContainerId`. Only then does the first api write go out.
   2. **Rotate.** Journal `requested` (token id and its `rotatedAt` as read in the preflight) with `inFlight: "rotate"`, then `POST /admin/tokens/<id>/rotate`. Its outcome goes through the table of decision 8 "Rotate outcome", which is the same for the first run and the resume. Only the row `ok` continues straight to step 3.
   3. **Stage and save.** The host file changes only through a rename, and only after the journal names the token whose secret it gets:
      1. **Stage.** Write the received `secret` and a newline to the staging file `secrets/.pulse-next.<file>.<id>`. `<file>` is the host file name (`admin-token` or `probe-token-<loc>`) and `<id>` is the id of the token that the answer belongs to: `tokenId` after a rotate, the created id after a create. The write is the safe write (temp name `.<name>.tmp-<hex>` `wx` 0600 in `secrets/`, the `atomicWrite` pattern of `cli/write-install.ts` lines 279–296, then fsync, rename to the staging name, fsync of the directory).
      2. Journal `staged` with `activeTokenId := <id>` and `inFlight: null` (the `POST` was answered, decision 8 "Barrier").
      3. **Install.** Rename the staging file over the host file and fsync the directory.
      4. Journal `saved`.
      - So the journal state alone says what the host file holds: in `requested` and `replacing` it holds the pre-rotation secret of `tokenId`; from `saved` on it holds the secret of `activeTokenId`. In `staged`, the existence of the staging file says whether step 3 ran (a rename is atomic, and nothing else removes a staging file). Decision 8 "Reconcile" uses exactly this.
      - **Errors in this step.** The CLI never decides from the error which write did or did not land. Any error from the first write of step 1 to the end of step 4 is handled as decision 8 "Stage errors" says: the in-process reconcile, from the files on disk. Example: the rename to the staging name succeeds and the directory fsync after it throws. The staging file exists, so the reconcile takes the `requested` row and the item goes to `staged`, not to `replacing`.
   4. **Refresh.** For a replacement (`replacementName` set), the post-check of decision 8 "Lost answer" step 4a runs first. Then journal `refreshing`, then `docker compose <prefix> run --rm --no-deps -T secrets-init` must exit 0. Then journal `refreshed`.
   5. **Switch.**
      - **Probe**, start-new-then-stop-old:
        1. Journal `handoff` with `oldContainerId` and `newContainerId: null`.
        2. `docker compose <prefix> up -d --no-deps --no-recreate --scale <svc>=2 <svc>`.
        3. The new container is the one container of the service whose id is not `oldContainerId`. Journal `handoff` with its id as `newContainerId`.
        4. Wait (bounded by `--timeout`, default 120 s) until the new container answers `/readyz` 200 through `docker exec -i <id> bun -e <script>`.
        5. Check that its `/run/pulse/probe-token` equals the new secret. The check runs inside the container, the expected secret goes in on stdin, the script compares with `timingSafeEqual`, and it prints only `same` or `different`. The check has a 10 s kill bound.
        6. Keep the old container running for 2000 ms more. The new probe's first run starts within 1000 ms of its scheduler start (fact 3), so its first result is earlier than the old probe's stop.
        7. `docker stop --time 10 <old id>`, then `docker rm <old id>`.
        8. Afterwards the service has exactly one container, `newContainerId`.
      - **Admin**:
        1. Check that the new secret answers `GET /admin/tokens/self` `200` with `activeTokenId`.
        2. When the console exists: journal `handoff`, then `docker compose <prefix> up -d --no-deps --force-recreate console`, then wait for its readiness (reuse `waitReady` with that one service).
        3. Run the same in-container equality check on `/run/pulse/admin-token`. Then let the console container read its own file and call `GET http://api:3000/admin/tokens/self`. It must answer `200` with `activeTokenId`.
   6. **Revoke (only after a replacement, decision 8).** Journal `revoking`, then `POST /admin/tokens/<revokeTokenId>/revoke` with the new secret of the host file as bearer for `admin` and the admin secret for `probe`. The revoke guard (decision 8) runs first. The step is done when the answer is `200`, or when any other answer is followed by `GET /admin/tokens/<revokeTokenId>` showing a non-null `revokedAt`.
   7. **Done.** Journal `done`, and print `rotated <admin|probe <loc>> token <activeTokenId>; two probes ran for <ms> ms; the old secret works until <previousValidUntil ISO>` (the middle part only for a probe). `<ms>` is the two-probe window W of Performance impact item 2 as Docker records it: `State.FinishedAt` of the old container minus `State.StartedAt` of the new one, both read with `docker inspect` after `docker stop` and before `docker rm`. On a resume where the old container is already gone, the part reads `two probes ran for an unknown time`.
   - API, status and notify never restart for either kind. The probes do not restart for `admin`. The console does not restart for `probe`.
   - Probe locations rotate one after another, so at most one extra probe container runs at a time.
   - The command returns after the switch. It does not wait for the 10-minute overlap: expiry is the api's job.
8. **Journal and recovery.**
   - **File.** `secrets/.pulse-rotation.json` (0600, written atomically with fsync like the secret files) holds `{format:1, kind, items:[…]}`. Each item has `tokenId`, `location?`, `file`, `service?`, `name`, `scopes`, `expiresAt`, `rotatedAtBefore`, `oldContainerId?`, `newContainerId?`, `activeTokenId?`, `revokeTokenId?`, `replacementName?`, `inFlight` (`null`, `"rotate"` or `"create"`; decision 8 "Barrier"), `inFlightInstance` (the api instance of decision 4 that the marked `POST` carries, or `null`), `lastAdminKept` (boolean, decision 8 "Lost answer" step 4a "Last admin") and `state`. It never holds a secret. `lastAdminKept` may be `true` only in an `admin` journal, in an item with `replacementName` set, from `refreshing` on. `dropping-orphans` and `dropping-replacement` need `replacementName` and `activeTokenId` set. `inFlight` `"rotate"` is valid only in `requested`, `"create"` only in `replacing`, and every other state has `null`. `inFlightInstance` is a string of the instance shape exactly when `inFlight` is not `null`. Token ids must match `^tok_[0-9a-f]{24}$`, container ids `^[0-9a-f]{64}$`, and `state` one of the states below; a journal that breaks a rule refuses with its path and the rule. The file is removed when every item is `done`.
   - **Staging files.** `secrets/.pulse-next.<file>.<id>` (decision 7 step 3) hold one secret each, never in the journal. The name must match `^\.pulse-next\.(admin-token|probe-token-[a-z0-9][a-z0-9-]{0,31})\.(tok_[0-9a-f]{24})$`. Items run one after another, so at most one staging file exists, and only for the item that is in `requested`, `replacing` or `staged`.
   - **States**, in order: `requested` → (`replacing` →) `staged` → `saved` → (`dropping-orphans` → `dropping-replacement` →) `refreshing` → `refreshed` → `handoff` → `switched` → (`revoking` →) `done`. The two `dropping-*` states belong to the drop path of "Lost answer" step 4a. They end with the removal of the item; the only way from `dropping-replacement` to `refreshing` is the last-admin rule of that step. Every state is written and fsynced before the side effect that it names. A state never moves back; in particular an item never returns to `replacing` once it was `staged`. An item enters `replacing` only after a reconcile of that item found no staging file for it (from `requested` through the lost-answer rule; never straight from an error).
   - **Owned files.** The host file of an item (its `file`) is owned by the journal. In an `admin` journal that is `secrets/admin-token`. In a `probe` journal it is each item's `secrets/probe-token-<loc>`, and `secrets/admin-token` is owned by no item: no step of a probe rotation writes, stages or renames it.
   - **Reconcile.** It is the first step of every resume and of every stage error (below). It runs before any api write and before any owned host file is read as a bearer. Its only api calls are the read-only confirmations of the `replacing` row. It reads the journal from disk, never from memory, so the in-process run and a rerun take the same path. Validation order:
     1. Read and validate the journal (decision 8 "File"). A bad journal refuses before anything else.
     2. Delete every leftover safe-write temp file in `secrets/` whose name is `.<name>.tmp-<hex>` for a host file, a staging file or the journal. Its content counts as not stored. Then fsync `secrets/`. If that fsync fails, exit 1 with the journal as it is on disk; nothing else is done.
     3. List the staging files. Match each one against the table below **without any api call**, by the journal state of its item, its `<file>` and its id only. Each staging file must pass the name rule and the file checks of decision 9. It must also belong to an item of the journal: in a `probe` journal an `admin-token` staging file, and in an `admin` journal a `probe-token-*` staging file, match no row. A staging file that matches no row refuses with exit 1, its path, and `docs/cli.md#token-recovery`; nothing is changed and no api call is made.
     4. Only the `replacing` row with a staging file needs a confirmation from the api. The bearer depends on the kind:
        - **admin.** The bearer is the staged secret itself, read from the staging file that passed step 3. A staging file is not a host file.
        - **probe.** The bearer is `secrets/admin-token`. It is the one host file that the reconcile may read, because no item of a probe journal owns it (see "Owned files"), so no earlier or later reconcile action changes it. The order is fixed, and a failed step refuses before the next one:
          1. the staging checks of step 3 have passed (no api call so far);
          2. `lstat` of `secrets/admin-token`: a regular file, not a link, no group or other bits (decision 9);
          3. the read of `secrets/admin-token`, then `tokenContentValid` on its content;
          4. the capability call of decision 5 with that content as bearer: `GET /admin/tokens/self` answers `200` with the `admin` scope;
          5. the confirmation `GET /admin/tokens/<X>` with the same bearer.
          The file must be read before the capability call, because that call needs its content.
        - A confirmation that does not answer as the row says (another status, another id or name, `revokedAt` set) refuses with exit 1 and nothing changed.
     5. Act on the matched rows, one item after another, in journal order.

        | Journal state of the item | Staging file | Meaning | Action |
        | --- | --- | --- | --- |
        | `requested` | `.<file>.<tokenId>` | the rotate answer was stored, the `staged` write was lost | journal `staged` with `activeTokenId := tokenId`, then install and journal `saved` |
        | `replacing` | `.<file>.<X>`, X ≠ `tokenId`, and the api confirms X (step 4): for `admin`, `GET /admin/tokens/self` with the staged secret answers id X and name `replacementName` (this works also after the old secret's overlap); for `probe`, `GET /admin/tokens/<X>` with `secrets/admin-token` shows name `replacementName` and `revokedAt` null | the create answer was stored, the `staged` write was lost | journal `staged` with `activeTokenId := X`, then install and journal `saved` |
        | `requested`, `replacing` | none | no answer was stored | the rules below (`rotatedAt` check, lost answer) |
        | `staged` | `.<file>.<activeTokenId>` | the install did not run | install, journal `saved` |
        | `staged` | none | the install ran, the `saved` write was lost | journal `saved` |
        | `saved` or a later state | none | normal | nothing; resume by state |
        | any state | a staging file that matches no row above (another id, another file, a second staging file, or any staging file from `saved` on) | inconsistent | refuse |

     - "Install" in the table is the rename of decision 7 step 3.3 and the fsync of `secrets/`. Each journal write in the table is fsynced like every state. If any of them fails, the reconcile exits 1. It does not retry and does not move to another row. The journal on disk then names the row that the next reconcile takes.
     - Only after the reconcile does the CLI read an owned host file as a bearer. That file then holds what the state says (decision 7 step 3). The one host file that the reconcile itself reads is `secrets/admin-token` in a `probe` journal (step 4), which no item owns.
   - **Stage errors (first run and resume).** An error anywhere in decision 7 step 3 (a thrown write, fsync, rename or directory fsync, or a journal write) is not a lost answer by itself. The CLI drops the copy of the answer's secret that it holds in memory and runs the reconcile for the journal at once, in the same process.
     - The reconcile finds a staging file for the answer's id: the `requested` or `replacing` row moves the item to `staged` and installs. The run then goes on at the refresh.
     - The reconcile finds no staging file: no answer is stored. From `requested`, the lost-answer rule applies (`replacing`). From `replacing`, the created token is unheld: "Lost answer" goes back to its step 2, within the limit of two create `POST`s per item and run. The journal on disk still names `inFlight: "create"` (only the `staged` write clears it), so the barrier runs first, and then the sweep revokes the token. The barrier is not needed for an answered create, but the CLI decides from the journal on disk, as a rerun would.
     - The item is `staged` or later: the rows `staged` or `saved` apply.
     - The reconcile itself fails (for example the fsync of `secrets/` throws again): exit 1, journal kept. The rerun's reconcile decides from the same files.
     - Going from an error in step 3 straight to `replacing` is wrong (Counterexamples "Stage boundary"). The staging file may exist, and the table refuses `replacing` with a staging file of `tokenId`.
   - **Resume order.** Every rerun with a journal runs these steps under the lock, in this order:
     1. the reconcile (above);
     2. the barrier ("Barrier" below), when the journal on disk names `inFlight` for an item (at most one item, because items run one after another);
     3. the capability check of decision 5, with the bearer of the item's state;
     4. the item's step by its state (below).
     - The barrier reads no token file and sends no bearer: its only api call is `GET /readyz`. So it runs whether or not any bearer still authenticates, and the CLI never exits because of a `401` (step 3 or later) while `inFlight` is set on disk.
     - A resume exits with `inFlight` still set in only two cases. One is a failed barrier, whose message says to run the command again. The other is a refusal of the reconcile, which comes before the barrier. That refusal happens only when a staging file exists or the journal is invalid, and a staging file belongs to a `POST` whose answer was parsed (decision 7 step 3).
     - The manual recovery ("Manual recovery" below) does not rely on this: it runs its own barrier first.
     - The first run follows the same order: the barrier comes before the readback after an unanswered `POST` ("Rotate outcome"), and a stage error runs the reconcile first ("Stage errors").
   - **Resume.** A rerun with a journal skips the overlap refusal for the items it names, rereads every item from the api, and resumes each item by its state:
     - `requested`: the class `none` of "Rotate outcome" below. When the journal names `inFlight: "rotate"`, the barrier runs first; then the CLI reads back the token and decides from that.
     - `replacing`: see "Lost answer" below. It starts at step 2, whose barrier runs when the journal names `inFlight: "create"`.
     - `staged`: handled completely by the reconcile; the item continues as `saved`.
     - `saved`: when `replacementName` is set, the post-check of "Lost answer" step 4a first. Then run the refresh (it is idempotent), then switch.
     - `dropping-orphans`, `dropping-replacement`: the drop path of "Lost answer" step 4a at the step that the state names, with the bearer rules there. No post-check runs again: `gone` is final (fact 7 "Revocation and expiry are final"), so the drop decision stands.
     - `refreshing`: run the refresh again, then switch. The post-check has passed, because `refreshing` is written only after it (or after the last-admin rule of the drop path, which sets `lastAdminKept`).
     - `refreshed`: switch.
     - `handoff` (probe): look at the containers of the service with `docker compose <prefix> ps --all --no-trunc --format json` and act on what is there. "Running" is `State` `running`.
       | Containers found | Action |
       | --- | --- |
       | only `oldContainerId`, running | scale to 2 as in step 5.2 |
       | `oldContainerId` running and exactly one other container X | `newContainerId` := X (journal), then continue at step 5.4 |
       | `newContainerId` running, `oldContainerId` stopped or gone | continue at step 5.4, skip the 2000 ms wait, then remove `oldContainerId` if it still exists |
       | `newContainerId` recorded but gone or not running, `oldContainerId` running | `docker rm -f` the recorded new id if it exists, journal `newContainerId: null`, scale to 2 again |
       | no running container of the service | `docker compose <prefix> up -d --no-deps <svc>`, take the one container as `newContainerId`, continue at step 5.4 (results stop until it is ready; the docs say so) |
       | more than one container other than `oldContainerId` | refuse with exit 1, list the ids, and point to `docs/cli.md#token-recovery` (remove the extra containers, run again) |
       - A `different` token in the new container stops and removes that container and runs the refresh once more. A second `different` exits 1 with the journal kept.
     - `handoff` (admin): run step 5 of admin again (the console recreate is idempotent).
     - `switched`: run the final sweep of "Lost answer" step 5 when `replacementName` is set, then go to `revoking` when `revokeTokenId` is set, else `done`. No barrier is needed here: `inFlight` is `null` from `staged` on.
     - `revoking`: step 6 again.
   - **Rotate outcome (one table for the first run and the resume).** The item is in `requested` and the reconcile found no staging file for it. The CLI never decides from the transport error alone whether the api rotated.
     - **Answer classes** of a rotate `POST`:
       - `ok`: `API_SCRIPT` printed status `200` and the body parses: `token.id` equals `tokenId`, `secret` matches `^pulse_[A-Za-z0-9_-]{43}$`, and `previousValidUntil` is a number later than the request start.
       - `rejected`: `API_SCRIPT` printed a complete answer with status `400`, `401`, `403`, `404`, `405`, `409`, `413` or `429` and a JSON body. These are the api's refusals. The api checks auth, the grant rule and the token state before it changes anything, and the rotate itself is one database transaction (api `docs/rest-api.md` lines 498–520, `src/token-store.ts` lines 266–294).
       - `ambiguous`: anything else. That includes a timeout, a broken pipe, a non-zero exit of `docker compose exec` without a status line, a `5xx`, any other status, and a `200` whose body does not parse.
       - `none`: no answer is known. This is the resume of a `requested` item, where the previous run may or may not have sent the `POST`.
     - **Barrier before the readback.** After `ambiguous`, and after `none` when the journal names `inFlight: "rotate"`, the barrier ("Barrier" below) runs before the readback. So the readback is final: a rotate that it does not show was not applied and never will be. After `rejected` the api has answered the `POST`, so no barrier is needed; the CLI writes `inFlight: null` with the next journal write of the item.
     - **Readback.** For every class except `ok`, the CLI reads `GET /admin/tokens/<tokenId>`. For `admin` the bearer is the host file `secrets/admin-token`. The reconcile has ended, and in `requested` that file holds the pre-rotation secret, which still works during the overlap of a rotation that landed. For `probe` the bearer is `secrets/admin-token` after its file checks (decision 9). The readback is classified by the first rule that matches, in this order:
       1. `gone`: `404`, or `200` with `revokedAt` not null, or `200` with `expiresAt` not null and not in the future. **Whatever `rotatedAt` says.** A token that is revoked or expired is never replaced: someone revoked it on purpose, or it ran out, and a replacement would undo that.
       2. `changed`: `200`, `revokedAt` null, `expiresAt` null or in the future, and `rotatedAt` differs from `rotatedAtBefore`;
       3. `same`: `200`, `revokedAt` null, `expiresAt` null or in the future, and `rotatedAt` equals `rotatedAtBefore`;
       4. `unknown`: anything else, including a timeout, a `401`, a `200` whose body does not parse, and a `200` whose `id` is not `tokenId`.
       - So `changed` always means "rotated and still active". A token that was rotated and then revoked (by another client, or by a person after the CLI's rotate landed) reads `gone`, **when the bearer still authenticates**.
       - **The bearer decides what can be seen** (fact 7 "Auth comes first"). The api answers `401` before it reads any metadata, so a readback whose bearer belongs to a revoked or expired token never sees `revokedAt`.
         - `probe`: the bearer is the admin secret, an independent token, so a revoked or expired probe token reads `gone`.
         - `admin`: the bearer is the pre-rotation secret of `tokenId` itself. A revoked or expired admin token, or one whose rotation overlap has ended, answers `401` and reads `unknown`, never `gone`. The CLI then exits 1 with `the admin token no longer authenticates (revoked, expired, or its rotation overlap ended); see docs/cli.md#token-recovery`, with the journal kept as it is (`inFlight: null` when a barrier ran), no `POST`, no create and no revoke. A rerun ends the same way: after its reconcile and barrier, its capability check (decision 5) answers `401` before any write. The way out is the manual recovery ("Manual recovery" below), the same for every journal state of an `admin` item. From `saved` on the host file holds R's secret, and the stop means that R's secret no longer authenticates: R was revoked, expired, or rotated by another client whose overlap has ended (fact 7). In every state the stop says nothing about `tokenId`: a rotate of `tokenId` may have landed with its answer lost, so it can be active with a secret that nobody in the installation holds.
     - **Table.**

       | Class | Readback | Meaning | Action |
       | --- | --- | --- | --- |
       | `ok` | not read | rotated, secret held | stage and save (decision 7 step 3) |
       | `rejected` | `same` or `gone` | the api refused, and the token is either unchanged or revoked or expired (also when it was rotated before it was revoked) | drop the item and every later item that is still `requested` from the journal (remove the journal when no item is left that is not `done`). Exit 1 with the status and a fixed text per status: `409` uses the api's reason from the readback (`in its rotation overlap until <ISO>`, `revoked`, `expired`). The host file is unchanged. |
       | `ambiguous` or `none` | `same` | the rotate did not happen and, after the barrier, cannot happen later | one more `POST` in this run (the first one after a `none`), again with `inFlight: "rotate"` written first, whose outcome goes through this table again. A second `ambiguous` + `same` in the same run exits 1 with the journal kept in `requested` and `inFlight: null` (its barrier has run). |
       | `ambiguous` or `none` | `gone` | the token was revoked or expired, possibly after a rotate that landed | as `rejected` + `gone`: drop, exit 1 with `token <id> was revoked or expired; no replacement was made`, the docs say to create a probe or admin token by hand. No create, no revoke. |
       | `rejected`, `ambiguous` or `none` | `changed` | the api rotated, the token is still active, and the answer is not held (or another client rotated it) | the lost answer below (`replacing`) |
       | any | `unknown` | not known | exit 1, journal kept in `requested` (with `inFlight: null` when the barrier ran or the class was `rejected`); the rerun reads back again |
     - A `rejected` + `changed` row means that another client rotated the token after the preflight read. An earlier `POST` of this item cannot be the cause: the barrier ran after every unanswered `POST` before the next one was sent. The lost-answer path recovers either way, because the CLI holds no secret of the new rotation.
     - The overlap refusal of decision 6 is skipped for a journal item. The table's `409` row is the only way an item in overlap ends the run.
     - A `POST` is sent at most twice per item and run.
   - **Lost answer.** It applies only in two cases. One is the row "→ `changed`" of "Rotate outcome", in the first run and on resume alike. The other is a stage error whose reconcile found no staging file for an `ok` answer ("Stage errors"): the api rotated and the secret is not stored. A staging error alone never triggers it, and neither does a transport error without a readback. A secret that is not in a staging file counts as lost, and a rotate `POST` is never repeated blindly.
     1. Journal `replacing` with `revokeTokenId := tokenId`, `replacementName` and `inFlight: null`: the name is the old name cut to 90 characters, a space, `r` and 6 random hex characters. `inFlight` is `null` because both entry cases follow an answered rotate or a barrier. The journal holds the name before the create, so a create that landed can be found again. The name stays the same for every create of the item.
     2. **Barrier, then sweep.** When the journal on disk names `inFlight: "create"`, the barrier ("Barrier" below) runs first. Then read `GET /admin/tokens`. Every token whose `name` equals `replacementName` and whose `revokedAt` is null is an orphan: this step runs only in state `replacing` after the reconcile found no staging file, and in that state no host file and no staging file holds a replacement's secret (decision 7 step 3). Revoke each orphan through the revoke guard. A revoke is confirmed by `200`, or by a readback `GET /admin/tokens/<id>` with `revokedAt` set. An orphan that is not confirmed revoked exits 1 with the journal kept in `replacing` and sends no create.
     3. **Check, then create.** Right before each create, after step 2 has run in this run, the CLI reads back the lost token `GET /admin/tokens/<tokenId>` (bearer as for the readback of "Rotate outcome") and classifies it with the same ordered rules:
        - `changed`: go on with the create.
        - `gone`: the lost token was revoked or expired after the CLI chose to replace it, for example by a person between two runs. Step 2 has just run with its barrier, so no replacement of the item is active. Drop the item as in the `gone` rows of "Rotate outcome" (exit 1, `token <id> was revoked or expired; no replacement was made`), with no create and no revoke. Creating the replacement here is wrong: it would make an active token for a location whose token was revoked on purpose.
        - `same` or `unknown`: exit 1 with the journal kept in `replacing` and `inFlight: null`, no create. (`same` cannot follow a `changed` readback, because `rotatedAt` never goes back; it is treated as a fault.)
        - The check is a readback of the item, so the order rule below applies: it never runs while `inFlight` is set and no barrier has run.
        - For `admin` the bearer is the pre-rotation secret of `tokenId` itself. When that token was revoked, the call answers `401`, which is `unknown`: exit 1 with `the admin token no longer authenticates` and no create, and the manual recovery below is the way out with another admin token. In that case the sweep of step 2 already answered `401` too (same bearer), so the run has exited there.
        - This check narrows the window but cannot close it: the api authenticated the create when the request started and creates after it has read the body (fact 7), so a revoke of `tokenId` can commit after this check and before the create. Step 4a handles that.
        Then journal `replacing` with `inFlight: "create"` (durable), then `POST /admin/tokens` with `{name: replacementName, scopes, location?, expiresAt?}` of the lost token. For `admin` the bearer is the host file, which in `replacing` still holds the pre-rotation secret of `tokenId` (valid until the lost rotate's `previousValidUntil`). For `probe` it is the admin secret. The answer is classed like a rotate answer: `ok` is a `201` whose body parses (`token.name` equals `replacementName`, the secret rule), `rejected` is a complete answer with a status from the `rejected` list, and anything else is `ambiguous`.
        - `ok`: step 4 (its `staged` write sets `inFlight: null`). If a stage error's reconcile then finds no staging file for the created id, the created token is unheld: back to step 2, whose barrier and sweep revoke it.
        - `rejected`: the api answered and made no token (fact 1: it refuses before any change). Journal `replacing` with `inFlight: null`, then exit 1 with the status, no second create in this run. No earlier create of the item can be pending, because a barrier ran after every unanswered one.
        - `ambiguous`: back to step 2. Its barrier ends the api process, so this create is then committed or never will be, and its sweep revokes the token if it was committed.
        - **Limit.** A create `POST` is sent at most twice per item and run. When step 3 is reached a third time, the CLI does not create. It has just run step 2 with its barrier, so it exits 1 with the journal kept in `replacing` and `inFlight: null`, no create pending and no unheld replacement active. The rerun starts at step 2.
        - **Order rule.** While the journal on disk names `inFlight` for the item, the CLI sends no `POST`, reads no token list for a sweep and reads back no token of the item until the barrier has run. This holds across runs, because the rerun reads `inFlight` from disk. The one exception is the reconcile's confirmation of a staging file (decision 8 "Reconcile" step 4): a staging file exists only for a `POST` whose answer was parsed, so that `POST` is not pending. When the confirmed row moves the item to `staged`, that write clears `inFlight`; when the confirmation refuses, nothing is written or sent.
     4. Stage and save as in decision 7 step 3 with the created id.
     4a. **Post-check (order guarantee against a racing revoke).** Between the durable `saved` and the `refreshing` write of an item with `replacementName` set, the CLI reads back the lost token, `GET /admin/tokens/<tokenId>`, and classifies it with the ordered rules of "Readback". The bearer is the admin secret for `probe` and the host file for `admin`, which from `saved` on holds the secret of R = `activeTokenId`, a token that authenticates whether or not `tokenId` was revoked. It runs in the first run and on every resume that finds the item in `saved` (also after the reconcile moved it from `staged`). `refreshing` is written only after it passed, so no item gets past the refresh without it.
        - **Guarantee.** The CLI never keeps a replacement R when a revoke or the expiry of `tokenId` committed in the api before the post-check readback. That includes every revoke that committed before R was created, which is the race of the ninth plan review. Reason: `saved` is written only after R's create was answered, and the api answers a create after it has committed it (fact 7). So the readback starts after R exists. The api is one process with one SQLite database, so the readback sees every write committed before it.
        - **After the post-check**, R is the item's token. A revoke of `tokenId` that commits later changes nothing that the CLI does: step 6 of decision 7 revokes `tokenId` anyway. To stop the location or the admin access then, a person revokes R; the CLI prints R's id, and `### Token recovery` says so. This is the one difference to a normal rotate, where the token keeps its id.
        - `changed`: go on with the refresh.
        - `gone`: the **drop path**. Each of its steps is named by a durable journal state before it acts, so a lost answer or a hard kill at any point resumes at the step where it stopped. For `admin` the last revoke of the path is R's revoke of itself, and after it lands R's secret answers `401` on every route (fact 7). That `401` looks the same as the `401` of a retired credential (another client rotated R, and the overlap ended) while R stays active. So it is not a confirmation: only a parsed `200` to R's revoke confirms it, and every other end of an `admin` drop goes to the manual recovery.
          1. Journal `dropping-orphans` (durable). From here the item never returns to `saved`, and no post-check runs again: `gone` is final (fact 7 "Revocation and expiry are final").
          2. **Orphans.** Read `GET /admin/tokens`. Revoke, through the revoke guard, every token named `replacementName` whose `revokedAt` is null and whose id is not R. With the barrier there are none; this is the drop path's backstop, like the final sweep. A revoke is confirmed by `200`, or by a readback `GET /admin/tokens/<id>` with `revokedAt` set or `expiresAt` not in the future (an orphan has the lost token's `expiresAt`). The bearer is the admin secret for `probe` and the host file (R's secret) for `admin`.
             - An unconfirmed revoke exits 1 with the journal kept in `dropping-orphans`; the rerun runs this step again.
             - A `401` in this state (the resume's capability check, the list, a revoke or a readback) means the bearer stopped authenticating before the CLI revoked R: for `admin` R was revoked, expired, or rotated by another client after the overlap (fact 7); for `probe` `secrets/admin-token` was revoked, expired or rotated elsewhere. The CLI can no longer list or revoke the orphans. It exits 1 with the message of "Readback" (`the admin token no longer authenticates (revoked, expired, or its rotation overlap ended); see docs/cli.md#token-recovery`), the journal byte-equal, and makes no further call. For `admin` the way out is the manual recovery below. For `probe` it is a working admin secret in `secrets/admin-token` and a rerun (no item owns that file).
          3. Journal `dropping-replacement` (durable), only after every orphan of step 2 is confirmed in this run. The CLI sends R's revoke in this state and in no other.
          4. **Replacement.** Revoke R = `activeTokenId` through the revoke guard with its drop exception (below). The bearer is the admin secret for `probe`. For `admin` it is the host file, R's own secret.
             - **`probe`.** Confirmed by `200`, or by a readback of R with the admin secret that shows `revokedAt` set or `expiresAt` not in the future. A resume in this state reads R back first and sends the revoke only when R is still active. Unconfirmed: exit 1, journal kept in `dropping-replacement`; the rerun runs this step again. A `401` with the admin secret: exit 1 as in step 2.
             - **`admin`.** Confirmed only by a parsed `200` to R's revoke `POST` in this run. In every other case (another status except the last-admin `409` below, a lost answer, `fenced`, or a resume in this state) the CLI calls `GET /admin/tokens/self` with the host file and decides by its answer:
               - `200` with id R: R is still active (the revoke did not land, or has not landed yet; a late landing only does what this step wants). On a resume, or after a `fenced` line, the CLI now sends the revoke. After a revoke that this run already sent and that was not answered with `200`: exit 1, journal kept in `dropping-replacement`; the rerun asks again.
               - `401`: R's secret no longer authenticates. That is not a confirmation (fact 7 "What a `401` says about a known secret"): R may be revoked (for example by this run's own revoke whose answer was lost) or expired, but it may also have been rotated by another client after the overlap, and then it is still active. R's secret cannot read R's state, and no other bearer exists in an `admin` journal. So the CLI exits 1 with `the admin token no longer authenticates (revoked, expired, or its rotation overlap ended); see docs/cli.md#token-recovery`. The journal stays byte-equal, and no further call is made. The manual recovery ("Manual recovery" below) checks R with another admin token.
               - anything else (`429`, a timeout, another id): exit 1, journal kept in `dropping-replacement`; the rerun asks again.
               - On a resume in this state the self call is the capability check of decision 5 (same bearer, same call). A `401` there stops the run as in every other state.
          5. **Remove the item** as in the `gone` rows of "Rotate outcome" (with every later item that is still `requested`; the journal is removed when no item is left that is not `done`), durable. Exit 1 with `token <tokenId> was revoked or expired during the rotation; its replacement <R> was revoked; no replacement was made`. This is written only after a confirmed revoke of R: a parsed `200`, or for `probe` a readback of R with the admin secret.
             - A hard kill or a failed write before this removal leaves `dropping-replacement`. For `probe` the rerun's readback shows `revokedAt` and step 5 runs without a second revoke. For `admin` the rerun's self call answers `401`, which confirms nothing, so the run stops and the manual recovery ends the item. This is the price of never trusting a `401`. It is reached only after a revoke race and a lost or unrecorded revoke answer.
             - The host file keeps R's secret, which no longer works, as the host file of a revoked `tokenId` would. For `admin` the installation then holds no working admin secret, and the console keeps a secret that no longer works. Another active admin token exists, because the api refuses to revoke the last one. `### Token recovery` says to write a working admin secret, made with that other token, into `secrets/admin-token` and run `pulse up`.
          - **Last admin.** For `admin`, R's revoke can answer `409` `cannot revoke the last active admin token` (fact 1). Then R is the only active admin token and the api forbids revoking it. The CLI journals `refreshing` with `lastAdminKept: true`, the only way from a `dropping-*` state to the refresh, and the item goes on with the refresh and switch as a normal replacement. When the item reaches `done`, in the first run or a resume, the command exits 1 with `token <tokenId> was revoked during the rotation, but its replacement <R> is the last active admin token and was kept; see docs/cli.md#token-recovery`. A lost `409` answer goes through the self call above (`200` with id R), and the rerun's revoke gets the `409` again.
          - **Why two states.** For `admin`, R's secret is the only bearer, so every orphan must be revoked before R's revoke is sent: `dropping-replacement` is written only after that, and R's revoke is sent in no other state. Each state is durable before its first revoke, so a rerun knows which revokes may have been sent. A `401` in either state stops the run with the journal kept. The journal is the record that the manual recovery needs: it names `replacementName`, `tokenId` and R. In the tenth spec a `401` in `dropping-replacement` removed the item. That was wrong when another client had rotated R and the overlap had ended (eleventh plan review).
        - `same`: impossible after a `changed` readback (`rotatedAt` never goes back), so a fault: exit 1, journal kept in `saved`.
        - `unknown`: exit 1, journal kept in `saved`; the rerun runs the post-check again. For `admin` a `401` here means R's secret stopped authenticating before the drop path started (R was revoked, expired, or rotated by another client after the overlap). The CLI then exits 1 with the message of "Readback", the journal byte-equal, and the manual recovery below is the way out.
     4b. Refresh and switch (decision 7 steps 4 and 5).
     5. **Final sweep** (state `switched`, also on resume). Read `GET /admin/tokens` and revoke, through the revoke guard, every token whose `name` equals `replacementName`, whose `revokedAt` is null and whose id is not `activeTokenId`. With the barrier it finds none; it is the backstop for a defect in that rule. When it revokes, it prints `revoked <n> unheld replacement token(s)`. An unconfirmed revoke exits 1 with the journal kept in `switched`; the rerun runs this step again. Then step 6 of decision 7 revokes `revokeTokenId`, and the journal can only be removed after both.
     6. Print `the rotate answer was lost; replaced token <revokeTokenId> with <activeTokenId>`.
     - Revoking the lost admin is not refused by the last-admin rule, because the replacement is active by then.
     - For `admin` in state `replacing` after the old secret's `previousValidUntil`, the CLI cannot authenticate. It exits 1 and names the recovery in the docs: the manual recovery below with another admin token, or a database backup.
   - **Barrier (unanswered writes).** A rotate or create `POST` without a parsed answer may still be pending in the api server after its client has ended (fact 7). Creates make a second token with the same name, and a late rotate would invalidate a secret the CLI already handed out. So the CLI treats the api state as final only after the api process has ended.
     1. **Marker.** Before each rotate `POST` the item's journal state (`requested`) is written with `inFlight: "rotate"`, before each create `POST` (`replacing`) with `inFlight: "create"`, durable, each with `inFlightInstance` set to the api instance that the `POST` carries (decision 4 "Instance fence"). A parsed answer of class `ok` or `rejected` means the api has finished the request. `inFlight` is cleared by the next journal write of the item: `staged` after `ok`, the drop or the `inFlight: null` write after `rejected`, the barrier's own write after it ran. An `ambiguous` answer, a stage error before `staged` and a killed run leave it set on disk.
     2. **When.** Whenever the journal on disk names `inFlight` for the item, the barrier runs before any readback, sweep or `POST` of that item, in the first run and on every resume. On a resume it also runs before the capability check and before any bearer is read ("Resume order"). It uses no bearer, so a revoked or retired admin secret cannot keep it from running. It never runs while `inFlight` is `null`, so a rotation whose every answer was parsed restarts no api.
     3. **Steps.**
        1. `docker compose <prefix> ps --all --no-trunc --format json api` must show exactly one container. Record its id.
        2. `docker compose <prefix> stop --timeout 10 api` must exit 0.
        3. `docker inspect --format json <id>` must show `State.Running` false and `State.Pid` 0. Then no process of the container is left: not the api server, and not any `API_SCRIPT` process that `exec` started in it (fact 7). Only that server writes the token store, so every earlier write of the item is committed or never will be.
        4. `docker compose <prefix> start api`, then `waitReady` for `api` with `--timeout`.
        5. **Fence check.** One read through `API_SCRIPT` (`GET /readyz`, no bearer) must print an instance that is not `-` and differs from `inFlightInstance`. Otherwise the restart is not proven: exit 1 as in "Failure" below. From here every write that carries `inFlightInstance` is refused by the fence wherever it runs, so no pending client of the earlier write, in this run or a killed one, can still send it.
        6. Journal the same state with `inFlight: null` and `inFlightInstance: null` (durable).
        7. Print `restarted the api to settle an unanswered token <rotate|create> (<ms> ms)`.
        - Steps 1–3 settle every write that has reached the api server; step 5 settles every write whose client has not yet started a process in the api container. Together they cover a write at any point on its way.
     4. **Failure.** A failure in steps 1–5 exits 1 with the journal kept and `inFlight` still set, and prints `the api may be stopped; run pulse token rotate <kind> again (or pulse up)`. The rerun runs the barrier again: `stop` of a stopped container exits 0. The api service has `restart: unless-stopped` (`common/services.yaml` line 9, copied by `pulseBase`), which Docker does not apply after a `stop`, so the api stays down until the rerun or `pulse up`.
     5. **Effect.** The api is down for its stop, start and readiness, a few seconds. The probes keep their results in their buffer and deliver them afterwards with their original `timestamp` (fact 3). Status and console answer errors meanwhile. Only the recovery paths reach the barrier.
     6. **Why no weaker rule.** The end of the client process (the settle scan of the fifth spec) does not prove that the api has read and handled the body. The api gives no order across connections (fact 7), so a create could still be applied after a sweep or after the final sweep. The stop alone (the barrier of the sixth to eighth specs) does not cover a client that has not reached the daemon yet: its process starts in the restarted api and sends the write there (ninth plan review). A `pgrep` for leftover clients does not cover it either: the CLI may run on another host than the daemon (`DOCKER_HOST`), and a client can end after it handed the request to the daemon. The fence does not depend on where or when the client runs. The final sweep (step 5) stays as a backstop.
   - **Manual recovery (`admin` journal, bearer gone).** An `admin` journal can stop for good with exit 1 and `the admin token no longer authenticates`, in any state: the host secret answers `401` and the CLI has no other bearer. The CLI never ends such an item by itself. `### Token recovery` gives this one procedure for every state. It needs another admin token X: an active token with the `admin` scope whose secret the person holds, for example one made in the console. Without one, the way out is a database backup. Every api call goes through the api container with the bearer on stdin, as the CLI does (decision 4); the docs give the commands.
     0. **Settle and fence first.**
        1. No `pulse` command runs for this directory: the check of decision 3 "Docs", and `.pulse-init.lock` is absent or stale. The person runs no `pulse` command until step 5.
        2. **Barrier by hand**, also when every item shows `inFlight: null`: `docker compose <prefix> stop api`; `docker inspect --format '{{.State.Running}} {{.State.Pid}}' <api container id>` must print `false 0`; then `docker compose <prefix> start api` and wait until it is ready. The stop ends every write that has reached the api server (fact 7). The new container run has a new api instance, so the fence refuses every pending client of any earlier run, however late it arrives (decision 4). From here no rotate or create that a `pulse` run ever sent can still be applied, and the lists of steps 1–3 are final.
        - Without step 0, a create that an earlier run sent and the api had already authenticated could commit after step 1 or after the journal is deleted. That would leave an active replacement whose secret nobody holds (eleventh plan review).
     1. **Replacements.** When the journal names `replacementName`: read `GET /admin/tokens` with X. Revoke every token whose `name` equals `replacementName`, whose `revokedAt` is null and whose id is not X's (from `GET /admin/tokens/self` with X). That includes R (`activeTokenId`) when it is still active, for example after another client rotated it. Confirm each one by `200`, or by `GET /admin/tokens/<id>` with `revokedAt` set.
     2. **The original token.** Read `GET /admin/tokens/<tokenId>` with X. When it is active (`revokedAt` null, `expiresAt` null or in the future) and it is not X, revoke it and confirm it. In every state a rotate of `tokenId` may have landed with its answer lost, so its current secret may be held by nobody. Its pre-rotation secret is in no host file once the item reached `saved`, and in `requested` and `replacing` it no longer authenticates. Leaving it active is wrong, also in `requested` (the tenth spec's steps for `requested` did that). The installation gets a new admin secret in step 4, so it needs `tokenId` no more. The docs name one exception: a person who rotated `tokenId` on purpose and holds its new secret uses that token as X.
     3. **Check.** `GET /admin/tokens` with X shows no active token named `replacementName` other than X, and `tokenId` revoked, expired or equal to X.
     4. **Files.** Delete every `secrets/.pulse-next.*` staging file (they hold secrets of tokens that are now revoked), then `secrets/.pulse-rotation.json`, the journal last. Write a working admin secret into `secrets/admin-token` (0600): X's own secret, or the secret of a new admin token made with X (`POST /admin/tokens` with the scopes `["read","checks","incidents","admin"]`).
     5. `pulse up`. `secrets-init` copies the new secret to the console.
     - The same procedure covers a journal whose reconcile refused (an `admin` staging file whose confirmation answered `401`): such a staging file belongs to a replacement named `replacementName`, so step 1 revokes it.
     - A `probe` journal needs no manual token steps. No item owns `secrets/admin-token` (decision 8 "Owned files"), so the person writes a working admin secret there and runs the command again. The rerun then runs the barrier, the sweeps and the post-check with the new bearer.
   - **Revoke guard.** Before every revoke (orphans in "Lost answer" step 2 and in the drop path's `dropping-orphans`, R in `dropping-replacement`, the final sweep, `revokeTokenId` in decision 7 step 6), the CLI calls `GET /admin/tokens/self` with the bearer it is about to use. It refuses, exit 1 with the journal kept and `refusing to revoke the token that authenticates this call (<id>); see docs/cli.md#token-recovery`, when the answered id equals the target. It also never revokes `activeTokenId`. The api allows a token to revoke itself while another admin is active (Grant and Last-admin rules, api `docs/rest-api.md` lines 498–500), so only the CLI can prevent it.
     - **Drop exception.** In state `dropping-replacement` (and in no other state) the drop path of "Lost answer" step 4a may revoke `activeTokenId` (R). For `admin` it may also revoke R with R's own secret as bearer, as the last revoke of that path. That is the only case: the item is removed right after it is confirmed, and nothing else holds or needs R's secret. The guard still refuses every other target that equals the calling token, so an orphan is never revoked with its own secret, and no revoke in the drop path comes after R's (the orphans are confirmed in `dropping-orphans`, before `dropping-replacement` is written).
   - **Interrupt.** SIGINT and SIGTERM are recorded and acted on only at the next step boundary. From writing `requested`, `replacing` or `revoking` until the api answer is handled, staged, installed and the next state after it (`saved`, or the next state after a revoke) is written, the signal waits. The in-process reconcile after a stage error is part of this section, and so are every barrier, the readback and the second `POST` of "Rotate outcome", every sweep of "Lost answer" (steps 2 and 5), the second create, and the post-check with its drop path (step 4a, from the post-check readback through the removal of the item in `dropping-replacement`, or the `refreshing` write of the last-admin rule). So a signal never ends a run between an unanswered `POST` and its barrier, except through a failure of the barrier, which keeps `inFlight` on disk. The barrier is bounded by its timeouts (10 s stop, `--timeout` readiness). The CLI then exits 130 with `interrupted; run pulse token rotate <kind> again to finish`. The journal stays. A hard kill inside this section is covered by the reconcile.
   - While the journal exists, a plain run without it is impossible: `pulse token rotate` always resumes it first, and `pulse upgrade --yes` refuses.

10. **Upgrade selection.**
    - The installed pulse images come from the parsed `compose.yaml` (`Bun.YAML.parse`, not the effective model). There is one per pulse.json service of kind `pulse`. The image name is `probe` for every service whose name starts with `probe`.
    - The command refuses before any change when:
      - an image is not `ghcr.io/lorenzh/pulse-<api|probe|status|notify|console>:<x.y.z>@sha256:<64 hex>`;
      - the probe services differ in image;
      - the effective image of a service in `docker compose config` (with the override) differs from the one in `compose.yaml` (`compose.override.yaml sets the image of <svc>; remove it to use pulse upgrade`);
      - the setup is `dev` (`dev builds from source; update the clones and run pulse up`).
    - **Data mounts.** The snapshot must hold every store that the pulse services write (fact 8). The CLI reads the effective model of the guard's resolution call (`docker compose config --format json`, `cli/docker.ts` lines 294–307, with the override). For every pulse.json service of kind `pulse` it looks at every mount of the service. Compose keeps them in five keys (fact 8): `volumes` (long form), `tmpfs`, `configs`, `secrets` and `volumes_from`. A check that reads only `volumes` misses a service-level tmpfs. So:
      - Each `volumes` entry must be either a `volume` entry whose `source` is a top-level volume key, or a `bind` entry with `read_only: true`. Anything else refuses: a writable `bind`, a `tmpfs`, a `volume` entry without `source` (anonymous), and any other type.
      - **`volumes_from`** must be absent, `null` or an empty list. Any entry refuses: it brings in the mounts of another container or service, which the CLI cannot see in this service's model.
      - **Mount paths.** The CLI builds the list of mount paths of the service, each normalized with the rule of `scripts/check-setup.sh` rule 8 (`def norm`, line 131): split on `/`, drop empty and `.` parts, a `..` removes the previous part, join with a leading `/`; `/var/run` and paths below it map to `/run`. The list holds:
        - the `target` of every `volumes` entry;
        - every `tmpfs` entry. The value may be `null`, a string or a list of strings (fact 8); the path is the text before the first `:`. Any other shape refuses;
        - the `target` of every `configs` entry, or `/<source>` when it has none (fact 8);
        - the `target` of every `secrets` entry, or `/run/secrets/<source>` when it has none.
      - **No mount overlaps a writable volume.** Let D be the normalized target of a writable `volume` entry of the service. Every other path P of the list must satisfy: P ≠ D, P does not start with `D + "/"`, and D does not start with `P + "/"` (and P is not `/`). A path that breaks this refuses: a tmpfs at `/data/`, `/data//` or `/data/x` shadows all or part of the store, a config at `/data/pulse.db` replaces the database file, and a mount above `/data` hides it. The rule does not depend on which of two nested mounts Docker puts on top (fact 8). A tmpfs, config or secret elsewhere (for example `/tmp` or `/run/secrets/x`) is allowed. The rendered services have no `tmpfs`, `configs`, `secrets` or `volumes_from` (`cli/render-compose.ts`), and their other mounts (`/run/pulse`, `/config`, `/demo/tls.sh`) do not overlap `/data`.
      - This is the same path rule that `check-setup.sh` rule 8 applies to `/run/pulse` for the committed setups. The CLI implements it in TypeScript (the CLI binary cannot run `jq`), with the same normalization and the same test paths as `scripts/check-setup.test.sh` lines 98–105, mapped to `/data`.
      - A `volume` entry is *writable* when `read_only` is absent or false. The snapshot set is the sorted, de-duplicated list of the sources of all writable `volume` entries of all pulse services. The key name does not matter: no `-data` suffix is needed, and a declared volume that no pulse service mounts writable is not in the set.
      - api, notify and console must each have exactly one writable `volume` entry whose `target` is exactly `/data`, the directory of their image's data path (fact 8). A missing or read-only `/data` volume refuses.
      - The data path variable of the service (`PULSE_DB`, `PULSE_NOTIFY_STATE`, `PULSE_CONSOLE_DB`) must be absent from the effective `environment` or equal the image default literally (`/data/pulse.db`, `/data/notify-state.json`, `/data/console.db`). Any other value, also one with `${…}` (the resolution call does not interpolate), refuses.
      - Each volume of the set is mounted by the snapshot helper under its name `<project>_<key>`. The guard has already checked that name (fact 8).
      - **Existing, owned volumes.** Every volume of the set must exist and be this install's (the "Volume check" of decision 13): `docker volume inspect --format '{{json .Labels}}' <project>_<key>` exits 0, and its labels have `io.github.lorenzh.pulse.install` equal to the install id and `com.docker.compose.project` equal to the project. The guard skips a missing volume (fact 8), so this check is new and does not rely on the guard. A missing volume refuses with `data volume <project>_<key> does not exist; run pulse up once before pulse upgrade; see docs/cli.md#upgrade`. Without it, the snapshot helper would create an empty, unlabelled volume (fact 8), the archive would hold nothing, and a rollback could not undo the migration of the store the stack creates later. Wrong labels refuse with `data volume <project>_<key> does not belong to this installation; see docs/cli.md#upgrade` (the guard already refuses this case, the check repeats it because it also runs later in the upgrade). An inspect error other than `no such volume` exits 1 with `docker volume inspect failed: <first line>`.
      - Refusal texts: `<svc> keeps <target> in a <type> mount; pulse upgrade can snapshot only named volumes; see docs/cli.md#upgrade` (`<type>` is `bind`, `tmpfs`, `volume`, `config` or `secret`; `<target>` is the path as Compose printed it, through `shown()`), `<svc> uses volumes_from; pulse upgrade can snapshot only named volumes; see docs/cli.md#upgrade`, `<svc> has no writable volume at /data; see docs/cli.md#upgrade` and `<svc> sets <VAR> to another path; see docs/cli.md#upgrade`. For an overlap, `<target>` is the other path P and `<type>` its kind; a writable volume that overlaps another writable volume is named with type `volume`.
      - The check, including the existing-volume check, runs in step 2 of decision 13, before provenance, so the preview refuses too. Nothing is pulled or stopped before it passes.
    - Versions are full stable SemVer `(0|[1-9]\d*)\.(0|[1-9]\d*)\.(0|[1-9]\d*)`, the stable core of `config/.github/workflows/release.yml` lines 34–37. They are compared numerically per part.
    - Without `--to`, each image moves to the highest stable tag on ghcr.io that is greater than its current version. With none, it stays.
    - `--to X.Y.Z` (a leading `v` is accepted and removed; anything else, including prereleases and leading zeros, is a usage error, exit 2) wants exactly that tag for every installed pulse image:
      - an image without that tag refuses the whole command;
      - an image whose current version is greater refuses (`no downgrades`);
      - an equal one stays.
    - When nothing changes, print `already up to date` and exit 0 without touching anything.

13. **Upgrade apply (`--yes`), the snapshot boundary and the rollback.**
    - **States** of `upgrade.json`:
      - `snapshotting` → `applying` → `done`;
      - `snapshotting` → `aborted`;
      - `applying` → `rolling-back` → `restored` → `rolled-back` | `rollback-failed`;
      - `rolling-back` → `rollback-failed`.
      - Each state is written atomically (temp file `wx`, fsync, rename, fsync of the directory) before the step it names. `rollback-failed` carries `restored: true|false`: `true` when it follows `restored`.
    - **Durable state.** A state write is *durable* when all four parts of the write returned without error. A write that throws in any part is resolved by "State-write errors" below and never counts as durable.
    - **Truthful state before start.** The CLI runs `docker compose up -d` only after one of these:
      - the `aborted` write of the abort path, durable or not. The abort path is entered only while the file on disk reads `snapshotting`, so the file then reads `snapshotting` or `aborted`, and the CLI has changed neither `compose.yaml` nor a volume;
      - a durable `applying` (the switch, step 10). A read-back `applying` after a failed write is not enough for the switch: it leads to the rollback;
      - a durable `restored` (the rollback).
      So a stack that runs while `upgrade.json` is not terminal always matches the manual recovery of that state (below).
      - In addition, every `up -d` of the upgrade, the abort and the rollback comes after a helper sweep (below) that ended with no helper left, and after a passing volume check (below) of every volume of `snapshotVolumes`: in step 2 of the abort, after each snapshot helper of step 6 for the switch, and after each restore helper for the rollback.
    - **Helpers.** The snapshot and restore containers are *helpers*. A helper is a standalone container outside Compose, so killing its client or the CLI does not end it (fact 5), and `pulse down` does not see it (fact 5).
      - **Labels.** Every helper is created with `--label io.github.lorenzh.pulse.install=<installId>` (the existing `INSTALL_LABEL` with the install id of `pulse.json`) and `--label io.github.lorenzh.pulse.helper=<snapshot|restore>`, besides its name.
      - **Two-step start.** The CLI never uses `docker run` for a helper. Each helper is started in two spawns:
        1. **Create.** `docker create --rm [-i] --name … <labels> <options> <image> <command>` (the full argv is in step 6 and rollback step 3). It must exit 0 and print exactly one line that matches `^[0-9a-f]{64}$`; that is the helper's id. Any other result is a failed helper: the helper sweep runs, and the step's failure path follows. A created container runs no process (fact 5).
        2. **Start.** `docker start -a <id>` for a snapshot helper (stdout to the `.tar.part` fd) or `docker start -a -i <id>` for a restore helper (stdin from the tar fd). Its exit code is the helper's exit code (fact 5). It is spawned only by the run whose create printed that id, in the same process, and never for any other id.
        - **Why two steps.** A process in a helper can only run after a `docker start` reached the daemon. That start is spawned only after the create returned, so its container is already listed by `docker ps --all` (fact 5). So:
          - A `docker create` client that a killed run left behind (killed before the container existed) can only add a container in state `created` later. No step ever starts it: the CLI starts only the id that its own create printed in the same process, and the manual recovery never runs `docker start`. It stays inert until the next helper sweep removes it.
          - A `docker start` client that a killed run left behind belongs to a container that exists. A sweep lists it and `docker rm -f` removes it. If the start reaches the daemon first, `rm -f` kills and removes the running helper; if `rm -f` comes first, the start fails with `No such container` (fact 5).
          - Therefore, after a sweep whose last list was empty, no helper process runs and none can start later. A one-step `docker run` does not give this: a pending `run` client creates and starts its container after any number of empty lists (the eighth plan review reproduced it).
        - A pending create can still create a missing named volume without labels (fact 5). The volume check before each create (below) passed in the killed run, so this happens only when a person removed the volume meanwhile (Risks "Data volume removed during an upgrade").
        - In the run itself, the CLI waits for its own create spawn (kill bound 30 s). If that bound kills the create client, the create counts as failed and the sweep follows; a container that the killed client still creates later is inert as above.
      - **Helper sweep.**
        1. List: `docker ps --all --quiet --no-trunc --filter label=io.github.lorenzh.pulse.helper --filter label=io.github.lorenzh.pulse.install=<installId>`. `--all` includes containers in state `created`.
        2. For each id: `docker rm -f <id>`. Docker returns from it after the container has been killed and removed, so no process of it changes a volume afterwards, and a later `docker start` of that id fails.
        3. List again. It must print nothing. Up to 3 rounds within 30 s; otherwise exit 1 with the ids left and `docs/cli.md#upgrade-recovery`, with no state write, no restore and no start.
        - It prints `removed <n> leftover helper container(s)` when n > 0.
        - A container in state `created` that appears after the sweep (a pending create of a killed run) does not break the guarantee: it never runs. The next sweep removes it.
      - **When it runs.**
        - In step 1 of every `upgrade --yes`, after the lock and the guard and before the refusal for a non-terminal snapshot directory. The lock is held, so a helper that exists now belongs to a run that has ended. A refused run has therefore still removed every leftover helper.
        - In step 1 of the abort, instead of a removal by name.
        - In the rollback before the first restore helper, and after every restore helper whose create or start fails, exits non-zero or throws, before the next state write.
        - Before every `up -d` of the upgrade, the abort and the rollback.
      - A restore helper exists only between the durable `rolling-back` and the durable `restored`. So a helper found by a sweep means the state on disk is `rolling-back` (or a failed write after it), and the volumes must be restored again.
    - **Volume check.** A helper mounts `<project>_<key>` with `-v`, and Docker creates that volume, without labels, when it does not exist (fact 8). So a helper never runs on a volume that this check has not just passed, and its result counts only when the check passes again after it.
      - **Check.** `docker volume inspect --format '{{json .Labels}}' <project>_<key>` exits 0, and the labels have `io.github.lorenzh.pulse.install` equal to the install id and `com.docker.compose.project` equal to the project. One shared function, also used by decision 10 "Data mounts" and by the guard's `checkVolumes` (Reuse).
      - **When.** In step 2 for every volume of the set (decision 10). Right before the create and right after the start has exited of every snapshot helper (step 6) and every restore helper (rollback step 3), for its volume. The check comes before the create, not only before the start, because the create already mounts the volume and would create a missing one (fact 5). In step 2 of the abort, for every volume of `snapshotVolumes`.
      - **Failure.** The volume was removed or replaced outside pulse while the upgrade held the lock. The CLI never starts a service on it and never deletes a volume:
        - in step 2: the refusal of decision 10, nothing changed;
        - around a snapshot helper, or in step 2 of the abort: the helper sweep, then stop. No `aborted` write, no deletion of archives, no start. The state stays `snapshotting`. Exit 1 with `data volume <project>_<key> is missing or not this installation's; the stack stays stopped; see docs/cli.md#upgrade-recovery`;
        - around a restore helper: the helper sweep, then `rollback-failed` with `restored: false`, no start, the same message.
      - A volume that a helper created has no labels, so the guard of the next `pulse up` refuses it (fact 8). The docs say to restore such a volume from a backup.
    - **Steps.**
      1. Preflight: lock (with the stale-lock break of decision 3), guard, the helper sweep, no rotation journal, and no snapshot directory under `.pulse-upgrade/` whose `upgrade.json` is `snapshotting`, `applying`, `rolling-back`, `restored` or `rollback-failed` (a directory without a readable `upgrade.json` counts as `snapshotting`). A refusal names that directory and `docs/cli.md#upgrade-recovery`. An existing `.pulse-upgrade/` must be a directory, not a link, with no group or other bits, and each entry in it must be a directory and not a link; otherwise refuse with the path and the rule.
      2. Selection, the data-mount check (decision 10 "Data mounts") and provenance, then a table of service, from version and 12-hex digest, to version and 12-hex digest, and `provenance verified`. Without `--yes`, print `run pulse upgrade --yes` (with the same `--to`) and exit 0 here. A preview writes no file and changes no container.
      3. `docker pull <ref>@<digest>` for every new image. A failure or an interrupt exits 1 or 130, and nothing is stopped.
      4. **Durable snapshot directory.** In this order, each part must return without error:
         1. If `.pulse-upgrade/` does not exist: `mkdir .pulse-upgrade` (0700), then fsync the install directory. If it exists (checked in step 1: a directory, not a link, no group or other bits), fsync the install directory anyway, because an earlier run's fsync may have failed.
         2. `mkdir .pulse-upgrade/<UTC stamp>-<6 hex>` (0700, fails if it exists), then fsync `.pulse-upgrade/`.
         3. Write `upgrade.json` `{format:1, from:{svc:ref}, to:{svc:ref}, composeSha256, snapshotVolumes:[<key>…], state:"snapshotting"}` as a state write (temp file, fsync, rename, fsync of the snapshot directory). `snapshotVolumes` is the snapshot set of decision 10 "Data mounts".
         - So when step 5 stops the stack, every entry on the path from the install directory to `upgrade.json` has been fsynced in its parent directory after it was created. A power loss from step 5 on cannot lose the directory or its `upgrade.json`, so the next `upgrade --yes` finds it and refuses (step 1), and the manual recovery finds it. A directory fsync makes the entries in that directory durable; the fsync of a file or of the directory itself does not make its own entry in the parent durable.
         - Any failure in 1–3 is the `snapshotting` row of "State-write errors": nothing is stopped yet.
         Print the start time; the downtime starts at the next step.
      5. `docker compose <prefix> stop`.
      6. For each key of `snapshotVolumes`, in its order (for the rendered layout: `api-data`, `console-data`, `notify-data`):
         - Create the helper (two-step start): `docker create --rm --name <project>-pulse-snapshot-<6 hex> <helper labels> --network none --user 0:0 --cap-drop ALL --cap-add DAC_OVERRIDE --security-opt no-new-privileges:true -v <project>_<key>:/from:ro <image of secrets-init from the resolved config> tar -C /from -cf - .`.
         - Open `<key>.tar.part` (0600, `wx`) and give its fd to the spawn as stdout of `docker start -a <id>`.
         - The volume check of `<key>` runs right before the create and right after the start has exited.
         - The helper must exit 0. Then fsync the file, compute its size and sha256, rename it to `<key>.tar`, and fsync the directory.
      7. Copy `compose.yaml` to `compose.yaml` in the snapshot (0600, `wx`, fsync of the file, then fsync of the snapshot directory). Its sha256 must equal `composeSha256`.
      8. **Snapshot-complete boundary.** Write `upgrade.json` with `state:"applying"` and `tars:{<key>:{bytes, sha256}}`. The keys of `tars` must equal `snapshotVolumes`; reading a file where they differ is a validation failure. The boundary is crossed when the file on disk reads `applying` with these `tars`: after a durable write, or after a failed write whose read-back shows them (for example the rename landed and the directory fsync threw). Print `snapshot <bytes> bytes in <ms> ms`.
      9. Edit `compose.yaml`:
         - Replace each old image string with the new one. The count of replacements must equal the number of services that used it.
         - Parse the new text again and check that it equals the old model with only those `image` values changed.
         - Write atomically with the old mode.
      10. `docker compose <prefix> up -d`, then `waitReady` with `--timeout` (default 300 s, 1–3600).
      11. On success: `upgrade.json` `done`, print `upgraded; the stack was down for <ms> ms; snapshot kept in <dir>`. The snapshot is the only way back to the older version. Exit 0.
    - **Abort before the boundary** (a failure or an interrupt in steps 4–8 while the file on disk reads `snapshotting`):
      1. The helper sweep ends every snapshot helper. Killing only the `docker run` client is not enough (fact 5). A failed sweep exits 1 with the state left as it is on disk and no start.
      2. `compose.yaml` was not edited. Its sha256 must still equal `composeSha256`. If not (only a person or another program can have changed it, as the lock excludes the CLI), the run stops: no start, no deletion, the state stays `snapshotting`, exit 1 with the recovery link. Then the volume check of every volume of `snapshotVolumes`; a failure stops the same way ("Volume check").
      3. Write `upgrade.json` `aborted`. No volume is touched: no restore helper runs.
      4. Only after a durable `aborted`: delete every `*.tar.part` and `*.tar` file in the snapshot directory and fsync it. If the `aborted` write fails, every archive stays, and the message adds `snapshot directory kept: <dir>`. A failed delete is printed with the file names and does not stop the abort.
      5. `docker compose <prefix> up -d`, then `waitReady`. Print `upgrade aborted before the switch: <reason>; the previous images were started again`. Exit 1, or 130 after an interrupt.
      - So archives are deleted only while the file on disk reads `aborted`, and the abort path is entered only while it reads `snapshotting`. An `applying` file never points to deleted archives.
    - **State-write errors.** An error in any part of a state write (temp write, temp fsync, rename, directory fsync) does not by itself say whether the new state landed. The CLI reads `upgrade.json` back from disk, validates it, and acts on what it reads:

      | Write that failed | Read back | Action |
      | --- | --- | --- |
      | `snapshotting` (step 4), or a `mkdir` or directory fsync of step 4 | anything | nothing is stopped yet. Remove the files the run created in the new directory and the directory (not `.pulse-upgrade/` itself), then exit 1 with `could not create the snapshot directory: <error>`. If that removal fails too, the next run refuses for the directory (counts as `snapshotting`). |
      | `applying` (step 8) | `snapshotting` as written in step 4 | the rename did not land: abort before the boundary |
      | `applying` | `applying` with the `tars` just computed | the rename landed, for example the directory fsync threw: the boundary is crossed, so roll back. The volumes and `compose.yaml` are still unchanged here, so the restore writes the same data. The archives stay, because the file on disk says the snapshot is complete. |
      | `aborted` | anything | step 4 of the abort: keep every archive, start the old images, exit 1 |
      | `rolling-back` | anything | `docker compose <prefix> stop` (new images may be running after a failed readiness; a stop changes no file and no volume), then no restore and no start. Exit 1 with `upgrade stopped: the state file could not be written; the stack is stopped; see docs/cli.md#upgrade-recovery`. |
      | `restored` | anything | the same stop. The volumes and `compose.yaml` are restored but no container is started. |
      | `done`, `rolled-back`, `rollback-failed` | anything | the stack is in its final shape. Print the result line, then `the state file could not be written; see docs/cli.md#upgrade-recovery`, exit 1. |
      | `applying` | unreadable, invalid, or another content | stop: no deletion, no restore and no start, exit 1 with the recovery link |

      - The read-back is a plain read after the error. It is not repeated, and the write is not retried.
      - Signals that arrive while a state write is resolved are recorded and acted on after the row's action, as in the rollback.
    - **Rollback after the boundary** (a failed edit, a failed `up`, a failed one-shot, a timeout, an interrupt from step 9 on, or the `applying` row of "State-write errors"):
      1. `upgrade.json` `rolling-back` (durable), then `docker compose <prefix> stop`.
      2. Verify every tar against `tars` (size and sha256) and the snapshot `compose.yaml` against `composeSha256` before any volume is changed. A mismatch restores nothing and goes to `rollback-failed` with `restored: false`. The stack stays stopped.
      3. The helper sweep. Then for each tar, a two-step start: `docker create --rm -i --name <project>-pulse-restore-<6 hex> <helper labels> --network none --user 0:0 --cap-drop ALL --cap-add CHOWN --cap-add DAC_OVERRIDE --cap-add FOWNER --security-opt no-new-privileges:true -v <project>_<key>:/to <same image> sh -c 'find /to -mindepth 1 -delete && tar -C /to -xpf - && sync -f /to'`, then `docker start -a -i <id>` with the tar fd as stdin. The start must exit 0.
         - `sync -f /to` flushes the filesystem that holds the volume (`syncfs`, fact 5) and exits non-zero when that fails. So exit 0 of the helper means the restored files of this volume are on disk. A tar extraction without the sync is not enough: the `upgrade.json` fsync does not flush the volume.
         - The volume check of `<key>` runs right before the spawn and right after the helper exits 0. A failure is handled as "Volume check" says.
         - A non-zero exit or a spawn error: the helper sweep, then `rollback-failed` with `restored: false`, and the stack stays stopped.
      4. Restore `compose.yaml` atomically from the snapshot copy (the safe write: fsync of the file and of the directory). A failure goes to `rollback-failed` with `restored: false`.
      5. `upgrade.json` `restored` (durable), written only after every restore helper of step 3 exited 0, including its sync, and step 4 returned without error. From here the volumes and `compose.yaml` hold the old version on disk, also after a power loss.
      6. `up -d`, then `waitReady` with the same timeout.
      - If the rollback is ready: state `rolled-back`, print `upgrade failed: <reason>; rolled back to the previous images and data; ready`, exit 1 (130 when an interrupt started it).
      - Otherwise: state `rollback-failed` with `restored: true`, print `upgrade failed and the rollback failed: <reason>; snapshot in <dir>; see docs/cli.md#upgrade-recovery`, exit 1 (130 when an interrupt started it).
      - Signals during the rollback are recorded, not acted on. The rollback is bounded by its timeouts.
    - **Hard kill and manual recovery.** A run killed without a chance to act, or stopped by a state-write error, can leave any non-terminal state, a stale lock (decision 3) and running helpers. The next `upgrade --yes` breaks the stale lock, removes the helpers, then refuses (step 1). `docs/cli.md#upgrade-recovery` gives the steps per state. Each step follows from facts on disk, and the "Truthful state before start" rule makes them hold:
      - **First, in every state: wait for the killed run's clients, then stop the helpers.**
        1. A killed `pulse` can leave Docker client processes behind (fact 5). Its Compose clients carry `--project-name <project>`, its helper clients `--name <project>-pulse-snapshot-…` or `--name <project>-pulse-restore-…` (decision 13, `operationPrefix`, `cli/docker.ts` lines 281–291). `pgrep -af -- '--project-name <project>( |$)|<project>-pulse-(snapshot|restore)-'` must print nothing; they end within seconds, so wait and run it again. This matters most for a pending `docker compose … up -d` of a run killed in step 10, which could start the new images during a manual restore.
        2. With the install id from `pulse.json`: `docker ps --all --quiet --filter label=io.github.lorenzh.pulse.helper --filter label=io.github.lorenzh.pulse.install=<installId>`, `docker rm -f` each id, and list again until it prints nothing. A helper in state `created` is removed the same way; never `docker start` a helper.
        (A refused `pulse upgrade --yes` has already done this under the lock; the docs still give the commands, because a person may reach this page without that run, and they do not suggest `pulse upgrade --yes` as a recovery step, since in a terminal state it would start an upgrade.) Only then run `pulse down`, a restore or `pulse up`. A restore helper that still runs can delete or extract files while a manual restore or a started api uses the same volume. `pulse down` does not stop it.
      - The manual restore command is the one of rollback step 3, including `sync -f /to`. For a person in a foreground shell the docs write it as one `docker run --rm -i` with the same options, labels, name and script; a person who reaches step 2 above again removes it like any helper.
      - no readable `upgrade.json`, or `snapshotting`: the CLI changed neither `compose.yaml` nor a volume. Remove the directory and run `pulse up`. If the run ended with `data volume … is missing or not this installation's`, or `pulse up` refuses a data volume as belonging to another installation, that volume was removed outside pulse during the upgrade and a helper may have created an empty one: do not remove its labels or declare it external; restore the volume from a backup first.
      - The snapshot directory and its `upgrade.json` are durable before the stack stops (step 4), so an upgrade that stopped the stack always leaves a snapshot directory with its `upgrade.json`, also after a power loss.
      - `aborted`: nothing to recover. The directory may be removed. It can still hold archives when the `aborted` write failed.
      - `applying`:
        - `compose.yaml` byte-equal to the snapshot copy: the new images never started. The edit is the only change and it is atomic, and a rollback writes a durable `rolling-back` before it restores anything. Do not restore. Remove or move the directory and run `pulse up`.
        - `compose.yaml` holds the `to` refs and `pulse status` exits 0: the upgrade worked and only `done` was not written. Remove or move the directory.
        - Otherwise: `pulse down`. Check every tar against `tars` with `sha256sum`. Restore each tar and `compose.yaml` with the commands of the rollback, then run `pulse up`.
      - `rolling-back`: the volumes may be partly restored. Do not start the stack first. Run `pulse down`, check the tars, restore every tar and `compose.yaml`, then run `pulse up`.
      - `restored`: the volumes and `compose.yaml` hold the old version. Do not restore again. Run `pulse up`.
      - `rollback-failed`: with `restored: true`, as `restored`, then find out why the old images are not ready. With `restored: false`, as `rolling-back` when every tar matches. Otherwise use a backup.
      - In every case, remove or move the directory before the next `pulse upgrade --yes`.
    - Data volumes are never deleted outside the restore. The `*-secrets` volumes are not in the snapshot set: the pulse services mount them read-only (fact 8), and `secrets-init` rewrites them from `secrets/` at each start.
    - **Rollback boundary, as stated in the docs.**
      - The stack is down from step 5 until ready, so there are no results during an upgrade.
      - A rollback loses every write after the snapshot.
      - The snapshot needs free disk space for one copy of the data volumes. A full disk fails the snapshot before the boundary, which starts the old images again with untouched data.
      - The data restore is what makes a rollback across schema steps (api 3 → 9, console migrations) possible. Restoring the pins alone does not: api `0.1.0` refuses schema 9.
14. **Logs.** `pulse logs [--dir <dir>] [--follow] [<service>]` runs `docker compose <prefix> logs [--follow] [<service>]` with stdout and stderr inherited and no kill bound.
    - `<service>` must match `^[a-z0-9][a-z0-9_.-]{0,62}$`; otherwise usage error, exit 2.
    - It must also be a service of the resolved project; otherwise exit 1, `unknown service <name>; services: <list>`.
    - The exit code is Compose's exit code (0 or 1).
    - On SIGINT or SIGTERM to the CLI, the child gets SIGTERM. The CLI waits for it and exits 130. No child stays behind.
    - The command adds no text of its own to the log stream.
15. **Continuity rule for the acceptance (needs approval at spec merge).** The issue asks for "no gap longer than one interval". The probe's own cadence is one interval plus timer lateness (fact 3), so a strict `<= interval` fails even with no rotation at all.
    - This spec gates on **gap <= interval + 500 ms** (10 % of the 5000 ms demo interval).
    - The same rule must also hold in a 60 s baseline before the rotation in the same run. That shows the 500 ms covers only normal lateness.
    - Merging this spec approves the allowance. A reviewer who wants another bound changes this line, not the test after a failure.

## Required behavior

### `pulse token rotate <admin|probe> [--dir <dir>] [--location <loc>] [--id <tok_…>] [--timeout <s>]`

- Decisions 3–9 apply.
- `--location` applies only to `probe` and limits the run to that location. `--id` needs `--location` and must match `^tok_[0-9a-f]{24}$`. `--timeout` is 1–3600, default 120, and bounds each readiness wait. Any other combination is a usage error, exit 2.
- With a journal, `<kind>` must equal the journal's kind and `--location`/`--id` must be absent or name a journal item; otherwise exit 2 with `a rotation of <kind> is unfinished; run pulse token rotate <kind>`.
- Output: one line per item and the overlap deadline. No secret, no secret digest, no bearer.
- Works in every setup with the token-store api, `dev` included.

### `pulse upgrade [--dir <dir>] [--to <x.y.z>] [--yes] [--timeout <s>]`

- Decisions 10–13 apply.

### `pulse logs [--dir <dir>] [--follow] [<service>]`

- Decision 14 applies.

## Risks

- **Compose `--scale` behavior.** The live test proves the start-new-then-stop-old handoff. That includes one container per probe service afterwards, and `pulse up` and `pulse status` working after the rotation. If Compose renumbers or recreates the container in a way that breaks this, the implementer requests a hold and does not fall back to stop-then-start, which breaks the gap rule (see Counterexamples).
- **Extra samples.** During the handoff two probe containers post for the same location for the window W. For I ≥ 200 ms the doubled runs per check are at most `floor(W / (I − e)) + 1` (Performance impact item 2): 2 at 5000 ms and 7 at 1000 ms for W = 6000 ms. Below 200 ms that formula is not used. The estimate there is `floor(W / max(I, R)) + 1` with R the run time of the check, about 600 to 3000 at the 1 ms minimum for W = 6000 ms. Both are documented as a known limit.
- **The api restarts on a recovery path.** The barrier (decision 8) stops and starts the api after every unanswered rotate or create. Status and console show errors for a few seconds, and probe results arrive late from the probe buffer (fact 3). A normal rotation never reaches it. If the barrier fails after the stop, the api stays down until a rerun or `pulse up`; the message says so.
- **Revoke of the old token after the post-check.** In the replacement path the item's token has a new id R. A revoke of the old token that commits after the post-check (decision 8 "Lost answer" step 4a) does not stop R, unlike a normal rotate, where the token keeps its id. The CLI prints R's id, and `### Token recovery` says to revoke R to stop that access. Only lost answers reach this path.
- **A revoked or retired admin token stops the admin rotation.** When the admin token no longer authenticates (revoked, expired, or rotated by another client after its overlap; fact 7), the CLI cannot read, sweep or revoke anything. It stops with exit 1 and no write, after its barrier has settled every write it sent (decision 8 "Resume order"). Until a person runs the manual recovery of decision 8 with another admin token, these may stay active with a secret that nobody in the installation holds: `tokenId` after a rotate that landed with its answer lost (any state); a replacement made by an unanswered create (`replacing`); an orphan (`dropping-orphans`); R after another client rotated it (from `saved` on). The `admin` drop path ends in the manual recovery whenever R's revoke answer was not a parsed `200`. The manual recovery needs another admin token. Without one, the way out is a database backup.
- **An owned host file edited during a journal.** The CLI never acts on a `401` (fact 7), so a person who writes another secret into `secrets/admin-token` while an `admin` journal exists can only make the CLI stop: at the self call (another id, or `401`) or at the switch check (decision 7 step 5). The docs say never to edit an owned host file while `secrets/.pulse-rotation.json` exists, and to follow `### Token recovery` instead.
- **Api instance unreadable.** If `/proc/1/stat` or the boot id cannot be read inside the api container (for example a hardened runtime that hides `/proc`), the instance is `-` and `pulse token rotate` refuses before its first write. The live `cli-rotate` job proves the read on the real api image.
- **Stale lock that is not broken.** A lock written on another host, in another pid namespace, on macOS by a pid that now runs again, or by an older CLI is never broken automatically (decision 3). The person removes it after checking; the docs say how.
- **Shared install directory under one hostname.** Decision 3 treats `host` as the machine. Two machines that mount one install directory and report the same hostname are not supported: the reboot row could break a live lock of the other machine. The docs say so.
- **Data volume removed during an upgrade.** The volume check (decision 13) runs right before and after each helper, so a person who removes a data volume between the check and the helper's mount makes the helper create an empty one. The check after the helper sees the missing labels and stops with no start; it cannot bring back the removed data. The lock does not cover `docker volume rm` by a person. A pending `docker create` of a killed run (decision 13 "Two-step start") can likewise create a volume that a person removed after the killed run's check; its container stays inert, and the guard refuses the unlabelled volume on the next `pulse up`.
- **Leftover Docker clients of a killed run.** Besides helper clients, a run killed in step 10 can leave a pending `docker compose … up -d`. The CLI never restores after such a kill (the rerun refuses), so only the manual recovery meets it. `### Upgrade recovery` therefore starts with waiting until no client of the project is left (decision 13 "Hard kill and manual recovery").
- **Compose versions and mount keys.** The data-mount check reads the five mount keys that Compose v2.40.3 prints (fact 8). A later Compose that adds a new mount key would not be checked. The implementer records `docker compose version` of the runner in the PR, and the live tmpfs refusal runs on that version.
- **Volume sync.** `sync -f` flushes the whole filesystem that holds the volume, which can take longer on a busy host. It runs only in a rollback. If the docker daemon's data root does not report writeback errors (Linux before 5.8), a lost write can stay unnoticed; the docs name the kernel requirement.
- **Interrupted rotation outside the overlap.** If a person does not rerun an interrupted rotation within the 10-minute overlap, a still-running old probe gets 401 and logs errors until the rerun removes it. The new probe keeps posting. The docs say to rerun at once.
- **0.1.0 → 0.1.1 upgrade needing manual steps.** If the live upgrade test shows a required config change, the implementer requests a hold. The upgrade must not grow config migrations.
- **#692 bumping the pins at the same time.** Decision 2 covers it.
- **`gh` on the runner.** GitHub-hosted runners ship `gh`. The job prints `gh --version` first and passes `GH_TOKEN: ${{ github.token }}`, with job permissions `contents: read` and `attestations: read`.
- **Overlap length in CI.** The rotation job waits for the real 10-minute overlap. The production overlap is not shortened.
- **New stable releases on ghcr.io.** The upgrade test picks its release pair by position (the two lowest stable tags), so later releases do not change it. Deleting tag `0.1.0` or `0.1.1` would break the test; that is intended.

## Performance impact

**api `bench/budgets.json` metrics: none expected.** No service code changes. The file (api `8959e04`) has the targets `api`, `config`, `contract`, `kit`, `notify`, `probe` and `status`, and no deploy entry. The pin bump runs releases whose numbers are measured in their own repositories.

The commands do have runtime costs on an installation. They are not in `bench/budgets.json`, so they are reported, not gated. Each one has a bound and a measurement:

1. **Second probe during a probe rotation.**
   - What: one extra probe container per location for the two-probe window W. W runs from the Docker start of the new container (`State.StartedAt`, the `start` event) to the Docker end of the old one (`State.FinishedAt`, the `die` event). It holds the new probe's start, its first runs, the CLI's readiness polls, the equality check, the fixed 2000 ms wait and the old probe's stop. Locations rotate one after another, so at most one extra probe runs at a time.
   - Size, from the probe budgets in api `bench/budgets.json` (lines 121–157): up to `peak_rss_mib` 83 MiB extra memory, `startup_cpu_ms` 377 ms extra CPU, and `startup_wall_ms` 1027 ms of start.
   - W has no bound from the probe alone. Expected: 4–8 s. Upper bound by construction: `--timeout` (readiness) + 10 s (equality check timeout) + 2 s + 10 s (`docker stop --time 10`). CI gates W ≤ 20000 ms (Acceptance 1).
   - Each api call and each in-container check adds one short `bun -e` process in the api, probe or console container. They run one at a time. The instance fence adds two small `/proc` reads per api call; a replacement adds one post-check readback.
   - The barrier (decision 8) runs only after an unanswered rotate or create `POST`: one stop and start of the api, a few seconds of api downtime per barrier, at most 4 per item and run (2 rotate and 2 create `POST`s). A rotation whose answers all parse runs none. Measured: the CLI prints `restarted the api … (<ms> ms)`; the unit tests count the barriers. The api's start cost is the api's own `startup_wall_ms` and `startup_cpu_ms` in `bench/budgets.json`.
   - Measured: the CLI prints `two probes ran for <W> ms` per location (decision 7 step 7). `rotate.sh` takes W independently from `docker events` and samples `docker stats --no-stream --format json` every second during the rotation. It reports the largest summed memory and CPU of the probe containers of one location, which the PR quotes against the single-probe baseline of the same run.
2. **Extra check traffic during the handoff.**
   - Extra load per check: the old probe's runs that start inside W, each one extra request to the target and one extra `POST /results`. The old probe starts no run after SIGTERM (fact 3), and the new one no run before its start, so every doubled run lies in W.
   - How the probe spaces runs: one check never overlaps itself. The next run is scheduled only after the previous run and its `onResult` have finished, with the delay `max(0, I − elapsed)` on the monotonic clock (probe `src/scheduler.ts` lines 46–72 at `92f55df`). So two starts of one check are `max(I, R_k)` apart, where R_k is the run time of the earlier run, from its start to the end of its `onResult`. Result timestamps are wall-clock times (fact 3), and e = 100 ms covers timer and clock earliness between them.
   - **Bound, valid domain I ≥ 200 ms.** Two runs of one probe and one check start at least I − e apart, so the old probe starts at most `floor(W / (I − e)) + 1` runs in W. The domain makes I − e ≥ I / 2 > 0, so the bound is at most `2W / I + 1`. With W = 6000 ms:
     - I = 5000 ms: at most 2;
     - I = 1000 ms: at most 7;
     - I = 200 ms: at most 61.
   - **Below 200 ms the bound is not used.** At I = 100 it divides by zero and below that it is negative. The contract allows I from 1 ms (fact 3).
   - **Estimate for I < 200 ms.** It is not a bound and nothing gates it. The old probe starts about `floor(W / max(I, R)) + 1` runs in W, where R is the shortest run time of that check during W (the request to the target plus `onResult`). At I = 1 ms, R decides: for a local target with R between 2 and 10 ms and W = 6000 ms, that is about 600 to 3000 doubled runs.
     - R is measured, not assumed: the result field `latencyMs` is a lower bound for R. So `floor(W / max(I, min latencyMs)) + 1` is an upper estimate from the api's own data.
   - The docs state the domain, the bound and the estimate as a known limit, and advise against a probe rotation on checks with I < 200 ms during busy times.
   - The first spec's "at most one extra sample" and the second spec's "W ≤ 2000 ms plus signal latency" were both wrong: W also holds the readiness and the equality check.
   - The sample statistic E that the tests use (Counterexamples "Extra samples") is a different quantity: the surplus of samples over a minimum gap-keeping subset. Its lemma gives E = 0 for one probe and E ≤ 2·floor(W / (I − e)) + 3 for a handoff.
   - Measured in `rotate.sh` per location: W from Docker events, E in the baseline (must be 0), over the rotation window (must be within the lemma bound) and after the handoff (must be 0). It also reports K, the samples in [T_s, T_d), next to the doubled-runs bound. Both formulas live in `cli/test/samples.sh` with their domains:
     - `doubled_runs_bound I W` prints `floor(W / (I − 100)) + 1` for I ≥ 200. Below 200 it exits 2 with `no bound below 200 ms`, so it can never divide by zero or print a negative count.
     - `extra_samples_bound I W` prints `2·floor(W / (I − 100)) + 3` only when the lemma condition A + 2e < I holds, that is I > 700. Otherwise it exits 2.
     - The CI check interval of 5000 ms (a literal in Acceptance 1) is inside both domains. `samples.test.sh` checks both domains with literals (Counterexamples "Extra samples").
3. **Upgrade downtime and copy I/O.**
   - Downtime D runs from `stop` to ready: stop (≤ 10 s grace per service, in parallel), snapshot, edit, `up -d` and readiness. The pull runs before the stop and is not part of D.
   - The snapshot reads every data volume once and writes the same bytes as tar files. A rollback reads them again and rewrites the volumes. The kept snapshot uses one extra copy of the data volumes on disk.
   - A rollback adds one `sync -f` per restored volume, which flushes the dirty pages of that filesystem; on an idle CI host this is well under a second. The helper sweep is one or two `docker ps` calls per use. Both are inside the rollback time that `upgrade.sh` reports.
   - Snapshot time is roughly the volume size divided by the disk throughput: a few MB on the demo (< 5 s), about 10 s per GiB at 100 MB/s.
   - Measured, three ways, all in `upgrade.sh`:
     - the CLI lines `snapshot <bytes> bytes in <ms> ms` and `the stack was down for <ms> ms`;
     - the size of the snapshot directory (`du -sb`);
     - the largest `always-healthy` result gap across the real upgrade (Counterexamples "Gap rule" statistic, without the bound). This is an api source, independent of the CLI.
   - The issue sets no downtime budget. The PR quotes the numbers.
4. **CLI binary size.** It grows by the new modules. The existing `cli-build` step "Binary size and init time" (`.github/workflows/ci.yml` lines 407–414) reports it. The PR quotes the size before and after.
5. **CI time.** `cli-rotate` takes about 21 min (the retired-credential case shares the overlap wait and adds about 1 min), because it waits the real 10-minute overlap and runs the resume case. `cli-upgrade` takes about 23 min (the two hard-kill cases each add a failed upgrade and a manual restore; the pending-create case waits up to 70 s more). Its `timeout-minutes: 40` stays. Both run in parallel with the existing jobs.

## Security impact

Security impact: yes
The change calls admin token routes, writes secret files, verifies image provenance, runs privileged one-shot containers on data volumes, and adds CI jobs with a token.

These checklist items apply:

- **Secrets in errors, logs and responses.**
  - Bearer tokens and new secrets travel only on stdin to `docker compose exec -T` or `docker exec -i`.
  - Argv, env, the journal and the output never carry them. The tests grep the captured output, the journal and the recorded spawn argv for every secret.
  - Api error bodies are not echoed. Only the status code and a fixed text are shown.
  - Token names from the api go through `shown()`.
  - `gh` and Docker stderr go through `firstLine` (`maskUserInfo`).
- **Auth order and status codes.**
  - The capability and identity checks run before the first api write.
  - Each api status gets a defined outcome: 401, 403, 404, 409 and 429 are named, and anything else is `unexpected status`.
  - **Unheld active tokens.** While the CLI's bearer authenticates, a lost answer does not leave an active token whose secret nobody holds once the command has ended with exit 0 or with a dropped item. When the bearer stops authenticating (an `admin` journal whose host secret is revoked, expired or retired after another client's rotate, or a `probe` journal whose `secrets/admin-token` is), the CLI stops with exit 1, the journal kept and no write. Before that stop, its barrier has run whenever `inFlight` was set (decision 8 "Resume order"), so no write it sent is still pending. Then these tokens may stay active with no held secret until a person runs the manual recovery (decision 8 "Manual recovery", Risks "A revoked or retired admin token stops the admin rotation"): in any state, `tokenId` after a landed rotate whose answer was lost; in `replacing`, a replacement made by an unanswered create; in `dropping-orphans`, an orphan; from `saved` on, R after another client rotated it. The CLI cannot prevent these: it has no credential left that the api accepts. The manual recovery ends all of them in every state, in a fixed order: the barrier by hand first (so no write of any earlier run can land later, and every pending client is fenced), then, with another admin token X, the revoke of every active token named `replacementName` and of `tokenId` unless it is X, a check, and only then the deletion of the journal. For a `probe` journal the person instead writes a working admin secret and reruns. Replacements carry the journal's random `replacementName` (the api does not make names unique, fact 7). Every rotate and create `POST` is marked `inFlight` in the journal before it is sent. When it is not answered, the barrier ends the api process before any readback, sweep or further `POST`, so no earlier write can be applied later. Every ambiguous or lost create is followed by a sweep, and the final sweep in `switched` revokes every token of that name except `activeTokenId` before the journal can be removed. The lost token is revoked after the switch (decision 8 "Barrier" and "Lost answer").
  - **Held secrets.** A held secret is never revoked, with one exception. The sweep of "Lost answer" step 2 runs only when no host or staging file can hold a replacement (decision 8 "Reconcile"), the final sweep (step 5) and the orphan step of the drop path leave out `activeTokenId`, the only replacement whose secret a file holds from `saved` on, a stage error always goes through the reconcile before it can count as a lost answer (decision 8 "Stage errors"), and the revoke guard refuses a revoke of the calling token or of `activeTokenId`. **The exception** is the drop path's revoke of R = `activeTokenId` (decision 8 "Lost answer" step 4a, the guard's "Drop exception"), whose secret the host file holds; for `admin` R is also the calling token. It is sent only in state `dropping-replacement`, after the post-check read the lost token `gone` and after every orphan was confirmed revoked. The item is removed right after the revoke is confirmed (a parsed `200`, or for `probe` a readback by the admin secret), so nothing goes on to use R's secret. When it is not confirmed, the journal stays and the item does not go on either. The host file then keeps a secret that no longer works, as it would after a person revoked the token.
  - Reconcile bearer: no owned host file is used as a bearer before the reconcile ends. In a probe journal the order is: the staging checks, the `lstat` checks of `secrets/admin-token`, its read and content check, the capability call with it, and only then the confirmation (decision 8 "Reconcile" step 4).
  - A replacement is created in exactly the two cases of decision 8 "Lost answer": (1) a readback `changed` (a changed `rotatedAt` on a token that is neither revoked nor expired) after a `rejected`, `ambiguous` or `none` class ("Rotate outcome"), and (2) an `ok` rotate answer whose secret the stage-error reconcile found in no staging file ("Stage errors"). In both the api has rotated the token and the new secret is not stored. In addition, every create needs a fresh readback `changed` of the lost token right before it ("Lost answer" step 3). A rotate that the api refused with `rotatedAt` unchanged, or whose readback is `same`, `gone` or `unknown`, never leads to a replacement. `gone` takes precedence over `changed`, so a revoked or expired token is never replaced, even when it was rotated before it was revoked.
  - **Order guarantee against a racing revoke.** The check before the create cannot see a revoke that commits while the api awaits the create's body (fact 7). So a replacement R is kept only after the post-check ("Lost answer" step 4a): a readback of the lost token that starts after R's `saved` write, so after R was committed, and shows the token active. A `gone` there writes `dropping-orphans`, revokes the orphans, writes `dropping-replacement`, revokes R and removes the item. The CLI therefore never keeps a replacement for a token whose revocation or expiry committed before the post-check, which includes every revocation before R existed. A revocation after the post-check meets R as the item's token; the CLI prints R's id and the docs say to revoke R to stop that access. For `admin`, the only exception is the api's last-admin rule, which the CLI reports with exit 1.
  - **`401` is not `gone`.** The api authenticates before it shows metadata (fact 7), so the CLI never reads a token's state through that token's own revoked secret. A `401` stops the run with exit 1, the journal kept and no write ("Readback", drop path steps 2 and 4). There is no exception. A `401` cannot tell a revoked or expired token from one that another client rotated and whose overlap has ended (fact 7 "What a `401` says about a known secret"). So it never confirms a revoke, also not R's revoke of itself in `dropping-replacement`. That case ends in the manual recovery, where another admin token reads R's real state.
  - **No write after the barrier from an earlier client.** Every rotate, create and revoke `POST` carries the api instance, and `API_SCRIPT` refuses to send it in another container run (decision 4 "Instance fence"). The barrier clears `inFlight` only after the instance has changed. So a `docker compose exec` client of a killed or timed-out call cannot create or rotate a token after the barrier, the sweeps or the final sweep, however late it reaches the daemon. The manual recovery starts with a barrier by hand for the same reason, so no such client can create a token after its sweep or after the journal is deleted.
- **Body and size limits.** Api answers are capped at 1 MiB in `API_SCRIPT`. Registry bodies are capped at 1 MiB, and registry pagination at 10 pages.
- **Input validation.**
  - Token ids match `^tok_[0-9a-f]{24}$`. Container ids match `^[0-9a-f]{64}$`. Service names and versions are validated. The journal and `upgrade.json` are validated on read like external input.
  - Api and registry JSON goes through own-property readers (`own()` in `cli/docker.ts`), never trusted as typed.
  - Locations match `^[a-z0-9][a-z0-9-]{0,31}$`, as in `secrets-init.mjs`.
  - The effective mounts of the pulse services are validated before an upgrade stops anything (decision 10 "Data mounts"): `volumes`, `tmpfs`, `configs`, `secrets` and `volumes_from`, with paths normalized as `check-setup.sh` rule 8 does. An override that moves data out of a named volume, or mounts anything at, below or above a writable data volume, refuses, so a rollback never "restores" a volume that does not hold the data.
- **SSRF and redirects.** The registry host is fixed to `https://ghcr.io`, with `redirect: "error"`. The api URL is fixed to `127.0.0.1:3000` inside the api container. No user input builds a URL or a path beyond the validated token id.
- **Atomic, path-safe writes.**
  - Secret files, the journal, `compose.yaml`, `upgrade.json` and the snapshot files are written `wx` with temp names in their final directory, fsynced and renamed, with the directory fsynced.
  - A new secret goes first to a 0600 staging file in the 0700 `secrets/` directory and reaches the host file only by rename. Staging files are name-checked, never read by `secrets-init`, and never left behind after a finished run.
  - Links and non-regular files are refused, and directory modes are checked.
  - The snapshot directory is 0700 with 0600 files, because it holds the databases. Tars are checked against their recorded sha256 before a restore deletes anything.
  - A restored volume is flushed (`sync -f /to`) before `restored` is written, so the state never claims data that is not on disk.
  - Helper containers carry labels, and the helper sweep removes every leftover one before any restore or start, so a killed run's helper cannot write into a volume that a later step uses. Helpers start in two steps (`docker create`, then `docker start` of the id that create printed, decision 13 "Two-step start"), so a Docker client that a killed run left behind can never start a helper after a sweep: a late create only leaves an inert `created` container, and a late start of a removed container fails.
  - The lock file is read as untrusted input (`lstat`, size limit, fixed line shape, the identity shapes of decision 3). A stale lock is broken only on the same host, for a gone or reused pid in the same boot and pid namespace or for a lock from an earlier boot, under a second exclusive file, and only when its bytes are unchanged (decision 3). The judgement uses kernel values from `/proc`, not `ps` output, so the environment of the reader (`TZ`, locale) cannot make a live lock look stale. The lock and break files hold no secret.
  - The snapshot directory chain is fsynced in each parent before the stack stops (decision 13 step 4), so the record of a stopped and changed stack survives a power loss.
  - Every data volume of the snapshot set must exist with this install's labels before the upgrade starts and around every helper (decision 13 "Volume check"), so a helper never snapshots or fills a volume that Docker created on the fly, and no service is started on one.
- **Dependency pins.**
  - Images are verified by attestation (repository, signer workflow, source ref, no self-hosted runner) before they are pulled by digest.
  - The snapshot and restore containers use the pinned `oven/bun` image of `secrets-init`, with `--network none`, `--cap-drop ALL`, only the capabilities that `tar` needs, and `no-new-privileges`. They have fixed names so an abort can remove them.
  - No new package or action.
  - The CI jobs use `persist-credentials: false` and the existing SHA pins. `GH_TOKEN` is the job token with `attestations: read`.

## Rollout order

One repository (deploy). No service, contract, kit or config change.

Who still runs during the rollout:

- **Installations on `0.1.0`** (written by an older CLI, or by this one before an upgrade) keep working. `token rotate` refuses there with a pointer to `pulse upgrade`, and `upgrade` moves them to the pinned release.
- **Installations written by an older CLI binary.** They are format 1, so the new commands accept them.
- **An older CLI binary on a new installation.** It still sees `.pulse-init.lock` and refuses while it exists, whatever its content. A new CLI never breaks the two-line lock of an older CLI (decision 3), so a running older `pulse init` is never interrupted. `secrets/.pulse-rotation.json` and `.pulse-upgrade/` are not in its managed file list (`cli/write-install.ts` lines 33–44), so `pulse init --force` neither touches nor reports them.
- **A rotated secret** (49 characters, `pulse_` prefix) passes `tokenContentValid` and the `secrets-init.mjs` token rule (lines 22 and 36–42). So an older CLI's `pulse init --force` keeps it, and `secrets-init` copies it.
- No breaking change, so the release line does not take a major step.

## Counterexamples

Each rule comes with a case that it must reject or that a wrong implementation gets wrong. Unit tests use these literals.

- **Gap rule** (decision 15).
  - **Inputs.** The check is `always-healthy`, with interval I = 5000 ms and allowance A = 500 ms. The window is [W0, W1] in host epoch ms, given per check in Acceptance 1.
  - **Sample set.** All results of that check with that location whose `timestamp` lies in the window, read with `GET /checks/always-healthy/results?limit=1000` and paged with `before` until a result older than the window start is seen. The pages must reach past the window start; otherwise the check fails.
  - **Statistic.** Sort the sample timestamps, add W0 and W1 as edges, and take the differences of neighbors. Every difference must be ≤ I + A. No averaging and no percentile.
  - **Examples.**
    - Timestamps `[0, 5004, 10009, 13000, 18003]` in the window [0, 18003] pass (largest difference 5005).
    - `[0, 5004, 10009, 15600]` fails (5591).
    - A stop-then-start probe whose last run started 4000 ms before a 3000 ms restart, plus a 600 ms first delay, posts its next result 7600 ms after the previous one. It must fail.
    - Results only from `us` must not hide a missing `eu`: the rule runs per location.
- **Extra samples.**
  - **Constants.** I = 5000 ms (check interval), A = 500 ms (gap allowance, decision 15), e = 100 ms (earliness: two runs of one probe and one check start at least I − e apart, fact 3).
  - **Sample set.** As for the gap rule: the sorted timestamps s_1 ≤ … ≤ s_N of one check and one location in the window, N ≥ 2. The window edges W0 and W1 are not samples.
  - **Statistic E (surplus).** A chain is a subset that contains s_1 and s_N and whose neighbor differences are all ≤ I + A. C is the size of the smallest chain, computed greedily: start at s_1; from the current sample, go to the latest later sample that is at most I + A after it; stop at s_N. E = N − C. E is only computed when the gap rule holds for the window (then the whole set is a chain); otherwise the check has already failed on the gap rule. No averaging, no percentile, integers only.
  - **Lemma** (needs A + 2e < I, true for 500 + 200 < 5000):
    1. **One probe gives E = 0.** A sample s_i with 1 < i < N can be left out of a chain only if s_{i+1} − s_{i−1} ≤ I + A. For one probe that difference is at least 2(I − e) > I + A.
    2. **Handoff bound.** The old probe's samples are all before T_d, the new probe's all at or after T_s, W = T_d − T_s (Docker events, Acceptance 1), and the window holds at least 2 samples before T_s and at least 2 at or after T_d. Let K be the number of samples in [T_s, T_d). Then E ≤ K + 1 ≤ 2·floor(W / (I − e)) + 3.
       - Proof. Every sample before T_s is old. Each of them except the last one (o_a) has old neighbors on both sides, so by part 1 it is in every chain. The same holds after T_d for every sample except the first one at or after T_d (n_b). So only o_a, n_b and the K samples in [T_s, T_d) can be left out. The sample before o_a and the sample after n_b are in every chain and are at least 2(I − e) > I + A apart, so at least one sample between them stays. That gives E ≤ K + 1. Each probe has at most floor(W / (I − e)) + 1 samples in a span of W, so K ≤ 2·floor(W / (I − e)) + 2.
  - **Fixtures** (I = 5000, A = 500, e = 100; the self-test `cli/test/samples.test.sh` uses them as literals):
    - **Phase offset of the second plan review.** Old `[-5000, 0, 5000]`, new `[3500, 8500, 13500]`, T_s = 3000, T_d = 5500, W = 2500. Samples `[-5000, 0, 3500, 5000, 8500, 13500]`. The smallest chain is `[-5000, 0, 5000, 8500, 13500]`, so C = 5 and E = 1. K = 2 (3500 and 5000), so the bound K + 1 is 3 and 2·floor(2500/4900) + 3 is 3. The old statistic (count of neighbor differences below I − 100) gives 3 here and is wrong.
    - **Nearly in phase.** Old `[-5000, 0, 5000]`, new `[300, 5300, 10300]`, T_s = 200, T_d = 5100, W = 4900. Samples `[-5000, 0, 300, 5000, 5300, 10300]`. Greedy: −5000 → 300 → 5300 → 10300, so C = 4 and E = 2. The bound is K + 1 = 3 (K = 2) and 2·floor(4900/4900) + 3 = 5. A gate of `floor(W / I) + 1` = 1 on E would reject this correct handoff.
    - **One probe with lateness.** `[0, 5004, 10009, 15013]` gives E = 0. `[0, 4950, 9950]` (50 ms early) gives E = 0.
    - **Edges are not samples.** One probe `[0, 5004, 10009]` in the window [−400, 10009] gives E = 0. A chain that starts at the edge −400 would reach 5004 directly (5404 ≤ 5500), leave out 0 and give 1. That is wrong.
    - **Old probe never stopped.** Old `[0, 5000, 10000, 15000, 20000]`, new `[2500, 7500, 12500, 17500]`. Greedy keeps 0, 5000, 10000, 15000, 20000, so E = 4. Any window after the planned T_d with two posting probes gives E > 0 and fails the check "E = 0 after T_d".
    - **Gap failure first.** `[0, 5004, 10009, 15600]` fails the gap rule (5591), and E is not computed.
  - **Domains of the two bounds** (literals for `samples.test.sh`; `doubled_runs_bound I W` and `extra_samples_bound I W`, Performance impact item 2):
    - `doubled_runs_bound 5000 6000` prints 2, `1000 6000` prints 7, `200 6000` prints 61.
    - `doubled_runs_bound 199 6000`, `100 6000` and `1 6000` exit 2 with `no bound below 200 ms`. A function that evaluates the formula there is wrong: at I = 100 it divides by zero, at I = 1 it gives `floor(6000 / −99) + 1` = −60.
    - `extra_samples_bound 5000 6000` prints 5 and `extra_samples_bound 4900 4900` prints 5 (floor(4900 / 4800) = 1). `extra_samples_bound 701 6000` prints 2·floor(6000 / 601) + 3 = 2·9 + 3 = 21. `extra_samples_bound 700 6000` exits 2: the lemma needs A + 2e < I.
