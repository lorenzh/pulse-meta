# Factory and contributing

pulse is built by Paragon Factory agents from issues in this repository. Do not change a target repository by hand for a feature. Write an issue instead.

1. Open a feature issue here. [AGENTS.md](../AGENTS.md) says how to write one.
2. The `spec` workflow (`issue-review`, `plan`, `plan-review`) writes a spec in `.factory/work/<issue>/plan.md` and the target list in `targets.json`. The result is a spec pull request here.
3. Merge the spec pull request to approve the spec.
4. `factory-fan-out.yml` opens one child issue per target, linked as "blocked by" along `dependsOn`, and starts the children that wait for nothing.
5. Each child runs the `build` workflow (`implement`, `review`, and `security` when the spec says `Security impact: yes`) in its repository and opens one pull request that says `Closes lorenzh/pulse-meta#<child>`.
6. If the base branch conflicts, run `factory start --issue <child> --workflow merge --apply`.
7. Merge the pull requests. `factory-unblock.yml` starts waiting children and closes the feature when all are done.

## Quality gates and failure reports

**Build review gates.** The `review` state (`.factory/prompts/review.md`) sends a change back to `implement` when any of these holds: a defect proved by a failing test or command, red or unfinished CI on the pull request (`gh pr checks --watch`, 15-minute limit), new tests that also pass on the base version of the changed source files (the mutation step; refactors and docs are exempt), acceptance evidence missing from the pull request body, a section with `Behavior change: yes` and no source change (only tests, fixtures, or docs) without a person's approval, a new check whose expected value comes from the file or code it checks, or a security checklist item without a test or command. When the implementer finds that the code already has the behavior, it requests a `needs-input` hold instead of a review; after such a hold the review holds too. It reads the whole diff, and it cannot return `complete` without that. Its outcome message ends with `verdict: ship` or `verdict: fix first`.

**Spec sections.** `plan` writes four sections before the repository sections, and `plan-review` sends the spec back when one is missing, empty, or contradicts the behavior: `## Security impact` (first line `Security impact: yes` or `no`, with a reason), `## Rollout order` (merge order and the older consumers on old pins at each step), `## Counterexamples` (one per hard rule; statistics defined exactly, never an average of percentiles), and `## Contract fields` (each new name with the search that shows no collision). Each repository section starts with a `Files:` list.

**Security state.** When the spec says `Security impact: yes`, the reviewer moves a clean change to `security` instead of `complete` (Factory has no conditional transitions, so the reviewer chooses). `security` (`.factory/prompts/security.md`, reviewer profile) runs the code locally, sends hostile inputs for each checklist item that applies, and records a test or command with its output for each. A finding goes back to `implement`; otherwise it completes. A spec without the section counts as `no`.

**Implementer evidence.** `implement` (`.factory/prompts/implement.md`) runs every acceptance check of its spec section, including the compose end-to-end test, runs the mutation step, and writes the results into the pull request body through `gh api -X PATCH` (`gh pr edit` fails on the token scopes). In its first run it opens the draft pull request itself. Build targets do not commit `.factory/`, so the pull request body is the only place for the evidence.

The security checklist covers secrets and server texts in errors, logs and responses; auth order and status codes; body and size limits on every method; input validation at trust boundaries, with validators that never throw; accessor and getter execution; SSRF, redirects and header forwarding; atomic, path-safe file writes; and dependency pins.

**Reviewer profile.** Both roles run on Claude (`.factory/config.yaml`, `models`): the worker on `claude-opus-5-5` at effort `medium`, the reviewer on `claude-opus-5-5` at effort `high`, with an adversarial prompt. The audit workflow uses `auditor`: `claude-opus-5-5` at effort `xhigh`.

**Agent CLI versions.** `factory-run.yml` installs Claude Code at the version in `FACTORY_CLAUDE_VERSION` (`latest` by owner decision; `2.1.314` when unset) and skips the Codex CLI, which no model in the loop uses. The repository variables `FACTORY_CLAUDE_VERSION` and `FACTORY_CODEX_VERSION` accept only an exact `MAJOR.MINOR.PATCH`, `latest` or `skip`. The step "Install agent CLIs" fails on anything else, such as a range or a `v` prefix.

**Failure comments.** When a job of `factory.yml`, `factory-run.yml`, `factory-fan-out.yml` or `factory-unblock.yml` fails, its last step comments on the issue with the run link, the failed step, and the command that starts it again. This also covers failures before the Factory claim, which leave no Factory comment.

**Sweeper.** `factory-sweep.yml` runs every 30 minutes. It comments once on each open issue that has a `factory/<workflow>/<state>` label, no open blocker, no hold, no active run, and no change for 60 minutes (repository variable `FACTORY_STALL_MINUTES`). An active run is any `factory-run.yml` run in status `in_progress`, `queued`, `waiting`, `requested`, or `pending`, found through every page of each status. It changes no labels and no claims. It does not comment again while its own or a failure comment is the last comment on the issue.

**Audit issues.** `factory-audit.yml` opens audit issues of four kinds. `.github/audits/open-issue.sh` holds the rules, and `.github/audits/<kind>.md` the issue text:

- `security`: daily, one target repository per run in rotation. The issue asks for an audit of `main` with hostile inputs along the security checklist.
- `performance`: Tuesday and Friday, one service or library repository per run in rotation (every target except config and deploy). The issue asks for measurements with numbers and commands: `EXPLAIN QUERY PLAN` for the request path and startup, a startup CPU profile, costs that grow with data, memory over a long run, test CPU per file, and for the website the JS/CSS budget and Lighthouse; compared with `bench/budgets.json` where it applies.
- `quality`: Monday, one target repository per run in rotation (the security list, one repository per week). The issue asks for code quality measured with the repository's own scripts and pulse-config's shared configuration, no new tools: lint and typecheck findings, cognitive complexity hot spots, duplicated logic across files or repositories, dead code (found with `grep` and `tsc`), test quality (coverage, untested risky branches, tests that assert nothing), swallowed errors and inconsistent error shapes, consistency with `AGENTS.md` and the other services, and docs that contradict the code. Every finding cites file and line; style-only items are notes, not issue candidates.
- `architecture`: Thursday, one issue for the whole system, naming every repository. The issue asks for machine checks: pin drift of contract, kit and config, the largest files and functions, duplicated helpers that belong in kit, docs that no longer match the code, earlier findings that are still true, and the dependency direction.

Each issue gets the label of its kind and, for security, performance and quality, `audit/<repo>` (both created with a description when missing). It gets no `target/<repo>` label: the audit runs on the meta target and only reads the repository. It also gets `factory/audit/audit`, and the job starts the audit at once (see the audit workflow below): `gh workflow run factory-run.yml --ref <default branch> -f issue=<n> -f admission=label`, after it checks that `<n>` is a canonical issue number. The dispatch is needed because a label set with the job token (`GITHUB_TOKEN`) triggers no `factory.yml`; GitHub creates runs for events of that token only for `workflow_dispatch` and `repository_dispatch`. `factory-fan-out.yml` starts its children the same way. The job has `actions: write` for it; it does not use the bot token, whose events `factory.yml` ignores. A dedupe hit starts nothing and changes no labels. The owner can still stop an audit: cancel its `Factory run #<n>` workflow run (`gh run cancel <run-id>`) and remove the `factory/audit/` label from the issue. Cost: under the fast schedule this is up to 11 audits per week (7 security, 2 performance, 1 quality, 1 architecture), each with at least two `xhigh` states. An open issue of the same kind (and the same repository) blocks a new one, which also caps the number of issues. A manual run (`gh workflow run factory-audit.yml -f kind=<kind> [-f target=<repo>]`) picks the kind and, optionally, the repository.

*Changing the schedule.* These are fast-development intervals, to be relaxed to weekly, monthly and monthly later. Each `cron` line at the top of `factory-audit.yml` maps to one kind in the `case` on `AUDIT_SCHEDULE` in `open-issue.sh` and in the `concurrency` group of the workflow, which puts scheduled and manual runs of one kind in one group. Change the line, its `case` pattern and its group pair together; `test.sh` fails when a cron line maps to no kind or to another group than its kind. The rotation does not depend on the interval: security takes the next repository each day, performance each half week (Monday to Thursday, Friday to Sunday), quality each week.

**Audit workflow.** The Factory workflow `audit` (`.factory/config.yaml`) runs an audit issue on the meta target. `factory-audit.yml` starts it when it opens the issue. It has no gates: merging the report pull request accepts the report.

1. `audit` (`.factory/prompts/audit.md`) reads `main` of the repositories in `.repos/`, works on copies when it installs or runs one, and changes nothing there. It writes `audits/<kind>/<scope>.md` and `.json` (scope is the repository, or `system` for architecture). The file names carry no date: a new audit replaces the report at its path, the report body states the audit date and the examined commit SHAs, and git history keeps older reports. Every checklist item of the issue is `checked`, `not applicable` or `blocked` with a reason. Each finding has an id, the repositories, file and line, a severity (P1 to P3), the command, its exit code, an output excerpt and the examined commit SHAs; performance findings add value, unit, repetitions, baseline and budget. At most 5 findings are issue candidates; the rest are notes. A performance audit reads the latest nightly bench of pulse-api and `bench/budgets.json` first and measures anew (`bun bench/run.ts --a <sha> --b <sha>`) only on a suspected deviation.
2. `audit-review` (`.factory/prompts/audit-review.md`, terminal) re-runs the command of every P1 and P2 finding, removes findings it cannot reproduce, corrects severities, and sends gaps (missing items, missing fields, checks that could have run) back to `audit`. Otherwise it completes and the pull request is ready for the owner.

The agent creates no issues and writes no comments. After the merge the owner picks the candidates that become issues and closes the audit issue (the report pull request says `Refs`, not `Closes`); an open audit issue blocks the next one of its kind and repository. Chaining workflows may take the issue step over later. Both states use the profile `auditor` (`claude-opus-5-5`, effort `xhigh`, owner decision) with a deadline of 120 minutes (`timeoutMs: 7200000`; the default 60 minutes stopped the first performance audit). The prompts budget the work to fit: no background or parallel subagents, at most one bench A/B comparison of 2 rounds per side, unfinished items `blocked`, and the structured outcome always returned.

*Security disclosure.* The pulse repositories are public, and so is the report. For a P1 or P2 security finding the committed report names location, class, impact and fix direction, but no working exploit, payload or reproduction command. The agent keeps its reproduction outside the repository. The two states run in separate jobs, so that local evidence does not reach the review: `audit-review` rebuilds the reproduction from location and class, and it removes any exploit text from the report.

*Labels.* The state labels `factory/audit/audit` and `factory/audit/audit-review` come from `factory state --apply`. Merging the report pull request triggers `factory-fan-out.yml`, which finds no plan and ends with a notice.

**Workflow script tests.** `.github/workflow-tests/test.sh` runs the scripts of the sweeper and the audit workflow against fixtures with a stub `gh` (needs bash, jq, python3 with PyYAML). It covers the rotation of each kind, dedupe on `audit/<repo>`, label creation, the start label and the dispatch of `factory-run.yml` (none on a dedupe hit or for a non-canonical issue number), `actions: write` on the job, the dispatch inputs, the mapping of every cron line to a kind, and that each issue text names the start label and the report instead of one issue per finding.

## Prompt injection and credentials

**Remaining risk.** The issue title, body and every comment, from any author, reach the agent. The agent runs with `permissionMode: auto` and holds the bot token (`GH_TOKEN`, write access to every pulse repository) and the Claude OAuth token in its environment. A comment on an issue with a `factory/` label can therefore try to make the agent push code or leak a token. Filtering comments by author needs a Factory feature (paragondata/factory#292). Giving the token only to the Factory publish, not to the agent, needs another one (paragondata/factory#292 or the linked upstream issue). Both are open.

**What the workflows do now.** No checkout keeps credentials (`persist-credentials: false`). No step runs `gh auth setup-git` or `gh auth login`. Git gets the token only through `GIT_ASKPASS` on the steps that run Factory, so no git config and no gh file stores one. Every action is pinned by commit SHA. The report loads d3 with Subresource Integrity.

**Interim rule.** Only the repository owner applies `factory/` labels. Before a person starts or restarts a run (label, `factory start`, `admission=restart`), they read every comment that arrived since the last run, and they remove or answer any comment that asks the agent to do something outside the issue.

Each repository's `AGENTS.md` holds its code conventions (test-driven development, end-to-end tests, lint). Its `docs/development.md` shows the commands.
