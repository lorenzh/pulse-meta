# Factory and contributing

pulse is built by Paragon Factory agents from issues in this repository. Do not change a target repository by hand for a feature. Write an issue instead.

1. Open a feature issue here. [AGENTS.md](../AGENTS.md) says how to write one.
2. The `spec` workflow (`issue-review`, `plan`, `breakdown`, `plan-review`) writes a spec in `.factory/work/<issue>/plan.md`, the target list in `targets.json`, and one task list per target in `tasks/<target>.json`. The result is a spec pull request here.
3. Merge the spec pull request to approve the spec and its task lists.
4. `factory-fan-out.yml` opens one child issue per target, linked as "blocked by" along `dependsOn`, and starts the children that wait for nothing.
5. Each child runs the `build` workflow in its repository, one task per run (see [Task loop](#task-loop)): `implement` and `task-review` for each step task, then `implement` of the final task, `review`, and `security` when the spec says `Security impact: yes`. It opens one pull request that says `Closes lorenzh/pulse-meta#<child>`.
6. If the base branch conflicts, run `factory start --issue <child> --workflow merge --apply`.
7. Merge the pull requests. `factory-unblock.yml` starts waiting children and closes the feature when all are done.

## Task loop

A child works through its task list one task per agent run, so that no run has to build a large section at once (the three `HARNESS_TIMEOUT` stops, #451, #526 and #549, were all large sections). The design follows the `spec-driven-development` skill: split only at real seams, one task at a time, a fresh reviewer after each implementer, and a review of the whole branch at the end.

**Task lists.** `breakdown` (`.factory/prompts/breakdown.md`, profile `breakdown-writer`) writes `.factory/work/<feature>/tasks/<target>.json` for every entry of `targets.json`: 1 to 8 tasks `T1`..`Tn`, the last one `kind: "final"`. Each task has `title`, `files`, `behaviorChange`, `spec` (the part of the section it implements), and `acceptance` (`command` and `expected`, a literal or an independent source). A change in one file or under about 200 changed lines is one task; tests go with their code; the final task holds the whole-change checks (compose end-to-end test, security checklist, pull request evidence). A small section is only its final task, and runs as before. `plan-review` runs `node scripts/factory-tasks.mjs --check <work dir>` (one file per target, the schema, every `Files:` path in a task), checks the cut, and sends spec defects to `plan` and task defects to `breakdown`. The task file never changes after the merge. `implement` may change other files than a task lists when the code needs it, with the reason in the commit; moving work between tasks needs a `needs-input` hold.

**Progress.** No file holds a done flag: a child cannot commit `.factory/`, and its meta clone is read-only. `scripts/factory-tasks.mjs --issue <child> --target <target> --base <sha>` (Node, no dependencies) derives the progress from the run comments of the issue, counting only comments of the bot (`FACTORY_GITHUB_ACTOR`, or the login of the `gh` token) and the historical `lorenzh-factory-bot` account with a run record: a `task-review` transition whose message ends with `task-accepted: Tn @ <sha>` or `task-rejected: Tn`, `implement` retries and holds, and send-backs of `review` and `security`. Each implement commit ends with the trailer `Task: Tn`. An owner comment line `task-carried: Tn @ <sha>` skips a task whose records GitHub hides after an account suspension. It is not an acceptance: the script lists it under `carried`, and `review` re-runs its checks. The script prints `status`, the task `next`, its `taskBase` (the commit of the newest acceptance, or the branch base), and its `rejections` and `retries`:

| `status` | `implement` does | then |
|---|---|---|
| `no-task-file` | the whole section, as before task lists (specs approved before them) | `review` |
| `open` | step task `next` | `task-review` |
| `fix-task` | the findings of the task review that rejected `next` | `task-review` |
| `final` | the final task, all checks, the pull request evidence | `review` |
| `fix-review` | the findings of the `review` or `security` run that sent the change back | `review` |
| `stuck` | nothing; `needs-input` hold | — |

`task-review` (`.factory/prompts/task-review.md`, profile `task-reviewer`) reviews only `git diff <taskBase>..HEAD` against the task: its acceptance commands, the required checks, the mutation step against `taskBase`, and the security items it touches. It does not wait for CI. Both verdicts go to `implement`. The final `review` still reads the whole diff and waits for CI, and it also sends the change back while a step task has no acceptance; a finding names the task it belongs to.

**Limits.** The third rejection of one task becomes a `needs-input` hold of `task-review`. More than two `retry` outcomes on one task make it `stuck`, and `implement` holds. A hold resets both counts of the task: the person's answer starts a new budget. `factory-run.yml` runs with `--chain-limit 24` (two runs per step task, up to 8 tasks, and room for repairs). There is no cost budget. A forged comment from another account does not count, but every agent holds the bot token and could write one (see "Prompt injection and credentials"); the final `review` is the only check against an agent that marks its own task accepted.

**Restart after a timeout.** When the run step of `factory-run.yml` stops with `HARNESS_TIMEOUT`, the step "Restart once after a harness timeout" (`.github/run/auto-restart.sh`) comments on the issue with the marker `<!-- pulse-factory-auto-restart <workflow>/<state> -->` and dispatches `admission=restart`. The work that the harness published stays on the branch, and `implement` continues the open task from `git log <taskBase>..HEAD`. It restarts a state once: when the newest marker of the bot names the same state and no run of that state finished after it, the failure comment below appears instead. Comments that arrived during the run reach the restarted agent unread by a person.

**Tests.** `node --test scripts/*.test.mjs` covers the task file rules, `--check`, and every status. `.github/workflow-tests/task-loop.sh`, sourced by `test.sh`, runs the script and the restart against a stub `gh`.

**Rollout.** Children that were fanned out before task lists keep `no-task-file` and run as before. A spec that gets task lists after its plan was written goes back to `breakdown` once. The state labels `factory/spec/breakdown` and `factory/build/task-review` come from `factory state --apply`.

## Shared findings

Sometimes one child of a feature answers a question that the spec asks several children, such as the TS7 question that #324 asked contract and config. Shared findings let the other children read that answer instead of working it out again (#576). Factory 0.8.0 publishes only the active target's branch, so pulse-meta publishes them itself.

**Where they live.** One branch per feature, `factory/findings/<feature>` in pulse-meta, holds one file, `.factory/work/<feature>/findings.md`. Never `main`: the publisher never pushes the default branch, never force-pushes, and nothing merges the branch. Context clones fetch only `HEAD`, so readers use the API: `gh api "repos/lorenzh/pulse-meta/git/ref/heads/factory/findings/<feature>" --jq .object.sha`, then `gh api "repos/lorenzh/pulse-meta/contents/.factory/work/<feature>/findings.md?ref=<sha>" -H 'Accept: application/vnd.github.raw'`. HTTP 404 from the first call means no findings; any other error is named in the outcome, never taken as absence.

**Writing.** `implement` (`.factory/prompts/implement.md`, "Shared findings") reads the findings before the task and appends a reusable finding as one JSON line to `.factory/findings-outbox.jsonl` in the root of the target clone. Git ignores it there (`exclude: [ /.factory/ ]`), so Factory never commits it. A line has exactly the keys `id` (`^[a-z0-9][a-z0-9-]{0,47}$`), `question` (at most 300 code points), `answer` (2000), `command` (500) and `result` (1000), each a non-empty one-line string without control or bidi characters, `<!--` or `-->`. The outbox holds at most 64 KiB, 256 non-blank lines and 10 distinct ids. Author, date and feature are never in the line: the publisher derives them. The writer rule forbids secrets, tokens, credentials, environment values, customer data and private details, because the repository is public.

**Publishing.** `factory-run.yml` deletes the outbox before the run step ("Clear the findings outbox"), so a reused checkout never publishes another issue's entries. After the run step, a fresh App token and "Publish the shared findings" run `node scripts/factory-findings.mjs publish` from the trusted checkout of `main`, with `always()`, not for a cancel or a skipped run, and with `continue-on-error`, so a publish failure never changes the job result, the restart or the continuation. The script:

- derives the feature from the job's issue only: a single `target/<name>` label (not `meta`), the first body line `Part of #<feature>: `, a `blocked_by` row of the feature with the child's number in this repository, and an open feature without a `target/` label. An issue without the line or a target label is not a child: a warning, no publish. A broken link is `not-linked`, a closed feature `parent-closed`.
- reads the outbox only after `lstat` checks (`.factory` a real directory, the outbox a regular file, no symlinks), `git check-ignore`, a real-path check, and an `O_NOFOLLOW` open of at most 64 KiB + 1 byte. It validates every line: the schema (duplicate keys are refused, because `JSON.parse` would drop the earlier value unchecked), the limits, valid UTF-8, and the token patterns, on each value and on the raw line (GitHub, Anthropic, OpenAI, Slack, AWS and npm tokens, private keys, JWTs, bearer values, and its own `GH_TOKEN`). An outbox is published whole or not at all. Errors name the line, id, field and rule, never a value.
- appends each entry as a block under a marker `<!-- finding <child>/<id> sha256:<hash> -->`, with `Author: #<child>` and the UTC date. The file is append-only: earlier bytes stay, and no entry is rewritten. The same identity with the same hash is a replay and is skipped, in the file or earlier in the outbox, so re-recording is idempotent; the same identity with another hash is a `conflict`. A foreign header, a file over 256 KiB, a branch without the file, or a branch commit that touches another path is `branch-invalid`.
- runs every `git` command without global or system config (`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`), without hooks, fsmonitor or pager. The agent controls the target clone's `.git/config` and could write `~/.gitconfig`: a `core.fsmonitor` there runs a command even during `check-ignore`, and `url.<x>.insteadOf` or `credential.helper` would redirect or capture the push. `check-ignore`, the only call in the target clone, also runs without `GH_TOKEN` in its environment.
- fetches the default branch and the findings branch into a fresh partial clone per attempt, commits only the findings path on top of the branch tip (or of the default branch on first creation), and pushes without force. A rejected push is retried with a fresh fetch, at most 5 attempts (backoff 1, 2, 4, 8 s). It logs `published N` with the commit SHA, also to the step summary.
- on any failure, comments on the child with the marker `<!-- pulse-factory-findings-failed -->` and the reason class (`invalid-outbox`, `not-linked`, `parent-closed`, `conflict`, `branch-invalid`, `push-failed`, `api-failed`). For `push-failed` and `api-failed` the comment also lists the validated lines, serialized from the parsed fields (the raw outbox text is never kept), and the next `implement` run records them again (appending only lines that the outbox does not already hold). It keeps the outbox after a failure and deletes it after a publish or a replay.

**Freshness.** Findings appear when the child's job ends, which can be up to 24 chained states later. Children that run in parallel may not see each other's findings; no `dependsOn` edge is added for it.

**Plan.** `plan` (`.factory/prompts/plan.md`) reads the feature's own findings, which exist only when a plan is redone after children ran. It publishes none: when several repository sections ask the same question, each says that the answer is a shared finding.

**Closure.** `factory-unblock.yml` runs "Remove the findings branch" (`scripts/factory-findings.mjs cleanup`) after every issue closure. A closed issue with a `target/` label other than `target/meta` is a child, and nothing happens; for any other issue it deletes `factory/findings/<issue>` (HTTP 404 or 422: already gone). The publisher checks the feature before each attempt and after a successful push, and deletes the branch itself when the feature closed meanwhile, so the close and the push converge on no branch. Reopening a feature starts without findings. A person removes a stuck branch with `gh api -X DELETE repos/lorenzh/pulse-meta/git/refs/heads/factory/findings/<feature>`.

**Permanent findings.** Nothing merges the findings into `main`. A finding that should last goes into a normal pulse-meta pull request by a person.

**Tests.** `node --test scripts/*.test.mjs` covers the ref guard, the validation rules and their counterexamples, the rendering, dedupe, `planAppend` and the link derivation. `.github/workflow-tests/findings.sh`, sourced by `test.sh`, runs the publisher and cleanup against a local bare repository with a stateful stub `gh` and a `git` wrapper: first, second and replayed publication, conflicts, re-recording, every refusal, the token patterns (no fixture value in any output), concurrent creation and update, bounded retries, the close/push race in both orders, cleanup answers, the prompt rules and the workflow wiring. Not yet proven live: whether Claude's sandbox writes the outbox, and whether the App token creates and deletes the branch; the first child that records a finding checks both (spec #576, acceptance 7).

## Quality gates and failure reports

**Build review gates.** The `review` state (`.factory/prompts/review.md`) sends a change back to `implement` when any of these holds: a defect proved by a failing test or command, red or unfinished CI on the pull request (`gh pr checks --watch`, 15-minute limit), new tests that also pass on the base version of the changed source files (the mutation step; refactors and docs are exempt), acceptance evidence missing from the pull request body, a section with `Behavior change: yes` and no source change (only tests, fixtures, or docs) without a person's approval, a new check whose expected value comes from the file or code it checks, or a security checklist item without a test or command. When the implementer finds that the code already has the behavior, it requests a `needs-input` hold instead of a review; after such a hold the review holds too. It reads the whole diff, and it cannot return `complete` without that. Its outcome message ends with `verdict: ship` or `verdict: fix first`.

**Spec sections.** `plan` writes four sections before the repository sections, and `plan-review` sends the spec back when one is missing, empty, or contradicts the behavior: `## Security impact` (first line `Security impact: yes` or `no`, with a reason), `## Rollout order` (merge order and the older consumers on old pins at each step), `## Counterexamples` (one per hard rule; statistics defined exactly, never an average of percentiles), and `## Contract fields` (each new name with the search that shows no collision). Each repository section starts with a `Files:` list.

**Security state.** When the spec says `Security impact: yes`, the reviewer moves a clean change to `security` instead of `complete` (Factory has no conditional transitions, so the reviewer chooses). `security` (`.factory/prompts/security.md`, profile `security-reviewer`) runs the code locally, sends hostile inputs for each checklist item that applies, and records a test or command with its output for each. A finding goes back to `implement`; otherwise it completes. A spec without the section counts as `no`.

**Implementer evidence.** `implement` (`.factory/prompts/implement.md`) runs every acceptance check of its spec section, including the compose end-to-end test, runs the mutation step, and writes the results into the pull request body through `gh api -X PATCH` (`gh pr edit` fails on the token scopes). In its first run it opens the draft pull request itself. Build targets do not commit `.factory/`, so the pull request body is the only place for the evidence.

The security checklist covers secrets and server texts in errors, logs and responses; auth order and status codes; body and size limits on every method; input validation at trust boundaries, with validators that never throw; accessor and getter execution; SSRF, redirects and header forwarding; atomic, path-safe file writes; and dependency pins.

**Model profiles.** Every state has its own profile in `.factory/config.yaml` (`models`). Each writer is reviewed by the other model family. Writers on Claude `claude-opus-5-5`: `planner` (effort `high`), `implementer` (`low`) and `auditor` (state `audit`, `xhigh`); their reviewers run on Codex `gpt-6.1-sol`: `spec-reviewer`, `plan-reviewer`, `task-reviewer`, `code-reviewer` and `security-reviewer` at `modelReasoningEffort: high` (the last two with adversarial prompts) and `audit-reviewer` at `xhigh`. The merge pair is swapped: `resolver` (merge conflicts) writes on Codex at `medium`, and `merge-reviewer` reviews on Claude at `medium`. Exception (owner decision): `breakdown-writer` writes the task files on Codex at `high`, so `plan-review` checks them from the same family; `factory-tasks.mjs --check` and the per-task `task-review` are the cross-checks. The `codex` harness gives every Codex profile the auto preset of `factory docs codex` (`sandboxMode: workspace-write`, `approvalPolicy: on-request`, `approvalsReviewer: auto_review`) and `networkAccessEnabled: true`, so a reviewer can install packages, run tests and start local servers. Change a state's effort in its profile only.

**Codex login.** Codex runs on a ChatGPT subscription login, not an API key. The repository secret `FACTORY_CODEX_AUTH_JSON` holds the content of an `auth.json`. Codex refreshes the login after about eight days and so invalidates the copy in the secret (`factory docs runners`, "Logins between jobs"). The step "Write the Codex login" of `factory-run.yml` picks the Codex home: `/home/runner/.codex-factory` on a self-hosted runner (the shared volume `codex-home`, see Runners), else `$RUNNER_TEMP/codex`. It writes the secret to `auth.json` there (mode 0600, directory 0700) only when that file is missing or empty, and never overwrites a non-empty one. It writes a temporary file in the same directory first and publishes it with one hard link, under a lock that waits at most 30 seconds, so a second job never reads half a login and never removes one that another job has just written. On a self-hosted runner the secret therefore seeds the login once, and Codex then refreshes it in place; the secret must hold a valid login for that first seeding. On a hosted runner the directory is new every run, so the secret is written every run, and the review states fail to log in once Codex has refreshed it elsewhere: then renew the secret from a fresh `codex login`. The run step alone gets `CODEX_HOME` pointing there. Every agent of the job, the Claude ones included, can read the file while it runs.

**Agent CLI versions.** `factory-run.yml` installs Claude Code at the version in `FACTORY_CLAUDE_VERSION` (`latest` by owner decision; `2.1.314` when unset) and the Codex CLI at the version in `FACTORY_CODEX_VERSION` (`0.165.0`; `skip` when unset). The repository variables `FACTORY_CLAUDE_VERSION` and `FACTORY_CODEX_VERSION` accept only an exact `MAJOR.MINOR.PATCH`, `latest` or `skip`. The step "Install agent CLIs" fails on anything else, such as a range or a `v` prefix.

**Failure comments.** When a job of `factory.yml`, `factory-run.yml`, `factory-fan-out.yml` or `factory-unblock.yml` fails, its last step comments on the issue with the run link, the failed step, and the command that starts it again. This also covers failures before the Factory claim, which leave no Factory comment. A first `HARNESS_TIMEOUT` of a state in `factory-run.yml` restarts the issue instead (see [Task loop](#task-loop)).

**Sweeper.** `factory-sweep.yml` runs every 30 minutes. It comments once on each open issue that has a `factory/<workflow>/<state>` label, no open blocker, no hold, no active run, and no change for 60 minutes (repository variable `FACTORY_STALL_MINUTES`). An active run is any `factory-run.yml` run in status `in_progress`, `queued`, `waiting`, `requested`, or `pending`, found through every page of each status. It changes no labels and no claims. It does not comment again while its own or a failure comment is the last comment on the issue.

**Audit issues.** `factory-audit.yml` opens audit issues of four kinds. `.github/audits/open-issue.sh` holds the rules, and `.github/audits/<kind>.md` the issue text:

- `security`: daily, one target repository per run in rotation. The issue asks for an audit of `main` with hostile inputs along the security checklist.
- `performance`: Tuesday and Friday, one service or library repository per run in rotation (every target except config, deploy and agent). The issue asks for measurements with numbers and commands: `EXPLAIN QUERY PLAN` for the request path and startup, a startup CPU profile, costs that grow with data, memory over a long run, test CPU per file, and for the website the JS/CSS budget and Lighthouse; compared with `bench/budgets.json` where it applies.
- `quality`: Monday, one target repository per run in rotation (the security list, one repository per week). The issue asks for code quality measured with the repository's own scripts and pulse-config's shared configuration, no new tools: lint and typecheck findings, cognitive complexity hot spots, duplicated logic across files or repositories, dead code (found with `grep` and `tsc`), test quality (coverage, untested risky branches, tests that assert nothing), swallowed errors and inconsistent error shapes, consistency with `AGENTS.md` and the other services, and docs that contradict the code. Every finding cites file and line; style-only items are notes, not issue candidates.
- `architecture`: Thursday, one issue for the whole system, naming every repository. The issue asks for machine checks: pin drift of contract, kit and config, the largest files and functions, duplicated helpers that belong in kit, docs that no longer match the code, earlier findings that are still true, and the dependency direction.

Each issue gets the label of its kind and, for security, performance and quality, `audit/<repo>` (both created with a description when missing). It gets no `target/<repo>` label: the audit runs on the meta target and only reads the repository. It also gets `factory/audit/audit`, and the job starts the audit at once (see the audit workflow below): `gh workflow run factory-run.yml --ref <default branch> -f issue=<n> -f admission=label`, after it checks that `<n>` is a canonical issue number. The dispatch is needed because a label set with the job token (`GITHUB_TOKEN`) triggers no `factory.yml`; GitHub creates runs for events of that token only for `workflow_dispatch` and `repository_dispatch`. `factory-fan-out.yml` starts its children the same way. The job has `actions: write` for it; it does not use the bot token, whose events `factory.yml` ignores. A dedupe hit starts nothing and changes no labels. The owner can still stop an audit: cancel its `Factory run #<n>` workflow run (`gh run cancel <run-id>`) and remove the `factory/audit/` label from the issue. Cost: under the fast schedule this is up to 11 audits per week (7 security, 2 performance, 1 quality, 1 architecture), each with at least two `xhigh` states. An open issue of the same kind (and the same repository) blocks a new one, which also caps the number of issues. A manual run (`gh workflow run factory-audit.yml -f kind=<kind> [-f target=<repo>]`) picks the kind and, optionally, the repository.

*Changing the schedule.* These are fast-development intervals, to be relaxed to weekly, monthly and monthly later. Each `cron` line at the top of `factory-audit.yml` maps to one kind in the `case` on `AUDIT_SCHEDULE` in `open-issue.sh` and in the `concurrency` group of the workflow, which puts scheduled and manual runs of one kind in one group. Change the line, its `case` pattern and its group pair together; `test.sh` fails when a cron line maps to no kind or to another group than its kind. The rotation does not depend on the interval: security takes the next repository each day, performance each half week (Monday to Thursday, Friday to Sunday), quality each week.

**Audit workflow.** The Factory workflow `audit` (`.factory/config.yaml`) runs an audit issue on the meta target. `factory-audit.yml` starts it when it opens the issue. It has no gates: merging the report pull request accepts the report.

1. `audit` (`.factory/prompts/audit.md`) reads `main` of the repositories in `.repos/`, works on copies when it installs or runs one, and changes nothing there. It writes `audits/<kind>/<scope>.md` and `.json` (scope is the repository, or `system` for architecture). The file names carry no date: a new audit replaces the report at its path, the report body states the audit date and the examined commit SHAs, and git history keeps older reports. Every checklist item of the issue is `checked`, `not applicable` or `blocked` with a reason. Each finding has an id, the repositories, file and line, a severity (P1 to P3), the command, its exit code, an output excerpt and the examined commit SHAs; performance findings add value, unit, repetitions, baseline and budget. At most 5 findings are issue candidates; the rest are notes. A performance audit reads the latest nightly bench of pulse-api and `bench/budgets.json` first and measures anew (`bun bench/run.ts --a <sha> --b <sha>`) only on a suspected deviation.
2. `audit-review` (`.factory/prompts/audit-review.md`, terminal) re-runs the command of every P1 and P2 finding, removes findings it cannot reproduce, corrects severities, and sends gaps (missing items, missing fields, checks that could have run) back to `audit`. Otherwise it completes and the pull request is ready for the owner.

The agent creates no issues and writes no comments. After the merge the owner picks the candidates that become issues and closes the audit issue (the report pull request says `Refs`, not `Closes`); an open audit issue blocks the next one of its kind and repository. Chaining workflows may take the issue step over later. `audit` uses `auditor` (`claude-opus-5-5`, effort `xhigh`, owner decision) and `audit-review` uses `audit-reviewer` (Codex `gpt-6.1-sol`, `xhigh`), so findings are reproduced by the other family; both have a deadline of 120 minutes (`timeoutMs: 7200000`; the default 60 minutes stopped the first performance audit). The prompts budget the work to fit: no background or parallel subagents, at most one bench A/B comparison of 2 rounds per side, unfinished items `blocked`, and the structured outcome always returned.

*Security disclosure.* The pulse repositories are public, and so is the report. For a P1 or P2 security finding the committed report names location, class, impact and fix direction, but no working exploit, payload or reproduction command. The agent keeps its reproduction outside the repository. The two states run in separate jobs, so that local evidence does not reach the review: `audit-review` rebuilds the reproduction from location and class, and it removes any exploit text from the report.

*Labels.* The state labels `factory/audit/audit` and `factory/audit/audit-review` come from `factory state --apply`. Merging the report pull request triggers `factory-fan-out.yml`, which finds no plan and ends with a notice.

**Factory report.** The page at <https://lorenzh.github.io/pulse-meta/> shows only the merged report. Three layers keep numbers, text and design apart:

1. *Numbers.* `factory-report-open.yml` runs daily (05:41 UTC) and on demand (`gh workflow run factory-report-open.yml`). It builds `report/data.json` with `report/data.mjs`, uploads it as the artifact `report-data` (7 days), and runs `.github/report/open-issue.sh`. The script opens nothing when the data fingerprint equals the one of `report/data.json` on `main`, the last merged report, or while a `Factory report:` issue with the label `report` is open. Otherwise it opens `Factory report: pulse (<date>)` with the labels `report` and `factory/report/report`, names `as-of`, the run id and the sha256 of the data in the body (`.github/report/issue.md`), and dispatches `factory-run.yml` like the audit opener. The fingerprint is a sha256 over the all-time numbers of `summary`; the clock, the 30-day window, the deltas and the report's own issues and runs are not in it, so a report does not trigger the next one.
2. *Text.* The Factory workflow `report` runs on the meta target. `report` (profile `reporter`, `claude-opus-5-5`, effort `high`) downloads the artifact, checks its hash, commits it unchanged, and writes only `report/narrative.json`: fixed slots for the lead, five chart notes, changes since the last report, the case study, three to six findings and three to six recommendations. `report-review` (profile `report-reviewer`, Codex `gpt-6.1-sol`, `modelReasoningEffort: medium`) runs `report/check.mjs`, checks every claim with `jq` against the data, and sends the text back or completes; it edits nothing.
3. *Design.* `report/index.html` is the fixed template, a dashboard in the losoft design system (tokens copied from lorenzh/losoft.dev, light and dark mode with a toggle as on losoft.dev): KPI tiles with the change since the last report, cost, runs or tokens per step, repository and day (one control switches all three), the feature table with sort and filters, the human fixes and events, the case study, then the text. It fills the slots with `textContent` only and formats numbers with the same formatter as the tiles. Merging the report pull request runs `factory-report.yml`: `check.mjs`, then the Pages deploy of `index.html`, `data.json` and `narrative.json`, then `.github/report/close-issue.sh` closes the report issue that `narrative.json` names. The workflow fetches no live data.

*What the agent sees.* `data.json` holds numbers, controlled names (steps, profiles, targets, event kinds) and references only: no issue titles, no commit messages. Run records count from `FACTORY_GITHUB_ACTOR` and the historical `lorenzh-factory-bot` account. Split comments also count from `github-actions[bot]` (`factory fan-out`) and the owner. Neither Factory account counts as human in commit statistics. Codex runs report no cost, so their cost is unknown (`runs_cost_unknown`), not 0, and every USD value counts known costs only; their tokens count. Detail tables and charts cover the last 30 days; `summary` keeps the all-time totals, the window (`win_*`), the change since the last merged report (`d_*`) and the case study (`case_*`, the most expensive feature finished in the window).

*History before 2026-11.* GitHub hides every comment, issue and pull request of the suspended `lorenzh-factory-bot` account, so its run records are gone. `report/archive.json` keeps the report numbers up to its `meta.as_of` (2026-10-31 22:32 UTC); it is read only. `data.mjs` adds it to the live data (`--archive <file>`, default `report/archive.json`, a missing file means none) and counts live records only after that time, so records that come back are not counted twice. The archive keeps aggregates only: fields it can only approximate (merged medians, the cached share) are listed in `meta.carry.approx`, and `meta.carry.gap_from`/`gap_to` name the time without records.

*The check.* `report/check.mjs` fails on: a changed file other than the two report files (C1, with `--base`); a data hash or `as_of` that differs from the issue (C2); a wrong shape, count or length, or a wrong `issue` (C3); a placeholder `{field|fmt}` whose field is not a number of `summary[0]` or is `null`, or that stands in a code span (C4); any digit or other numeric character of any script (`\p{N}`: full-width digits, fractions, superscripts, Roman numerals) outside a placeholder, a reference or a code span (C5); a `#N` or `pulse-<repo>#N` that is not in the data (C6); HTML, links or token patterns (C7). Quantity words and digits in code spans are warnings for the reviewer. `report-check.yml` runs on `pull_request_target` for every pull request that touches `report/**` or `.github/**`: the workflow as it is on the base branch, a checkout of the base commit only, a read-only token. `.github/report/check-pr.sh` fetches the pull request's `data.json` and `narrative.json` through the API as data and runs the base commit's `check.mjs` on them; no code of the pull request runs, so a report run can change neither the check nor the workflow that judges it. On a `factory/<issue>-…` branch it adds the template lock against the pull request's changed-file list (any path but the two report files fails, `.github/` included) and compares hash and `as-of` with the issue. Tests: `node --test 'report/*.test.mjs'`.

*Labels.* `factory/report/report` and `factory/report/report-review` come from `factory state --apply`, which the owner runs once after the merge and before the first report. The opener creates `report`. Cost: one `high` Claude state and one `medium` Codex state per day with new activity; the report's own runs show as `report_runs` and `report_usd`, outside every other number.

**Workflow script tests.** `.github/workflow-tests/test.sh` runs the scripts of the sweeper and the audit workflow against fixtures with a stub `gh` (needs bash, jq, python3 with PyYAML). For the Factory report it covers the fingerprint skip, the dedupe, the issue body, the dispatch, the closing of the report issue after the deploy, and the pull request check from the base commit (template lock, a weakened `check.mjs`, altered data, a typed number). For the audits it covers the rotation of each kind, dedupe on `audit/<repo>`, label creation, the start label and the dispatch of `factory-run.yml` (none on a dedupe hit or for a non-canonical issue number), `actions: write` on the job, the dispatch inputs, the mapping of every cron line to a kind, and that each issue text names the start label and the report instead of one issue per finding. For shared findings, `findings.sh` runs the publisher and cleanup against a local bare repository (see [Shared findings](#shared-findings)) and checks the prompt rules and the findings steps of `factory-run.yml` and `factory-unblock.yml`.

## GitHub App

If `vars.FACTORY_APP_ID` is set, the admission, run, continuation and unblock jobs use App tokens.
Otherwise they keep `secrets.FACTORY_GITHUB_TOKEN`. An App failure never falls back to the PAT.
Audit, report, fan-out and failure-report steps keep their built-in `GITHUB_TOKEN`.

Grant these **repository permissions**:

| Permission | Access | Purpose |
| --- | --- | --- |
| Contents | Read and write | Clone repositories and push branches. This also covers creating and deleting the `factory/findings/*` branches of pulse-meta. |
| Issues | Read and write | Read dependencies. Write issues, labels and comments. |
| Pull requests | Read and write | Create and update PRs. Read merge state. Mark drafts ready. |
| Actions | Read and write | Dispatch runs. Read jobs, logs and artifacts. |
| Workflows | Read and write | Push changes to `.github/workflows/`. Dispatch alone needs only Actions write. |
| Checks | Read | Read PR checks. |
| Commit statuses | Read | Read status contexts in PR checks. |
| Metadata | Read | Read repository metadata. GitHub grants this automatically. |

No organization or user permissions are needed.
Keep `FACTORY_PACKAGES_TOKEN` separately for GitHub Packages (`read:packages`).

Owner setup:

1. Register an App under [Developer settings → GitHub Apps](https://github.com/settings/apps/new) with these permissions.
2. Disable its webhook. These workflows need no webhook server or user authorization.
3. Install it on `lorenzh`. Select the 12 repositories in `.factory/config.yaml`: `pulse-meta`, `pulse-contract`, `pulse-probe`, `pulse-api`, `pulse-status`, `pulse-notify`, `pulse-config`, `pulse-kit`, `pulse-website`, `pulse-console`, `pulse-deploy`, `pulse-agent`.
4. Generate a private key. Store the full PEM in the pulse-meta Actions secret `FACTORY_APP_PRIVATE_KEY`.
5. Pause active runs. Set the pulse-meta Actions variable `FACTORY_GITHUB_ACTOR` to `<app-slug>[bot]`.
6. Set the pulse-meta Actions variable `FACTORY_APP_ID` to the numeric App ID to enable App mode.
7. Start a short issue with `factory-run.yml`. Check comment attribution, PR checks and continuation.

`runtime.recordAuthor` holds the same login without `[bot]`, for Factory Manager and local commands.

To return to PAT mode, clear `FACTORY_APP_ID`, restore the PAT login in `FACTORY_GITHUB_ACTOR` and set `runtime.recordAuthor` to it.
The PAT must still be valid.

The pinned `actions/create-github-app-token` v2.2.2 mints repository-scoped tokens and revokes them after the job.
The identity check uses its `app-slug` output instead of `/user` in App mode.
REST and events use `<slug>[bot]`. Factory 0.8.0 reads GraphQL comment authors as `<slug>`.
The run and cancel commands strip `[bot]` from `--record-author`.
The task script inherits the full REST login from `FACTORY_GITHUB_ACTOR` and bypasses `/user`.
Report, task and restart filters also accept historical `lorenzh-factory-bot` comments.
Git keeps its existing commit identity.

App pushes, PRs and labels can trigger workflows ([GitHub trigger rules](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)).
`factory.yml` ignores events from both Factory accounts to prevent recursive starts.
Explicit dispatches start `factory-run.yml`. Built-in `GITHUB_TOKEN` dispatches also work.

**Limits.** Tokens [expire after one hour](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation).
Factory 0.8.0 does not refresh them during a state. The configured two-hour audits can lose API and push access.
The workflow mints just before Factory starts and again for timeout recovery.
Factory runner history matches only one author. Stop old runs before switching and restart unfinished issues with `admission=restart`.
History filters cannot recover comments that GitHub hides after an account suspension.
The provider `currentUser()` and facade `cancelInterruption()` still need a user token. The workflow CLI paths bypass them.

References: [Factory runner identity](https://github.com/paragondata/factory/blob/v0.8.0/packages/cli/docs/runners.md#pull-requests-get-no-automatic-ci), [GitHub provider](https://github.com/paragondata/factory/blob/v0.8.0/packages/provider-github/docs/github.md), [App token action](https://github.com/actions/create-github-app-token/tree/v2.2.2), [App permissions](https://docs.github.com/en/rest/authentication/permissions-required-for-github-apps).

## Prompt injection and credentials

**Remaining risk.** The issue title, body and every comment, from any author, reach the agent. The agent runs with `permissionMode: auto` and holds the bot token (`GH_TOKEN`, write access to every pulse repository) and the Claude OAuth token in its environment. A comment on an issue with a `factory/` label can therefore try to make the agent push code or leak a token. Filtering comments by author needs a Factory feature (paragondata/factory#292). Giving the token only to the Factory publish, not to the agent, needs another one (paragondata/factory#292 or the linked upstream issue). Both are open.

**What the workflows do now.** No checkout keeps credentials (`persist-credentials: false`). No step runs `gh auth setup-git` or `gh auth login`. Git gets the token only through `GIT_ASKPASS` on the steps that run Factory, so no git config and no gh file stores one. Every action is pinned by commit SHA. The report loads d3 with Subresource Integrity. The report agent sees only numbers and references from the bot's records (see Factory report above).

**Shared findings.** The findings file of a feature (see [Shared findings](#shared-findings)) is a channel from one agent to another, and so a prompt-injection path. Readers treat it as untrusted data, never as instructions, and use a finding only as evidence that they check. The publisher validates the schema, the sizes and the token patterns, but it cannot prove that a text is harmless or free of private data; the writer rule is the first line of defense. Every agent still holds a token that could push the branch directly and bypass the publisher (paragondata/factory#292).

**Interim rule.** Only the repository owner applies `factory/` labels. Before a person starts or restarts a run (label, `factory start`, `admission=restart`), they read every comment that arrived since the last run, and they remove or answer any comment that asks the agent to do something outside the issue.

Each repository's `AGENTS.md` holds its code conventions (test-driven development, end-to-end tests, lint). Its `docs/development.md` shows the commands.

## Runners: self-hosted first, GitHub-hosted as fallback
`factory.yml`, `factory-run.yml`, `factory-unblock.yml`, `factory-sweep.yml`, `factory-audit.yml` and `factory-report-open.yml` start with a job `runner` that calls `runner-pick.yml`. It answers `runs-on`: the self-hosted runners (labels `self-hosted`, `pulse-meta`, `bwrap`) when they are available, else `ubuntu-24.04`. Jobs that react to pull requests (`factory-fan-out.yml`, `report-check.yml`) and the report build and Pages deploy stay on GitHub-hosted runners, so no pull request code runs on the self-hosted host.

The manual `docker-probe.yml` does not use the pick: it runs on the Docker-capable test runner (label `docker-test`) and checks the rootless Docker daemon and that the entrypoint's access token stays out of reach of a job. Start it with `gh workflow run docker-probe.yml`; the input `runner` (a JSON array of labels, for example `["self-hosted","pulse-meta"]`) points it at other runners.

`GITHUB_TOKEN` cannot list runners. The script `scripts/runner-heartbeat.sh` runs every minute on the runner host (cron), counts idle online runners and writes the variables `RUNNERS_IDLE` and `RUNNERS_BEAT`. No idle runner, a heartbeat older than 180 s or a missing variable means hosted. Set the variable `RUNNERS_FORCE=hosted` to switch the self-hosted runners off by hand.

Limit: the pick is made once per run. A runner that dies between the pick and the job start leaves the job queued (GitHub waits up to 24 hours); cancel the run and start it again. The self-hosted runners have no sudo, so the bubblewrap steps of `factory-run.yml` rely on the preinstalled `bwrap`; node comes from `actions/setup-node`.

Codex login on the self-hosted runners: all replicas of the compose service `pulse-meta` mount one named volume `codex-home` at `/home/runner/.codex-factory`, writable for the user `runner`. The first job seeds `auth.json` there from the secret `FACTORY_CODEX_AUTH_JSON`, and every later job on any replica uses that one login, which Codex refreshes in place (see "Codex login" above). A Codex home that is not writable fails the step "Write the Codex login"; there is no fallback to the secret. A Codex home that is writable but not a mount point (`mountpoint`, or else a device other than the parent's) only gets a warning: each runner container then keeps its own copy of the login, and these copies can invalidate each other at a refresh. Mount the volume when that warning shows. To renew the login by hand, delete `/home/runner/.codex-factory/auth.json` on a runner (or remove the volume with `docker volume rm codex-home`) after putting a valid login in the secret; the next job seeds it again. Or run `codex login` with `CODEX_HOME=/home/runner/.codex-factory` inside a runner container as the user `runner`. Two jobs that refresh the login at the same moment can race; Codex login errors in the review states point to that or to an expired login.
