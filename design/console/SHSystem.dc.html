Back up and restore

Run these on the host, next to compose.yaml.

# pulse-api database $ docker compose exec api bun run backup /data/backup-2026-10-30.db # console database (users, sessions, activity) $ docker compose exec pulse-console bun run backup /data/console-2026-10-30.db

Restore

# 1. stop both services $ docker compose stop api pulse-console # 2. copy the backups over the databases $ cp ./data/backup-2026-10-30.db ./data/pulse.db $ cp ./data/console-2026-10-30.db ./data/console.db # 3. delete the old -wal and -shm files $ rm -f ./data/pulse.db-wal ./data/pulse.db-shm ./data/console.db-wal ./data/console.db-shm # 4. start again $ docker compose up -d

pulse does not schedule or store backups. Run the commands from cron and copy the files off the host.

Where checks come from

checks.jsonFile state: ok · last applied 14:01
31 checks from the file

pulse-api watches /etc/pulse/checks.json and reloads it on change. These checks are read-only in the console: edit the file, commit it, and the change shows within seconds.

When the file is invalid or unreadable, pulse-api keeps the last valid version, shows its message here and on Checks, and console checks can still be changed.

consolestored in pulse-api
4 checks created in the console · 1 shadowed

Kept in the database, not in the file. A console check cannot take an id the file uses. If the file gains that id later, the console check is shadowed: it does not run and can only be deleted or exported. Export writes env names, never literal values.
