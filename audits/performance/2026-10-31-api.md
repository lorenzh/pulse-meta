## Issue candidates

### performance-api-2026-10-31-1 (P2): each ingest commits with a synchronous disk flush on the event loop; every route waits behind it

- Location: `src/service.ts:704` (`transaction`: `BEGIN` ... `COMMIT` per `POST /results`) and `src/db.ts:159` (`new Database(path)`). The only PRAGMAs in `src/` are `user_version`, `foreign_keys` and `foreign_key_check` (`grep -n PRAGMA src/*.ts`), so the SQLite defaults apply. `sqlite3 mem.db 'PRAGMA journal_mode;'` gives `delete` for the file after the run (the rollback journal), and the default `synchronous` is FULL. The `sqlite3` CLI shows `2` for its own connection; the API's per-connection value was not read. The tmpfs comparison below measures the flush cost directly.
- Command: `bun mem.ts`, as in item 4 (bench rates), on the same 1x seed. Three storage variants: the file on disk, the file on `/dev/shm` (tmpfs, where a flush costs nothing), and the file switched to WAL (`sqlite3 pulse.db.orig 'PRAGMA journal_mode=WAL'`, the API's default `synchronous`). The bench A/B of item 3 adds evidence. Exit code 0.
- Excerpt (1 minute of load each, client-side latency):

```
disk:  /results n=1797 p50 5.3 ms p95 219.6 ms | /checks n=599 p50 10.9 ms p95 249.7 ms | /latency n=60 p50 17.4 ms p95 353.1 ms   cpu 6.29 s
tmpfs: /results n=1794 p50 1.3 ms p95 1.9 ms   | /checks n=598 p50 6.1 ms p95 7.0 ms     | /latency n=60 p50 13.9 ms p95 15.3 ms   cpu 6.00 s
WAL:   /results n=1794 p50 1.7 ms p95 45.4 ms  | /checks n=598 p50 5.7 ms p95 70.0 ms    | /latency n=60 p50 13.7 ms p95 94.0 ms   cpu 5.42 s
5 min on disk: /results p95 182.2 ms, /checks p95 200.9 ms, /uptime p95 193.2 ms, /latency p95 198.8 ms, /checks/:id/latency p95 199.1 ms
bench B: p95_get_latency_ms 129 ms (rounds 74.58, 183.27), p95_get_check_latency_ms 127 ms; budgets 53 and 55 ms
```

- Value: p95 of `GET /latency` 198.8 ms (5 minutes on disk, n = 300). In the bench, 129 ms.
- Repetitions: one 5-minute run, three 1-minute runs (one per storage variant), and 2 bench rounds per side.
- Baseline: the same load and data on tmpfs: p95 15.3 ms for `GET /latency` and 1.9 ms for `POST /results`. The CPU time is almost the same (6.00 s against 6.29 s per minute), so the extra time is spent waiting for the disk, not computing.
- Budget: `p95_get_latency_ms` 53 ms and `p95_get_check_latency_ms` 55 ms (reported, not gating). Both are over budget on A and B. `p95_post_results_ms` 312 ms and `p95_get_checks_ms` 392 ms are not exceeded.
- Why it matters: Bun runs every request on one thread, and `bun:sqlite` is synchronous. Each of the 30 commits per second waits for the disk while every other request waits. One request takes about 3 to 15 ms with no other load, but under the bench load the p95 of every route is about 180 to 250 ms.
- Fix direction: no flush per ingest. For example, WAL with `synchronous=NORMAL`, which keeps the data durable up to the last checkpoint and is safe against corruption. Or several results in one transaction. Measure with the bench p95 metrics.

- Repetitions: 3 server runs x 30 requests per route.
- Baseline: the 1x bench seed (391 results per check today): 4.7 ms for `/latency` and 3.6 ms for `/checks`.
- Budget: `p95_get_latency_ms` 53 ms (reported): one unloaded request takes 8 times the budget. `p95_get_checks_ms` 392 ms (reported): one unloaded request takes 88 % of the budget.
- Why it matters: the cost rises linearly from 00:00 UTC to the end of the day. The status page polls `/checks`, `/components` and `/components/uptime` every 5 s by default (`pulse-status` `src/poller.ts:326-340`; `/uptime` and, when enabled, `/latency` are read at lines 229 and 250). With 6 ingests per second, every poll misses the cache, so the API's one thread is busy for about 1 s of every 5 s for one status page, and finding 1 comes on top. Ingests and other reads wait meanwhile.
- Fix direction: keep running per-day aggregates instead of reading them again, for example a running good/total count for today, as the closed days already have, and today's latency percentiles from a bounded or incremental structure. Alternatively, let an ingest invalidate only what it changes. A bench seed with today's density, in `bench/seed.ts`, would make the cost visible.

### performance-api-2026-10-31-3 (P3): the first `GET /checks` and the first `GET /uptime` after a start read the whole 30- and 90-day window in one synchronous call

- Location: `src/service.ts:757` (`uptimeOf`: after a start, `closedTallies` is empty, so `firstRead` is the first day of the window and one `dailyUptime` query aggregates all of it).
- Command: the growth script of item 3: a fresh copy of the seeded database, start, wait for the backfill, then the first request to each route. 3 runs per data set, exit code 0. Also the `curl` reproduction of finding 2: `cold GET /checks`.
- Excerpt: `1x: /checks max 206.2, 209.9, 206.7 ms; /uptime max 210.9, 211.0, 214.6 ms` and `10x: /checks max 2356.0, 2352.2, 2354.4 ms; /uptime max 2414.6, 2408.4, 2412.2 ms` (the maximum of each run is its first, cold request; the later requests take 18.6 and 17.9 ms). The `curl` reproduction gave `cold GET /checks 200 0.208754 s` (1x) and `cold GET /checks 200 0.608469 s` (1x plus a full day at 3 locations).
- Value: 2,354.4 ms for the first `GET /checks` at 10x, then 2,412.2 ms for the first `GET /uptime`.
- Repetitions: 3 runs per data set.
- Baseline: 206.7 ms and 211.0 ms at 1x.
- Budget: `p95_get_checks_ms` 392 ms (reported). This is one request per start, so the bench p95 does not show it.
- Why it matters: the call runs on the API's only thread. After every restart, all requests wait behind it, including the probes' `POST /results`: about 4.8 s at 10x the bench data. The bench seed covers 30 days, so a 90-day history at the default retention gives longer stalls.
- Fix direction: build the closed-day tallies in batches with yields after the start, as the latency backfill does, or store them per day like `latency_daily`.
