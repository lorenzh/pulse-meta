## Issue candidates

Checks below omit attack details for P1 and P2 findings. Private reproductions stay outside the repository and are removed after review.

### SEC-1 `security-console-2026-11-08-1` (P3): an API check id with a lone UTF-16 surrogate makes the Checks list and the automatic incident detail answer 500

- Location: `src/check-pages.ts:126` (`idQuery`: `encodeURIComponent(id)`, used for every row link of the Checks list) and `src/api-path.ts:8` (`apiIdSegment`: `encodeURIComponent(id)`), called with API data at `src/incident-read.ts:172` (`incident.checkId`) and `src/check-detail-pages.ts:235` (`view.id`).
- Class: an encoder that throws on input that a validator let through. `encodeURIComponent` throws `URIError` on a string that is not well-formed UTF-16. The contract check id rule is "non-empty string" (`schema.ts:270`, also the `POST /admin/checks` input rule in pulse-api `src/check-write.ts:149`), so a JSON `\u` escape of a lone surrogate passes validation.
- Check: a fake pulse-api whose `/admin/config` and `/checks` answers hold one check id that ends in a lone surrogate (a JSON `\u` escape). Then `GET /`, `GET /checks` and `GET /checks/check?id=web` as the Owner. A second fake serves an automatic incident on such a check id, then `GET /incidents` and `GET /incidents/automatic?id=<n>` as a Viewer. Probe exit 0.
- Effect: `GET /checks … 500 "internal error\n"`, `GET /incidents/automatic?id=8: 500 text/plain`, log `"msg":"request failed","error":"URIError"`. `GET /` and `GET /incidents` stay `200`; the same pages with ordinary ids give `200`.
- Impact: whoever can define a check id through the checks file of pulse-api (`checks.json`), or an api that answers with such an id, takes the Checks list down for every console user until the id is gone. Console forms cannot send such an id: form bodies and queries are decoded as UTF-8. Whether pulse-api keeps the surrogate after its own database round trip was not tested; the checks file is served as it was read.
- Fix direction: treat ids that are not well-formed (`!id.isWellFormed()`) like the unaddressable ids `.` and `..`: render them as text without a link and call no API for them. Or let the contract id rule refuse strings that are not well-formed. Add a test with such an id on the list, detail and incident pages.

### SEC-2 `security-console-2026-11-08-2` (P2): pre-session token isolation permits unauthenticated cross-client denial of sign-in

- Location: `src/form-tokens.ts:93`.
- Class: unauthenticated cross-client resource exhaustion of the shared pre-session form-token store (availability).
- Check: private local HTTP control and hostile-input comparison, independently rebuilt and run by audit-review. Invocation, request sequence and payload withheld from the public report. Probe exit 0.
- Effect (sanitized): valid sign-in control `303`, `expired=false`; isolated hostile-input case `409`, `expired=true`; existing signed-in Team page `200` in both cases. All assertions passed.
- Impact: an unauthenticated client can invalidate other clients' open sign-in forms, denying new sessions while interference continues. Setup and account-link forms share the affected store. Existing signed-in pages remain usable. P2: ordinary anonymous network input causes cross-client availability loss without privileged access or malformed upstream data. The local probe verifies affected sign-in forms, not a universal inability to sign in under every request interleaving.
- Fix direction: isolate anonymous clients' resource use and prevent one client from evicting another client's valid forms. Preserve CSRF binding, expiry and single-use checks. Add cross-client availability regression coverage.

## Notes

- **N1** (environment lookup): Bun's `fetch` uses `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` from the environment for every pulse-api call. With `HTTP_PROXY` set and an `http` API URL, the proxy received `GET http://api.invalid:3000/admin/config` with the admin bearer token in clear text (setup `action=test` against a real `bun src/main.ts`). Docker sets these variables in a container when the client config has `proxies`. The README and `docs/configuration.md` do not mention proxies. The same note exists for pulse-probe (N1 of its audit). Direction: document it, or call pulse-api without the environment proxy.
- **N2** (path safety): `openDatabase` chmods an existing path with `chmodSync`, which follows a symlink (`src/database.ts:148`). A symlink at `PULSE_CONSOLE_DB` to a text file left the target at `600` (was `644`) before the start failed with `SQLITE_NOTADB`. The mode only gets stricter, and planting the link needs write access to the data directory.
- **N3** (write before the body check): the access gate touches a `full` session older than 60 s before `Origin`, the content type and the body limit run (`src/server.ts:265`). An oversized POST of a signed-in browser therefore updates `sessions.last_seen_at` and refreshes the cookie with its `413`. This follows the documented order, where the gate comes first, and no state of the request is saved.
- **N4** (loopback mode is not access control): the `Host` rule stops DNS rebinding, but a client that reaches the port can send `Host: 127.0.0.1`. With `PULSE_CONSOLE_HOST=0.0.0.0` and no public URL, `GET /setup` over a non-loopback address gave `421` with its own `Host` and `200` with `Host: 127.0.0.1`. The image binds `0.0.0.0`, and the README tells operators to publish the port on host loopback only (`-p 127.0.0.1:8082:8082`).
- **N5** (upstream text in responses): on a refused write from a pulse-api that sends the wire header, the console shows the api's `ErrorResponse.error` text (contract cap 1000 characters, escaped) in the page (`src/check-write.ts:155` and `:165`, R8). Without the wire header, or for 5xx and redirects, only fixed texts appear. pulse-api decides what that text holds.
- **N6** (`bun audit`): 1 moderate advisory, `minimatch@10.2.6` (GHSA-g3hv-75wg-m249, globparts amplification), reached only through `eslint` in the dev dependency pulse-config. It is not in the production install or the image.
- **N7** (CI): `deploy-dev` checks out pulse-deploy, api, probe, status and notify at `ref: main`, a mutable ref. The job has `contents: read`, no secrets and `persist-credentials: false`. `release` does not need it (`needs: [check, docker, browser]`).
- **N8** (unpinned build tools): the Dockerfile build stage runs `apk add --no-cache git` without a version, to fetch the GitHub dependencies; git is not in the final image. The `browser` job's `bunx playwright install --with-deps chromium` downloads a browser that no hash pins.
- **N9** (ops routes): `/healthz`, `/readyz` and `/metrics` answer without a session and outside the loopback `Host` rule, as documented. `/metrics` holds counters by fixed path label and auth result only.
- **N10** (setup connection test): before setup, whoever holds the setup grant can make the console send `GET <url>/admin/config` with the admin token to any http(s) URL, including link-local addresses (`checkApiUrl("http://169.254.169.254")` is accepted). The answer texts tell reachable from unreachable apart. The setup code (16 random bytes, 5 failures per client per 15 minutes) is the trust root here, by design.
- **N11** (throttle keys): the sign-in throttle locks an account after 5 failures in 15 minutes, and the client key is the socket peer. Behind a reverse proxy, all clients share the proxy's key. Both are documented (`docs/configuration.md:175`), and so is the lockout of the Owner account by wrong passwords.
