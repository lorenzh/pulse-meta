## Issue candidates

SEC-1 is `P2`. The other candidates are `P3`: each needs a hostile or broken pulse-api, a proxy in front of it, or an operator setting that nobody would choose on purpose. The commands below describe each check without its input.

### SEC-1 `security-status-2026-11-06-1` (P2): a compressed upstream answer gets around the 5 MiB body cap, and status uses memory up to its decoded size

- Location: `src/server.ts:389` to `:402` (`fetchRaw`: `recordingFetch` passes the contract's init on to Bun's `fetch`) and `src/api-poll.ts:24` to `:33` (readiness poll). Both use contract `fetchJson`, whose init is only `{ signal }` (pinned `dist/client.js:77`, `src/client.ts:130`; still the same on contract `main`, `src/client.ts:131`). So Bun asks for `gzip, deflate, br, zstd` and decodes the body before the byte count of contract `readText` sees it. The root cause is the contract finding `security-contract-2026-11-03-1`; this is its effect on status.
- Class: decompression bomb (resource exhaustion) that gets around a documented body limit.
- Check: the fake api answers `GET /checks` with a brotli body of 1,624 bytes that decodes to 1 GiB. First one anonymous `GET /api/checks` on the running service; then no client request at all, only the readiness poll for 12 s. RSS of the status process sampled every 0.1 s with `ps`. Exit 0 for both runs (the HTTP answer is the documented one); the effect is in the RSS.
- Effect: one request: `status=502 bytes=32 time=2.84`, `{"error":"invalid API response"}`, RSS `66,468 kB` before, peak `1,321,780 kB`, `1,087,292 kB` after. Readiness poll only: RSS `75,940 kB` before, peak `1,339,204 kB` within 12 s, `upstream requests: /checks,/checks`. An uncompressed 6 MiB body for comparison: `502`, RSS `75,748 kB` before and a peak of `76,360 kB`.
- Impact: status is the public-facing service. One answer from whatever the api URL reaches can make it allocate more than 1 GiB: the api, a proxy in front of it, any origin that a redirect leads to (SEC-2), or an attacker on the path of a plain-http `PULSE_API_URL` (pulse-deploy sets `http://api:3000`, `common/services.yaml:21`). The readiness poll repeats this every `POLL_MS` without any visitor. Visitors add a new upstream read per path at most every `PULSE_STATUS_CACHE_MS` (default 2000 ms), or on every request when it is 0. A memory-limited container is killed, and the status page goes down exactly when the api misbehaves. `README.md:63` and `docs/operation.md:153` promise a 5 MiB cap that does not bound memory.
- Fix direction: stop Bun from decoding ahead of the cap in the `fetch` that status passes to `fetchJson` (the proxy's `recordingFetch` and the readiness poll's `doFetch`). Set Bun's `decompress: false` and refuse a response whose `Content-Encoding` is not `identity`, or move to a contract version that does this inside `fetchJson` (contract `main` does not yet). Add a test with an encoded answer.

### SEC-3 `security-status-2026-11-06-3` (P3): the proxy serves a non-list upstream body unfiltered, also with details hidden

- Location: `src/api-filter.ts:257` (`if (!Array.isArray(body)) return pathname === "/api/manual-incidents" ? undefined : body;`), used by `buildAnswer` at `src/server.ts:561`. Without components, or with checks shown, nothing after it checks the shape.
- Class: fail-open privacy filter: the allow-list depends on the upstream sending a list.
- Check: the fake api answers 200 `application/json` on each list route with a JSON object that holds a check URL with user info and a query token, and a `headers.authorization` value. `GET` the matching `/api/*` route on the running service: once with details shown, once with all settings at their defaults (`PULSE_STATUS_HIDE_DETAILS=true`). Exit 0. The effect is in the body.
- Effect: `/api/checks`, `/api/uptime`, `/api/latency`, `/api/maintenance` and `/api/incidents?status=open` answer `200` with an `ETag`, and their body is the upstream object byte for byte, user info, query token and header value included (`secret-in-body=1`). The same holds with the defaults. `/api/components` answers `502 invalid API response` (it fails closed). A list body on the same instance gives `[{"id":"web","name":"Web","type":"http","state":"down","lastReason":null,"locations":[]}]`.
- Impact: `docs/operation.md:85` says the answer is built from a fixed list of fields per endpoint, "so a new upstream field stays private". `docs/operation.md:89` says the proxied JSON has no `url`, `host`, `port` or `keyword` while details are hidden. Both hold only while pulse-api sends a list. An api bug, a later api version that wraps a list in an object, or a proxy that answers 2xx JSON of its own would publish every field of that object to anyone. The answer also gets an `ETag` and is cached like a good one.
- Fix direction: fail closed. Treat a non-list body as `invalid API response` on every list route, as `/api/manual-incidents` already does (`filterApiBody` returns `undefined`, and `buildAnswer` answers 502). Add a test per route.

### SEC-2 `security-status-2026-11-06-2` (P3): the proxy, the page render and the readiness poll follow redirects to other origins and from https to http

- Location: `src/server.ts:389` to `:402` and `src/api-poll.ts:24`. Contract `fetchJson` sets no `redirect` option (pinned `dist/client.js:77`, `src/client.ts:130`), so Bun's `fetch` follows redirects. The contract finding is `security-contract-2026-11-03-3`. Status passes its own `fetch` wrapper, so it could refuse redirects itself, as pulse-notify does.
- Class: SSRF and downgrade via redirect on the api connection.
- Check: the fake api answers `GET /checks` with a 302 to another port, and `GET /uptime` with a 307 to another path on that port. An https api (throwaway certificate, `NODE_TLS_REJECT_UNAUTHORIZED=0` in this run only) answers every path with a 302 to plain http. `GET /api/checks` and `/api/uptime` on the running service. Exit 0. The effect is in the body and in the request log of the other origin.
- Effect: cross-origin 302: `200 [{"id":"EVIL-ORIGIN-DATA","name":"evil","type":"http","state":"up"}]`. 307 to another path: `200 [{}]`, and the other origin logged `/internal-only`. https to http: `200` with the plain-http host's data (`requests at the plain-http host: 3`, `/checks,/checks,/components`). A redirect to a `file:` URL gives `502 API unreachable`. No `authorization`, cookie or client header reached the other origin.
- Impact: whoever can make the api origin, or a proxy in front of it, send a redirect makes status read its public data from another host, or over plain http where it can be forged. The page then shows forged states, incidents and manual incidents. status also sends requests to any URL that the redirect names (blind SSRF from the status host), and the allow-list filters return the fields they keep. A redirect also leads to the SEC-1 effect from a host that the operator never configured.
- Fix direction: pass `redirect: "error"` (or `"manual"`, and treat 3xx as an `http` failure) in the `fetch` wrapper that status gives to `fetchJson` for the proxy and the readiness poll, or move to a contract version that sets it.

### SEC-4 `security-status-2026-11-06-4` (P3): credentials in a `PULSE_STATUS_LOGO` URL are published in the page and repeated in the startup error

- Location: `src/server.ts:145` to `:155` (`resolveLogo` accepts user info and returns the raw value as `src`), and `src/server.ts:152` (`PULSE_STATUS_LOGO: invalid URL ${logo}`).
- Class: secret in a response and in an error text.
- Check: start the service with `PULSE_STATUS_LOGO=https://logouser:<password>@cdn.example/logo.svg` and `GET /`. Then start it with an https logo value that has user info and cannot be parsed. `env -i ... bun --no-env-file src/main.ts`.
- Effect: the page has `<img class="logo" src="https://logouser:<password>@cdn.example/logo.svg" alt="pulse">`; the CSP has only the origin (`img-src 'self' data: https://cdn.example`). The second start gives `pulse-status: PULSE_STATUS_LOGO: invalid URL https://u:<password>@[bad`, exit 2. The service log has no line with the password. `<password>` stands for the test value, which appeared in full.
- Impact: an operator who points the logo at a protected asset store publishes its credentials to every visitor. A typo in such a value puts the password into the startup log. `PULSE_API_URL` and `PULSE_STATUS_PUBLIC_URL` are never repeated, and `PULSE_STATUS_PUBLIC_URL` refuses credentials (`readPublicUrl`, `src/settings.ts:38`); the logo setting does neither.
- Fix direction: refuse a logo URL with user info (and a query or fragment, if they are not needed), as `readUrl` does for `PULSE_STATUS_PUBLIC_URL`. Do not repeat the value in the error.
