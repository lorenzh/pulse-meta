# Security audit: pulse-notify (2026-10-31)

## Scope

- Issue: lorenzh/pulse-meta#450 (periodic security audit of `main` in pulse-notify).
- Repositories and examined commits:
  - notify `584eabd05abcadc8f5a1035307e2c09a7a84c933` (newest `main`, clone in `.repos/notify`).
  - meta `b8d8e3d268ac3ed104565420f828fcc60f01547c` (`docs/approved-packages.md`).
  - contract `61f7bf88c38ab4827fb47e9409e18d37b9a7ccd3` and kit `fa79ba8cd93949fc0cf87f7b41bdaf261dbe4dc6`: the versions that notify pins, read in the installed copy (`src/client.ts`, `src/validate.ts`, `src/ops-server.ts`). Both pins are ancestors of `main` (contract `main` `ebcbbb613328494185833f7133f1242910986948`, kit `main` `6a06ec25d26d90be12eba133972b59077dd0e17d`; `main` is 2 commits ahead in both).
  - config `51e95b0eb463b27a196a33b428607bd92443e4f0`: the pinned reusable `check.yml`, read through the GitHub API.
- Method: a copy of notify in `mktemp -d`, `bun install --frozen-lockfile`, Bun 1.4.0 on Linux. `bun run check` passes (272 tests, exit 0). Hostile-input probes ran as extra test files in the copy only, against local servers on `127.0.0.1` (fake pulse-api, webhook receiver, HTTP proxy, SMTP stub, TLS server with a throwaway certificate). The service ran once with `bun run start` against a fake api, with the ops listener on. The Docker image was built from the copy. All 32 probes ran in one go with coverage off: exit 0. One expectation test per finding (`SEC-1` to `SEC-9`) fails with exit 1 on this commit. Reproductions stay outside the repository; they are not committed.
- Surface: notify has no application HTTP server. Its inbound surface is the ops listener (`/healthz`, `/readyz`, `/metrics`, from pulse-kit), the config file, environment variables, secret files, the state and lock files, and the `failed` CLI. Its outbound calls go to pulse-api (GET) and the channels (webhook, Slack, Teams POST, SMTP, file).

## Issue candidates

All findings are `P3`: each needs a contrived input (hostile api data, a hand-edited state file, a reserved channel id, a planted symlink) or is a policy drift with low impact. The commands below describe each check without its input.

### SEC-1 `security-notify-2026-10-31-1` (P3): one malformed api item stops every notification

- Location: `src/notifier.ts:408` (`String(id)` in `#reportRejected`) and `src/notifier.ts:331` (`String(r.id)` for manual incidents), called in `#poll` before any channel is polled.
- Class: an unguarded type conversion of untrusted data after validation. A rejected item is logged with its raw `id`. Converting an id that `String()` cannot convert, or one so deep that the conversion overflows the stack, throws out of the poll.
- Check: a fake api returns one valid new incident and one incident whose `id` cannot be converted to a string. Then run one poll and the running service. Exit 1 (`SEC-1` expectation).
- Effect: `consecutiveFailedPolls=1 validIncidentDelivered=false`. On the running service: `poll failed unexpectedly {"error":"No default value"}` on every poll. In the test, the deep variant logs `Maximum call stack size exceeded.`. `/healthz` and `/readyz` answer `503 polls failing (11 in a row)`. The valid incident is delivered only after the bad item is gone. The same item in `/manual-incidents` also blocks automatic incidents.
- Impact: while the api serves such an item, no channel gets any notification, and the health check fails, so an orchestrator restarts the container in a loop. This breaks the documented rule that a malformed item is skipped (`README.md`) and that a failed manual feed still lets automatic incidents through (`docs/channels.md:80`).
- Fix direction: build the dedupe key and the log field without converting the raw value, for example from `typeof` or a bounded `JSON.stringify` in a `try`. Never let reporting throw out of `#poll`.

### SEC-3 `security-notify-2026-10-31-3` (P3): the api reader follows redirects across origins and from https to http

- Location: `src/api.ts:117` to `:127` (`getArray` calls contract `fetchJson` with the default `fetch`). The contract (`client.ts:133`) sets no `redirect` option, so `fetch` follows redirects.
- Class: SSRF and downgrade via redirect.
- Check: an https api (throwaway certificate) answers `302` with a plain-http location on another port. Read `/incidents`. Exit 1 (`SEC-3` expectation).
- Effect: `https api 302 -> plain http host: accepted, requests at the http host: 1`. Cross-origin redirects (another port, another host name) are followed too.
- Impact: whoever can make the api origin, or a proxy in front of it, send a redirect makes notify read its incident feed from another host or over plain http. A network attacker can then forge or hide incidents. The webhook, Slack and Teams senders refuse redirects; the api reader does not.
- Fix direction: pass a `fetch` that sets `redirect: "error"` (or `"manual"`, and treat 3xx as a failure) to `fetchJson`, or add the option to the contract client.

### SEC-2 `security-notify-2026-10-31-2` (P3): text of the api response body reaches the poll error and the log

- Location: `src/api.ts:86` to `:88` (`invalid-json` returns the `JSON.parse` message). It is logged by `src/notifier.ts:369` (`api poll failed`).
- Class: upstream reply text in errors and logs.
- Check: a fake api answers 200 with a body that is not JSON (as an HTML page from a login proxy would). Exit 1 (`SEC-2` expectation).
- Effect: `error: JSON Parse error: Unexpected identifier "<upstream token>"`. Bun puts the first unexpected token of the body into the message, up to about 200 characters (a 5,001-character token gave a 245-character message). In a second probe, a value of a JSON-like body reached the error.
- Impact: a token from an upstream or proxy response, for example a session value on a login page, can land in the service log.
- Fix direction: map `invalid-json` to a fixed text such as `GET <path> did not return valid JSON`, as the `http` and `too-large` cases already do.

### SEC-4 `security-notify-2026-10-31-4` (P3): memory grows without bound for each distinct malformed item

- Location: `src/notifier.ts:152` (`#reported`, a `Set` that is never cleared). Keys are added at `:400` (the check error text, which holds arbitrary key names) and `:408` (the raw id).
- Class: memory exhaustion from upstream data.
- Check: a fake api returns, on each poll, one malformed item with a different large id. 50 polls, no-op logger, heap measured after a forced GC. Exit 1 (`SEC-4` expectation).
- Effect: `50 polls, one distinct 1 MB malformed item each: heap growth 50.6 MB`. The `/checks` feed gives the same result (50.6 MB).
- Impact: a hostile or broken api can grow the process by up to the body cap (5 MiB by default) per feed and poll, until it runs out of memory.
- Fix direction: key the dedupe on a bounded value (incident id when it is a number, else a short hash), cap the set's size, and cut logged values (see SEC-5).

### SEC-10 `security-notify-2026-10-31-10` (P3): the `docker` CI job uses a checkout pin that is not approved, without `persist-credentials: false`

- Location: `.github/workflows/ci.yml:24` (notify); `docs/approved-packages.md` (meta, "Runtime and CI").
- Class: unapproved CI action pin and persisted credentials.
- Check: `grep -n "uses:" .github/workflows/ci.yml`; `grep -c persist-credentials .github/workflows/ci.yml`; look for the pinned SHA in `docs/approved-packages.md`.
- Effect: `24: - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1`; `persist-credentials` count `0` (exit 1); the SHA is not in the approved list (exit 1). The list names `actions/checkout` `fbc6f3992d24…` (v5.1.0), "always with `persist-credentials: false`". `gh api repos/actions/checkout/git/ref/tags/v7.0.1` confirms that the SHA is the v7.0.1 commit. The pinned pulse-config `check.yml` uses the same SHA, with `persist-credentials: false`.
- Impact: low. The job has `contents: read`, and `.dockerignore` keeps `.git` out of the build context. But the token stays in `.git/config` while `docker build` runs on PR code, and the pin is outside the approved list.
- Fix direction: add `persist-credentials: false` to the step. Then either update the approved list to the v7.0.1 SHA that the targets and pulse-config use, or pin the approved SHA.

## Notes

Findings that are not issue candidates:

- **SEC-5 `security-notify-2026-10-31-5` (P3)**: raw upstream item data in logs, without a size cap. Location: `src/notifier.ts:403` (`reason: error`; the contract error names unknown keys) and `:411` to `:414` (`incidentId: id`, logged raw). Check: a fake api returns a check with a 100,000-character unknown key and an incident whose id is a 200 KB object; one poll. Exit 1. Effect: `check skipped: malformed data: 100061 bytes; incident skipped: malformed data: 200073 bytes` for one log line each. Fix direction: log the type and a truncated value only. SEC-4 fixes the same code.
- **SEC-6 `security-notify-2026-10-31-6` (P3)**: `failed list` throws on an out-of-range time in the state file. Location: `src/failed-cli.ts:27` (`new Date(entry.at).toISOString()`); `src/ledger.ts:60` accepts any number as `at`. `migrate` also takes `payloads` unchecked (`src/ledger.ts:83`): a non-object payload is listed with an empty event and `resend` reports it as `resent`. Check: a state file with a failed entry whose `at` is beyond the `Date` range; run `failed list`. Exit 1. Effect: `failed list: uncaught RangeError: Invalid Date` (not exit 0, 1 or 2 as documented). Only a hand-edited or damaged state file triggers it.
- **SEC-7 `security-notify-2026-10-31-7` (P3)**: a reserved channel id reaches `Object.prototype`. Location: `src/channel-schema.ts:42` (`id: z.string()`, no restriction) and `src/ledger.ts:321`, `:370`, `:392` (`this.#data.channels[channelId] ?? {}` on a plain object). Check: a config with channel id `__proto__`; seed the ledger. Exit 1. Effect: `config accepts id __proto__: true; Object.prototype gained the key: true`. `hasChannel` stays false, so that channel is seeded on every poll and never notified, and its state is never saved. Needs the operator to choose such a name. Fix direction: restrict ids to a safe pattern, or use null-prototype objects or `Map`s in the ledger.
- **SEC-8 `security-notify-2026-10-31-8` (P3)**: the ledger writes through a symlink at its fixed temp path. Location: `src/ledger.ts:177` to `:185` (`openSync(\`${path}.tmp\`, "w")`, then `rename`); the lock heartbeat at `src/ledger-lock.ts:110` to `:112` works the same way. Check: plant a symlink at `<state>.tmp` that points to another file, then seed the ledger. Exit 1. Effect: `file behind the planted temp symlink now starts with: {"version":2,"channels":`, and the state path becomes the symlink. Needs write access to the state directory (`/data` in the image belongs to the service user; `fs.protected_symlinks` covers sticky world-writable directories). Fix direction: create the temp file with `wx` (`O_EXCL`) and a random suffix.
- **SEC-9 `security-notify-2026-10-31-9` (P3)**: config and state parse errors repeat a token of the file. Location: `src/config.ts:306` and `src/index.ts:118`. Check: a config with a bare word outside quotes; a state file that is not JSON. Exit 1. Effect: `config file <dir>/notify.json is not valid JSON: JSON Parse error: Unexpected identifier "<file token>"`; `cannot use state file <dir>/state.json: JSON Parse error: Unexpected identifier "<file token>"`. The text inside a broken string is not repeated (`Unterminated string`). The webhook `url` is the only credential the config may hold (`docs/configuration.md:84`).

Observations without a defect:

- **N1**: Bun's `fetch` uses `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` from the environment for the api, webhook, Slack and Teams calls. Check: a child process with `HTTP_PROXY` set to a local listener posts to an http webhook URL with a query. Effect: the proxy saw `POST http://192.0.2.10:8080/hook?token=<query secret> HTTP/1.1`, exit 0. For https only the host name reaches the proxy (CONNECT). The docs do not mention this; they say "pulse-notify does not log URLs".
- **N2**: user info in `PULSE_API_URL` is accepted and redacted in logs, but Bun 1.4.0 never sends it (`authorization: null`, also for a raw `fetch`). An api behind basic auth cannot be reached this way. This is not a leak; the docs could say so.
- **N3**: `bun audit` reports `minimatch@10.2.6`, moderate, GHSA-g3hv-75wg-m249 (fixed in 11.0.1). The package comes in through the ESLint toolchain of pulse-config (dev only). It is not in the production install (4 packages) or the image.
- **N4**: the Docker build stage runs `apk add --no-cache git` without a version pin. It is used only to fetch the git dependencies and is not in the final image (`which git`: none).
- **N5**: pulse-config is a dev dependency by git SHA, but `docs/approved-packages.md` lists only pulse-contract and pulse-kit as internal packages.
- **N6**: the ops listener has no authentication. The image binds it to `0.0.0.0:9100`, so `/metrics` and `/readyz` are open to the container network. They show channel ids, counters and the readiness reason only.
- **N7**: during SEC-1, `pulse_notify_polls_total{outcome="ok"}` kept rising (218) while `pulse_notify_consecutive_failed_polls` was 11: `pollDone("ok")` is counted before the step that throws.
- **N8**: an SMTP server that answers `MAIL FROM` with a non-numeric line ends the event as permanent (`SMTP address is not valid`), not as a retryable error. No server text is shown.
- **N9**: the contract and kit pins are 2 commits behind `main`. The newer contract commit accepts only http and https check URLs; notify reads only check ids and names.
