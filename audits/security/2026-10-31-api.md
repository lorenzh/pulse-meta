## Checklist

### 1. Secrets and server texts (tokens, header values, SMTP or upstream replies, file contents) in errors, logs and responses: `checked`

- Public reads: `curl` of `/checks`, `/uptime`, `/latency`, `/components`, `/components/uptime`, `/incidents`, `/locations`, `/maintenance`, `/manual-incidents`, `/metrics`, `/readyz`, `/checks/api-secret/results` and `/checks/api-secret/latency`, each searched with `grep -Ec` for the literal header value, the body, the env name, the heartbeat secret and the three tokens. Result: `leaks=0` on every route (all `HTTP200`).
- `GET /admin/config` with the admin token: header names only (`"headers":["X-Api-Key","Authorization"]`), plus `hasBody` and `hasSecret`. No value of any kind. A create with a literal header and a body answered `{"id":"new1",...,"method":"POST","headers":["X-K"],"hasBody":true} HTTP201`. A heartbeat `PUT` without `secret` kept the stored secret and answered `"hasSecret":true`.
- `422` answers of admin writes give the field path and the rule, never the value. Examples: `checks[4].headers.X-K: must be at most 4096 visible ASCII/obs-text characters or spaces`, `checks[5].secret is required: 16 to 128 characters from A-Z a-z 0-9 . _ ~ -`, `checks[5].secret still has the example placeholder secret`, `checks[5].url: must be an http: or https: URL`.
- Hot reload: 7 hostile checks files were applied with `SIGHUP`. 6 were rejected. The seventh, an `{"env": ...}` reference with an extra key, was accepted (see Notes). Each rejection line names the path and the rule only, for example `config reload rejected: <path>: checks[3].secret is required: 16 to 128 characters ...`, `... checks[0].headers.X-A: must be at most 4096 visible ASCII/obs-text characters or spaces`, `... is not valid JSON`. The API stayed up (`/readyz` `HTTP200`).
- Startup: 15 broken settings and files. Each printed one line `pulse-api: <message>` and exited with code 2. No line held a token or secret value (search count `0`). Examples: `tokens[0] (location "east") token must not contain whitespace (PULSE_TOKENS_FILE=<path>)`, `admin tokens[0] is also a probe token: use a separate token (...)`, `cannot open database <path> (PULSE_DB): unable to open database file`.
- Logs: after all runs, `grep -Ec` for every secret, token and test marker over stdout and stderr returned `0`. Auth failures log only the route pattern, the status and the token kind (`"msg":"admin auth failed","route":"/admin/config","status":"403","token":"probe","suppressed":"0"`). Failed writes log only the status, kind and action.
- Tests in the copy: `sentinel: tokens, the heartbeat secret and the placeholder never reach a log line`, `sentinel: header values, env names, bodies and secrets stay out of every output`, `GET /checks never serves the secret`. They ran with 11 others under a name filter: `14 pass, 0 fail`. The exit code was 1 only because of the 80 % coverage gate on a filtered run.
- SMTP replies: not applicable, because the API sends no mail. Upstream replies: the API makes no upstream request. It stores and serves the `reason` text of the probe as received (see Notes). As documented, `GET /probe/checks` gives literal header values and bodies to probe tokens.

### 2. Authentication before any other check; status codes and their order on admin routes: `checked`

The local script made 47 requests. The answers follow the order in `docs/rest-api.md`:

- `/admin/*`: no token, `Basic` auth or an unknown bearer gives `401 {"error":"unauthorized"}`. A probe token gives `403 {"error":"forbidden"}`. Both come before `405`: `POST /admin/config` and `PATCH /admin/checks` without a token give `401`, and with the admin token `405`. Both also come before the body: a 2 MB body without a token gives `401`, with a probe token `403`, with the admin token `413`. With the admin token, the remaining order is `400` bad JSON, `428` without `If-Match`, `400` for `If-Match: *`, `400` for an id mismatch, `412` for a stale revision, `422` for an invalid body, `409` for an existing or still referenced id, and `404` for an unknown id or index. A read-only checks directory gives `503 checks file is read-only (EACCES)`.
- Feature off (no `PULSE_API_ADMIN_TOKENS_FILE`): with the admin bearer, `GET /admin/config`, `POST /admin/checks`, `POST /manual-incidents` and `DELETE /manual-incidents/1` give `404`. No log line.
- Manual-incident writes: without a token `401`, also with a 20 KB body. A probe token gives `401`. An unknown id with the admin token gives `404` only after authentication.
- Probe routes: `POST /results` gives `401` before `413`. `GET /probe/checks` gives `401` for no token and for the admin token. Heartbeat: a wrong secret, an unknown id and a probe token all get the same `401 {"error":"unauthorized"}`.
- Path tricks against `/admin/config` without a token: absolute-form target, dot-segments, encoded dot-segments, backslashes, bad escapes. Results: `401` or `404`, never `200`.
- Tests: `admin: the status order of the spec`, `auth: 401 beats 400 and 404`, `401 bodies are identical for wrong secret, missing secret and unknown id`. Pass.
- On manual-incident routes and on `/results`, `/probe/checks` and `/heartbeat`, the method (`405`) and the id shape (`404`) are checked before authentication. This is documented and tested (`a 405 is decided before auth and logs nothing`). See Notes.

### 3. Body and size limits on every method, also before any write: `checked`

- Over-limit bodies get `413` after authentication and before any write:
  - `POST /results`: 2 MB (limit 1,000,000 bytes).
  - `POST /admin/checks`: 2 MB, both with `Content-Length` and chunked.
  - `DELETE /admin/checks/web`: 2 MB. Nothing was deleted.
  - `POST /manual-incidents`: 20 KB (limit 16 KiB).
  - `POST /heartbeat/backup` with the correct secret: 2 KB (limit 1 KB).
- 300 MB chunked streams:
  - `GET /checks`: `HTTP200` in 0.45 s.
  - `POST /results`, `POST /heartbeat/backup` and `DELETE /manual-incidents/1` without auth: `HTTP401` in at most 0.42 s.
  - Authenticated `POST /results`, `/admin/checks`, `/manual-incidents` and `/heartbeat/backup`: `HTTP413` in at most 0.34 s.
  - API RSS was 70,308 KB before and at most 75,952 KB after.
- Keep-alive desync check: a body that the server does not read and that holds a whole second request, sent to `GET /checks`, `GET /healthz`, unauthenticated `POST /results`, `POST /admin/checks`, `DELETE /manual-incidents/1` and `POST /heartbeat/x`. Each gave `responses=1`. The control case (two pipelined requests) gave `responses=2`.
- Bun's parser: `Content-Length` plus `Transfer-Encoding`, two `Content-Length` headers, or a negative `Content-Length` gives `400`. A 64 KB header gives `431`.
- Deeply nested JSON up to 800 KB on `/results`, `/manual-incidents` and `/admin/checks` gives `400` or `422`, never `500`.

### 4. Input validation at every trust boundary; validators never throw on any input type: `checked`

- Fuzz script with 265 cases. Inputs: `undefined`, `null`, `NaN`, `Infinity`, BigInt, Symbol, a function, `Date`, a null-prototype object, `__proto__` keys, arrays, a throwing `Proxy` and accessors. Targets: `validateResult`, the contract validators `validatePostResultRequest`, `validateManualIncidentInput`, `validateManualIncidentUpdateInput`, `validateCheck` and `validateComponent`, the parsers `parseConfig`, `parseTokens` and `parseAdminTokens`, and `findByToken`. Output: `cases: 265, threw: 2, getter runs: 2`. Both throws are `parseConfig` with a throwing `Proxy`, which `JSON.parse` cannot produce (Notes). Every validator returned a value.
- Query parameters: `limit=99999999999999999999` gives `400 limit must be a positive integer`, `since=-1` gives `400 since must be a non-negative integer`, a bad escape in a check id gives `400 bad check id`.
- Environment settings (`PORT`, `PULSE_CHECKS_RELOAD_INTERVAL_MS`, `PULSE_LOG_LEVEL`, `PULSE_RETENTION_DAYS`, `PULSE_LOCATION_SILENT_MS`, `PULSE_DB`): one line each, exit 2.
- Probe input: a token for location `east` that posts location `west` gets `403 location does not match token`. A result for a heartbeat check gets `403`. A timestamp one hour ahead gets `400`. A `__proto__` key in the body changes nothing: the result is stored under the location of the token.
- Finding `security-api-2026-10-31-1`: the request target is parsed without a guard. A target that the URL parser rejects throws and gets a `500`.

### 5. No accessor or getter of untrusted input runs: `checked`

- All untrusted HTTP bodies and files go through `JSON.parse`, which never creates accessors (`JSON.parse makes accessors? false`).
- The contract validators read own data properties only. An accessor on each of the 6 required result fields counts as absent: `getter runs=0`, `result.<field>: is required`.
- Finding `security-api-2026-10-31-3`: `validateResult` then reads the optional fields `location`, `attempts` and `certDaysLeft` by plain property access. A getter therefore runs on a direct call. This cannot happen over HTTP.

### 6. SSRF: allowed targets, environment lookups, redirects (cross-origin, https to http), forwarded headers: `checked`

- The API never resolves an `{"env": NAME}` header reference. It stores the reference and serves it to probes as written; the probe resolves it.
- Allowed check targets: `file:` and `gopher:` URLs get `422 checks[11].url: must be an http: or https: URL`. An admin can add link-local and loopback `http` URLs (`201`). See Notes; the probe fetches them.

### 7. File writes atomic and path-safe: `checked`

## Issue candidates

### security-api-2026-10-31-1 (P3): a request target the URL parser rejects gets 500 and an error-level stack trace

- Location: `src/server.ts:535`, in `handle`: `new URL(req.url ?? "/", "http://localhost")` runs without a guard. `routeOf` at `src/server.ts:205` guards the same call.
- Class: unhandled exception on malformed input, before authentication.
- Check (no payload): a raw HTTP/1.1 `GET` without a token, whose request target the WHATWG URL parser rejects, sent 200 times to a local instance by a Bun script over `node:net`. Then: the status lines, the count of new stderr lines with level `error`, and the 5xx series of `/metrics`. Script exit code `0`.
- Output:

  ```text
  {"HTTP/1.1 500 Internal Server Error":200}
  error lines added: 200
  pulse_api_http_requests_total{route="unmatched",code="500"} 202
  {"level":"error","msg":"request failed","error":"TypeError: Invalid URL\n    at URL (unknown)\n    at handle (<copy>/src/server.ts:535:19)\n ..."}
  ```

  The same target with an ops path (`/healthz`) also gets `500`.
- Impact: any client without a token can write one error-level log line with a stack trace per request and raise the 5xx request counter. This means log volume and false alerts. The API answers `500 internal error` where `400` is the right answer. No data or secret is exposed, and the log line does not hold the request target.
- Fix direction: parse the request URL in a guard, as `routeOf` already does, and answer `400` before any route, with no error log.

## Notes

### security-api-2026-10-31-3 (P3, note): `validateResult` runs getters of optional fields

- Location: `src/server.ts:161` (`parseLocation(b.location)`), plus `src/server.ts:117-123` and `src/server.ts:173-175` (`attempts`, `certDaysLeft`).
- Command: a Bun script that imports `validateResult` from a copy of `src/server.ts` and calls it with a result body whose field is an accessor. It counts the getter runs. Exit code `0`.
- Output:

  ```text
  validateResult accessor checkId: getter runs=0 result=result.checkId: is required
  validateResult accessor location: getter runs=1 result=accepted
  validateResult accessor attempts: getter runs=2 result=accepted
  validateResult accessor certDaysLeft: getter runs=2 result=accepted
  JSON.parse makes accessors? false
  ```

- The contract validator counts accessor fields as absent. The API then reads the same fields by plain property access, so a getter runs, up to twice. A getter could return a checked value first and a different value for the stored result.
- This cannot happen over HTTP, because bodies come from `JSON.parse`. It is not an issue candidate.
- Fix direction: build the `Result` from the validated value of the contract, or read the optional fields as own data properties.

### Other notes (no finding)

- Admin writes accept link-local and loopback `http` URLs as check targets (`201`). The API itself never connects anywhere. The probe fetches these targets for an admin or for the person who edits the checks file. A target policy, if wanted, belongs to the pulse-probe audit.
- `GET /checks` is public and serves the `url` of a check as written. Credentials in a URL (userinfo or a query token) would be public. The docs say that reads are public and that secrets go into `{"env": ...}` headers, but they do not warn against credentials in the URL. This was read from `src/service.ts` (`toCheck` serves `url`) and not tested with userinfo.
- An admin write over a symlinked checks file replaces the link with a regular file in the same directory and leaves the target unchanged. This is path-safe, but the link is lost, and later edits of the target are not seen. `docs/operation.md` does not say this.
- `POST /results` accepts unknown top-level keys and stores control characters in `reason` as sent: NUL and ESC came back from `/checks/web/results`. Manual incidents refuse control characters. Consumers of `reason` must escape it.
- On `/manual-incidents/*`, `/results`, `/probe/checks` and `/heartbeat/*`, a wrong method (`405`) or an id that is not a number (`404`) is answered before authentication. This shows only the shape of a route. It is documented and tested.
- Failed authentication is not rate limited. Admin failures are logged once per minute per route, status and token kind, and are always counted in `pulse_api_admin_auth_failures_total`. Tokens and secrets have at least 16 characters.
- `parseConfig` throws a plain `Error` (no `ConfigError`) for a `Proxy` whose traps throw. `JSON.parse` cannot produce such an input.
- The top-level check object rejects unknown keys, but nested objects of the contract do not. An `{"env": NAME}` header reference and a `jsonAssert` item accept extra keys. The checks file keeps those keys, and `GET /probe/checks` and `GET /admin/config` serve them. A `validateCheck` run on contract `ebcbbb6` gives `{"env":"PULSE_HEADER_X","extra":1} -> ok, stored as {"X-K":{"env":"PULSE_HEADER_X","extra":1}}`. The admin write behaves the same way (`jsonAssert` item with `"x":1` gets `201`). This is a contract matter, and nothing secret is involved.
- `jsonAssert[].equals` nested 1,000 levels deep is accepted (`201`) and served by `GET /admin/config` and `GET /probe/checks`. `jq` with its default depth limit fails on that answer. 10,000 levels or more get `422 checks[9]: is not a valid value`.
- `bun audit` reports `minimatch@10.2.6` (moderate, GHSA-g3hv-75wg-m249), reached only through the lint toolchain of pulse-config (`eslint`). It is not in the image.
- The build stage of the `Dockerfile` runs `apk add --no-cache git` without a version. Only that stage uses it. `compose.yaml` builds probe, status and notify from `#main` of their repositories rather than from a fixed SHA (first-party, documented).
- `.dockerignore` does not list `admin-tokens.json`. The `Dockerfile` copies only `package.json`, `bun.lock` and `src/`, so the file never reaches the image, only the build context.
