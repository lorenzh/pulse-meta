## Issue candidates

### SEC-1 `security-probe-2026-11-04-1` (P2): an accepted location setting makes every HTTP check report down

- Location: `src/location.ts:5`, `src/location.ts:14` and `src/check.ts:502`.
- Class: missing startup validation before using an environment setting in an outbound HTTP header.
- Check: command, input and procedure withheld under the public security disclosure rule. `audit-review` independently rebuilt SEC-1 outside the repository and reproduced it; expectation exit 1.
- Effect (sanitized review output): settings accepted; HTTP `down` 3/3, TCP `up` 3/3; control HTTP `up`; graceful service shutdown exit 0. Input and reproduction procedure withheld.
- Impact: some documented location names accepted at startup make every HTTP check report down with only `request error`. This creates false incidents with one location and false down votes that can affect quorum with several. The review independently confirmed the failure against local peers.
- Fix direction: validate `PULSE_LOCATION` against its downstream header encoding at startup, with exit 2 and a message naming the setting, or safely encode the location before forming the `user-agent` header. Document the accepted values.

### SEC-2 `security-probe-2026-11-04-2` (P3): the api client follows redirects to another origin and from https to http

- Location: `src/client.ts:386` (`postResult` calls `fetch` without a `redirect` option) and `src/client.ts:281` (`requestChecks` calls contract `fetchJson`, which sets no `redirect` option at contract `src/client.ts:130`).
- Class: SSRF and downgrade via redirect on the api connection.
- Check: a fake api answers `POST /results` with a 307 to another origin, and `GET /probe/checks` with a 302 to another origin; an https api redirects to plain http. Then the running service against an api that answers every `POST /results` with a 307 to another origin. Exit 1 (`SEC-2` expectation).
- Effect: `outcome=accepted postsAtOtherOrigin=1`. 307 and 308 re-send the result body to the other origin and count it as `accepted`. On the running service: api posts 6, posts at the other origin 6, `pulse_probe_results_posted_total{check="web",outcome="ok"} 6`, no log line. The check list is read from the other origin, also over plain http after an https api. Bun drops the `Authorization` header on each of these hops, so the probe token does not leave the api origin.
- Impact: whoever can make the api origin, or a proxy in front of it, answer with a redirect makes the probe deliver its results elsewhere while it counts them as delivered, and read its check list from another host or over plain http. A network attacker on that plain-http leg can then choose which targets the probe connects to. The probe sends `{ env }` secrets only to bound hosts, so it does not send them to the other origin.
- Fix direction: pass `redirect: "error"` (or `"manual"`, and treat 3xx as a failure) on `POST /results`, and give `fetchJson` a `fetch` that does the same (or add the option to the contract client).

### SEC-3 `security-probe-2026-11-04-3` (P3): text of an api response body reaches the log

- Location: `src/client.ts:220` (`invalid-json` copies the `JSON.parse` message). It is logged by `src/client.ts:372` (`fetching checks failed`) at startup and by `src/reloader.ts:50` (`reloading checks failed`) on reload.
- Class: upstream reply text in logs.
- Check: a fake api answers `GET /probe/checks` with 200 and a body that is not JSON and starts with a bare word. Then the same on the running service. Exit 1 (`SEC-3` expectation).
- Effect: `fetching checks failed: invalid JSON: JSON Parse error: Unexpected identifier "<upstream token>"; retrying in 10000ms` on the running service; `markerInLog=true` in the test.
- Impact: a token from the api or from a proxy reply can land in the probe log when the body has a bare word at the first invalid position. The HTTP checks avoid this on purpose (`src/check.ts:346`), but the api client does not.
- Fix direction: map `invalid-json` to a fixed text such as `invalid JSON`, as the `http` and `too-large` cases already do.

### SEC-4 `security-probe-2026-11-04-4` (P3): the id of an invalid check is logged without a length cap

- Location: `src/client.ts:246` to `:247` (`skipping invalid check <id>: <error>`).
- Class: unbounded upstream data in logs.
- Check: a fake api serves an invalid check with a 1,000,000-character id and three with 100,000-character ids; one load. Exit 1 (`SEC-4` expectation).
- Effect: `longest log line=1000051 chars`; the four lines have 1,000,051, 100,051, 100,051 and 100,051 characters for a 1.3 MB body. The contract accepts ids of any length.
- Impact: a hostile or broken api can write up to the 5 MiB body cap into the log on each load. Each id is logged once, but the memory of logged ids is reset after 10,000 ids, so many distinct ids can repeat on each reload. The comment at `src/client.ts:179` already treats such an api as hostile, but only for the dedupe keys.
- Fix direction: cut the id in the log line (for example with `quote` from `src/reason.ts`), or log its hash or position.

## Notes

Findings that are not issue candidates:

- **SEC-5 `security-probe-2026-11-04-5` (P3)**: a header named `__proto__` is dropped without a log line. Location: `src/client.ts:144` and `src/check.ts:556` (`value[name] = raw` on a plain object). The contract accepts the name (a valid token). Check: a fake api serves a check with the headers `__proto__` and `x-other`; load it and run it. Exit 0 (observation). Effect: `checks 1 status up headers at target: accept,accept-encoding,connection,host,user-agent,x-other`. Assigning a string to `__proto__` is a no-op, so no prototype changes; the header is just missing. Fix direction: build the header map with `Object.create(null)` or a `Map`, or reject the name in the contract.

Observations without a defect:

- **N1**: Bun's `fetch` uses `HTTP_PROXY` and `HTTPS_PROXY` from the environment for the api calls too, not only for HTTP checks. Check: a child process with `HTTP_PROXY` pointing at a local listener loads the checks from a plain-http api and runs an HTTP check with a literal header. Effect: the proxy saw `GET http://192.0.2.10:8080/probe/checks HTTP/1.1 | Authorization: Bearer <token>` and the check's header. This is how a proxy works; the docs mention the proxy only for checks (`docs/configuration.md:290`).
- **N2**: `bun audit` (exit 1) reports `minimatch@10.2.6`, moderate, GHSA-g3hv-75wg-m249 (fixed in 11.0.1). It comes in through the ESLint toolchain of pulse-config (dev only) and is not in the image.
- **N3**: the Docker build stage runs `apk add --no-cache git` (`Dockerfile:2`) without a version pin. It is used only to fetch the git dependencies and is not in the final image (`which git`: none).
- **N4**: pulse-config is a dev dependency by git SHA, but `docs/approved-packages.md` lists only pulse-contract and pulse-kit as internal packages.
- **N5**: the contract, kit and config pins are 9, 7 and 2 commits behind `main`. The newer contract commits change how validators read objects (`fix: read top-level response elements only as own data`). probe passes only `JSON.parse` output to them, so this does not change probe's exposure.
- **N6**: the ops listener has no authentication. The image binds it to `0.0.0.0:9100` (`Dockerfile:10`), so `/metrics` and `/readyz` are open to the container network. They show check ids, counters and the readiness reason only.
- **N7**: by design, a `jsonAssert` reason quotes the value found in the target's body, cut to 80 characters (`json /a: expected "x", got "<value>…"`, 108 characters for a 500-character value). This is documented (`docs/configuration.md:114`). A check author who points a check at an endpoint that returns secrets can copy them into results.
- **N8**: `PULSE_PROBE_BLOCK_PRIVATE_RANGES` does not block `::ffff:0:0/96` (IPv4-translated), which the docs list does not name. On this host such an address did not reach a local IPv4 listener (`ECONNREFUSED`). The docs already list NAT64, 6to4 and Teredo as not blocked.
- **N9**: when the api answers `POST /results` with 301, 302 or 303 to another origin, `fetch` follows with a `GET /results` there, and the result is dropped as `rejected` (test: `outcome=rejected`, the other origin saw `GET /results` with an empty body). The fix for SEC-2 also covers this case.
