# Security audit: pulse-contract (2026-11-03)

## Scope

- Issue: lorenzh/pulse-meta#678 (periodic security audit of `main` in pulse-contract). Audit date: 2026-11-03.
- Repositories and examined commits:
  - contract `7ce23aaf3fa3e038f65ecfed755188b83bde143f` (newest `main`, clone in `.repos/contract`). api, probe, status and notify all pin this commit.
  - meta `ef3473ddc1284dc312d497b320c554a206c841b3` (`docs/approved-packages.md`).
  - probe `89f12324a6e77d5a716beacc22e178b8e1112284`: consumer check for finding 2 (`loadChecks` in a copy). api `2d4a6b23d532e66ad30840a778ac21ab465647dc`, status `d268b5b1b0afcf9bc94ce508934ddd879bb90df0` and notify `3f120cc0efcf80fd68c5974dd603b9b4d1ae000c`: read only, to see how they call `fetchJson` and the validators.
  - config `51e95b0eb463b27a196a33b428607bd92443e4f0`: the reusable `check.yml` that contract CI pins, read through the GitHub API (config `main` is 11 commits ahead of the pin, and the pin is its ancestor).
- Method: a copy of contract in `mktemp -d`, installed with `bun install --frozen-lockfile` on Bun 1.4.0 (Linux). `bun run check` passes in the copy: lint, build, typecheck, 192 tests, 99.19 % line coverage, exit 0. The build leaves `dist/` unchanged. Hostile-input probes ran as scripts outside the repository, against the copy's `src/` and local servers on `127.0.0.1`: plain HTTP, a raw TCP server, and TLS with a throwaway certificate. Every finding has an expectation test (`SEC-1` to `SEC-6`) that states the safe behavior. Each one fails with exit 1 on this commit. Reproductions stay outside the repository; they are not committed.
- Surface: pulse-contract is a library with no server, no settings and no file I/O. Its runtime surface is (a) 39 exported validators (probed as 42 cases, one per check type), which take untrusted JSON from request bodies, config files and other services, (b) `fetchJson`, `getManualIncidents` and `getManualIncident`, a JSON GET client that probe, status and notify use to read pulse-api, (c) `checkWireVersion`, and (d) constants that the services enforce (`ADMIN_STATUS_ORDER`, `ADMIN_MAX_BODY_BYTES`, `TOKEN_MAX_BODY_BYTES`).

## Issue candidates

The P2 finding is described without its input, as the disclosure rule requires. The P3 checks also leave out their inputs where the check would work against a running service. Each check below names its expectation test.

### SEC-1 `security-contract-2026-11-03-1` (P2): compressed responses get around the `fetchJson` body cap and use memory up to their full decoded size

- Location: `src/client.ts:130` to `:134`. The request init is only `{ signal }`, so Bun's `fetch` asks for `gzip, deflate, br, zstd` and decodes the response itself. `src/client.ts:75` to `:101` counts only the bytes the reader gets.
- Class: decompression bomb (resource exhaustion) that gets around a documented body limit.
- Check: a local server answers one GET with a brotli-encoded or zstd-encoded body of a few KiB that decodes to 1 to 2 GiB. Call `fetchJson` with the default 5 MiB cap and sample peak RSS in a fresh Bun process. `SEC-1` expectation (peak RSS growth under 64 MiB): exit 1.
- Effect: `SEC-1 kind=too-large peakRssDeltaMiB=1305 compressedBytes=1681`. In fresh processes: brotli of 2 KiB → +1,336 MiB peak in 2.1 s; 3 KiB → +2,568 MiB in 4.3 s; zstd of 32 KiB → +2,056 MiB. Growth is linear in the decoded size. gzip and deflate stay at +178 MiB. An uncompressed endless body adds +13 MiB. Bun decodes the body as it arrives: a body cancelled without a read still gave +1,330 MiB, and so did a request sent with `Accept-Encoding: identity`. Only Bun's `decompress: false` request option kept it at +2 MiB.
- Impact: one response of a few KiB makes the process that calls `fetchJson` allocate memory up to the decoded size, so a memory-limited container is killed. This hits every caller that passes Bun's `fetch`: probe (check list), status (api poll) and notify (incident feed). It also hits non-2xx answers, because the body is decoded even when it is never read. The response can come from the api origin, from any origin that a redirect leads to (SEC-3), or from an on-path attacker on a plain-http api URL. The documented 5 MiB cap (`README.md`, `docs/index.md` "API client") does not bound memory.
- Fix direction: stop the runtime from decoding ahead of the cap. Set Bun's `decompress: false` on the request init (other runtimes ignore it). Then either refuse a response whose `Content-Encoding` is not `identity`, or decode it in a streaming decoder inside the byte-counting loop that stops at `maxBytes`. Add a test with an encoded response.

### SEC-2 `security-contract-2026-11-03-2` (P3): a header entry named `__proto__` is never validated, and pulse-probe then loads no checks

- Location: `src/schema.ts:141` (the `headers` record), `src/validate-core.ts:241` to `:247` (`recordView` keeps the own key) and `src/validate-core.ts:314` (the input object is returned). zod 4.6.7 skips a record key named `__proto__` without parsing its value (`node_modules/zod/v4/core/schemas.js:1762`).
- Class: validation bypass through a reserved prototype key name (type confusion in the validated value).
- Check: a check parsed from JSON whose header record has an entry under that key name with a value of a wrong type. Run `validateCheck` and `validateAdminCheckInput`, then pulse-probe `loadChecks` (in a copy) with that check and one valid check. `SEC-2` expectation: exit 1.
- Effect: `SEC-2 validateCheck ok=true validateAdminCheckInput ok=true`. Values that should fail all pass as that entry: values of a wrong type (also inside `{ env }`), a variable without the `PULSE_HEADER_` prefix, a value with CR/LF, and a value over the 4,096-character limit. The entry also does not count toward the 20-header limit or the 16 KiB total. pulse-probe: `loadChecks throws TypeError` (a property read on the unvalidated entry in `src/client.ts:148`), and the valid check is not loaded either. Literal values and a variable without the prefix are dropped or refused by the probe, so it reads no other environment variable.
- Impact: a writer of checks (an admin token on the api, or the checks file; api `src/config.ts:160` and `:249` validate with `validateCheck`) can store one check that every probe fails to load. A probe that starts up retries without end. A running probe keeps its old list and never applies changes. The validated type `Record<string, string | { env: string }>` does not hold, so any consumer can crash on it.
- Fix direction: reject an own `__proto__` key in the header record in the contract (in `recordView` or a check on the input), or validate every own entry value without relying on zod's record loop. Add tests for that key under each header rule.

### SEC-3 `security-contract-2026-11-03-3` (P3): `fetchJson` follows redirects to other origins and from https to http

- Location: `src/client.ts:130` (`const init: RequestInit = { signal };`, no `redirect` option) and `:134`.
- Class: SSRF and downgrade via redirect.
- Check: a local origin answers 302 or 307 with a location on another host name and port. A TLS origin answers 302 to plain http. Call `fetchJson` with a credential in a custom header. `SEC-3` expectation: exit 1.
- Effect: `SEC-3 crossOrigin ok=true httpsToHttp ok=true`. The redirect target got 1 request each time, and its body came back as the value. The custom header `x-api-key` arrived at the other origin and at the plain-http host. `Authorization` and `Cookie` were dropped by Bun.
- Impact: whoever can make the api origin (or a proxy in front of it) answer with a redirect makes probe and status read their checks or status data from another host or over plain http, where it can be forged. Credentials in custom headers cross to that host. It also widens SEC-1. notify protects itself (`redirect: "manual"` in `src/api.ts:137`); probe and status do not.
- Fix direction: set `redirect: "error"`, or `"manual"` and treat a 3xx as an `http` error, in the init that `fetchJson` builds. Every consumer then gets it, and notify's wrapper becomes redundant.

### SEC-4 `security-contract-2026-11-03-4` (P3): the upstream wire-header value appears unshortened in `fetchJson` errors

- Location: `src/version.ts:26` (`got "${header}"`), reached from `src/client.ts:135` to `:146`.
- Class: upstream reply text in errors and logs.
- Check: a local server answers with a long `x-pulse-contract` value that holds a marker (200 and 500). `SEC-4` expectation: exit 1.
- Effect: `SEC-4 kind=wire-mismatch errorLength=4089 upstreamTextInError=true`. With an 8,014-character header, the error object was 8,089 characters as JSON. With a 500, the `http` error carries the text in `wire.error`.
- Impact: a header value from the api or a proxy (up to the runtime's header limit) reaches every consumer log line that prints the error. The value is neither cut nor escaped.
- Fix direction: put a fixed text in the error (`x-pulse-contract: expected 1`), or at most a short, escaped prefix of the value.

### SEC-5 `security-contract-2026-11-03-5` (P3): the `invalid-json` error carries text from the response body

- Location: `src/client.ts:111` to `:115` (the `JSON.parse` message becomes `message`).
- Class: upstream reply text in errors and logs.
- Check: a local server answers 200 with a body that is not JSON and has a bare word where the parser fails. `SEC-5` expectation: exit 1.
- Effect: `JSON Parse error: Unexpected identifier "<upstream token>"`. A token inside a JSON-like value appears too. A body that starts with `<` gives only `Unrecognized token '<'`. This is the root cause of notify finding `security-notify-2026-10-31-2`.
- Impact: a token from an upstream or proxy reply can reach the logs of probe, status and notify when the bare word comes first at the failing position.
- Fix direction: use a fixed `message`, such as `response is not valid JSON`, as the `http` and `too-large` cases already do.

## Notes

- **SEC-6 `security-contract-2026-11-03-6` (P3, not a candidate): getters on `Object.prototype` run in schema refinements.** Locations: `src/audit.ts:96`, `src/schema.ts:561`, `:689`, `:882`, `src/admin.ts:118` and `:132`. These refinements read fields from zod's output object, which inherits `Object.prototype`. When a getter without a setter sits there, zod's assignment fails without an error. The getter then runs, and valid input is rejected. `SEC-6` expectation: `getterRuns=1 validEntryOk=false`, exit 1. This contradicts `docs/index.md:359` ("never run a getter") and the comments at `src/validate-core.ts:211` and `src/schema.ts:250`. It needs code that already runs in the process; data alone cannot add such a getter. Fix direction: read the fields in refinements as own data properties (`Object.hasOwn`/descriptor), or check the refinements against the own-data copy instead.
- N1: an accessor on an optional field reads as absent, and the result is `ok: true` (31 cases, for example `headers`, `body`, `jsonAssert`, heartbeat `secret`, component `description`). Validators return the same object, so a caller that later reads the field runs the getter and can get a value of any type. A Proxy can do the same through its `get` trap (`src/validate-core.ts:288` to `:292` documents this). Every consumer validates `JSON.parse` output, which has no accessors, so this is a documented limit, not a finding.
- N2: on a `network` error, `fetchJson` returns the runtime error as `cause` unchanged. In Bun 1.4.0 its `path` property holds the full request URL, including user info and query (`JSON.stringify(cause)` shows it; `message` and `String(cause)` do not). Consumers decide what to log: probe keeps the `Error` (`src/client.ts:214`), and status wraps it (`src/poller.ts:217`).
- N3: a `maxBytes` of NaN or Infinity turns the cap off. An endless body then ran until `timeout` after 2 s and RSS grew by 1.4 GiB; -1 gives `too-large` at once. This is a caller option, not untrusted input; probe and status pass none, and notify passes its own default.
- N4: error texts repeat input key names (unknown keys, header names), for example `check.headers.<name>: ...`, but no values. Key names are not secrets. An error can still grow as long as the key, because no limit is applied.
- N5: `bun audit` reports `minimatch 10.2.6` (moderate, GHSA-g3hv-75wg-m249) through pulse-config → eslint. It is dev-only: the production install has only `zod`. It is fixed by a newer eslint in pulse-config.
- N6: validation time near the 5 MiB cap: one check with about 107,000 uptime days 157 to 204 ms; about 30,800 minimal checks 208 to 279 ms; a `jsonAssert.equals` object with 250,000 keys 185 to 211 ms; 250,000 unknown keys 87 to 101 ms; 100,000 manual-incident updates 99 to 108 ms (3 runs each). Nothing is superlinear.
- N7: a check `url` may point to loopback, private or link-local addresses (`http://169.254.169.254/...` and `http://[::1]:22/` are accepted). This is by design for an uptime monitor; the probe's `src/address-policy.ts` holds the target policy. A query string in the `url` is accepted, and `GET /checks` serves the URL.
- N8: `getManualIncidents` and `getManualIncident` drop the path of a base URL that has a query (`<base>/api?x=1` requests `/manual-incidents`). This is a correctness note, not a security problem.
- The prior notify audit (`audits/security/notify.md`, SEC-2 and SEC-3) traced two of its findings into this client. This audit checked both again on the contract commit (SEC-5, SEC-3) and did not copy them.
