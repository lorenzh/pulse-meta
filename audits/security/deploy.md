# Security audit: pulse-deploy (2026-11-09)

## Scope

- Audit date: 2026-11-09 (UTC). Issue: lorenzh/pulse-meta#948 (periodic security audit of `main` in pulse-deploy).
- Repositories and examined commits:
  - deploy `d47d8b90146601f97dad7de3dcf625a14e4bf018` (newest `main`, clone in `.repos/deploy`).
  - meta `6a09e6e9a0e5724b232a34312075b67068007dcc` (`docs/approved-packages.md`, earlier reports for the format).
  - config `04108fa0c67d9a79c0f6d1ade4dd78df3ad8a4a7`: only as the pinned dev dependency and reusable workflow that deploy names. Its code was not audited here.
- Surface: pulse-deploy ships no service of its own. It holds the Compose setups (`minimal`, `full`, `demo`, `dev`) with `common/services.yaml`, the one-shot `secrets-init` helper (`scripts/secrets-init.mjs`, root in a container with no network), the host scripts (`init-secrets.sh`, `wait-ready.sh`, `bump-images.sh`, `check-setup.sh`, `measure.sh`), the demo helpers (`demo/targets.mjs`, the only HTTP server in a setup; `demo/init.mjs`; `demo/tls.sh`), and the `pulse` CLI (`init`, `up`, `down`, `status`), which writes an install directory and drives `docker compose`. Its trust boundaries are: CLI flags and prompt answers, files in the install directory (`pulse.json`, `.env`, `config/notify/notify.json`, `secrets/*`, `compose.override.yaml`), the environment (`DOCKER_HOST`, `COMPOSE_*`), Docker and Compose output, the `/in` files and environment of `secrets-init`, the ghcr.io answers to `bump-images.sh`, and the release workflow.
- Method: a copy of deploy in `mktemp -d` (made with `cp -a`, because the runner has no `rsync`). Bun 1.4.0, Docker 29.9.2, Compose 2.40.3. `bun install --frozen-lockfile`: exit 0, 118 packages. `timeout 600 bun test cli`: 317 pass, 0 fail, exit 0. `bun run build` compiled `dist/pulse` (`pulse 0.1.0`), and every CLI test used that binary. Repository tests in the copy, all exit 0: `scripts/check-setup.sh` (all rules passed), `scripts/secrets-init.test.sh` (66 cases, Docker), `scripts/init-secrets.test.sh` (7), `scripts/bump-images.test.sh` (17, stub curl), `scripts/wait-ready.test.sh` (1), `e2e/redact.test.sh` (54). Further tests:
  - a fuzz script over 21 exported validators and parsers (483 calls);
  - about 25 hostile `pulse init` invocations with a marker value;
  - `secrets-init` in the pinned `oven/bun` image with hostile `/in` files and environment;
  - a real `full` stack started with `pulse init` and `pulse up` (project `auditfull`, loopback-only console, status on port 18080), checked, then removed with `pulse down --volumes`;
  - project-guard bypass attempts against that stack;
  - planted symlinks and hard links in an install directory;
  - a 100 MiB body sent to `demo/targets.mjs`.

  The runner has no `shellcheck`, so the shell lint of the repository did not run. Reproductions stay outside the repository and are not committed. No Docker container, volume or network of the audit remains (`docker ps -a`, `docker volume ls`: 0 entries named `audit*`).

## Issue candidates

All findings are `P3`. Each needs a contrived input or a compromised pinned dependency. None of the commands below attacks a running instance.

### 1. `security-deploy-2026-11-09-1` (P3): the release build job exposes a `contents: write` token to `bun install` and the compile step

- Location: `.github/workflows/release.yml:38` to `:43` (job `build`: `permissions: contents: write` and job-level `env: GH_TOKEN: ${{ github.token }}`), `:51` (`bun install --frozen-lockfile`), `:53` (`bun build --compile`); `package.json:17` (`"prepare": "lefthook install || true"`).
- Class: excess token scope in CI (supply chain).
- Check: in a copy, `rm .git/hooks/pre-commit; CI=true bun install --frozen-lockfile --force; ls .git/hooks | grep -v sample`, plus `bun pm untrusted`. Exit 0.
- Effect: `118 packages installed`, then `pre-commit` exists again. The root `prepare` ran the lefthook native binary under `CI=true`. `bun pm untrusted` lists only pulse-config's `prepare` as blocked, so lefthook's `postinstall` (`node postinstall.js`) runs too. That script skips its own install under `CI`, but the root `prepare` does not.
- Impact: in the release `build` job, every install-time script and native binary of a dev dependency runs with a token that can create tags, edit releases and upload assets. So can the compile step. The token is needed only by `gh release upload` at `:72`. A compromised dev dependency or install script could replace or add release binaries of the CLI before `publish` writes `SHA256SUMS`. The checksums would then match the swapped binary. The pins are exact and carry `sha512` integrity hashes, which keeps the risk low.
- Fix direction: set `GH_TOKEN` only on the upload step (and in `create` and `publish`), not at job level in `build`. Run `bun install --frozen-lockfile --ignore-scripts` in the release jobs, since the build needs no hook.

### 2. `security-deploy-2026-11-09-2` (P3): a deeply nested `config/notify/notify.json` makes `pulse up` crash with a raw stack trace

- Location: `cli/lifecycle.ts:33` to `:39`. `notifyEnvRefs` walks the parsed file with unbounded recursion. `runUp` at `cli/lifecycle.ts:105` re-throws anything that is not a `CommandError`, and `cli/main.ts:89` has no catch-all.
- Class: unhandled exception on a malformed input file (validator throws).
- Check: `pulse init --yes --setup full` into a fresh directory (project `auditdeep`), then replace `config/notify/notify.json` with one channel that holds 100,000 nested objects (600,031 bytes), then run `pulse up --dir <install>`. The same check also called `envPreflight` directly at depths 1,000 to 50,000.
- Effect: exit 1, 6,064 bytes on stderr. Two lines of minified CLI source, then `RangeError: Maximum call stack size exceeded.`, `at r (/$bunfs/root/pulse:530:2293)` repeated, `at async br (/$bunfs/root/pulse:547:30)` and `Bun v1.4.0 (Linux x64)`. No container was created (0). In the direct calls, depth 20,000 passes and depth 50,000 throws `RangeError`.
- Impact: a broken or hostile `notify.json` in an install directory makes `pulse up` fail with a dump of the bundled source instead of one error line that names the file and the rule (`AGENTS.md`: "Error lines name the file and the rule only"). Nothing is started and no secret is shown. A plain JSON syntax error is handled (`config/notify/notify.json is not valid JSON`).
- Fix direction: walk the channels iteratively, or with a depth limit that refuses deeper input as `CommandError("config/notify/notify.json: …")`. Add a catch-all in `cli/main.ts` that prints `pulse <cmd>: unexpected error (<name> <code>)` and exits 1, as `scripts/secrets-init.mjs:275` does. That also covers finding 3.

## Notes

### Findings that are not issue candidates

- `security-deploy-2026-11-09-3` (P3): `pulse init --force` reads `secrets/console-secret-key` whole, without a size check, in a preflight that runs outside the error handling (`cli/write-install.ts:158`, called from `:346`).
  - Check: an install made with `pulse init --yes --setup full`, then `secrets/console-secret-key` replaced by a 5 GiB sparse file (mode 0600), then `pulse init --yes --setup full --force <install>`, with the RSS sampled every 0.1 s.
  - Effect: exit 1 and a peak RSS of 5,278,592 kB. Stderr holds `ENOMEM: not enough memory, read 'big1/secrets/console-secret-key'`, a stack trace (`at Ks (/$bunfs/root/pulse:535:1779)` …) and minified source lines. A FIFO at the same path is refused cleanly.
  - Comparison: `secrets-init` with a 3 GiB input prints one line (`secrets-init: unexpected Error ENOMEM`).
  - Fix: refuse a key or token file larger than a few hundred bytes before the read, and let the catch-all of finding 2 handle the rest.
- `security-deploy-2026-11-09-4` (P3): `maskUserInfo` (`cli/docker.ts:104`) masks user info only up to the first `/`, `?`, `#` or space. It needs at least one `/` after the scheme; both `:/` and `://` are accepted.
  - Check A: `DOCKER_HOST=<tcp URL whose unencoded password holds a "/"> pulse status --dir <install>`. Exit 3 with `cannot reach the Docker daemon: Failed to initialize: unable to resolve docker endpoint: parse "tcp://u:pa/<marker>@127.0.0.1:1": invalid port ":pa" after host`, which shows the marker. A marker in the host path is shown too: `Cannot connect to the Docker daemon at tcp://127.0.0.1:1/<marker>`.
  - Check B: in a unit run of 14 shapes, 6 keep the marker: a raw `/`, `#`, `?` or space in the password, `https:u:p@h`, and `token=…`, which is not a URL.
  - Context: Docker prints the same text when it is called directly, and the value comes from the operator's own environment.
  - Fix: mask from the scheme to the last `@` before whitespace or a quote.

### Other notes

- N1: `shown()` (`cli/args.ts:146`) keeps the path of an http(s) URL. `pulse init --yes --setup full <dir> https://hooks.example/services/T0/B0/<marker>` gives `pulse: unexpected argument https://hooks.example/services/T0/B0/<marker>; see pulse init --help` (exit 2). This is by design, but webhook URLs often carry their secret in the path. It shows only for a stray positional.
- N2: `--webhook-url` is stored in `config/notify/notify.json` with mode 0644 (`stat`: `644`). A URL fragment is kept in it as well. The interactive wizard warns about clear text (`cli/prompt.ts:420`). The flag path prints no warning. `docs/cli.md:129` documents clear-text URLs for checks only.
- N3: in files mode, `secrets-init` passes `PULSE_LOCATION` to `tokens.json` unchecked (`scripts/secrets-init.mjs:170`). `PULSE_PROBE_LOCATIONS` is checked (`:175`). A value with quotes gives `secrets-init: files mode done` and `{"tokens":[{"location":"<marker>\",\"x\":\"y","token":"<token>"}]}`. It is JSON-escaped, so there is no injection, but the api has to refuse it.
- N4: no write is followed by `fsync` before its rename (`cli/write-install.ts:292`, `scripts/secrets-init.mjs:87`), so a power loss can leave an empty file. `demo/init.mjs:55` rewrites `/shared/checks.json` in place with `writeFileSync`. When `docker compose up` runs again on a running demo, the api can read a truncated file while it reloads. Not reproduced.
- N5: `bun audit` reports 1 moderate advisory, `minimatch@10.2.6` (GHSA-g3hv-75wg-m249). It is a dev dependency only, through `eslint@10.13.0` of pulse-config, and is not in the CLI binary.
- N6: with `--smtp-password-env` or `--webhook-secret-env`, `compose.yaml` gets a bare key (`HOOK_SECRET:`). `docs/cli.md:171` says it gets a reference `${NAME}`. Compose fills the key from the shell or `.env`: `docker compose config` shows `{"HOOK_SECRET":"<value from .env>",…}` in notify's environment. So the secret is a container environment variable, which any Docker user can read with `docker inspect`. The `full` setup passes its subscription SMTP password as a `secrets-init` file instead.
- N7: status is published on all interfaces in `full`, `dev` and the CLI's `full` (`*:8080`; in the running stack `HostIp ""`). This is the intended public status page, listed in the port table. The console, api and mailpit are loopback only.
