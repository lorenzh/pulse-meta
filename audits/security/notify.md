## Issue candidates

### security-notify-2026-11-07-1 (P2): database channels can send any notify secret to an SMTP host that the api chooses

- Location: `src/remote-channels.ts:172` (`resolveDatabaseChannel`: every database channel may resolve any `PULSE_NOTIFY_SECRET_*` variable, `allowedEnv` at `:142`, and any top-level file of `PULSE_NOTIFY_SECRET_DIR`, `secretPath` at `:123`); `src/config.ts:147` (`resolveSmtp`: the host and port come from the definition, the password from that reference). The contract accepts any host name for `smtp.host` (contract `src/notify-channels.ts:152`), and the api stores any definition that the contract accepts (`api/src/notify-channel-routes.ts:135`).
- Class: secret exfiltration (confused deputy). A secret reference is not bound to a destination, so the party that writes the channel picks where the secret goes.
- Check (described without the input): the fake api serves one database email channel. The channel's SMTP host is a stub server that the api picks, and its password reference names a secret that the operator set for another purpose. One run uses a `PULSE_NOTIFY_SECRET_*` variable, one uses a file in `PULSE_NOTIFY_SECRET_DIR`, and one uses implicit TLS to a non-loopback address whose certificate a CA trusted by notify signed. The service runs in token mode until one incident is delivered, then the check reads what the stub got at AUTH. Expectation check (the stub must not receive a notify secret): exit 1 in all 3 runs.
- Effect: the stub logs `AUTH PLAIN user=<user chosen by the api> password=<value of the operator's PULSE_NOTIFY_SECRET_SLACK_URL>` (loopback), `password=<content of a file in PULSE_NOTIFY_SECRET_DIR>`, and over TLS to `127.0.0.2` `password=<value of PULSE_NOTIFY_SECRET_TEAMS_URL>`. notify logs only `"msg":"notification delivered","channel":"mail"`, with no warning.
- Impact: whoever holds an api token with the `admin` scope can read the value of every `PULSE_NOTIFY_SECRET_*` variable and every top-level file in `PULSE_NOTIFY_SECRET_DIR`: Slack and Teams webhook URLs, webhook signing secrets, SMTP passwords. This includes the console Owner role (`console/docs/team.md:22`), automation tokens and stolen tokens. The design keeps these values out of the api and the console: database channels "hold references only, never a secret value" (`docs/channels.md:203`), and "the api … never reads a secret" (`api/docs/rest-api.md:557`). The probe closes the same class with `PULSE_PROBE_HEADER_HOSTS`, which binds each header secret to hosts (`api/docs/operation.md:207`). notify has no such binding, and its docs do not say that an admin token has this power.
- Fix direction: let the operator bind each secret reference to the destinations it may go to, as the probe does. For example, add a notify setting that maps each `PULSE_NOTIFY_SECRET_*` name and secret file to the SMTP hosts (and URL hosts) allowed for it, or an allow-list of SMTP hosts for database channels. Refuse a database channel that breaks the binding, with a fixed rejection reason. Until then, document that an `admin` token is as sensitive as every secret that notify can resolve.
